## 要約

OpenAI は 2026-11-19、ChatGPT の性能劣化を Codex で自動的に調べて直す社内システム **Performance Factory** の技術解説を公開しました。これは新機能の発表ではなく、**自社での運用事例の紹介**です。Codex の運用設計を考える読者にとって、実際の構成と失敗からの学びが具体的に読める資料です。

最初のワークフローは Regression Workflow です。性能アラートが鳴るとタスクが作られ、エージェントが原因を調べて記録し、修正案を出します。人が確認してデプロイしたあと、別のエージェントが性能が元の水準に戻ったかを確認します。公式は、約3か月で**1,700件超の調査を追跡し、600件超で根本原因を特定**した（1日あたり約17件の自動調査）と述べています。

## 何が変わったか

公式が示す、手作業からの進化は6段階です。

- 手作業の調査（30以上の性能ツールを蓄積）
- Codex を相談相手として使う
- 調査手順を `perf-forensics` という共有スキルにまとめる（過去の劣化事例に基づく評価で改良）
- 人がアラートを Codex に貼り付ける「中継役」になっていることに気づく
- アラートから Codex を自動起動し、結果を Slack に投稿
- タスクの状態を管理して担当を渡し歩く「ファクトリー」へ

システムは4つの部品でできています。

- **タスク管理**: ワークフローを設定ファイルと Markdown のプロンプトで定義し、状態・遷移・人が必要な段階を指定
- **ディスパッチループ**: 次の作業が可能なタスクにエージェントを割り当てる
- **クラウド上の Codex 実行**: 社内ネットワーク内の環境で、コードとメトリクス・ログ・トレースなどにアクセス。サービス ID で権限を絞り、行為の出所を追える
- **購読**: GitHub のレビューコメントや CI 失敗、デプロイ完了などでエージェントを再開させる

実運用で得た工夫と数字も示されています。

- **敵対的レビュー**: 診断に反論する別の Codex セッションを置く。最初の説明で止まってしまう誤診を減らす目的
- **精度**: 手動で100件の原因提案をレビューし、**正確と評価したのは70%**。残り30%は追加の検証が必要か、因果が確立していなかった
- **修正のほうが難しい**: 提案された修正が必要以上に複雑だったり、新しい問題を持ち込んだりする例があり、修正案にも敵対的レビューを追加。キャッシュ追加のように設計判断が絡む変更は、サービスに詳しい人の判断が要る

## 業務インパクト（一般企業向け）

エージェントを「作業者」として本番運用する際の**設計の型**として参考になります。ポイントは3つです。

- **状態を会話の外に持つ**: 状況と調査結果をタスクに記録し、エージェントや人が交代できるようにしている
- **権限を絞る**: サービス ID で動かし、どの操作がエージェント由来かを追跡できるようにしている
- **最終判断は人**: 修正のマージとデプロイは人が決める

注意点として、数字は OpenAI 社内の報告で、他社の環境で同じ結果になる保証はありません。また、仕組みの前提として、30以上の性能ツールと過去事例に基づく評価データという**蓄積があった**ことが読み取れます。ツールや評価データが整っていない組織が同じ効果を得られるとは限りません。

## 副業・個人活用視点

個人開発や小規模な案件でも、**「調査手順をスキルとして文書化し、評価データで磨く」**という流れは真似しやすい部分です。繰り返し発生する障害調査やログ確認の手順を `SKILL.md` のような形にまとめ、過去の事例で試すだけでも効果があります。

一方、Performance Factory のようなタスク管理とクラウド実行の基盤を個人で作るのは大がかりです。まずは、1つの手順をスキル化して手動で回し、**診断を別セッションに疑わせる**運用から試すのが現実的です。診断の70%という精度を踏まえ、結論をそのまま信用しない前提で使ってください。
