## 要約

OpenAI は 2026-11-18、Codex がユーザーの PC 上でコマンドを実行するときのサンドボックスを解説する記事「Inside the Codex sandbox」を公開しました。バージョンリリースの告知ではなく、**すでにある仕組みの設計意図と設定方法をまとめた技術解説**です。

Codex の作業で最も多く、リスクもあるのが「ユーザーのコンピューターでコマンドを動かす」ことです。そこで Codex は、ファイルとネットワークの制限を**ユーザー自身が決められる**サンドボックスを備えています。その制限をまとめた設定が **permission profile（権限プロファイル）** で、記事はこの考え方を軸に進みます。

記事の中心は3点です。(1) 既定の境界をどう決めたか、(2) 自分や組織の用途に合わせてどう変えるか、(3) 制限が実際に効いているかをどう確かめるか。

## 何が変わったか（記事が説明していること）

- **既定のプロファイル `:workspace`（Git リポジトリを作業ルートにした場合）**
  - 書き込みはワークスペース内に限る。ただし `.git` や `.codex` は読み取り専用で、Git フックや `.codex/config.toml` を直接書き換えられない
  - 読み取りは、OS 側の権限の範囲で広く許可する。コンパイラやビルドツールがリポジトリ外の SDK や設定を読むため。**その代わり、API キーを含む設定ファイルなど、リポジトリ外の機密ファイルも読めてしまう場合がある**と公式が明記している
  - ネットワークは既定で無効。外部へのアップロードや情報の持ち出しを防ぐ一方、依存パッケージのダウンロードも止まるため、必要なら別途許可する
- **公式が認める残るリスク**: 制限があっても、たとえば `node_modules` 内のパッケージにエージェントが悪意あるコードを仕込み、エディタの保存時に実行される、といった経路は残りうる。そのため、サンドボックスだけでなく学習・アラインメントと組み合わせた「多層防御」だと説明している
- **設計方針**: VM やコンテナに作業を移すのではなく、macOS・Linux・Windows それぞれの OS の仕組みで、**今使っている環境のままコマンドを制限する**。たとえば Mac で iOS アプリを作るとき、Docker の中では Mac 固有のビルドツールやシミュレータが使えないため、という理由が挙げられている
- **共通の呼び出し口**: コマンド、作業ディレクトリ、環境変数、権限プロファイル、（通信を一部許可する場合は）ネットワークプロキシを渡して、サンドボックス内でプロセスを起動する。子プロセスにも同じ制限が引き継がれる
- **コマンドごとの権限リクエスト**: モデルは個別のコマンドに追加権限や制限外での実行を要求できるが、**許可するかどうかはハーネス側が決める**（ユーザーへの確認、または自動レビューへの回付）
- **独自プロファイルの定義**: `config.toml` の `[permissions.<名前>]` に書く。`extends = ":workspace"` で組み込みを継承でき、パスごとに `read` / `write` / `deny` を指定する。例として `**/*.env` や `secrets` を `deny` にする設定が示されている
- **ネットワークの3択**: 全面遮断（`:workspace` の既定）、直接の全面許可（`:danger-full-access` の既定）、プロキシ経由でドメインごとに許可・拒否。ドメイン規則は完全一致とワイルドカードに対応し、**明示的な deny が allow より優先**される
- **設定の重ね合わせと管理者による制限**: 複数の `config.toml` は表（テーブル）単位で再帰的にマージされ、配列は丸ごと置き換わる。管理者は `requirements.toml`（システムファイルやクラウド配布のポリシー）で `allowed_permission_profiles` を指定し、たとえば `:danger-full-access = false` として選べるプロファイルを絞れる。クラウド側の要件はシステムファイルより優先される
- **`codex sandbox` コマンド**: Codex の設定で定義したプロファイルの下で任意のコマンドを実行できる。「VS Code に悪意ある保存時フォーマッタを仕込む」ような書き込みが、`.vscode` を読み取り専用にした `dev` プロファイルで実際にブロックされるかを試す用途が例示されている

OS ごとの具体的な制限の実装（macOS・Linux・Windows）にも記事は触れていますが、本記事の根拠は公式記事の前半に限っています。詳細は原文を確認してください。

## 業務インパクト（一般企業向け）

Codex を社内で展開する場合、サンドボックスは「入れてあるから安心」ではなく、**どのプロファイルを既定にし、何を禁止するかを決める設定項目**です。記事から実務で拾える論点は次の3つです。

1. **読み取り範囲が広い点を前提にする。** 既定では作業ディレクトリ外の機密ファイルも読める場合があります。API キーや認証情報を置いている端末では、`deny` で対象パスを明示するか、そもそも別の端末・別のアカウントで使うかを検討してください。
2. **通信は「全部閉じる」か「ドメインを列挙する」かで運用する。** 依存パッケージの取得を許可すると、持ち出し経路も開きます。許可するドメインを最小に保ち、deny を併用する形が公式の設定例に沿っています。
3. **管理者が `allowed_permission_profiles` で危険なプロファイルを無効化できる。** 全面アクセスを禁止して `:read-only` などを既定にする、といった統制ができます。導入時のポリシー文書に、許可するプロファイルの一覧を載せると運用しやすくなります。

導入前の確認には `codex sandbox` が使えます。ポリシーを決めたあと、**実際にブロックされることをコマンドで確かめる**手順を、社内の検証項目に入れておくと安全です。

## 副業・個人活用視点

個人で使う場合は、クライアント案件のリポジトリと自分の機密ファイルを同じ端末に置いていることが多いはずです。記事の考え方から、次の使い方ができます。

- 案件ごとに `dev` のような専用プロファイルを作り、`.env` や `secrets` を `deny` にしておく
- 通信が必要な作業だけ、ドメインを限定して許可する。普段は遮断のままにする
- 受託開発の納品物として、「AI エージェントにどこまで権限を与えて作業したか」を説明できるようにしておく。権限の設定ファイルは、そのまま説明資料の根拠になる

なお、サンドボックスは安全を保証するものではなく、公式自身も他の対策との併用を前提にしています。認証情報の入った端末では、設定の見直しとあわせて、作業内容を自分で確認する習慣を残してください。
