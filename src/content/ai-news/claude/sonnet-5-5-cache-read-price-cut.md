## 要約

Anthropic が2026年10月7日、**Claude Sonnet 5.5 のプロンプトキャッシュ読み取り単価を引き下げました。** 100万トークンあたり **$0.20 から $0.10** へ、つまり半額です。

価格表の表現で言うと、**基準入力価格に対する倍率が標準の 0.1x から 0.05x になった**ということです。Sonnet 5.5 の基準入力価格は $2 / MTok なので、その 5% が $0.10 にあたります。**キャッシュ書き込みとその他の価格は変わりません。** 5分キャッシュの書き込みが $2.50、1時間キャッシュの書き込みが $4.00、通常の入力が $2、出力が $10。動いたのは読み取りだけです。

**0.05x という倍率は、現在ごく一部のモデルにしか適用されていません。**

| モデル | キャッシュ読み取り倍率 | キャッシュ読み取り単価 |
| --- | --- | --- |
| Claude Fable 5.1 / Mythos 5.1 | 0.025x | $0.25 / MTok |
| Claude Opus 5.5 | 0.05x | $0.20 / MTok |
| **Claude Sonnet 5.5** | **0.05x** | **$0.10 / MTok** |
| その他のモデル | 0.1x（標準） | 基準入力価格の10% |

**Haiku 5.5 は 0.1x のままです**（10万トークン以下で $0.01、10万トークン超で $0.05）。つまり 0.05x の優遇は、**現行ラインナップの主力2モデル（Opus 5.5 と Sonnet 5.5）に限った措置**です。

**キャッシュが元を取るタイミング自体は変わりません。** 公式ドキュメントの説明では、5分キャッシュ（書き込み 1.25x）なら読み取り1回、1時間キャッシュ（書き込み 2x）なら読み取り2回で損益分岐します。書き込み価格が動いていないため、この分岐点は従来どおりです。**変わるのは、分岐点を超えた後の傾きです。** 同じ前置きを何度も読むワークロードほど、効果が大きくなります。

該当するのは、**長いシステムプロンプトや大きなドキュメントを前置して何度も問い合わせる構成**、そして**エージェントの多ターン実行**です。エージェントは会話履歴が伸びるほどキャッシュ読み取りが増えるので、ターン数の多い処理が素直に安くなります。

**コード変更は不要です。** 価格体系の変更だけで、API の挙動や `cache_control` の書き方は変わりません。倍率は **Batch API の割引やデータレジデンシーの倍率と積算されます。**

## 何が変わったか

- **Sonnet 5.5 のキャッシュ読み取りが $0.20 → $0.10 per MTok**（倍率 0.1x → 0.05x）
- **キャッシュ書き込みは据え置き**（5分 $2.50 / 1時間 $4.00）
- 通常の入力 $2 / 出力 $10 も据え置き
- 0.05x が適用されるのは **Opus 5.5（$0.20）と Sonnet 5.5（$0.10）のみ**
- Fable 5.1 / Mythos 5.1 はさらに低い 0.025x（$0.25）、その他は標準 0.1x
- **Haiku 5.5 は 0.1x のまま**（10万トークン以下 $0.01、10万トークン超 $0.05）
- **損益分岐点は変わらない**（5分キャッシュで読み取り1回、1時間キャッシュで2回）
- **コード変更は不要。** `cache_control` の書き方や API 挙動は変化なし
- 倍率は **Batch API 割引・データレジデンシー倍率と積算**
- 適用先は Claude API（first-party）と Claude Platform on AWS。Bedrock / Google Cloud は各社の価格体系

## 業務インパクト（一般企業向け）

**まず「何もしなくても安くなる」種類の変更です。** コード変更も設定変更も不要なので、Sonnet 5.5 でキャッシュを使っている組織は、10月の請求から読み取り分が半分になります。この手の値下げは稟議も検証も要らないので、**単に請求書を見て確認すれば済みます。**

**ただし「キャッシュを使っていれば」という条件が付きます。** ここが実務上の分かれ目です。プロンプトキャッシュは `cache_control` を明示的に書かないと効きません。**自社の実装でキャッシュが本当に効いているかを確認する良い機会です。** API レスポンスの `usage` に `cache_read_input_tokens` と `cache_creation_input_tokens` が出るので、ここが 0 のままなら値下げの恩恵は一切ありません。「キャッシュを設定したつもりで効いていない」は実際によくあります。

**キャッシュの設計を見直す価値が上がりました。** 読み取りが安くなったぶん、**「前置きを長くして使い回す」設計の採算が改善しました。** 社内規程や製品マニュアルをシステムプロンプトに固定で前置し、問い合わせだけを差し替える構成は、読み取り回数が多いので効果が大きい側です。逆に、1回しか読まない使い捨ての前置きには意味がありません。損益分岐点（5分キャッシュで1回、1時間キャッシュで2回）が変わっていないので、**「何回読むか」を基準にキャッシュ期間を選ぶ**という判断は従来どおりです。

**モデル振り分けの材料も変わりました。** Opus 5.5 のキャッシュ読み取りが $0.20、Sonnet 5.5 が $0.10。**基準入力価格の比（$4 対 $2）と同じ2倍の関係に揃いました。** これまでは Sonnet 5.5 のキャッシュ読み取りが $0.20 で Opus 5.5 と同額だったため、キャッシュを多用する構成では Sonnet の価格優位が目減りしていました。それが解消され、**キャッシュ込みでもきれいに「Sonnet は Opus の半額」と説明できる**ようになりました。コスト試算の説明がしやすくなるという意味で、提案書を書く側には実利があります。

**Bedrock / Google Cloud 経由の組織には適用されません。** パートナー運用のクラウドプラットフォームは各社が独立した価格体系を持ちます。クラウド経由で Claude を使っている場合は、AWS や Google Cloud の価格ページで確認してください。

## 副業・個人活用視点

**長い前置きを使い回す自動化が、より安く回せます。** 個人で作りがちな構成として「自分の文体サンプルや執筆ルールをシステムプロンプトに固定して、記事のネタだけ差し替える」というものがあります。これは**まさに読み取り回数が多い構成**なので、効果が出る側です。1時間キャッシュに入れて連続で10本書けば、2回目以降の8回ぶんの読み取りが半額になります。

**キャッシュを「使えていない」状態から抜ける動機になります。** プロンプトキャッシュは知っていても設定していない人が多い機能です。**`cache_control` を1つ足すだけ**（自動キャッシュならリクエストのトップレベルに1つ）なので、手間に対する効果が大きくなりました。レスポンスの `usage` で `cache_read_input_tokens` が増えているかを確認するところまでやると、効いているかどうかが分かります。

**受託案件のコスト試算では、説明が1行シンプルになります。** 「Sonnet 5.5 は Opus 5.5 の半額」が、キャッシュ読み取りまで含めて成立するようになりました。これまではキャッシュを多用する構成だと「ただし読み取りは同額です」という補足が必要でしたが、**倍率が揃ったので例外の説明が消えました。** 見積りの前提説明が短くなるのは、そのまま提案の通りやすさに効きます。

**なお Haiku 5.5 は 0.05x の対象外です。** 同日公開の Haiku 5.5 は 0.1x のままで、10万トークン以下なら読み取り $0.01。絶対額では最安ですが、**「0.05x 優遇」は主力2モデル限定**という点は押さえておいてください。モデルごとに倍率が違う構造になったので、コスト試算では倍率を1つずつ確認する必要があります。
