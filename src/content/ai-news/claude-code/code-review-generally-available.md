## 要約

**Claude Code の Code Review が research preview を終了し、一般提供（GA）になりました。** 提供対象は **Claude Team と Claude Enterprise の組織**です。

**この機能が何を解こうとしているかは、公式の問題設定を読むと分かります。** コーディングエージェントによってコードを**書く**速度は上がりました。しかし**レビューの速度は上がっていません。** 結果として、ボトルネックが実装からレビューへ移ります。

**ここは体感しやすい変化です。** エージェントに実装させれば PR は1日に何本も出ます。ところがレビューする人間の数と時間は変わりません。**PR が積み上がり、マージされないまま古くなり、ベースブランチとの差が開いていきます。** 「速く書けるようになった」ことが、そのまま「速くリリースできる」にならない理由がここにあります。

**Code Review は、人間のレビュアーが見る前に PR を読んでバグを指摘する機能です。** 人間を置き換えるのではなく、**人間が読む前の状態を整える**位置に置かれています。

**GA で変わった点は3つ挙がっています。**

**1つ目は速度です。** 大半のレビューが約3倍速くなり、**従来の約20分から6〜10分**になりました。**この差は運用上かなり大きいです。** 20分かかると、PR を出した人はいったん別の作業へ移ります。戻ってくるのは早くて数十分後、場合によっては翌日です。**6〜10分なら、その場で待てます。** 指摘を読んで直してもう一度出す、という流れが1回の作業時間の中で閉じるかどうかが、この境目で変わります。

**2つ目は品質です。** 重要なバグをより多く捕まえることを狙うとされています。あわせて、**各指摘の形が決められています。** **問題・何が引き金になるか・修正方法**を数文でまとめた簡潔な形です。

**この「形を決めた」という部分は軽く見えて重要です。** レビュー自動化が失敗する典型は、**指摘が多すぎて読まれなくなること**です。一般論の警告や、起こりえない条件のための指摘が並ぶと、開発者は全部まとめて無視するようになります。「何が引き金になるか」を書かせる形式は、**その指摘が現実に踏まれる経路を示せるかどうか**を自然に要求します。

**3つ目は柔軟性です。** 管理者が**リポジトリごとに Quick / Standard / Deep のレビュー深度を選べます。**

**ここが導入設計の中心になります。** 全部を Deep にすれば見落としは減りますが、短縮したはずの待ち時間が戻ります。逆に全部 Quick では、込み入った箇所を通してしまいます。**リポジトリの性質ごとに割り振るという前提の設計**です。

**有効化の手順は、管理者と開発者で非対称です。**

**管理者側**は、Claude Code 設定で Code Review をオンにし、**GitHub App をインストール**して、対象リポジトリを選びます。**開発者側**は、有効化後の新しい Pull Request に対して**設定なしで自動実行されます。**

**この非対称は、導入の難所がどこにあるかを示しています。** 開発者の学習コストはほぼゼロです。一方で**GitHub App のインストールと対象リポジトリの選定は、組織の権限を持つ人の作業**です。つまり詰まるのは技術ではなく、**情シスやリポジトリ管理者の承認**の側です。

**対応プラットフォームは GitHub App のみが挙がっています。** GitLab や Bitbucket についての記載はありません。**GitHub 以外を使っている組織は、現時点では対象外**と読むのが妥当です。

**クレジットには期限が切られています。** 対象となる Claude Enterprise 組織は、**2027-01-15 までに最低 $10,000 分の Code Review クレジットを請求できます。** そして**クレジットは請求から30日で失効します。** プロモーション規約が適用されます。

**この2つの日付の関係に注意が必要です。** 請求の期限は 2027-01-15 ですが、**請求してしまうと30日で消えます。** つまり「とりあえず早めに請求しておく」は損になりえます。**検証する対象リポジトリと期間を決めてから請求する**という順序になります。

## 何が変わったか

- **Code Review が research preview を終了し、Claude Team / Claude Enterprise で一般提供**
- **レビュー時間が約20分から6〜10分へ**（大半のレビューで約3倍速）
- **指摘の形式が「問題・引き金・修正方法」を数文で**まとめた簡潔な形に
- **管理者がリポジトリ単位で Quick / Standard / Deep の深度を選べる**
- 有効化は管理者が Claude Code 設定でオン → **GitHub App をインストール** → 対象リポジトリ選択
- 開発者側は**設定不要**。有効化後の新規 PR に自動で走る
- 対応プラットフォームは **GitHub App のみ**が明示
- 対象 Claude Enterprise 組織は **2027-01-15 までに最低 $10,000 分のクレジットを請求可能**、**請求から30日で失効**
- ドキュメントは `code.claude.com/docs/en/code-review`

## 業務インパクト（一般企業向け）

**まず効くのは、レビュー待ちが開発速度の上限になっている組織です。**

エージェントを本格的に使い始めた開発組織では、**PR の生産量とレビュー能力の差**が目に見えて出ます。この状態で人を増やすのは簡単ではありません。**一次指摘を6〜10分で返す仕組みが入ると、人間のレビュアーの役割を移せます。** 「バグを探す」作業から、**「この設計で進めてよいかを判断する」**作業へ寄せられます。後者は自動化しにくく、かつ人間がやる価値が高い部分です。

**レビュー深度の割り振りが、情シス・開発管理の設計課題になります。** 管理者権限でリポジトリ単位に決める構造なので、**「どのリポジトリを Deep にするか」の基準を言語化する必要があります。** 課金や認証に関わるコード、外部公開 API、個人情報を扱う経路は Deep、社内向けの管理画面や使い捨てのツールは Quick、といった割り振りです。**この基準を決めずに全部を既定値のまま運用すると、速度とコストのどちらかで不満が出ます。**

**GitHub 以外を使っている組織は待ちになります。** 公式が挙げているのは GitHub App のみです。GitLab / Bitbucket / Azure DevOps を主系に使っている組織では、**この機能を前提にした開発プロセスの見直しはまだできません。** 逆に言えば、GitHub へ寄せる判断の後押しにはなります。

**クレジットの扱いは、稟議のタイミングに影響します。** 請求期限は 2027-01-15 ですが**請求から30日で失効する**ため、**「予算を確保してから請求する」のではなく「検証体制を整えてから請求する」**順序になります。対象リポジトリ、計測する指標（レビュー待ち時間、指摘の的中率、手戻りの回数）、担当者を決めた上で請求する流れを先に組んでおくのが安全です。

**レビュー結果の扱いについては、組織側でルールが必要になります。** 自動レビューが通った PR を人間が読まずにマージしてよいのか、Deep で指摘ゼロなら承認を省略できるのか。**公式はそこまで定めていません。** ここを曖昧にすると、「自動レビューがあるから大丈夫」という暗黙の期待だけが広がります。**自動レビューは人間の承認を置き換えないという線**を、導入時に明文化しておく価値があります。

**Team / Enterprise 限定である点も確認しておく必要があります。** 個人プランや Pro では対象外です。チーム全体で使うには、**プランの移行自体が前提**になります。

## 副業・個人活用視点

**この機能自体は Team / Enterprise 向けなので、個人がそのまま使う対象ではありません。** ただし副業・受託の観点では、別の形で効きます。

**「レビュー体制の設計」を提案メニューにできます。** Code Review を入れること自体は管理者の数クリックです。価値が出るのは**その後の設計**、つまり深度の割り振り基準、自動レビューと人間の承認の線引き、計測する指標の決め方です。**ここは製品の設定ではなく、組織ごとに考える作業**なので、外部の支援が入る余地があります。「導入する」ではなく「**導入した後の運用ルールを一緒に決める**」という提案の形が取れます。

**クレジットの期限が、提案のきっかけになります。** 2027-01-15 という請求期限と30日の失効は、**対象組織にとって動く理由になります。** 「クレジットがあるうちに検証を回しておきませんか」という話は、予算の新規確保を伴わないため通りやすい種類の提案です。既に Claude Enterprise を使っている顧客がいるなら、声をかける材料になります。

**個人の受託開発でも、レビューの考え方は持ち込めます。** 一人で開発していると、**レビューという工程そのものが抜けます。** Code Review が有料プラン限定でも、「PR を出してから人間が読む前に一度機械に読ませる」という工程の意味は変わりません。手元の Claude Code で差分を読ませてから納品する、という運用に置き換えられます。**「問題・引き金・修正方法」という指摘の形式は、そのまま自分用のレビュー指示として使えます。** 一般論の警告を減らし、現実に踏まれる経路があるものだけを挙げさせる書き方です。

**納品物の品質説明にも使えます。** 受託では「どうやって品質を担保したか」を聞かれます。**レビュー工程を工程として説明できるかどうか**で、受け取られ方が変わります。深度の考え方（重要な経路は深く、使い捨ては浅く）は、**規模の小さい案件でも説明として成立します。**

**学習の素材としては、指摘の読み方が一番価値があります。** 自動レビューの指摘には、正しいものと、現実には踏まれないものが混ざります。**「この指摘は本当に起こるのか」を自分で判断する練習**は、レビューを受ける側としても、する側としても効きます。公式が指摘の形式に「引き金」を含めているのは、まさにその判断を可能にするためです。
