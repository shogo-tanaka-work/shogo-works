## 要約

2026-08-27、Claude Code の **2.1.248** が公開されました。日次パッチとしては珍しく、**権限・資格情報・課金**の3方向に同時に踏み込んだ内容です。

中心にあるのは **`--restricted`** という新しい起動モードです。`CLAUDE_CODE_RESTRICTED=1` でも同じ効果になります。何をするかというと、コマンドやコードを実行する組み込みツールと `WebFetch` を（`--tools` で明示しない限り）**取り除き**、ファイル操作を**作業ディレクトリの中だけ**に限定し、`bypassPermissions` を**拒否**します。

ここまでなら既存の権限設定でもある程度は表現できます。決定的に違うのは最後の1点です。**ユーザー設定・プロジェクト設定・ローカル設定のファイルをすべて無視します。**

この差は実運用で大きな意味を持ちます。従来の権限モードは「設定ファイルで書かれた許可ルール」の上に成り立っていました。つまり、**設定ファイルを書き換えられる立場の人は、権限を緩められた**ということです。`--restricted` はその前提を切ります。実行時のフラグまたは環境変数で指定した制限が、設定ファイルの内容に関係なく効く。**制限をかける人と、設定を書く人が別でよくなった**わけです。CI、共有マシン、外部の人が触るリポジトリ——この分離が要る場面は少なくありません。

もう1つ、こちらは新機能ではなく**修正**ですが、重要度は同等かそれ以上です。`/ultrareview` とローカル起点のクラウドセッションが、**未コミットの `prod.env` 形式ファイルや `*.tfvars`、資格情報ファイルのエディタ swap / 一時 / バックアップ（`key.pem.tmp`、`id_rsa.swo` のような名前）をアップロードしていました。** これらは手元に留まるよう修正されています。

この不具合の性質を正確に押さえておく価値があります。多くの人は `.gitignore` に `.env` や `*.tfvars` を書いています。しかし**エディタが作る一時ファイル（`.swp`、`.swo`、`.tmp`、`~` 付き）まで網羅している人は多くありません**。git の管理外にあるファイルがクラウドへ送られるという経路は、`.gitignore` を見ても気づけない。

**`/usage-credits`** も追加されました。AWS Marketplace 経由で課金している Enterprise、セルフサーブ Enterprise、Enterprise トライアルの組織で、メンバーが管理者に対して**利用上限の引き上げを申請**できます。あわせて、この機能が使えない組織（`DISABLE_EXTRA_USAGE_COMMAND` で非表示にしている等）に対してレート制限メッセージが `/usage-credits` を案内してしまう不具合も直っています。

そのほか、エージェント frontmatter の **`experimental.cacheTtl`**（`"5m"` / `"1h"`）でエージェント単位のプロンプトキャッシュ TTL を指定できるようになり、サーバー管理設定の読み込み失敗を **`/doctor` と `/status` に理由つきで出す診断**が入り、**Bedrock / Vertex / Foundry およびテレメトリ無効時でもセッション間メッセージング（`SendMessage` / `ListAgents`）が使える**ようになりました。

地味ですが効く修正として、長時間セッションで **OAuth トークン更新のたびにツール定義が再描画され、1時間に1回程度プロンプトキャッシュを取りこぼしていた**（同時に拡張思考の文脈も失われていた）問題が直っています。長く回すセッションのコストと品質の両方に効きます。Workflow ツールの説明も**約5.7k トークンから約1k トークンへ削減**され、スクリプト記述のリファレンスは `workflow-authoring` スキルへ分離されました。

## 何が変わったか

- **`--restricted` / `CLAUDE_CODE_RESTRICTED=1` を追加**。コマンド・コード実行系の組み込みツールと `WebFetch` を除去（`--tools` で個別指定した場合を除く）、ファイル操作は作業ディレクトリ内に限定、`bypassPermissions` を拒否、**ユーザー／プロジェクト／ローカルの設定ファイルをすべて無視**
- **セキュリティ修正**: `/ultrareview` とローカル起点のクラウドセッションが、未コミットの `prod.env` 形式ファイル・`*.tfvars`・資格情報ファイルの swap / 一時 / バックアップ（`key.pem.tmp`、`id_rsa.swo` 等）をアップロードしていた問題を修正
- **`/usage-credits` を追加**（AWS Marketplace 経由課金の Enterprise、セルフサーブ Enterprise、Enterprise トライアル）。使えない組織にこのコマンドを案内していた不具合も修正
- エージェント frontmatter に **`experimental.cacheTtl`**（`"5m"` / `"1h"`）
- `claude self-hosted-runner --client-label <label>`（`SELF_HOSTED_RUNNER_CLIENT_LABEL`）でランナーの登録ラベルを上書き
- サーバー管理設定の読み込み失敗を起動時警告と `/doctor` / `/status` に表示
- `/web-setup` で GitHub CLI トークンに `workflow` スコープが無い場合に警告
- **Bedrock / Vertex / Foundry、テレメトリ無効時でもセッション間メッセージング（`SendMessage` / `ListAgents`）が利用可能に**
- 長時間セッションで OAuth トークン更新後にツール定義が再描画され、約1時間に1回プロンプトキャッシュを取りこぼしていた問題を修正
- Workflow ツールの説明を約5.7k → 約1k トークンへ削減（リファレンスは `workflow-authoring` スキルへ）

## 業務インパクト（一般企業向け）

**`--restricted` は「AI に何をさせないか」を実行側で固定できる初めての手段です。** ここが実務上の要点です。

これまで Claude Code の権限は、突き詰めると設定ファイルの話でした。`.claude/settings.json` に何を書くか、managed settings で何を強制するか。しかし**設定ファイルを読む前提である以上、設定ファイルに手が届く経路はすべて抜け道になりえます**。`--restricted` はそこを切りました。実行するコマンドラインか環境変数に制限が書かれていれば、リポジトリの中身が何であれ制限が効きます。

具体的にどこで効くか。**CI パイプラインです。** PR に含まれる `.claude/settings.json` の変更が、そのまま CI 上の Claude Code の権限を変えてしまう——という構造は、外部コントリビュータを受け入れるリポジトリでは無視できません。`--restricted` を CI 側で固定すれば、リポジトリ側の設定に依存しなくなります。**共有の開発サーバー**、**評価目的で他社のコードを読ませる場面**も同じです。

ただし**万能ではない**ことも押さえてください。コマンド実行と `WebFetch` を落とすということは、**ビルド・テスト・依存解決を伴う作業はできない**ということです。コードレビュー、静的な調査、ドキュメント生成といった読み取り中心のタスクに向いています。「安全だから常に付ける」と決めると、使えるタスクの範囲が急に狭まります。**用途ごとに使い分ける前提の機能**です。

**資格情報ファイルの送信修正は、バージョン更新を急ぐ理由になります。** 影響を受けたのは `/ultrareview` とローカルから起動するクラウドセッションで、対象は「未コミット」かつ「資格情報系の名前を持つファイル、およびそのエディタ一時ファイル」でした。心当たりのある組織は、更新に加えて**該当期間に扱った資格情報のローテーションを検討する**のが安全側の判断です。技術的な影響範囲は限定的でも、資格情報の扱いは「たぶん大丈夫」で済ませない領域です。

**情シス・セキュリティ部門の観点では、この修正が示す一般則の方が長く効きます。** `.gitignore` は git のためのものであって、**AI ツールが読むファイルの範囲を定義するものではありません**。エディタの swap ファイル、バックアップ、`.tmp`。git の管理外にあるという理由でレビューの対象からも外れているファイルが、別の経路でクラウドへ出る。AI コーディングツールの導入審査では、**「何を送らないか」の定義がどこに書かれているか**を確認項目に入れるべきです。

**`/usage-credits` は、Enterprise の運用フローに1つ経路を足します。** これまで上限に当たったメンバーは、Slack なり口頭なりで管理者に頼むしかありませんでした。CLI から申請できるということは、**申請が記録として残る**ということでもあります。誰がいつ何を理由に上限を上げたか。コスト管理の観点では、この可視化の方が本体かもしれません。

**Bedrock / Vertex / Foundry でセッション間メッセージングが使えるようになった点**も、クラウドプロバイダー経由で導入している企業には実質的な機能追加です。これまで「Anthropic 直接契約だと使えるが、Bedrock だと使えない」という機能差が運用の説明を複雑にしていました。差が埋まる方向の変更は、社内マニュアルの分岐を減らします。

## 副業・個人活用視点

**クライアントのコードを預かる仕事をしているなら、`--restricted` は説明材料として使えます。** 受託でコードレビューや調査を請けるとき、「AI に読ませていいか」は必ず論点になります。ここで「実行系のツールを外し、作業ディレクトリの外は触らず、設定ファイルによる権限緩和も効かないモードで動かします」と**具体的に説明できる**のは強い。抽象的に「安全に扱います」と言うより、フラグ1つの話に落とせる方が信用されます。

**契約書や作業指示書に書ける粒度になった**という言い方もできます。「`--restricted` モードで実行する」は検証可能な約束です。「気をつけます」は検証できません。**AI を業務に組み込む側の信頼は、こういう検証可能な約束の積み重ねで作られます。**

**一方で、自分の環境の資格情報ファイルは今日確認する価値があります。** `.env` を `.gitignore` に書いているのは当然として、`.env.swp` は？ `terraform.tfvars.bak` は？ 過去に `vim` が異常終了したときに残った swap ファイルが、リポジトリのどこかに眠っていませんか。今回の修正は**そのファイルが送られていた**という話です。心当たりがあるなら、更新したうえで手元を掃除しておく。副業でクライアントの認証情報を預かる立場なら、なおさらです。

**支援先へ提案する立場なら、「AI ツールの導入審査に『送信されないファイルの定義』を入れる」という提案が今なら通ります。** 実例が出たばかりだからです。抽象的なセキュリティ論より、**実際に起きた不具合を1つ挙げて審査項目を1つ足す**方が話が早い。多くの企業の AI ツール審査は「どのモデルを使うか」「データが学習に使われるか」で止まっていて、**ローカルのどのファイルが送られるか**まで見ていません。ここに気づいているだけで、提案の質が変わります。

**`experimental.cacheTtl` はコストに直接効きます。** エージェント単位でプロンプトキャッシュの TTL を `"1h"` にできるということは、**間隔を空けて何度も呼ぶ用途でキャッシュが効き続ける**ということです。定期実行のエージェント、長時間の調査タスク。個人でトークン費用を払っている立場なら、この1行の設定が月額に効きます。あわせて入った「OAuth トークン更新でキャッシュを取りこぼす」修正も同じ方向で、**長く回すほど効いてくる**種類の改善です。
