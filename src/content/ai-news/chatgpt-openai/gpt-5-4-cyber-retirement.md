## 要約

OpenAI の Deprecations ページの **Upcoming deprecations 最上段に `gpt-5.4-cyber` が追加されました。**

- **announcement date: 2026-09-11**
- **shutdown date: 2026-10-01**
- **推奨移行先: `gpt-5.6-cyber`**

`gpt-5.4-cyber` は OpenAI のセキュリティ特化モデル系列です。後継の `gpt-5.6-cyber` は 2026-08-10 に提供が始まっており、**GPT-5.6 Sol をベースに、ゼロデイの発見とエクスプロイトチェーンの構築に向けて訓練されたモデル**とされています。提供経路は **Daybreak 防御プログラムの審査制ティア（Daybreak Red）に限られます。**

**対象となる利用者は広くありません。** 審査を通った組織だけが使える面なので、一般の API 利用者には影響しません。ただし、**使っている組織にとっては期限が明確に切られた作業です。** 本記事の公開時点で、退役まで**約2週間**しかありません。

**この記事を書いている理由は、影響範囲の広さではなく、告知の見つけにくさです。**

審査制ティア経由で提供されるモデルは、**公式ブログでも ChatGPT のリリースノートでも扱われません。** 気づく経路は実質的に Deprecations ページの一覧だけです。そして退役告知は、**気づいた時点で残り日数がすでに決まっている**という性質を持ちます。announcement から shutdown まで **20日**しかないケースを、月に1回の棚卸しで拾うのは困難です。

なお、Upcoming deprecations の他の行（2026-08-26 の Transcription 4モデル → 2027-02-26、2026-07-20 の audio / realtime / transcription 群 → 2027-01-20、2026-06-11 の GPT-5 / o3 snapshots → 2026-12-11 など）には、本日時点で変更は見られません。

## 何が変わったか

- **`gpt-5.4-cyber` が Upcoming deprecations に追加**された（announcement date 2026-09-11）
- **shutdown date は 2026-10-01**。本記事時点で残り約2週間
- **推奨移行先は `gpt-5.6-cyber`**（2026-08-10 提供開始、GPT-5.6 Sol ベース）
- 提供経路は **Daybreak 防御プログラムの審査制ティア（Daybreak Red）**に限られ、対象組織は限定的
- announcement から shutdown までの猶予は **20日**

## 業務インパクト（一般企業向け）

**`gpt-5.4-cyber` を使っていない組織にとって、この告知の価値は「退役情報をどう拾っているか」を点検する契機である点にあります。**

モデル退役は、AI を業務に組み込んだ組織が定期的に食らう運用イベントです。そして厄介なのは、**通知の来方が一定でないこと**です。大きなモデルの退役は公式ブログやリリースノートで扱われますが、**今回のような特化モデル・審査制ティアのモデルは、Deprecations ページにしか載りません。**

**点検すべきことは3つあります。**

1. **使っているモデル ID を一覧化しているか。** コードに直書きされたモデル名が散在している状態では、退役告知を見ても影響範囲が分かりません。**「このモデルを使っている箇所」を検索一発で出せるかどうか**が、対応速度をそのまま決めます。設定に集約されていれば1行の差し替えで済み、散在していれば調査から始まります。
2. **Deprecations ページを定期的に見ているか。** 公式ブログだけを追っていると、**今回の告知は拾えません。** 月1回では 20日の猶予に対して遅い可能性があります。**週1回を目安にするのが現実的です。**
3. **移行先が決まっている前提で動けるか。** 今回は推奨移行先が明示されています（`gpt-5.6-cyber`）。ただし **ベースモデルが GPT-5.4 系から GPT-5.6 系に変わるため、出力の傾向は変わります。** 差し替えて即本番、ではなく、**検証の時間を残り2週間の中に確保する必要があります。**

**期限管理の観点で、もう1点。** 今回の猶予は20日ですが、同じページの他の行は数ヶ月から1年以上先です。**「退役は遠い先の話」という感覚でいると、短い猶予のものを取りこぼします。** 一覧の最上段だけを見るのではなく、**残り日数でソートして見る**のが実務的な読み方です。

## 副業・個人活用視点

**個人開発者が `gpt-5.4-cyber` を使っている可能性は、ほぼありません。** 審査制ティアの提供なので、個人で申請が通る性質のものではありません。

**それでも、この告知から持ち帰れる実務的な習慣が1つあります。モデル ID を設定に集約することです。**

個人開発では、モデル名をコードに直接書くのが最短です。動くので、そのまま残ります。**問題が起きるのは退役の告知が来たときで、複数のスクリプト・複数のリポジトリに散った文字列を探すことになります。** 個人の場合は「どこで使ったか」の記憶に頼るしかなく、**思い出せないものが必ず出ます。**

対処は単純で、**環境変数か設定ファイルにモデル ID を1箇所だけ書く**ことです。効果が出るのは退役のときだけですが、その1回で確実に効きます。**この習慣は、受託案件を納品した後にも効きます。** 納品先で退役対応が必要になったとき、**設定1行の変更で済むかコード調査が必要かで、対応の見積りが変わります。**

**もう1つ、受託の観点で使える論点があります。**

**「モデル退役への対応」は、保守契約の中身として説明しやすい項目です。** AI を使ったシステムを納品したあと、「何を保守するのか」が曖昧になりがちです。**モデル退役は必ず起きて、期限があり、対応しないと止まる。** この3つが揃っているので、**保守の必要性を具体的に説明できます。** 「Deprecations ページを週次で確認し、影響範囲を報告し、期限内に差し替えます」という形にすると、作業内容が見えます。

**注意点。移行先が明示されていても、出力は変わります。** ベースモデルが変われば挙動が変わるのは当然で、**「推奨移行先に差し替えたから同じ結果が出る」とは限りません。** 顧客に説明するときは、**差し替え作業と検証作業を分けて見積もってください。** 差し替えは数分でも、検証は数日かかります。ここを一緒にすると赤字になります。
