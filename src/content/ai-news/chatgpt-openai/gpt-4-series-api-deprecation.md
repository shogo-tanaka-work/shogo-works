## 要約

OpenAI が公式の deprecations ページへ、**2026-10-14 付けで GPT-4 系モデルの退役エントリ**を追加しました。**2027-01-14 に API から削除されます。**

**対象は「GPT-4 系すべて」ではなく、特定スナップショット4系統です。** ここを正確に押さえないと、棚卸しの範囲を誤ります。

| モデル | 対象のモデル ID |
| --- | --- |
| GPT-4o | `gpt-4o-2024-08-06`、`gpt-4o-2024-11-20` |
| GPT-4o mini | `gpt-4o-mini-2024-07-18` |
| GPT-4.1 | `gpt-4.1-2025-04-14` |
| GPT-4.1 mini | `gpt-4.1-mini-2025-04-14` |

**推奨移行先はすべて `gpt-6-luna` の一本です。** モデルの性格ごとに別の移行先を示す形にはなっていません。**mini 系も同じ移行先**が案内されています。

**GPT-4-turbo はこのエントリに含まれません。** 同じページの別エントリで、別の停止日が設定されています。「GPT-4 の退役」という言い方でまとめて扱うと、対応すべき日付がずれます。

**ファインチューニング済みモデルは、ベースモデルと同じ停止スケジュールに従います。** 自社データで学習させたモデルを `gpt-4o-2024-08-06` ベースで運用しているなら、**そのモデルも 2027-01-14 に止まります。** 単なるモデル ID の置き換えではなく、**再学習の計画が必要になる**ケースです。影響の重さが他の退役と違う点はここです。

**日付の構造を読み違えないことが重要です。** エントリの文面は「2026年10月14日に、対象モデルを使っている開発者へ、2027年1月14日の退役と API からの削除を通知した」という形です。**告知が窓内、停止は約3か月後**です。今日止まる話ではありません。

**ただし、2027年1月に停止日が集中しています。** 同ページの直近エントリを並べると次のようになります。

| 告知日 | 対象 | 停止日 | 移行先 |
| --- | --- | --- | --- |
| 2026-10-14 | **GPT-4o / GPT-4o mini / GPT-4.1 / GPT-4.1 mini** | **2027-01-14** | `gpt-6-luna` |
| 2026-10-01 | GPT-5.3-Codex / GPT-5.1 / GPT-5.4-Nano | 2027-04-01 | `gpt-6-sol` / `gpt-6-luna` |
| 2026-10-01 | text-to-speech 系 | **2027-01-06** | `gpt-realtime-2.1-mini` |
| 2026-08-26 | transcription 系 | 2027-02-26 | `gpt-live-transcribe` / `gpt-transcribe` |
| 2026-07-20 | レガシー audio / realtime / transcription 系 | **2027-01-20** | モデルにより異なる |
| 2026-06-11 | GPT-5 / o3 系 | 2026-12-11 | `gpt-5.6-*` |

**2027年1月だけで、1月6日・1月14日・1月20日の3系統が止まります。** さらにその前月、2026年12月11日に GPT-5 / o3 系があります。**年末年始をまたいで4つの期限が並んでいる**のが現在の状況です。

**この並びが実務の結論を決めます。** GPT-4o の件だけを個別に対応すると、1月に入ってから別系統の停止で同じ作業を繰り返します。**一度にモデル ID を洗い出すほうが明らかに効率がよい**局面です。

## 何が変わったか

- **2026-10-14 付けで GPT-4 系4モデルの退役が告知**された（公式 deprecations ページ）
- 対象は特定スナップショット: `gpt-4o-2024-08-06`、`gpt-4o-2024-11-20`、`gpt-4o-mini-2024-07-18`、`gpt-4.1-2025-04-14`、`gpt-4.1-mini-2025-04-14`
- **停止日は 2027-01-14**（告知から約3か月）
- **移行先はすべて `gpt-6-luna`**。モデル別の個別指定はない
- **GPT-4-turbo は対象外**（別エントリ・別の停止日）
- **ファインチューニング済みモデルはベースモデルと同日に停止**
- 2027年1月には **1月6日（TTS 系）/ 1月14日（本件）/ 1月20日（レガシー audio・realtime・transcription 系）** の3系統が並ぶ
- その前月 **2026-12-11 に GPT-5 / o3 系**の停止がある

## 業務インパクト（一般企業向け）

**棚卸しの対象は、コードだけではありません。** モデル ID は想像以上に多くの場所に書かれています。アプリケーションのコード、環境変数、設定ファイル、プロンプトテンプレート、バッチ処理のスクリプト、社内ツール、業務部門が作った自動化。**「誰が書いたか分からないが動いている」ものほど見落とします。** 特に業務部門側で作られた自動化は、情シスの台帳に載っていないことが多いです。

**ファインチューニング済みモデルがある組織は、見積りの性格が変わります。** モデル ID の置き換えは数時間の作業ですが、**再学習は学習データの再整備・評価・比較が必要**です。`gpt-6-luna` で同じ品質が出るかは実際に試すまで分かりません。**3か月は、再学習と評価を回すには十分だが、着手が2027年に入ってからだと足りない**という長さです。該当する組織は、年内に検証を始める判断が要ります。

**2027年1月の集中は、段取りの問題として扱うべきです。** 1月6日・1月14日・1月20日に別系統の停止が並び、さらに2026年12月11日があります。**4回に分けて対応すると、棚卸し・テスト・リリースの一式を4回繰り返します。** いまの時点で全系統のモデル ID を一度に洗い出し、停止日順に並べた移行計画を1本作るほうが、総工数が明確に下がります。年末年始の稼働が落ちる時期をまたぐ点も計画に入れておく必要があります。

**「スナップショットを固定していたから安全」は、ここでは成り立ちません。** モデル ID に日付を含めてスナップショットを固定するのは、挙動の再現性を確保する正しい運用です。ただし**固定したスナップショットには退役日が来ます。** 固定運用をしている組織ほど、**どのスナップショットをどこで使っているかの一覧を持っているはず**なので、棚卸しは速く終わります。持っていない場合は、この機会に作る価値があります。

**移行先が一本に絞られている点は、判断を軽くします。** GPT-4o と GPT-4o mini のようにコストと速度で使い分けていた構成でも、公式の推奨は `gpt-6-luna` の一本です。**「mini 相当の安い移行先」を探す作業が不要**という意味では楽ですが、**mini 前提のコスト試算は組み直しが必要**です。移行前にトークン単価を確認してください。

## 副業・個人活用視点

**モデル退役の棚卸しは、受注しやすい形の案件です。** 作業内容が明確（モデル ID を探して置き換え、動作確認）で、**期限が公式に決まっている**ため、提案のタイミングを作りやすいです。「2027年1月14日までに終わらせる必要があります」という一文が、そのまま提案の根拠になります。相手の社内で誰も気づいていないことも珍しくありません。

**提案の形は「1件対応」ではなく「期限一覧付きの棚卸し」にします。** GPT-4o だけを直して終わると、1月に入ってから別系統で同じ依頼が来ます。**4つの期限を1枚の表にして、全部まとめて洗い出す提案**にすると、単価も納得感も上がります。**この表を自分で持っていることが、提案の速さになります。** 公式の deprecations ページは更新されるので、月次で見る習慣を作ると強いです。

**ファインチューニング済みモデルがある案件は、別案件として切り出せます。** ID の置き換えと再学習は難易度も工数も違います。**学習データの再整備・新モデルでの評価・品質比較**まで含めると、継続的な関与になります。「同じ品質が出るか検証します」という提案は、相手にとって断りにくい内容です。

**モデル退役の記録を自分で蓄積すると、資産になります。** 告知日・対象モデル・停止日・移行先を1つの表に積み上げていくと、**「このベンダーはスナップショットを何か月で切るのか」**が見えてきます。今回は告知から停止まで約3か月です。この感覚は、**顧客へモデル選定を助言するときの根拠**になります。単発の記事より、更新を続ける一覧のほうが読まれ続けます。

**個人開発でも、固定していたモデル ID は確認しておく価値があります。** 自分の小さなツールが `gpt-4o-mini-2024-07-18` で動いているなら、2027年1月14日に止まります。**動かなくなってから気づくと、原因の切り分けに時間を取られます。** 止まる日が分かっているものは、分かっているうちに直すのが安い対処です。
