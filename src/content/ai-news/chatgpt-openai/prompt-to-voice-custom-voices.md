## 要約

OpenAI は 2026-10-16、**prompt-to-voice を全APIユーザーへ提供開始**しました。**音声の特徴を文章で書くと、その音声が生成されます。**

これまで独自音声を作るには、話者の同意録音とリファレンス音声が必要でした。しかもその経路（録音ベースの音声作成）は**対象顧客限定で、営業への問い合わせが前提**です。つまり「自社サービスの声を用意する」には、声優の手配、収録、同意の取得、そして OpenAI 側の審査という工程が並んでいました。**今回、文章だけで音声を作る経路が、条件なしで全APIユーザーに開きました。**

作成は `POST /v1/audio/voices` に `type: "prompt"` を送ります。パラメータは `type` / `name` / `prompt` / `model`（例 `"auto"`）、それに任意の `script_hint` です。`script_hint` は2,000字までの読み上げ例で、省略すると自動生成されます。**訛り、年齢感、声の高さ、音色、話速、特徴の強さといった要素は、個別のパラメータではなく、すべて `prompt` の文章の中に書きます。**

レスポンスには `object: "audio.voice"` / `id` / `name` / `created_at` / `type` / `prompt` が入ります。**音声のプレビューは返りません。** 実際にどう聞こえるかは、GPT-Live セッションを張って確かめることになります。

使うときは `session.audio.output.voice.id` に音声 ID を指定します。**prompt から作った音声の場合、`session.instructions` にも音声の説明を入れる**という点が公式に明記されています。プリセット音声は `"marin"` のような文字列で渡すのに対し、カスタム音声はオブジェクトで渡します。音声はセッション開始時に決まるため、切り替えるには新しいセッションを張り直します。

**同じ日に、GPT-Live へ9つの音声が追加されました。** ドイツ語3（Nuri / Juni / Flitz）、フランス語2（Brise / Sillage）、ヒンディー語1（Nira）、**日本語2（Harema / Shida）**、韓国語1（Noeul）です。前日の 2026-10-15 に ChatGPT 側へ降りた GPT-Live-1.1 の音声追加に対して、**こちらは API 側の追加**にあたります。

## 何が変わったか

- **prompt-to-voice が全APIユーザーへ提供開始**。API と音声 Playground の両方から作成できる
- 作成は `POST /v1/audio/voices`、`type: "prompt"`。パラメータは `type` / `name` / `prompt` / `model`、任意で `script_hint`（2,000字まで）
- **作成は無料**。課金は通常の GPT-Live セッション料金に乗る
- **上限は prompt 生成音声が1組織100件**（アプリが顧客向けに作る音声も含む）。録音ベースは20件
- GPT-Live に9音声追加（**日本語は Harema / Shida**）
- `gpt-live-1` は英語の訛りに対応。訛りは `session.instructions` に「Speak British English.」のように書く
- 必要な権限は `api.voices.read` / `api.voices.write` とカスタム音声アクセス、**プロジェクトスコープの API キー**
- **`/v1/audio/voices` 経由の音声作成は Zero Data Retention と併用できない**
- 利用条件として、実在の人物・著名人・架空キャラクターの模倣依頼は禁止、子どもの声は不可、**合成音声であることを聞き手に伝えること**、来歴メタデータとウォーターマークの保持が求められる

## 業務インパクト（一般企業向け）

**まず効くのは、音声エージェントの立ち上げ速度です。** コールセンターの一次応答、予約受付、社内ヘルプデスクの音声版といった案件で、これまでは「どの声でいくか」を決める工程に、声優の手配と収録が挟まっていました。**文章で複数案を作って聞き比べ、決まってから収録を検討する**という順番に変えられます。試作段階のコストが、ほぼセッション料金だけになります。

**一方で、導入前に確認すべき条件が増えました。** 大きいのは2つです。

1つは **Zero Data Retention との非互換**です。ZDR を前提に OpenAI の利用を通している組織は少なくありません。**その環境では `/v1/audio/voices` 経由の音声作成ができません。** 「音声エージェントを作りたい」という話が来たとき、**先に ZDR の適用範囲を確認する**必要があります。あとから分かると、設計のやり直しになります。

2つめは**開示義務**です。公式は、合成音声であることを聞き手に伝えること、来歴メタデータ・ウォーターマーク・その他の合成由来を示す指標を保持することを求めています。**電話応対で「ただいま AI が対応しています」と名乗る運用を、UX 側と詰めておく**必要があります。名乗らせない方向で設計すると、規約違反と信頼の問題が同時に起きます。

**上限100件という数字は、使い方によっては早く当たります。** 「顧客ごとに声を変える」SaaS を作る場合、アプリが顧客向けに作る音声もこの100件に含まれます。**顧客数が三桁に乗る設計なら、最初から音声の共有・使い回しを前提に組む**必要があります。

**生成音声の一意性は保証されない**という記載にも注意が必要です。「当社専用の声」として対外的に打ち出すなら、**法務とブランド側に、他社と似た声が出る可能性を共有しておく**のが安全です。

## 副業・個人活用視点

**個人にとっては、ここが一番大きい変化かもしれません。**

録音ベースの音声作成は「対象顧客限定、営業へ問い合わせ」でした。**個人や小規模受託は、実質そこに入れませんでした。** 今回の prompt 経由は条件がなく、**プロジェクトスコープの API キーがあれば今日から試せます。** 録音機材も、スタジオも、同意書のやり取りも不要です。

**案件としては「音声エージェントの試作」が売りやすくなります。** 店舗の予約電話、士業の一次ヒアリング、教室の問い合わせ対応。**声の候補を3つ作って聞かせる**ところまでを初回の打ち合わせでやると、話が具体になります。従来はここに収録コストがあったため、受注前に持っていけませんでした。

**日本語音声が2つ増えた（Harema / Shida）点も、実務では地味に効きます。** プリセットの選択肢が少ないと、どの案件も同じ声になります。カスタム音声と合わせて、**案件ごとに声を変えられる**ようになりました。

**ただし、受託で売るなら開示義務まで込みで設計してください。** 「AI だと分からない音声エージェント」を期待する相手はいます。規約上それはできません。**最初の提案で「合成音声であることを名乗る前提です」と言い切る**ほうが、後で揉めません。これは制約の説明ではなく、**要件定義ができる人の仕事**として見てもらえる部分です。
