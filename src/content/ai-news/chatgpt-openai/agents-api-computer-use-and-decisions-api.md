## 要約

DevDay 2026 の開発者向け発表の中心が **Agents API** です。

**Agents API 自体は新しくありません。2026-09-11 からパブリックベータで提供されています。** マネージドなエージェント実行基盤で、役割分担がはっきりしています。**セッション、オーケストレーション、文脈圧縮（context compaction）、復旧を OpenAI 側が受け持ち、開発者はツールと実行環境を定義する。**

**DevDay で、ここに複数の機能が入りました。**

**OpenAI ホストのブラウザによるコンピュータ操作（computer use）**。エージェントが GUI を持つソフトウェアを操作してタスクを完了できます。**MCP サーバーへの接続**。**並列サブエージェント**。**永続セッション状態**。そして **Codex 由来のマルチエージェント機能、ツール検索、ツール呼び出し、文脈圧縮**がアプリケーション側から使えるようになりました。

**同時に、別枠の新しい API が2つ発表されています。**

**Decisions API** は、**あらかじめ定義した有限の選択肢に対する実時間の判定**に特化した API です。開発者はテキストまたは画像で文脈を渡し、返ってきた回答を**分類・ルーティング・エージェントの次アクション選択**に使います。**限定プレビューで提供開始、広範な提供は数日以内**とされています。

**Bedrock Managed Agents** は AWS との共同発表です。**OpenAI のエージェントを AWS 内部で完結して動かす**構成で、Agents API の中核から OpenAI と Amazon が共同で構築し、AWS のリソースとネイティブに動くよう調整されています。**限定プレビュー**。

## 何が変わったか

- **Agents API**（2026-09-11 からパブリックベータ）に DevDay で機能追加
- **OpenAI ホストのブラウザによるコンピュータ操作（computer use）**に対応
- **MCP サーバーへの接続**に対応
- **並列サブエージェント**と**永続セッション状態**に対応
- **Codex 由来のマルチエージェント機能・ツール検索・ツール呼び出し・文脈圧縮**を利用可能に
- **Decisions API** を発表。有限の選択肢に対する実時間判定に特化。**限定プレビュー、広範な提供は数日以内**
- Decisions API は**テキストまたは画像で文脈を渡し、分類・ルーティング・次アクション選択に使う**
- **Bedrock Managed Agents** を AWS と共同発表。**OpenAI エージェントを AWS 内部で完結実行**。**限定プレビュー**
- Agents API 側の分担は変わらず: **セッション・オーケストレーション・文脈圧縮・復旧は OpenAI、ツールと実行環境は開発者**

## 業務インパクト（一般企業向け）

**この発表の実務的な意味は、「エージェント基盤を自前で作る理由が減った」ことです。**

社内でエージェントを動かそうとすると、モデル呼び出しそのものより、**周辺の仕組みで手間がかかります**。会話が長くなったときに文脈をどう圧縮するか。途中で落ちたときにどこから再開するか。複数のエージェントを並列に動かすときの調整。セッションの状態をどこに持つか。

**これらは全部、作っても差別化にならない部分です。** 顧客に価値を感じてもらえるのは、そのエージェントが何をするかであって、セッション管理の出来ではありません。**Agents API は、まさにこの部分を引き受けると宣言しています。**

**判断としては、「いま自前で作っているものの、どこまでを残すか」の見直しになります。**

残すべきは、**自社の業務知識が入る部分**——どのツールを持たせるか、どういう手順で判断させるか、どこで人間に確認を取るか。**引き渡してよいのは、セッション管理、リトライ、文脈圧縮**といった汎用部分です。

**ただし、パブリックベータであることは忘れないでください。** 仕様は変わります。**本番の基幹業務を、いま全面的に載せる段階ではありません。** 新規に作るものから試す、既存のものは並走させる、という進め方が妥当です。

**コンピュータ操作（computer use）への対応は、適用範囲を広げます。**

API を持たない業務システムを、GUI 経由で操作できるようになります。**これは日本企業にとって特に意味があります。** 社内の基幹系や業界特化のパッケージに API が無く、それが自動化の障壁になっている——よくある構図です。

**ただし、GUI 操作の自動化は壊れやすい**という性質は変わりません。画面が変われば動かなくなります。RPA で散々経験されてきたことです。**AI が操作するから壊れないわけではありません。** 適用するなら、**画面変更の頻度が低く、失敗しても手戻りが小さい業務**から始めてください。

**Decisions API は、地味ですが使いどころが明確です。**

「この問い合わせはどの部署へ回すか」「この文書はどのカテゴリか」「次に取るべきアクションはA/B/Cのどれか」——**選択肢が有限で、答えが1つに決まる判断**です。これらを汎用のチャット API で処理すると、**出力形式が安定しない**という問題が常につきまといます。JSON で返せと指示しても、たまに崩れる。

**選択肢を先に定義する API は、この問題を構造的に解きます。** 分類・ルーティングの処理を持っている組織は、**既存の実装を置き換える価値があります**。限定プレビューですが、広範な提供が数日以内とされているので、すぐ試せる見込みです。

**Bedrock Managed Agents は、これまで話が止まっていた層に効きます。**

**「データが AWS を出てはいけない」**という制約を持つ組織があります。金融、医療、公共、あるいは顧客との契約でそう決まっている受託開発。この制約は、AI 活用の議論を入口で止めてきました。

**OpenAI のエージェントが AWS 内部で完結して動くなら、この制約と両立します。** 限定プレビューですが、**この条件で止まっていた案件は、話を再開する価値があります**。前提が変わったので、以前の「できません」がそのままとは限りません。

## 副業・個人活用視点

**個人開発者にとって、Agents API は「作らなくていいものが増えた」という話です。**

エージェントを自作した経験がある人なら、**面倒なのはモデル呼び出しではないことを知っています**。会話履歴が長くなって詰まる、途中で落ちて最初からやり直し、並列に走らせたら状態が混ざる。**この辺りを OpenAI 側に任せられるなら、作るものは減ります。**

**個人のプロダクト開発では、これは速度に直結します。** 差別化にならない部分に時間を使わず、自分のアイデアの部分だけ作る。**まず試すなら、いま自作のループで回しているものを1本、Agents API へ載せ替えてみる**のが分かりやすいです。

**Decisions API は、個人の小さな自動化でも効きます。**

メールの振り分け、記事のタグ付け、問い合わせの一次判定。**「AI に分類させたいが、出力形式が安定しなくて後処理が面倒」**という経験は、自動化を組んだことがある人なら必ずあります。**選択肢を先に定義できるなら、後処理のコードが消えます。**

**受託・コンサルの文脈では、Bedrock Managed Agents が最も直接的な商材です。**

**「データを AWS から出せないので AI 活用は見送り」と結論した案件**を、どれくらい抱えているでしょうか。日本企業では珍しくない結論です。**前提が変わったので、掘り起こせます。**

持っていき方は、売り込みではなく**再確認**の形が良いと思います。「以前、データの持ち出し制約で見送った件ですが、AWS 内部で完結する構成が限定プレビューで出ました。要件が変わるかもしれないので、一度お時間いただけますか」。**事実の通知として自然に送れます。**

ただし、**限定プレビューであることは正直に伝えてください。** 「できるようになりました」と言い切ると、後で困るのは自分です。**「選択肢が生まれた段階」であって「今すぐ本番投入できる」ではありません。**

**発信のネタとしては、「作る / 借りるの境界が動いた」という切り口が読まれると思います。**

1年前は、エージェント基盤を作るのが開発者の仕事でした。いまは、**どこを借りてどこを作るかを決めるのが仕事**になりつつあります。**この境界は、ベンダーの発表のたびに動きます。** 今回は「セッション管理・文脈圧縮・復旧」が借りる側へ移りました。

**この視点で過去1年の発表を並べ直すと、それ自体が1本の記事になります。** 個別のニュース紹介より、こういう整理の方が長く読まれます。エンジニア向けの発信で差をつけるなら、こちらの方向です。
