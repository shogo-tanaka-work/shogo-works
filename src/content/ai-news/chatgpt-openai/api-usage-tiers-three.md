## 要約

OpenAI が 2026-10-06 付の API changelog で、**有料の利用ティアを5段階から3段階へ統合した**と告知しました。新しいティア名は **Build / Launch / Grow** です。

**昇格は自動です。** 組織の**累計クレジット購入額**が各ティアの下限に達すると、申請なしで上がります。rate limits ドキュメントに載っている条件は次の通りです。

**Free** は対象地域のユーザー向けで、月 $100 までの利用。**Build** は累計購入 $5 で月間利用上限 $500。**Launch** は累計 $100 で $5,000。**Grow** は累計 $500 で $200,000 です。

**実務上もっとも大きい変化は、最上位の到達条件が下がったことです。** 従来の最上位ティアは**累計 $1,000** が条件でした。新しい **Grow は累計 $500** で到達します。**半減です。**

**つまり、レート上限で詰まっていた組織が、以前より早く上限緩和に到達できます。** 「レート上限に当たるので処理を分散させる」「夜間バッチへ寄せる」といった**設計上の妥協を、課金で解決できる閾値が下がった**ということです。$500 は多くの企業にとって検証段階で通過する額です。

**一方で、段階が減ったぶん飛び幅は大きくなっています。** 月間利用上限は **$500 → $5,000 → $200,000** です。Launch と Grow の間が40倍開いています。**「あと少しで次の段階」という感覚が持ちにくく、自社がどこにいて次に何が変わるのかは、以前より意識的に確認する必要があります。**

レート上限はモデル系列ごとに示されています。**Astra / Sol / Terra 系**は Build が 5,000 RPM・1,000,000 TPM、Launch が 10,000 RPM・4,000,000 TPM、Grow が 15,000 RPM・40,000,000 TPM。**Luna 系**は Build が 5,000 RPM・2,000,000 TPM、Launch が 10,000 RPM・10,000,000 TPM、Grow が **30,000 RPM・180,000,000 TPM** です。

**Luna 系の Grow が突出している点は、設計判断に関わります。** TPM で見ると Astra / Sol / Terra 系の Grow（40,000,000）に対して Luna 系は 4.5倍（180,000,000）です。**大量処理を安いモデルに寄せる設計が、レート上限の側からも支持される**構造になっています。

## 何が変わったか

- **有料の利用ティアが5段階から3段階（Build / Launch / Grow）へ統合**された（2026-10-06）
- 昇格は**累計クレジット購入額に応じて自動**。手動の申請手続きはない
- ティア条件（累計購入額 / 月間利用上限）
  - **Free**: 対象地域のユーザー / 月 $100
  - **Build**: $5 / $500
  - **Launch**: $100 / $5,000
  - **Grow**: $500 / $200,000
- **最上位の到達条件が累計 $1,000 から $500 へ半減**した
- レート上限（RPM / TPM）
  - Astra / Sol / Terra 系: Build 5,000 / 1,000,000 → Launch 10,000 / 4,000,000 → Grow 15,000 / 40,000,000
  - Luna 系: Build 5,000 / 2,000,000 → Launch 10,000 / 10,000,000 → **Grow 30,000 / 180,000,000**
- 段階が減ったため、月間利用上限の飛び幅は **$500 → $5,000 → $200,000** と大きくなった

## 業務インパクト（一般企業向け）

**最初にやることは、自社の現在ティアと月間利用上限の確認です。**

ティア構造が変わった以上、**以前の「Tier 3 相当」のような社内呼称は通用しません。** 社内ドキュメント、運用手順書、情シスの台帳に旧ティア名が書かれているなら、**Build / Launch / Grow へ置き換えてください。** 障害対応の手順書に「Tier が足りないので上限に当たっている」と書いてあると、調査する人が混乱します。

**次に、レート上限を前提にした設計の見直しです。** 「レート上限に当たるから」という理由で入れた作り込み——リトライのバックオフ、キュー、処理の時間帯分散——は、**累計 $500 で Grow に到達するなら不要になる可能性があります。** 作り込みはそれ自体が保守コストです。**課金で解消できるなら外す方が安い**ケースは珍しくありません。累計購入額の到達状況を確認してから判断してください。

**請求計画には注意点があります。** 条件は「**累計**クレジット購入額」です。月額の支出ではなく、これまでに購入した合計です。**つまり一度到達したら戻りません**（公式は降格について記載していません）。検証で購入した額も累計に含まれます。**一方で月間利用上限は別の軸**です。Grow に到達しても、月 $200,000 を超える利用はできません。**「ティア条件」と「月間上限」を混同すると、予算の見積もりを間違えます。**

**大量処理を抱えている組織は、モデル選定とレート上限を合わせて設計してください。** Luna 系の Grow は 180,000,000 TPM で、Astra / Sol / Terra 系の 40,000,000 TPM の4.5倍です。**単価が安いモデルの方がレート上限も緩い**という構造なので、「大量の単純処理は Luna 系、難しい処理だけ上位モデル」という振り分けが、コストと上限の両面で合理的になります。これは**モデルを1つに決めない設計**が有利、ということです。

**社外向けの資料を持っている場合は、確認日を入れてください。** 利用ティアの構造は、今回のように段階数ごと変わります。**「5段階」と書いた資料は、この日を境に誤りになりました。** 比較表や提案書にティア構造を書くなら、確認日を明記するのが最低限の防御です。

## 副業・個人活用視点

**個人開発と小規模受託にとっては、むしろ下側の条件が重要です。**

**Build は累計 $5 で到達します。** つまり**$5 購入した時点で月 $500 まで使える**ということです。個人の検証や小さな受託案件なら、これで足ります。**「API を試すのに大きな初期費用が必要」という誤解を、具体的な数字で解けます。**

**受託の見積もりでは、$500 / $5,000 / $200,000 という月間上限の階段を知っておくと強いです。** 「この規模の処理なら Launch（累計 $100）で収まります」と言えるのと、「レート上限がどうなるか分かりません」としか言えないのでは、**提示できる確度が違います。** そして**条件が累計購入額という単純な数字なので、クライアント側でも検証できます。** 検証可能な見積もりは信頼されます。

**既存クライアントに対しては、見直し提案のきっかけになります。** 「レート上限に当たるから夜間に回している」という運用を抱えている現場は、**その作り込みが不要になっているかもしれません。** 累計購入額の状況を確認して、Grow に到達していれば**作り込みを外す提案**ができます。**機能を足す提案より、不要になった作り込みを外す提案の方が、評価が長持ちします。**

**技術記事を書くなら、旧構造との対照が刺さります。** 「5段階から3段階へ」「最上位が $1,000 から $500 へ」という変化は、**検索して出てくる既存記事のほとんどが古い情報になった**ことを意味します。**この種の「既存情報が一斉に古くなった瞬間」は、記事の需要が立ちやすいタイミングです。** ただし**公式ドキュメントを一次情報として確認し、確認日を明記してください。** 古い記事を元に書くと、自分が誤情報の拡散側に回ります。

**自分の運用コストの見直しにも使えます。** 個人で複数の AI ツールに課金していると、API の累計購入額がいくらになっているかを把握していないことが多いです。**すでに Grow に到達しているなら、使えるレート上限が上がっているので、バッチ処理の作り方を変えられます。** まず自分の請求画面を見るのが最短です。
