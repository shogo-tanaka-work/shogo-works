## 要約

OpenAI が 2026-08-19、**Private Safety Processing** をプレビュー公開しました。API の Zero Data Retention（ZDR）を維持したまま、安全監視の範囲を「1回のやり取り」から「複数の関連するやり取り」へ広げる仕組みです。

前提として ZDR は、対象となる API 顧客に対する3つの約束です。リクエストの処理後にプロンプトと応答を保持しない。顧客のコンテンツを OpenAI の担当者が閲覧できるようにしない。企業顧客のデータは明示的なオプトインが無い限りモデルの学習に使わない。データを外に出せない業種にとって、これは導入可否を決める条件そのものです。

一方で OpenAI は、深刻なリスクが「1回のやり取りでは見えない」ことを問題として挙げています。安全機構の突破を繰り返し試す、複数アカウントに分担させる、正当な研究を装う、といった行動は、単発のプロンプトとしては無害に見えます。エージェントが長時間タスクを実行する場合も同様で、「停止を指示された後も動き続ける」ような意図からの逸脱は、経過を通して見ないと判定できません。従来の ZDR 対応の安全機構はやり取りを1件ずつ評価していたため、この横断的な視点を持てませんでした。

ここが今回の発表の背景です。近年のフロンティアモデルの提供では、**安全監視のためにセンシティブなコンテンツの保持を顧客側に求める**ケースが出ていました。OpenAI は、これが多くの組織のセキュリティ義務や顧客への約束と衝突すると認めたうえで、「ZDR を提供し続けられるように設計したのが Private Safety Processing である」と説明しています。

仕組みとしては、既存の自動保護をやり取り横断へ拡張します。重要なのは、**拡張しても OpenAI の担当者がコンテンツ本体にアクセスしない**点です。ZDR デプロイではコンテンツは顧客が管理するインフラ上に残ります。加えて OpenAI 側のストレージに置く選択肢も開発中で、その場合は顧客が管理する鍵で暗号化され、OpenAI は鍵の複製を持ちません。リスクが検知されたときに OpenAI へ渡るのは「どの種類の活動か」を示す限定的なシグナルだけです。そのシグナルをもとに措置の要否を判断します。

顧客側は、アラートや措置の内容を自社システムにある情報で調査できます。異議を申し立てたい、正当な活動であることを説明したい、確認された不正利用の調査に協力したい、という場合は、顧客の判断で必要な情報を OpenAI へ共有します。

現在は一部の early customer でテスト中です。**2026年9月に段階的な提供開始と技術ホワイトペーパーの公開が予告されています。**

なお脚注で、法令上の報告義務がある児童性的虐待コンテンツ（CSAM）の疑いがある画像については、ZDR デプロイでも従来どおり手動レビューと報告のために保持される旨が明記されています。この点は今回の発表で変わっていません。

## 何が変わったか

- ZDR 対応の安全機構が、単一のやり取りの評価から**複数の関連するやり取りを横断したパターン検知**へ拡張される（プレビュー）
- ZDR デプロイでは顧客が管理するインフラ上にコンテンツが残る構成のまま、横断検知が動く
- OpenAI 側ストレージを使う選択肢を開発中。その場合は**顧客が管理する鍵で暗号化**され、OpenAI は鍵の複製を持たない
- 検知時に OpenAI へ渡るのは活動種別を示す限定シグナルのみ。フラグが立った場合でも担当者はコンテンツ本体にアクセスしない
- 顧客はアラートと措置を自社システムの情報で調査でき、共有するかどうかは顧客の判断
- 現在は early customer でテスト中。**2026年9月に段階的提供開始と技術ホワイトペーパー公開を予定**
- CSAM 疑いのある画像の保持は ZDR でも従来どおり継続（変更なし）

## 業務インパクト（一般企業向け）

金融、医療、法務、研究開発のように「データを預けられないから最新モデルを使えない」と結論していた組織にとって、判断をやり直す材料になります。ただし現時点はプレビューで、提供開始は9月です。**いま社内で決めるべきは採用可否ではなく、9月に評価するための準備です。**

情シスと法務のレビュー項目は具体的に変わります。これまでの論点は「OpenAI がコンテンツを保持するか」の一点でしたが、今後は「横断検知の対象になるコンテンツはどこに置かれるか」「鍵を誰が管理するか」「検知シグナルとして何が外へ出るか」「措置を受けたときにどう調査し、どう異議を申し立てるか」の4点に分解されます。ベンダー評価シートやデータ処理契約のチェック項目を、この粒度に更新しておくと9月の判断が速くなります。

もう一つ、社内で説明が必要になるのが「コンテンツを見られないのに、なぜ不正利用を検知できるのか」という点です。自動システムが評価し、人間へ渡るのは種別シグナルだけ、という構造を先に共有しておかないと、現場からは「結局中身を見ているのでは」という疑念が出ます。技術ホワイトペーパーが9月に出るので、それを待って社内向けの説明資料をまとめるのが現実的です。

エージェントを業務に組み込んでいる、あるいは検討している組織は、OpenAI が挙げた「停止を指示された後も動き続ける」型のリスクを自社の監視設計にも当てはめて見直す価値があります。プロバイダー側の監視が入るからといって、自社側の実行ログや停止手順が要らなくなるわけではありません。

## 副業・個人活用視点

個人開発者や小規模事業者が直接 ZDR の対象になるケースは多くありませんが、この発表は仕事の取り方に効いてきます。

企業向けに AI 機能を実装する案件では、「顧客データが OpenAI 側に残るのか」という質問がほぼ必ず出ます。ここで ZDR の3つの約束と、今回の Private Safety Processing がその約束をどう維持しようとしているかを、自分の言葉で説明できる人はまだ多くありません。**技術選定の相談に呼ばれる立場になるかどうかは、この種の説明ができるかで決まります。**9月のホワイトペーパー公開は、提案資料を更新する良いタイミングです。

コンサルティングや研修を提供している場合は、「安全監視とデータ保持のトレードオフ」というテーマ自体が講義素材になります。OpenAI が「一部のフロンティアモデルの提供では保持を求めていた」と認めたうえで設計を変えた、という経緯は、AI ガバナンスが実際にどう動いているかを示す具体例です。抽象的な原則論より説得力があります。

規制業種の顧客を持っている場合は、9月の提供開始を待たずに「いま何が決まっていて、何がまだ決まっていないか」を整理して渡すだけでも価値があります。プレビュー段階の情報を正確に切り分けられることは、それ自体が信頼につながります。
