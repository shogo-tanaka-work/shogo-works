## 要約

OpenAI は 2026-09-08、API changelog で**画像生成モデル2種の追加**を公表しました。**GPT Image 2.5 Sunburst** と **GPT Image 2.5 Flare** です。

注目すべきは、これが**単一モデルの世代交代ではない**点です。公式の説明では、**Sunburst は編集精度を優先するワークフロー向け**、**Flare は日常的な画像生成を高速かつ高品質にこなす用途向け**と、役割で分けられています。「上位版と廉価版」ではなく、**得意分野の違う2本**という提示のされ方です。

両モデルとも、**Image API** と **Responses API の image generation tool** の両方から利用できます。既存の画像生成コードがどちらの経路であっても、モデル名の指定を変えれば届く位置に置かれました。

品質設定も拡張されています。両モデルで **`xhigh` と `max`** が新たに使えるようになりました。そして課金は、**GPT Image 2 と同じトークンレート**を用いると明記されています。新モデルの追加に合わせて単価体系が変わったわけではありません。

なお changelog 本文には具体的な価格数値が載っておらず、**image generation guide と pricing ページを参照**する形になっています。実装前にはそちらで最新の数値を確認してください。

## 何が変わったか

- **GPT Image 2.5 Sunburst**（編集精度重視）と **GPT Image 2.5 Flare**（高速・日常用途）の2モデルが追加された
- **Image API** と **Responses API の image generation tool** の双方から呼べる
- 品質設定に **`xhigh`** と **`max`** が追加された（両モデル対応）
- 課金は **GPT Image 2 のトークンレートを踏襲**（新レート体系ではない）
- 具体的な価格と実装詳細は image generation guide / pricing 側を参照する構成

## 業務インパクト（一般企業向け）

**モデル選定の問いが変わります。**

これまで画像生成 API を業務に組み込む際の判断は、実質的に「最新のモデルを使う」で足りていました。世代が上がれば品質も上がるという前提が成り立っていたためです。今回、**同じ 2.5 世代の中に精度側と速度側の2本が並んだ**ことで、その判断は「どちらの性質が要るか」へ組み替わります。

具体的には、**処理の性質でルーティングを分ける設計**が現実的になります。既存画像への修正指示を反映させる、レイアウトを崩さずに一部を差し替える、といった**編集系の処理は Sunburst**。カタログのサムネイル生成、社内資料の挿絵、大量のバリエーション出しなど、**1件あたりの完璧さより処理量が効く用途は Flare**。1つのアプリで両方を使い分ける構成は、十分に組む価値があります。

**コスト面の見通しは立てやすい変更です。**課金が GPT Image 2 のトークンレート据え置きと明記されているため、モデルを差し替えても単価の再交渉や再見積もりは基本的に不要です。**変わるのは品質設定の使い方の方**で、`xhigh` や `max` を安易に既定値にすると、必要のない工程まで高コスト側へ倒れます。品質設定は「全体の既定」ではなく「処理ごとの指定」として設計してください。

**検証は必要です。**公式の説明は「Sunburst は編集精度向け」「Flare は高速向け」という定性的なもので、ベンチマーク数値は示されていません。自社の実データ、たとえば自社商品の写真や自社のブランドガイドに沿った図版で、**両モデルを同一プロンプトで並べて比較する**工程を挟んでから本番へ入れるのが妥当です。用途特化の主張が自社のデータでも成り立つかは、試さないと分かりません。

## 副業・個人活用視点

**個人開発では「Flare を既定にする」が素直な出発点**になります。

副業や個人開発で画像生成を組み込む場合、対象はサムネイル、OGP 画像、記事の挿絵、モックアップといった用途が中心になりやすく、これは公式が Flare に割り当てている「日常的な生成」そのものです。速度が出るモデルを既定に置き、**編集の作り込みが必要な場面だけ Sunburst へ寄せる**という構成が、コストと待ち時間の両面で扱いやすくなります。

**品質設定の追加は、個人利用ではむしろ注意点として効きます。**`xhigh` や `max` は魅力的に見えますが、トークンレート課金である以上、**品質を上げれば従量課金も上がります**。個人開発では月額の上限を自分で管理することになるため、まず既定の品質で試し、**出力が実用に足りない場面を特定してから**上位設定へ上げる順序をおすすめします。全部を最高品質で回すのは、金額の見通しが立たなくなる最短経路です。

**受託でクライアント向けに画像生成を組み込んでいる場合、この2本立ては説明材料になります。**「速い方と綺麗な方を用途で切り替えています」という設計は、単に最新モデルを使っているという説明より、**判断の根拠が伝わる形**です。見積もりの内訳としても、処理の性質ごとにモデルと品質設定を割り当てた表を出せば、コストがどこで発生しているかが可視化されます。

一点、**changelog に価格数値が載っていない**ため、料金を前提にした提案をする前に pricing ページの実数値を確認してください。GPT Image 2 のレート踏襲という記述だけで見積もりを固めると、品質設定ごとの差分を取りこぼす可能性があります。
