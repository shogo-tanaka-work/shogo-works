## 要約

OpenAI は 2026-09-09、**GPT-6 Astra が ChatGPT Work、Codex、API で利用可能になった**と公式ポストで告知しました。

Astra 自体の発表は 9月3日です。ただしその時点の公式表記は「**限られた組織へロールアウト中、一般提供ではない**」というもので、いつ誰が使えるようになるかは確定していませんでした。今回の 09-09 の発表は、**その提供範囲が確定したことを告げるもの**です。ChatGPT Plus / Pro / Business / Enterprise に加え、OpenAI API、Microsoft Azure、Amazon Bedrock 経由でも提供されます。

**このモデルの特徴は、コンピュータ操作を前提に設計されている点です。**公式は「多くの AI システムは、価値を出す前にデータの整備、ワークフローの再設計、カスタム連携の構築を企業に要求する」という前提を挙げ、Astra はそれを変えると述べています。**API を持たないアプリケーションであっても、人間が使うのと同じ画面操作で作業できる**ため、既存の業務フローへ前準備なしで入れられるという主張です。

価格は **入力 100万トークンあたり $10、出力 $50**。OpenAI は単価ではなく**タスクあたりのコスト**で語っており、「より少ないトークンとリトライでタスクを完了するよう訓練した」としています。ベンチマークでは Terminal-Bench 4.0 で 57.9%（GPT-5.6 Sol2 は 37.3%、Claude Fable 5.1 は 55.8%）を示し、**Claude Fable 5.1 比で推定 API コストが約63%低い**と説明しています。いずれもベンダー自己申告の数値である点は差し引いて読む必要があります。

**企業導入の観点で重要なのは、統制手段が同時に用意されたことです。**管理者は、**承認済みのサイトとデスクトップアプリへアクセスを限定**でき、**アップロードとダウンロードを管理**でき、**閲覧履歴を制御**できます。加えて、影響の大きい操作（consequential action）の前に承認を求める確認ポリシーと、安全でない・未認可のツール呼び出しに対する自動レビューが組み込まれています。そして **Enterprise では既定で無効**であり、管理者が明示的に有効化しない限り使えません。

安全性についても踏み込んだ記述があります。OpenAI 内部のコンピュータ操作安全性ベンチマーク（機密情報の露出、ダッシュボードの過度な共有、データ削除といったシナリオ）で、**意図しない結果の発生が GPT-5.6 Sol 比で 89%減、Claude Fable 5.1 比で 74.7%減**としています。一方で Astra は、**Preparedness Framework のサイバーセキュリティ Critical しきい値に到達した初のモデル**でもあり、能力が上がったぶん保護を強化したと明記されています。

あわせて、ChatGPT Desktop に **Oracle Analytics、Power BI（Microsoft Fabric）、Navan、Avalara** のエンタープライズプラグインが追加されました。

## 何が変わったか

- **GPT-6 Astra が ChatGPT Work / Codex / API で利用可能**になった（09-03 は「限られた組織」向け）
- API のモデル名は `gpt-6-astra`。**Microsoft Azure と Amazon Bedrock** 経由でも提供
- 対象は ChatGPT Plus / Pro / Business / Enterprise。**Pro / Business / Enterprise では GPT-6 Astra Pro** も利用可能
- **Enterprise は既定で無効**。管理者が有効化する（適用レートカードと契約に基づく）
- 価格は **入力 $10 / 出力 $50 per 1M tokens**
- 管理者コントロール新設: **承認済みサイト・デスクトップアプリへの制限、アップロード/ダウンロード管理、閲覧履歴の制御**
- **確認ポリシー**（影響の大きい操作の事前承認）と、未認可ツール呼び出しの**自動レビュー**
- ChatGPT Desktop に **Oracle Analytics / Power BI / Navan / Avalara** のプラグインを追加
- **Preparedness Framework のサイバーセキュリティ Critical しきい値に到達した初のモデル**
- 適格な API 顧客は対象エンドポイントで **Zero Data Retention** を申請できる（承認制）

## 業務インパクト（一般企業向け）

**この更新の本質は、モデルの性能ではなく「既定でオフ」という設計にあります。**

Enterprise で既定オフということは、**使うかどうかを誰かが決めなければならない**ということです。何もしなければ使えないままで、業務は止まりません。したがって、放置していても事故は起きません。ただし、**現場から「使いたい」という要求が上がってきたときに、判断する材料を持っているか**が問われます。

**判断が難しいのは、Astra が画面を操作するモデルだからです。**従来のチャット型 AI に対する統制は、突き詰めれば「何を入力してよいか」の管理でした。機密情報を貼り付けない、個人情報を送らない。入力を絞れば、出力の範囲も自ずと決まります。**コンピュータ操作を伴うモデルでは、この前提が成り立ちません。**入力そのものは無害な指示でも、モデルがブラウザやデスクトップアプリを操作した結果として、ダッシュボードの共有範囲が広がる、ファイルが外部へアップロードされる、データが消えるといった事象が起こり得ます。OpenAI 自身が安全性ベンチマークの例として挙げているのが、まさにその3つです。

**だからこそ、今回同時に用意された管理者コントロールを、機能一覧としてではなく統制設計の道具として読む価値があります。**「承認済みサイトとデスクトップアプリへの限定」は、**モデルが触れる範囲そのものを閉じる**手段です。「アップロード/ダウンロードの管理」は、**組織の境界を越えるデータの移動**を押さえます。「確認ポリシー」は、**取り返しのつかない操作の直前で人間を挟む**仕組みです。この3つは、粒度も効き方も違います。全部を一度に設計しようとせず、**まず範囲を閉じ、その中で運用しながら広げていく**のが現実的です。OpenAI 自身も「限定的な構成から始めて、時間をかけて広げられる」と書いています。

**コストの見方も変わります。**入力 $10 / 出力 $50 は、単価としては安くありません。ただし OpenAI が主張しているのは**タスクあたりのコスト**で、「少ないトークンとリトライで完了する」という設計です。この主張が自社の業務で成り立つかは、**実際に走らせて課金額を見るまで分かりません。**ベンチマーク上の効率がそのまま自社のワークフローに転移する保証はないため、**評価はトークン単価ではなく「1件の業務を終えるのにいくらかかったか」で行うべき**です。有効化を検討するなら、代表的な業務を数件走らせて実測する工程を組んでください。

**サイバーセキュリティ Critical しきい値の到達も、そのまま読み流さない方がよい情報です。**これは OpenAI 自身の枠組みで「危険な能力水準に達した」と宣言したということです。同時に保護を強化したとしていますが、**能力が高いモデルを社内に入れるということは、そのモデルが誤った、あるいは誘導された指示に従ったときの被害範囲も大きくなる**ということです。プロンプトインジェクションに対する耐性は「強化した」とあるだけで、ゼロになったとは書かれていません。**外部から取得したコンテンツ（Web ページ、受信メール、共有ドキュメント）をモデルに読ませながら、同じセッションで操作権限を与える構成**は、リスクが積み上がる典型です。ここは設計で分けるべきところです。

**現実的な進め方としては、次の順序が妥当です。**(1) 有効化するかを決める。(2) 有効化するなら、まず承認済みサイト・アプリを絞った限定構成にする。(3) アップロード/ダウンロードと確認ポリシーを設定する。(4) 代表業務でコストと精度を実測する。(5) 実測結果を見て範囲を広げるか判断する。**既定オフである以上、慌てる必要はありません。**判断の材料を揃えてから決められる、というのが今回の設計のありがたいところです。

## 副業・個人活用視点

**個人にとっては、まず ChatGPT Plus / Pro で使える点が実利です。**Enterprise は既定オフですが、個人プランでは制約なく利用できます。Pro プランでは GPT-6 Astra Pro も使えます。

**狙い目は、API を持たないツールを跨ぐ作業です。**副業や受託の実務では、クライアントの業務システム、古い管理画面、ブラウザでしか触れない SaaS など、**自動化したいのに API が無い**という場面が繰り返し出てきます。従来はここで手作業に戻るか、スクレイピングを自作するかでした。**画面操作で扱えるモデルは、この隙間に直接効きます。**請求データの突合、複数管理画面からの情報収集、フォーマットの決まった資料作成といった、単純だが手が止まる作業が候補です。

**コストの考え方は企業と同じで、単価ではなくタスク単価で見てください。**入力 $10 / 出力 $50 は、雑に長い文脈を投げていると効きます。逆に、少ない手数で終わる設計にできれば、時間単価と比較して十分に見合います。**受託であれば、この差は見積もりの根拠になります。**「手作業で3時間の作業を、モデル利用料 $X と確認30分で終える」という形で提示できれば、値付けの説明がしやすくなります。

**クライアント環境で使う場合は、前提の確認が要ります。**相手が Enterprise 契約なら、**既定オフです。**管理者が有効化していなければ、Astra を前提にした提案は成立しません。加えて、承認済みサイト・アプリの制限が効いていれば、**触れる範囲がこちらの想定と違う**ことがあります。作業開始後に発覚するとスケジュールに響くため、見積もり段階で「Astra が有効か」「アクセス制限の設定内容」を確認事項に入れてください。

**支援側に回る場合、今回の管理者コントロールはそのまま商材になります。**多くの中小企業は「AI を使わせるか、使わせないか」の二択で止まっています。**範囲を閉じて始め、実績を見て広げる**という設計を、具体的な設定項目とセットで提示できれば、判断の入口を作れます。ここで重要なのは、機能を並べることではなく、**コンピュータ操作を伴うモデルは入力の管理だけでは統制できない**という論点を伝えることです。従来のチャット型 AI 向けに作られた社内ガイドラインは、この種のモデルには足りません。その差分を説明できる人は、まだ多くありません。
