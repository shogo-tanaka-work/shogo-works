## 要約

Cloudflare は Birthday Week 2026 の2日目（**2026-09-29T13:00:00Z**）に **Threat Signals** を発表し、**発表時点で GA（Generally Available）**としました。

Threat Signals は、**公開されている脅威情報（OSINT）を RSS フィードから取り込んで自動処理するプラットフォーム**です。公式の説明は「オープンソースの脅威レポートを自動で解析し、構造化された指標（indicators）を抽出し、脅威のコンテキストを WAF ルールへ直接つなぐ」です。

**Cloudflare が「agentic skills（エージェント的スキル）」と呼んでいるのは、従来は脅威アナリストが手作業でやっていた仕事を再現する自動ワークフローです。** 具体的には、レポートの要約、IoC（侵害指標）の抽出、タグ付け、コンテキストの維持です。

**この「スキル」という言い方には注意が必要です。** 公式記事には **MCP への言及がありません。** アクセス経路はダッシュボードと API で、**Claude の Agent Skills や MCP サーバーのような、外部のエージェントから呼べる仕組みではありません。** Cloudflare 内部で動く自動処理に「スキル」という名前が付いている、と理解するのが正確です。

**実務的に効くのは、無料枠の設計です。** **全 Cloudflare アカウント**が、**RSS フィード1本の選択、30日間のデータ保持、API とダッシュボードのアクセス**を無料で得ます。Enterprise 階層（Essentials / Advantage / Elite）では、フィード数の拡張、独自データセット、カスタムスキル、保持期間の延長が付きます。

アクセス場所はダッシュボードの **Application Security → Threat Intelligence → Threat Signals** です。

**価値の所在は「脅威情報を読む人がいない」という現実にあります。** 脅威レポートは毎日出ます。読んで、自社に関係するかを判断し、IoC を抽出して防御側へ反映する——この工程には専門性と時間が必要で、**多くの組織はそこに人を置けていません。** 結果として、購読はしているが読まれていないフィードが溜まります。**Threat Signals は、その読解と反映の部分を自動化して、WAF ルールまで繋ぐという設計です。**

**なお本記事は追補です。** 本サイトでは Birthday Week 2026 の発表を日次で追っていましたが、**本件は 09-29 の巡回で記録を落としており、2026-10-05 に出た Birthday Week のまとめ記事と既存メモを突き合わせた際に判明しました。** 発表から6日遅れの記事化である点をお断りしておきます。

## 何が変わったか

- **Threat Signals が 2026-09-29 に GA として公開された**
- **OSINT の RSS フィードを取り込み、自動で処理する**（レポート要約、IoC 抽出、タグ付け、コンテキスト維持）
- Cloudflare はこれらの自動ワークフローを **agentic skills** と呼んでいる
- **抽出した脅威コンテキストを WAF ルールへ直接つなげる**
- **全アカウントに無料枠**: RSS フィード1本、30日間のデータ保持、API + ダッシュボードのアクセス
- **Enterprise 階層（Essentials / Advantage / Elite）**: フィード拡張、独自データセット、**カスタムスキル**、保持期間の延長
- アクセス場所: ダッシュボードの **Application Security → Threat Intelligence → Threat Signals**、および API
- **MCP への言及はない**。外部エージェントから呼ぶ仕組みではなく、Cloudflare 内部の自動処理

## 業務インパクト

**最初に確認すべきは、自社が今どれだけ脅威情報を「読めていないか」です。**

Threat Signals の価値は機能の新しさではなく、**人が足りていない工程を埋めること**にあります。したがって検討の出発点は「この機能が欲しいか」ではなく、**「購読しているフィードのうち、実際に読んで防御へ反映できているものがどれだけあるか」**です。ゼロに近いなら、無料枠でも効果があります。既に専任のアナリストがいて運用が回っているなら、優先度は下がります。

**無料枠がある点は、導入判断のプロセスを変えます。** **予算承認を要さずに試せる**ため、「まず1フィードで試して、有効なら Enterprise 階層を検討する」という進め方ができます。セキュリティ製品は PoC の調整に時間がかかるのが普通なので、**予算なしで始められること自体が実務上の利点**です。

**ただし無料枠の制約は実運用には足りません。** **フィード1本・30日保持**です。脅威情報は複数ソースを突き合わせて初めて精度が出るので、**1本では「自社に関係するか」の判断材料が揃いません。** 30日保持も、インシデント発生後に過去を遡る用途には短いです。**無料枠は評価用、本番は Enterprise 階層という設計**だと理解しておく方が、社内説明で齟齬が出ません。

**WAF ルールへの接続は、便利さと危険が同居します。** 脅威コンテキストを WAF へ直結できるということは、**自動抽出された IoC が誤っていた場合、正当なトラフィックを遮断しうる**ということです。公式記事は接続の仕組みを示していますが、**誤検知時の挙動や、適用前のレビュー工程の有無は読み取れません。** 本番環境へ入れる前に、**ルールの自動適用と手動承認のどちらで運用できるか**を確認してください。ここを確認せずに有効化すると、障害の原因が「脅威情報の自動反映」であることに気付くまで時間がかかります。

**「agentic skills」という名称に引っ張られないことも重要です。** 社内説明で「エージェントが脅威情報を処理します」と伝えると、**MCP やエージェント連携の話と混同されます。** 実体は Cloudflare 内部の自動ワークフローなので、**「脅威レポートの定型処理が自動化されている」と説明する**のが誤解を生みません。

## 副業・個人活用視点

**個人開発や小規模サイトの運用では、無料枠の範囲でそのまま使えます。**

**ただし、個人サイトに対する攻撃の多くは汎用的なスキャンです。** OSINT の脅威情報が扱うのは特定の攻撃キャンペーンや新しい脆弱性の悪用で、**個人サイトの実際のリスクとは必ずしも重なりません。** 「無料だから入れる」より、**WAF の基本ルールとレート制限を先に整える**方が効果が大きいのが実情です。

**効いてくるのは、受託案件でセキュリティの話をする場面です。**

**「うちはセキュリティに人を置けない」という相談は、中小規模の案件でほぼ必ず出ます。** ここで出せる選択肢の数が、提案の質になります。**Cloudflare を既に使っている顧客なら、追加契約なしで脅威情報の自動処理を始められる**という提案は、コストをかけずに「何かやっている」状態を作れる点で通りやすいものです。

**制約を先に言えるかどうかが信頼の分かれ目です。** フィード1本・30日保持では本格運用にならないことを**提案時点で伝える**と、後から「期待と違う」と言われません。**「無料枠で効果を測って、必要なら上位階層へ」という段階を明示する**のが、この製品の正しい売り方です。

**学習素材としては、「スキル」という語の使われ方の実例になります。** 2026年の AI 関連の告知では、「スキル」「エージェント」「エージェント的」という語が、**実装の中身がまったく違うものに対して同じように使われています。** 今回は MCP も外部呼び出しもない内部の自動処理が「agentic skills」です。**用語ではなく実装を確認する習慣**を付ける題材として、わかりやすい例です。
