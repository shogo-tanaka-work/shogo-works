## 要約

Cloudflare が 2026-08-22 の changelog で、**Wrangler と Cloudflare API MCP server の OAuth 認可が optional scopes に対応した**ことを公開しました。対象製品は Agents と Workers です。

これまで OAuth の同意画面は、クライアントが要求したスコープを**全部承認するか、全部拒否するか**の二択でした。今回の変更で同意画面に `Edit Permissions` ボタンが加わり、optional として定義されたスコープを個別に外せるようになりました。required スコープは選択済みのまま外せません。どのスコープを optional にするかはクライアント側の設定で決まります。

**この変更が MCP で効く理由は、MCP サーバーの権限要求の構造にあります。** MCP サーバーは、接続したエージェントが「理論上使いうる」操作をすべてカバーするために、広い権限をまとめて要求する設計になりがちです。Cloudflare 自身が公式ブログで、この構造を all-or-nothing の同意画面が正当化しにくくなった理由として挙げています。読み取りだけさせたいのに書き込みや削除まで含まれている、という状況で、利用者側には「全部許可する」か「接続しない」しか選択肢がありませんでした。

スコープの評価対象は、**その認可フローで実際に要求されたものだけ**です。クライアントに設定されている全スコープが並ぶわけではないため、同意画面は目の前のタスクに必要な範囲に収まります。optional スコープが要求されていない場合、同意画面の見た目はこれまでと変わりません。

実装側で注意が要るのは、**発行されるアクセストークンが実際に許可されたスコープだけを反映する**点です。要求したスコープが全部通る前提で作られたクライアントは、部分許可されたトークンで想定外の失敗をします。断られたスコープが後で必要になった場合は、再認可して追加で許可する流れになります。

今回の対応は、2026-08-20 に Cloudflare の OAuth 基盤側で optional scopes が一般提供されたこと（`From all-or-nothing to task-based OAuth consent`）を受けたものです。基盤の機能が出た2日後に、Wrangler と Cloudflare API MCP server という自社の主要クライアントへ適用された形になります。既存の OAuth アプリは、opt-in しない限り変更なしでそのまま動きます。

## 何が変わったか

- Wrangler（`wrangler login`）と Cloudflare API MCP server の OAuth 認可で、optional スコープを個別に外せるようになった
- 同意画面に `Edit Permissions` ボタンを追加。optional スコープをトグルで選択できる
- required スコープは選択済みで固定。外せない
- スコープの評価対象は、その認可フローで要求されたものだけ（クライアント設定の全スコープではない）
- 発行されるアクセストークンは、実際に許可されたスコープのみを持つ
- 断ったスコープが必要になった場合は、再認可して追加許可する
- optional スコープが要求されない認可フローでは、同意画面の挙動は従来どおり
- 既存の OAuth アプリは opt-in しない限り変更なしで動作する

## 業務インパクト（一般企業向け）

**MCP サーバーの社内承認をどう出すか、という問題に直接効く変更です。** 社内で AI クライアントに MCP サーバーを繋ぐとき、情シスやセキュリティ側が最初に見るのは「何ができてしまうか」です。これまでの all-or-nothing では、要求スコープの中に1つでも危険な操作が含まれていると、**サーバー全体を承認できない**という結論になりがちでした。結果として、便利だが承認が下りない、あるいは承認プロセスを迂回して個人アカウントで繋ぐ、という二択に追い込まれます。

optional scopes が入ると、この判断が「サーバーを許すか」から「**どのスコープを許すか**」に変わります。承認条件を「読み取り系のスコープのみ許可、書き込み・削除は個別申請」のような形で書けるようになるため、**社内規程として運用可能な粒度**に落ちます。すでに MCP 接続を禁止している組織にとっては、禁止を解除する条件を作り直す材料になります。

**運用手順の見直しも必要です。** `Edit Permissions` は同意画面上の操作なので、実際に何を外すかは接続する担当者が決めます。ここを個人判断に任せると、人によって付与範囲が違う状態になります。承認済みの構成を手順書に落とし、**スクリーンショット付きでどのトグルを外すかまで指定する**のが現実的です。同意画面はその認可フローで要求されたスコープしか出さないため、クライアントのバージョンが上がると表示が変わりうる点も手順書に注記が要ります。

**既存の接続は自動では絞られません。** 今回の変更は新しい認可フローに効くもので、過去に全スコープで承認したトークンがその場で縮むわけではありません。最小権限を実際に効かせるには、既存の接続を洗い出して再認可する作業が要ります。棚卸しの対象は、Wrangler でログインしている開発者の端末と、Cloudflare API MCP server を登録している AI クライアントの両方です。

**自社で MCP サーバーを提供している場合は、設計側の宿題が出ます。** クライアント設定で required と optional をどう分けるかは提供側の判断です。ここを「全部 required」にすると、利用者側は今までどおり全部承認するしかありません。逆に細かく optional にすれば、部分許可されたトークンで動くようにサーバー側とクライアント側を作る必要があります。**エラーを返すのではなく、使えない操作を機能一覧から落とす**設計にできるかが、実用性の分かれ目になります。

## 副業・個人活用視点

個人で Cloudflare Workers を触っている場合、まず効くのは `wrangler login` の権限範囲です。**個人アカウントは業務と趣味が同じアカウントに同居しがち**で、全スコープを渡すと、副業案件の検証用に入れたツールが本業や個人サイトのリソースにも触れる状態になります。optional スコープを外せるようになったことで、案件ごとに必要な範囲だけを渡す運用が取れます。

**AI クライアントに Cloudflare API MCP server を繋いでいる人は、優先度が高い変更です。** エージェントに Cloudflare の操作を任せる構成では、想定していない操作が走るリスクが常にあります。デプロイと設定変更は任せたいが DNS とアカウント設定は触らせたくない、という切り分けが同意画面で表現できるようになりました。**一度全部許可してしまうと、後から絞るには再認可が要る**ため、今のうちに繋ぎ直しておくほうが手間は少なくて済みます。

クライアント開発をしている人にとっては、**部分許可されたトークンで動くクライアントを作る**という要件が現実の設計課題として出てきます。これはポートフォリオの題材としても使えます。「全権限を前提にしない」設計は、企業向けのツールを作る側の基本姿勢であり、面談でも説明しやすい論点です。要求スコープを required と optional に分けた根拠を書けると、権限設計を理解していることの証明になります。

なお、この変更は Cloudflare の OAuth 基盤に 2026-08-20 に入った機能の適用先という位置づけです。**同じ仕組みが他の Cloudflare クライアントにも広がる可能性**があるため、Cloudflare 関連の OAuth 連携を持っている人は、同意画面が変わったときに「なぜ変わったか」を説明できる状態にしておくと、周囲への説明コストが下がります。
Cloudflare が 2026-08-22 の changelog で、**Wrangler CLI と Cloudflare API MCP server の OAuth 認可に「任意スコープ（optional scopes）」を導入した**と発表しました。認可時の同意画面に権限を編集する導線が追加され、クライアントが要求するスコープのうち任意のものを個別にオン / オフできます。

これまでは、各クライアントが要求するスコープを**まとめて承認するしかありませんでした**。つまり「そのツールが求める全権限を渡すか、そのツールを使わないか」の二択です。今回の変更で、その中間が生まれました。**必須スコープは選択されたまま外せませんが、任意スコープは自分のワークフローに必要な分だけに絞れます**。

見た目は同意画面の UI 変更です。ただ、changelog のタグが `Agents` と `Workers` になっている点、そして対象に **Cloudflare API MCP server** が含まれている点を合わせて読むと、意味が変わってきます。MCP server は AI エージェントが Cloudflare のアカウントを操作するための入口です。**そこに渡す権限を、人間が認可の時点で削れるようになった**というのが本件の実質です。

運用面の設計も公式に示されています。付与しなかったスコープが必要なコマンドやツール呼び出しに当たった場合は、**クライアントを再認可してそのスコープを付与する**。これは「最小で始めて、詰まったら足す」という進め方が公式に想定されているということです。事前に必要な権限を完全に洗い出してから認可する必要はありません。

なお、どのスコープが必須でどれが任意なのかという一覧は、changelog 本文には掲載されていません。公式は参照先として `wrangler login` のドキュメントと「Edit optional permissions」を挙げています。**実際のスコープ構成は認可時の同意画面で確認する**ことになります。

## 何が変わったか

- Wrangler CLI と Cloudflare API MCP server の OAuth 認可が、**任意スコープに対応**
- 認可時の同意画面に、**付与する権限を編集する導線**が追加された
- 任意スコープは個別にオン / オフできる。**必須スコープは選択が固定**され外せない
- 任意スコープを絞ると、そのツールがアクセスできる範囲が絞られる
- 付与しなかったスコープが必要になった場合は、**クライアントを再認可して個別に追加**する
- 対象は changelog のタグ上 `Agents` と `Workers` の2製品
- スコープ名の具体的な一覧は changelog に記載がない（同意画面および `wrangler login` のドキュメント側）

## 業務インパクト（一般企業向け）

**エージェントに本番インフラを触らせる構成を検討している組織にとって、これは判断材料が1つ増えた変更です。** MCP server 経由で Cloudflare のアカウントを操作させる場合、これまでは要求される全権限を渡すことが前提でした。読み取りだけさせたいのに、設定変更や削除の権限まで一緒に付いてくる。この構造が理由で導入を見送っていた組織は少なくないはずです。**任意スコープが入ったことで、「渡せる範囲まで渡して使う」という選択肢が生まれました。**

**まず決めるべきは、誰が同意画面を操作するかです。** 任意スコープは認可する人間が選びます。開発者が自分の判断で全部オンにすれば、変更前と何も変わりません。**権限を絞れる機能は、絞る運用を決めて初めて意味を持ちます。** 具体的には、Cloudflare アカウントに対する MCP 接続を誰が認可してよいか、どのスコープを標準で外すか、例外を認める場合の承認経路はどうするか。この3点を先に決めてから展開してください。

**再認可の運用も設計に含めてください。** 「足りなくなったら再認可する」は、裏を返せば**作業の途中で認可フローに戻される**ということです。開発者が急いでいるときに再認可を求められれば、次からは最初に全部オンにするようになります。これを防ぐには、よく使う操作に必要なスコープの組み合わせを社内で標準化し、「この用途ならこのセット」と示せる状態にしておくことです。**最小権限は、都度考えさせると必ず形骸化します。**

**監査の観点では、認可時点の記録が残るかどうかを確認しておく価値があります。** どのクライアントにどのスコープを渡したかは、インシデント時に真っ先に確認する情報です。MCP クライアントは開発者のローカル環境で動くことが多く、組織側から見えにくい領域でもあります。**認可の判断をローカルに閉じたままにしない**ための記録の残し方を、あわせて決めておいてください。

この変更は Cloudflare 固有ですが、**構図としては他のベンダーにも波及していく話です。** エージェントに API を触らせる需要が増えれば、「全権限を渡すか使わないか」の二択はどこでも問題になります。今のうちに権限設計の考え方を社内で作っておくと、次に別のツールで同じ選択を迫られたときに使い回せます。

## 副業・個人活用視点

**Cloudflare を使った開発や運用を請けている立場なら、これは提案材料になります。** クライアントの環境に MCP 接続を持ち込むとき、「必要な権限だけを渡す構成にできます」と言えるかどうかで、話の通りやすさが変わります。特に、情シスが AI エージェントの導入に慎重な組織では、**権限を絞れること自体が導入可否の分かれ目**になります。

個人で Wrangler を使っている場合も、**認可を一度やり直す価値はあります。** これまでに認可したクライアントは、当時の仕様で全スコープを持ったままです。今の自分のワークフローに必要な範囲を確認して、再認可で絞り直しておくと、ローカル環境が侵害されたときの被害範囲が変わります。手元の作業だから、で済ませない方がよい領域です。

**研修や教材の題材としても使いやすい変更です。** 「最小権限の原則」は概念としては誰でも知っていますが、実際に手を動かして体験する機会は多くありません。同意画面でスコープを絞り、足りなくなって再認可する。この一往復を実際にやってみると、**最小権限が理想論ではなく運用コストとのトレードオフである**ことが体感できます。MCP やエージェント運用の研修を組む場合、実機で試せる題材として組み込む価値があります。

**MCP まわりの権限設計を語れること自体が、当面は差別化になります。** エージェントに何をさせるかの議論は多いのに、何をさせないかの議論は追いついていません。Cloudflare のこの変更のように、ベンダー側が権限を細かく切れる仕組みを出し始めた今が、**「権限をどう設計するか」を提案の軸に据えるタイミング**です。
