## 要約

Cloudflare は 2026-10-01、**Artifacts** をオープンベータにしました。

**Artifacts は「Git を話すバージョン管理ファイルシステム」です。** 公式の説明では、**プロジェクト / ユーザー / セッション / タスク単位**にリポジトリを分けて持つ使い方を想定し、**数百万リポジトリ規模へのスケール**を前提にしています。

**この「単位」の列挙が、製品の狙いを示しています。**

**従来、Git リポジトリは「プロジェクトに1つ」が基本でした。** チームが1つのリポジトリを共有し、ブランチで作業を分けます。**この前提は、作業する主体が人間で、数が十数人規模であることに依存しています。**

**エージェントが並列で作業する状況では、この前提が崩れます。** 10体のエージェントが同時に同じリポジトリを触れば、**ブランチの管理とマージの調整だけで手一杯になります。** 「セッション単位」「タスク単位」でリポジトリを払い出すという発想は、**衝突を構造的に避ける**ための選択です。

**オープンベータで使える機能は5点です。**

**(1) Workers 連携。** Workers Builds 経由で接続し、**本番ブランチへの push で Worker をデプロイ、他ブランチは preview 環境を作ります。**

**(2) プログラムからのリポジトリ管理。** Workers の **Artifacts バインディング**で、リポジトリの**作成・fork・検査**、ファイル読み取り、**Git トークンの発行**ができます。

**(3) イベント購読。** **作成・削除・push・clone** といったライフサイクルイベントに反応できます。

**(4) データのローカライゼーション。** リポジトリのデータを **US または EU** で保存・処理できます。

**(5) 監視。** 操作数・pull・push・エラーのメトリクスを、**ダッシュボードまたは Analytics API** で追えます。

**提供条件。対象は Workers Paid プラン**で、**課金開始は 2026-10-14** です。

**同日、関連する公募が告知されました。** Cloudflare は **「次の Git プラットフォームを Workers と Artifacts の上に作ってほしい」**という公募を開始し、**数百から数千のエージェントが同一コードベースで同時に協働する**状況に対応する設計を求めています。**締切は 2026-10-14**、応募要件は 5〜10分のデモ動画・オープンソースのコード（MIT / Apache / BSD）・利用手順。**上位3チームはサンフランシスコの Cloudflare Connect に招待**され、**1位には Cloudflare クレジット 25,000 ドル**が提供されます。

**なお、課金開始日について公式内に食い違いがあります。** changelog は **2026-10-14**、公募記事は **2026-10-15** と記載しています。**実際の請求日は公式の料金ページで確認してください。**

## 何が変わったか

- **Artifacts がオープンベータ**。Git 互換のバージョン管理ファイルシステム
  - **プロジェクト / ユーザー / セッション / タスク単位**でリポジトリを分ける想定
  - **数百万リポジトリ規模**へのスケールを前提
- **Workers 連携**: Workers Builds 経由。本番ブランチの push で Worker をデプロイ、他ブランチは preview 環境
- **プログラムからのリポジトリ管理**: Artifacts バインディングで作成・fork・検査、ファイル読み取り、**Git トークン発行**
- **イベント購読**: 作成 / 削除 / push / clone
- **データのローカライゼーション**: **US または EU** で保存・処理
- **監視**: 操作数 / pull / push / エラーのメトリクス（ダッシュボード、Analytics API）
- **対象は Workers Paid プラン。課金開始 2026-10-14**（公募記事では 2026-10-15 と記載。**公式内で1日の差**）
- 同日の公募: 「次の Git プラットフォーム」コンテスト。**締切 2026-10-14**、1位に **Cloudflare クレジット 25,000 ドル**

## 業務インパクト（一般企業向け）

**この更新の意味は、製品そのものより「前提が変わり始めている」点にあります。**

**まず、現時点で多くの企業に直接の影響は無いことを書いておきます。** Artifacts はオープンベータで、対象は Workers Paid プランです。**既存の GitHub / GitLab 運用を置き換える話ではありません。** 導入検討の対象になるのは、**Workers 上でエージェントを動かしている組織**に限られます。

**そのうえで、押さえておく価値がある論点を3つ挙げます。**

**1つ目は、「リポジトリを払い出す」という運用の是非です。**

**セッションやタスクごとにリポジトリを作る方式は、衝突を避けられる代わりに、管理対象を増やします。** 数百万リポジトリへスケールする設計だと公式が言っているのは、**数が増えること自体を前提にしている**という意味です。

**ここで問題になるのは、ライフサイクルです。** 作ったリポジトリを**いつ消すのか**。タスクが終わったら消すのか、監査のために残すのか。**残すなら、どれが生きていてどれが死んでいるかをどう判別するのか。** 公式は作成・削除・push・clone のイベント購読を提供しているので、**ライフサイクル管理を自分で実装できる**作りになっています。逆に言えば、**自分で実装しないと管理されません。**

**この手の仕組みを導入するときの失敗は決まっています。** 作る側の自動化だけを作り、**消す側を作らないことです。** 結果として数万のリポジトリが残り、どれが必要かが誰にも分からなくなります。**導入を検討するなら、消す条件を先に決めるべきです。**

**2つ目は、データのローカライゼーションです。**

**US または EU でリポジトリのデータを保存・処理できる**という点は、EU 向けのサービスを持つ組織には直接の意味があります。**コードや生成物がどこに保存されるかは、GDPR の議論に乗る**ことがあります。

**ただし、日本の組織にとっては選択肢が US / EU の2つであり、国内保存はできません。** 「国内でないと駄目」という要求がある案件では、この製品は選べません。**確認しないまま検討を進めると、終盤で止まります。**

**3つ目は、Git トークンの発行がプログラムからできる点です。これはセキュリティの論点です。**

**Worker からリポジトリを作り、Git トークンを発行して、エージェントに渡す。** この流れは便利ですが、**トークンの発行が自動化されるということは、トークンの管理も自動化が必要**ということです。

**考えるべき点は3つあります。** **発行したトークンの有効期限は何か。** **誰がどのトークンを持っているかを追えるか。** **漏れたときに失効させられるか。** 公式は操作数や pull / push のメトリクスを提供しているので、**異常な使用の検知は可能**な作りです。ただし**検知の仕組みは自分で組む**ことになります。

**公募について、1点だけ触れます。**

**締切が 2026-10-14 で、公開から2週間です。** これは**新規に作り始めるチームを募っているのではなく、すでに作っているチームを拾う設計**と読めます。自社で参加を検討する場合、**既存の取り組みがあるかどうかで判断すべき**で、この公募のために着手するのは時間的に無理があります。

**むしろ注目すべきは、公募の問題設定そのものです。** 「数百から数千のエージェントが同一コードベースで同時に協働する」状況をどう扱うか。**これは Cloudflare が解けていない（だから外部に投げた）問題**であり、**今の時点で業界に答えが無い**ということを示しています。**自社でエージェントの並列実行を進めるなら、この部分は自分で設計することになります。**

## 副業・個人活用視点

**個人開発者にとって、Artifacts の面白さは「リポジトリを使い捨てにできる」ことです。**

**個人で何かを試すとき、リポジトリを作るのは少し重い作業です。** GitHub で新規リポジトリを作り、名前を決め、公開範囲を決める。**試すだけのコードに名前を付けるのが面倒で、結果として既存のリポジトリに雑多なものを突っ込む**ことになりがちです。

**プログラムからリポジトリを作れるなら、この手間が消えます。** 「とりあえず作って、不要なら消す」という運用ができます。**エージェントに作業させるときに、作業ごとにリポジトリを払い出す**という使い方は、個人規模でも意味があります。

**具体的な使いどころを2つ挙げます。**

**1つ目は、エージェントの並列実行です。** 同じ課題に対して複数のアプローチを並列で試したいとき、**ブランチで分けると履歴が混ざります。** リポジトリごと分ければ、**完全に独立した試行**になり、良かったものだけを残せます。

**2つ目は、preview 環境の自動生成です。** **本番ブランチの push で Worker をデプロイし、他ブランチは preview を作る**という仕組みは、個人のプロジェクトでも便利です。試作を見せるための URL が自動で出るのは、受託の提案でも効きます。

**ただし、個人利用での制約を2つ書きます。**

**1つ目。対象は Workers Paid プランです。** 無料枠では使えません。月5ドル程度の支出が前提になります。

**2つ目。課金開始が 2026-10-14（または 10-15）です。** **ベータだから無料、という状態は2週間しかありません。** 試すのは構いませんが、**作りかけで放置すると課金が始まります。** 使わないなら消す、という片付けを 10月中旬までにやる必要があります。公式内で日付が1日ずれているので、**料金ページで確認してから予定を立ててください。**

**受託の文脈では、現時点で提案材料にするのは早いと考えます。**

**理由は2つあります。** **オープンベータであること**と、**既存の GitHub 運用を置き換える動機が顧客側に無いこと**です。「Git を Cloudflare に移しましょう」という提案は、**移行コストに見合う理由を説明できません。**

**提案になり得るのは、新しく作るものに限ります。** たとえば「エージェントが生成した成果物をバージョン管理して顧客に渡す仕組み」のような、**既存のリポジトリ運用と競合しない用途**です。この場合、**GitHub に大量のリポジトリを作るより Artifacts のほうが素直**という説明が立ちます。

**学習の観点では、公募の問題設定を自分で考えてみる価値があります。**

**「数千のエージェントが同じコードベースを同時に触るとき、何が壊れるか」** を考えると、Git の前提が見えてきます。**Git のマージは「人間が意図を持って衝突を解決する」ことを前提にしています。** レビューも同じで、**人間が読む速度がボトルネックになります。**

**この前提を外したときに何が必要かを考えるのは、良い思考訓練です。** 衝突解決を自動化するのか、衝突が起きない分割をするのか、レビューの単位を変えるのか。**答えは出ていませんが、問いの立て方を知っておくと、自分がエージェントを並列化するときに同じ壁にぶつかったときの見通しが良くなります。**

**もう1つ、「作る自動化と消す自動化」の非対称性に注目してください。** 自動で作る仕組みは楽しく作れますが、**消す条件を決めるのは退屈で、だから後回しになります。** そして後回しにすると、必ず管理不能な数のリソースが残ります。**これは Artifacts に限らず、自動化を設計するときの一般的な落とし穴です。**
