## 要約

Cloudflare は2026-10-30、**Durable Objects のコード更新を既定で遅延適用にしました**。設定を変えなくても、次回のデプロイから挙動が変わります。

- **従来**: デプロイすると、稼働中のオブジェクトにも新しいコードが即座に適用された。処理中の作業が中断したり、開いている接続が閉じたりすることがあった
- **現在**: 稼働中のオブジェクトは、ハイバネート（休止）に入るまで**現行のコードで動き続ける**。休止後の次のリクエストから、新しいコードで起動する
- **待つ上限**: `max_delay` の既定は **300秒（5分）**。それを過ぎると新しいコードに切り替わる

Hibernation API を使った WebSocket は、オブジェクトが休止後に新しいコードへ移っても**接続が維持されます**。

## 何が変わったか

- 既定の方式が `deferred`（遅延）になった。`max_delay` は 0 秒から 86,400 秒（24時間）まで、ミリ秒単位で指定できる
- Wrangler の設定では `durable_objects` の下の `code_update_strategy` に `mode`（`deferred` または `immediate`）と `max_delay` を書く
- 単発のデプロイだけ変えたい場合は、`wrangler versions deploy` に `--durable-objects-code-update-mode` を渡す（`immediate` または `deferred <期間>`）
- **即時適用に戻す**には、`mode` を `immediate` にする。障害対応で新しいコードをすぐ反映したいときや、デプロイの仕組みが新コードを前提にしているときが該当する
- **ベストエフォート**であり、Cloudflare のランタイム更新などで、`max_delay` の前にオブジェクトがリセットされることがある

## 業務インパクト（一般企業向け）

**デプロイ時の「処理が途切れる」問題は減ります。** チャット、共同編集、予約の排他制御など、Durable Objects に状態を持たせたサービスでは、更新のたびに接続が切れる原因になっていました。既定で改善されるため、夜間にしかデプロイできなかった運用を見直せる可能性があります。

**一方で、新しい前提が生まれます。** デプロイ直後の最大5分間、**同じオブジェクト群の中で旧コードと新コードが併存**します。次のような更新は影響を受けます。

- 保存する状態の形式を変える更新（旧コードが新しい形式を読めない、またはその逆）
- クライアントとのメッセージ形式を変える更新
- 旧コードで動くオブジェクトと、新コードで動くオブジェクトが互いに呼び出し合う構成

こうした更新では、旧新の両方が読める形（互換期間を設ける）に分けて出すか、`immediate` を明示するかを、リリース手順に書いておくと安全です。

**注意点**: 本記事は Cloudflare の更新情報に基づき、実際の切り替え時間や、ゲートウェイ越しのデプロイ（段階的デプロイ、REST API）での挙動は検証していません。詳細は公式ドキュメントの Durable Objects のコード更新の項を参照してください。

## 副業・個人活用視点

**受託で Durable Objects を使ったサービスを運用しているなら、まず手元のリリース手順に「旧コードが最大5分動く」前提を足してください。** 小さな修正のデプロイは、これまでより安全になります。

**確認する価値があるのは、保存形式を変えた直後の挙動です。** 検証環境で、旧コードのオブジェクトが動いている最中に新しいコードをデプロイし、読み書きが壊れないかを見ると、本番での取りこぼしを避けられます。

**急ぎの修正を出すときは、`--durable-objects-code-update-mode immediate` を覚えておくと便利です。** 障害対応で、5分待てない場面に使えます。

**情報源の制約**: 本記事は Cloudflare の changelog（2026-10-30）に基づく。必要な Wrangler のバージョンは公式ページに記載がなく、実際の切り替え挙動は未検証。
