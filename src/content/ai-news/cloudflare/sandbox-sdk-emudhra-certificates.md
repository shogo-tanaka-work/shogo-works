## 要約

eMudhra の中間認証局8つの秘密鍵が復元できる状態にあり、これらにチェーンする証明書は**任意のホスト名で偽造できます**。Cloudflare Sandbox SDK の **0.12.14 より前のイメージ**はこれらを信頼していました（changelog 2026-10-22）。

コンテナから直接出る HTTPS 通信、たとえば `mountBucket()`、バックアップ、`gitCheckout()`、トンネル、サンドボックス内で動くコードの通信は、偽造証明書で傍受され得ます。

## 何が変わったか

- **0.x**: `@cloudflare/sandbox@0.12.14` を入れ、Dockerfile の `FROM` を同じ版のイメージ（例: `docker.io/cloudflare/sandbox:0.12.14`）に変えて再デプロイする。`-python`、`-opencode`、`-musl` の接尾辞は残す。`next` プレリリースは `0.13.0-next.825.1` 以降。デプロイのロールアウトで実行中のサンドボックスは新イメージに入れ替わる
- **0.x で更新できない場合（0.8.7 以降）**: `interceptHttps = true` と `outbound` で HTTPS を Worker 経由にし、443 番ポートの証明書を Cloudflare に検査させる。`cloudflared` のトンネルなど他ポートの TLS は対象外で、注入された証明書を無視するクライアントは接続できなくなる
- **1.x**: SDK 自体は TLS 接続を持たないため更新不要。イメージが信頼する証明書を決めるので、ベースイメージを `docker pull` し、ビルドキャッシュを消して再ビルドし、デプロイしたうえで実行中のサンドボックスを停止する。スナップショットは作成元のイメージに戻るため、新しいイメージから作り直す
- **確認方法**: サンドボックス内で公式が示す検証用ホストに `curl`、`node`、`bun` など使っているクライアントで接続し、**すべて失敗すること**を確かめる
- **イメージ側の変更**: 0.12.13 で CA バンドル、Node.js、`cloudflared`、pip が該当証明書を拒否するようになり、0.12.14 で Bun も拒否するようになった

## 業務インパクト（一般企業向け）

**Sandbox を使った AI エージェントや社内ツールを動かしているチームは、棚卸しが必要です。** 自社のサンドボックスが 0.x か 1.x か、どの版のイメージで動いているかを確認し、上の手順に沿って更新します。

1.x の落とし穴は、`wrangler deploy` がローカルのイメージとビルドキャッシュを使う点です。`docker pull` とキャッシュ削除を飛ばすと、古い CA 証明書を含んだままのイメージを再び出荷してしまいます。実行中のサンドボックスは、起動時のイメージを止めるまで使い続けます。

更新後は検証用ホストへの接続が失敗することを確認し、その結果を作業記録に残してください。セキュリティ部門への報告にも使えます。

## 副業・個人活用視点

**自分の Cloudflare アカウントで Sandbox を使った検証環境や納品物がある場合も、同じ確認をしておくと安心です。** 小さなプロジェクトでも、`FROM` の版を上げて再デプロイするだけで済む場合が多く、作業は短時間です。

クライアントに Sandbox ベースの仕組みを納品している場合は、保守の連絡として「証明書の信頼設定を更新した」旨を伝える材料になります。証明書の失効や侵害は、アプリのコードを触っていなくても対応が必要になる種類の変更だと理解しておくと、今後の保守計画に役立ちます。
