## 要約

**Workers AI に `@cf/daily-co/phonellm-mini-alpha-2`（PhoneLLM Mini Alpha 2）が追加されました。** 提供元は **Daily の Pipecat** チームです。

**用途は音声エージェントとリアルタイムアプリに絞られています。** モデルが**素早く応答し、会話の途中で正しいツールを呼ぶ**ことを求められる場面を想定しています。

**このモデルが存在する理由は、公式のレイテンシの説明に書かれています。ここが本題です。**

**音声エージェントでは、言語モデルが speech-to-text と text-to-speech の間に挟まります。** つまり**モデルの遅延が、そのまま発話者の待ち時間に積み上がります。**

**この構造が、音声でのモデル選択を他の用途と別物にします。** テキストのチャットなら、応答が3秒かかっても画面を見ながら待てます。**電話では3秒の無音は不自然です。** 相手は「切れたのか」と思います。音声認識に数百ミリ秒、読み上げに数百ミリ秒かかる上に、**モデルの思考時間が乗ります。**

**結果として「賢いが遅いモデル」は、この用途では使えません。** 性能のベンチマークで上位のモデルを選ぶ、という通常の判断が通りません。**求められるのは、必要な精度を満たす中で最も速いモデル**です。

**PhoneLLM Mini はその方向に振った設計です。**

**学習の素性が明示されています。** Pipecat が **NVIDIA Nemotron 3 Nano 30B** を、**電話・カスタマーサポートのシナリオで事後学習（post-training）**しました。その結果、**reasoning モードなしでも指示追従とツール呼び出しが良い**とされています。

**「reasoning モードなしでも」という部分が設計の割り切りです。** 推奨設定にそれが表れています。

**公式の推奨設定は `temperature: 0` と `chat_template_kwargs: { enable_thinking: false }` です。** **reasoning を明示的に切って使う前提**です。

**これは性能を諦めているのではなく、用途に合わせた判断です。** 電話応答で求められるのは、長い推論の末に最適な答えを出すことではありません。**「何を聞かれたか」を正しく把握し、必要なら正しいツールを呼び、短く答えること**です。この種のタスクでは、**事前に当該ドメインで学習させておく方が、汎用モデルに毎回考えさせるより速くて安定します。**

**`temperature: 0` の推奨も同じ方向です。** 応答の揺れを許容しない。電話対応では**毎回同じ質問に同じ答えを返す**方が望ましいためです。

**アクセスは2経路あります。** **Workers AI バインディング（`env.AI.run()`）** と **REST API（`/ai/run`）** です。

**音声エージェントのサンプル構成も示されています。** Cloudflare が提供する Pipecat 音声エージェントのサンプルは、**Durable Object 内で動き、Realtime SFU 経由で WebRTC を使います。** 既定のモデルは **DeepSeek V4 Flash** ですが、**コーディングエージェントにプロンプトを渡せば PhoneLLM 構成でデプロイできる**と記載があります。

**この構成が成立する前提として、Python Workers が一般提供になったことが挙げられています。** Pipecat は Python のフレームワークなので、**Python Workers の GA が音声エージェントを Workers 上で動かす道を開いた**という関係です。

**公式に記載がない項目があります。ここは確認が必要です。**

**価格は未記載です**（Workers AI の価格ページを参照とされています）。**コンテキストウィンドウも未記載です**（モデルページを参照）。**そしてモデル名に `alpha-2` が入っています。** **alpha 版である点は、本番適用の判断では前提として扱うべきです。**

## 何が変わったか

## 業務インパクト（一般企業向け）

**該当するのは、電話応答や音声での問い合わせ対応を自前で組もうとしている組織です。** 既存のコールセンターシステムを使っている場合は、すぐ関係する話ではありません。

**この更新が示す実用的な論点は、モデル選択の基準です。**

**音声用途では「最も賢いモデル」を選ぶ判断が間に合いません。** レイテンシが積み上がる構造があるためです。**ところが社内の検討では、テキスト用途と同じ基準でモデルを比較してしまいがちです。** ベンチマークのスコアや、長文処理の能力で選ぶ。**音声では、それが通話品質を直接下げます。**

**PhoneLLM Mini の設計は、この基準の違いを明示しています。** 電話・サポート領域に絞って事前学習し、reasoning を切り、temperature を 0 にする。**汎用性を捨てて速度と安定性を取っています。** 音声エージェントの検討では、**「この用途に特化したモデルがあるか」を先に探す**のが筋だという示唆です。

**`temperature: 0` の推奨は、業務用途では利点として読めます。** 顧客対応では**同じ質問に毎回同じ答えを返す**ことが求められます。応答が揺れると、クレームや説明責任の問題になります。**揺れを抑える設定が公式の推奨になっているのは、業務適用を前提にした設計**です。

**本番適用の判断には追加確認が必要です。** **alpha 版であり、価格とコンテキストウィンドウが本告知に記載されていません。** 音声エージェントでは、**会話の履歴をどこまで保持できるか**が応答品質に直結するため、コンテキストウィンドウは重要な数字です。**モデルページでの確認が前提**になります。価格についても、通話量が多い用途では**トークン単価が事業性を決めます。**

**構成面では、Durable Object + Realtime SFU（WebRTC）というサンプルが参考になります。** 音声エージェントは**セッション状態を持つ**必要があるため、Durable Object との組み合わせは理にかなっています。**既存の Workers 環境を持っている組織なら、新しい基盤を立てずに試せる**点は検証コストを下げます。

**「コーディングエージェントにプロンプトを渡せばデプロイできる」という記載は、評価コストの観点で見る価値があります。** サンプルの既定モデルを差し替える作業を、エージェントに任せられる前提で書かれています。**PoC の立ち上げが数時間の作業で済む可能性**があります。ただし**公式の記載を鵜呑みにせず、実際に通して確認する**必要はあります。

## 副業・個人活用視点

**音声エージェントは、個人や小規模事業者にとって受託の対象になりやすい領域です。** 電話応対の一次受け、予約の受付、営業時間外の問い合わせ対応。**人を置けない規模の事業者にとって、ニーズが分かりやすい**種類の仕組みです。

**Workers AI 上で組める構成が示されたことは、提案の現実性を上げます。** 音声エージェントは従来、**専用のプラットフォームや電話回線の手配**が前提でした。Durable Object + Realtime SFU + Workers AI で組める構成なら、**既存の Cloudflare 環境の延長で試作できます。** 試作のコストが下がると、提案の前に動くものを見せられます。**音声は実際に聞かないと判断できない**ので、ここは効きます。

**ただし alpha 版である点は、提案時に伝えるべきです。** 顧客に黙って alpha のモデルを本番に入れると、仕様変更で問題が起きたときに自分が責任を負います。**「現時点では alpha なので、PoC として作り、本番適用は GA を待つ」という段取り**で提案するのが筋です。この伝え方ができるかどうかは、継続して仕事をもらえるかに関わります。

**学習の素材としては、「レイテンシが積み上がる構造」の理解が最大の収穫です。** speech-to-text → モデル → text-to-speech という並びで、**各段の遅延が合計される。** この構造を理解していると、**どこを速くすれば効くのかが判断できます。** モデルだけ速くしても、音声認識が遅ければ体験は変わりません。**システム全体で遅延の予算を配分する**という考え方は、音声以外のリアルタイム処理にもそのまま使えます。

**「用途特化モデル」という選択肢を知っておく価値があります。** 汎用の大きいモデルを使うのが当然になっていますが、**特定領域に絞って学習させた小型モデルの方が、速度と安定性で勝つ場面があります。** PhoneLLM Mini はその実例です。**顧客に「一番賢いモデルを使ってほしい」と言われたときに、用途に応じた説明ができる**かどうかで、提案の質が変わります。

**発信の素材としては、実測のレイテンシに価値があります。** 公式は設計意図を書いていますが、**実際に何ミリ秒で応答が返るか、日本語の音声でどう振る舞うかは記録されていません。** Durable Object 構成での実測、DeepSeek V4 Flash との比較は、**公式ドキュメントにない情報**です。alpha 版のうちの記録は、GA 後に比較対象としても価値が残ります。
