## 要約

Cloudflare は 2026-10-17、ローカル開発ツール **Local Explorer** から **Worker の `scheduled()` ハンドラへ Cron Trigger を単発で投入できる**ようになったと告知しました。

**地味に見えますが、これは今まで手作業だった部分です。** Workers の Cron Triggers（スケジュール実行）をローカルで試すには、従来は**自分でリクエストURLを組み立てて叩く**必要がありました。公式ポストはこの点を明示して「もう URL を組む必要はない」と書いています。

使い方は、`cf dev` / `wrangler dev` / Cloudflare Vite プラグインでローカル開発サーバーを起動し、そのURLの **`/cdn-cgi/local/explorer`** を開いて **Cron Triggers** を選ぶだけです。要件は **Wrangler 4.139.0 以降、または Vite プラグイン 1.60.0 以降**で、Worker が `scheduled()` を export していること。

**実行の選択肢は2系統あります。** 1つは `Configured Crons` で、**すでに設定済みの cron 式**をそのまま投入します（実行時刻は既定 `Now`、UTC 日時または epoch ミリ秒でプリセットを追加できる）。もう1つは**アドホック実行**で、cron 式を直接入力するか、5フィールドUTCスケジュールのビルダーを使います。ビルダーは間隔・日次・平日・月次に加えて、**Quartz 系の `L` / `W` / `LW` / `#`** に対応しています。アドホック式には、環境側に対応する Cron Trigger が設定されている必要はありません。

**確認できる内容も明記されています。** 実行結果には outcome、**`noRetry()` が適用されたかどうか**、投げられた cron 式、実行時刻が出ます。`noRetry()` の状態が見えるのは実用的です。スケジュール実行の失敗時にリトライさせるかは実装側の判断ですが、**その判断が意図どおり効いているかは、従来はログを追うしかありませんでした。**

**もう一つの軸が、エージェント向けの HTTP API です。** 同じ操作が **`POST /cdn-cgi/local/explorer/api/local/scheduled?worker=<WORKER_NAME>`** として開かれています。body は `{"cron":"0 * * * *","scheduled_time":1745856238000}` のような形で、cron 式が必須、`scheduled_time` は任意の Unix ミリ秒です。

さらに、Local Explorer の API 全体は **`/cdn-cgi/local/explorer/api` で OpenAPI 記述**されており、**AI エージェントを検出すると開発サーバーがこのエンドポイントを案内する出力を出します。** ツールの側が「エージェントが来る」ことを前提に、自分の使い方を提示してくる設計です。

**注意点が3つ明記されています。** アドホック実行と保存したプリセットは**ブラウザ内に留まり**、`cloudflare.config.ts`・Wrangler 設定・デプロイ済みの Cron Trigger を変更しません。**ローカル開発では cron が自動実行されません**（投入は手動のみ）。完全なログとトレースは、その開発セッションで **Observability を有効にしている場合**に見られます。

## 何が変わったか

- **Local Explorer から `scheduled()` ハンドラへ Cron Trigger を単発投入できる**（リクエストURLの自作が不要になった）
- 要件は **Wrangler 4.139.0 以降 / Vite プラグイン 1.60.0 以降**、Worker が `scheduled()` を export していること
- アクセス方法は、開発サーバー起動後に **`/cdn-cgi/local/explorer`** を開き **Cron Triggers** を選択
- **`Configured Crons`**: 設定済み cron 式を実行。実行時刻は既定 `Now`、UTC 日時または epoch ミリ秒でプリセット追加可
- **アドホック実行**: cron 式を直接入力、または5フィールドUTCスケジュールのビルダー。間隔・日次・平日・月次、Quartz 系の `L` / `W` / `LW` / `#` に対応。環境側の Cron Trigger 設定は不要
- 実行結果に **outcome、`noRetry()` の適用状況、投げられた cron 式、実行時刻**が出る
- **HTTP API**: `POST /cdn-cgi/local/explorer/api/local/scheduled?worker=<名前>`、body は `{"cron":"...","scheduled_time":<Unixミリ秒>}`（cron 必須、時刻は任意）
- Local Explorer の API は **`/cdn-cgi/local/explorer/api` で OpenAPI 記述**。**AI エージェント検出時に開発サーバーがエンドポイントを案内**
- アドホック式とプリセットは**ブラウザ内に留まる**。設定ファイルとデプロイ済み Cron Trigger は変更されない
- **ローカル開発では cron は自動実行されない**（手動投入のみ）
- 完全なログ・トレースには **Observability の有効化**が必要

## 業務インパクト（一般企業向け）

**cron で動く処理は、壊れていても気づくのが遅い種類のものです。**

日次バッチ、定期的なデータ同期、レポート生成。この手の処理は、**失敗しても誰も画面を見ていません。** しかも検証しづらい。「毎朝9時に動く」という設定が正しいかを確かめるには、**本番に入れて翌朝を待つ**か、URLを自作して叩くしかありませんでした。

今回変わったのは、その検証が**UIの操作になった**ことです。効くのは次の3点です。

**1. cron 式の書き間違いを、デプロイ前に潰せる。** cron 式は読みづらく、「毎月末」「平日のみ」あたりで間違えます。ビルダーが Quartz 系の `L` / `W` / `LW` / `#` に対応しているので、**式を書く前に意図を選べます。**

**2. `noRetry()` の挙動を確認できる。** スケジュール実行が失敗したときにリトライさせるかは、業務処理では重要な分岐です。二重実行してはいけない処理（請求、通知、外部APIへの登録）でリトライが効いてしまうと、**障害より厄介な事故**になります。実行結果に `noRetry()` の状態が出るのは、ここを事前に確認できるという意味です。

**3. 本番の設定を触らずに試せる。** アドホック式とプリセットはブラウザ内に留まり、**デプロイ済みの Cron Trigger を変更しません。** 「検証のために本番スケジュールを一時的に変える」という危ない運用を避けられます。

**ただし誤解しやすい点があります。** ローカル開発では **cron は自動実行されません。** 「ローカルで一晩動かして様子を見る」ことはできず、できるのは**単発投入**です。長時間の挙動やスケジュールの積み重なりを見たい場合は、別の方法が必要です。

**そしてログについて。** 完全なログとトレースには **Observability の有効化**が要ります。有効にしていない開発セッションでは、結果の outcome は見えてもその中身の追跡が弱くなります。**先に有効化しておく**のが実用的です。

## 副業・個人活用視点

**受託で Workers のバッチ処理を書いている人には、そのまま効きます。**

cron で動く処理の納品は、**検証コストが読みにくい**仕事です。「動くことを確認しました」と言うために、本番に入れて翌日確認する、という時間が挟まります。それが単発投入で済むなら、**その分の見積りが変わります。**

**検証の見せ方としても使えます。** 「毎月末に動く処理です」と言われた発注側は、それを確認する手段を持ちません。Local Explorer で月末の cron 式を投入して結果を見せれば、**納品物の確認が成立します。** `noRetry()` の状態まで出るので、「二重実行しない設計です」という説明も画面で裏が取れます。

**エージェント向け API のほうは、もう一段先の話です。**

`POST /cdn-cgi/local/explorer/api/local/scheduled` が開かれているので、**スケジュール実行のテストをエージェントに任せられます。** 「cron 式を変えたら、その式で単発投入して結果を確認する」という手順を、エージェントの作業ループに入れられる、という意味です。

**注目したいのは、開発サーバーが AI エージェントを検出してエンドポイントを案内する、という部分です。** ツールの側が、エージェントに自分の使い方を提示してくる。これは Cloudflare が 10-16 に出した `cf docs search`（エージェントが公式ドキュメントを読む経路）と同じ方向の設計です。**2日連続で「エージェントが読む・叩く前提の入口」を足している**ことになります。

個人開発でも素直に使えます。定期実行の処理を書いたとき、**動作確認を翌日まで待たない**だけで、手が止まる回数が減ります。地味ですが、こういう待ち時間の削除は積み上がります。
