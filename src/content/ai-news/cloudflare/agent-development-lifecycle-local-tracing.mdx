## 要約

Cloudflare が 2026-08-04、従来の SDLC（Software Development Lifecycle）に代わる概念として **ADLC（Agent Development Lifecycle）** を提唱しました。問題設定はシンプルで、AI エージェントが実装する速度に対して、レビュー・デプロイ・保守が追いついていない、というものです。同日、その主張を裏づける実装がまとめて公開されました。

開発者に一番直接効くのが、**`wrangler dev` / `vite dev` のローカル OpenTelemetry トレース**です。ローカルで Worker を呼び出したとき、構造化された OTel トレースと、それに対応するコンソールログが自動でキャプチャされるようになりました。対象はハンドラ呼び出し、`fetch()` 呼び出し、バインディング呼び出しで、追加の計装コードは要りません。

面白いのは、この機能が**エージェント向けの導線を明示的に持っている**点です。ツールが AI エージェントのセッションを検出すると、ターミナルに `/cdn-cgi/explorer/api` へのヒントを表示します。この **Local Explorer API** は OpenAPI スキーマを提供し、テレメトリの検出、トレースとログのクエリ、バインディング状態の検査ができます。つまりエージェントは、標準出力を眺めて推測するのではなく、構造化されたデータを問い合わせて失敗箇所を特定できます。そのまま「コードを修正 → リクエストを再実行 → 結果を検証」のループを、デプロイなしで回せます。

人間が置き去りにされているわけではなく、Local Explorer のブラウザ UI で同じトレースとログを確認できます。スパン、タイミング、属性、エラー情報が表示されます。

もう 1 つの発表が **`@cloudflare/ci`** です。Workflows 上に構築された CI/CD ツールで、Artifacts リポジトリに対して push をトリガーにパイプラインを実行します。ビルド・テスト・lint・デプロイと依存関係のキャッシュに対応し、数百万リポジトリ規模を想定しているとされています。

このほか、Cloudflare 社内でのエンジニアリング標準の自動適用、Astro の GitHub issue を自動トリアージして修正まで回す「ソフトウェアファクトリ」の事例も同日に公開されています。

## 何が変わったか

- `wrangler dev` / `vite dev` がローカル実行時に OTel トレースとコンソールログを自動キャプチャ（追加の計装不要）
- ハンドラ呼び出し、`fetch()` 呼び出し、バインディング呼び出しが自動的にトレース対象
- AI エージェントのセッションを検出すると、ターミナルに Local Explorer API（`/cdn-cgi/explorer/api`）のヒントを表示
- Local Explorer API は OpenAPI スキーマを提供し、テレメトリ検出・トレース/ログのクエリ・バインディング状態の検査に対応
- エージェントがデプロイせずに「特定 → 修正 → 再実行 → 検証」をループできる
- 人間は Local Explorer のブラウザ UI で同じトレース（スパン、タイミング、属性、エラー）を確認できる
- `@cloudflare/ci`：Workflows 上の CI/CD。Artifacts リポジトリへの push をトリガーに、ビルド / テスト / lint / デプロイと依存キャッシュを実行

## 業務インパクト（一般企業向け）

社内で Claude Code や Codex のようなコーディングエージェントを使っているチームにとって、この発表の意味は「エージェントの試行錯誤が速くなる」ことではありません。**エージェントが確認できる情報の質が上がる**ことです。

現状、エージェントがバグを直すときに読んでいるのは、たいていテストの失敗出力かログの標準出力です。情報が足りなければ、エージェントは `console.log` を挿し込んで再実行し、また読むという遠回りをします。構造化テレメトリを直接クエリできるなら、この往復が減ります。開発リードの立場では、エージェントの作業ログが短くなる = レビュー対象の差分が本質的な修正だけに近づく、という効果が期待できます。

一方で、注意すべき点もあります。エージェントがローカル環境の内部状態（バインディングの中身を含む）を API 経由で読めるということは、開発環境に置いてある値がエージェントの文脈に入るということです。ローカルの `.dev.vars` などに本物の認証情報を置いている構成では、その扱いを見直す契機になります。「ローカルだから安全」という前提は、エージェントが機械的に環境を検査できる状況では成り立ちにくくなります。

`@cloudflare/ci` は、Cloudflare をホスティング先として使っている組織には検討価値がありますが、既存の GitHub Actions などを置き換える判断は別途必要です。Artifacts リポジトリ前提である点、Workflows の課金体系に乗る点を確認してから評価するのが順当です。

ADLC という概念そのものについては、まだ Cloudflare が提唱している段階で業界標準ではありません。ただし「実装は速くなったがレビューとデプロイが詰まる」という問題認識は、エージェントを実務投入している組織なら共通して持っているはずです。自社の詰まりがどこにあるかを言語化する枠組みとしては使えます。

## 副業・個人活用視点

Workers で受託案件をやっている個人には、素直に効く改善です。ローカルでの再現とデバッグは、時間当たりの生産性を最も左右する部分で、そこにトレースが入るとエージェントに任せられる範囲が広がります。「エラーが出たら Claude Code に投げる」を、より少ないやり取りで完了させられます。

案件の見せ方としても使えます。納品時に「ローカルで再現してトレースを確認する手順」を手順書に含めておくと、引き継ぎ後にクライアント側で調査できる状態を作れます。属人化しにくい納品物は、継続案件につながりやすくなります。

学習の観点では、OpenTelemetry を実際に触る入口として手頃です。トレース・スパン・属性といった概念は、説明を読むより実行結果を見た方が早く掴めます。`wrangler dev` を叩くだけで自動的にトレースが出るなら、計装の学習コストなしに概念だけ先に理解できます。この理解は Cloudflare 以外の環境（自前の OTel 構成、他社の可観測性 SaaS）にもそのまま持ち越せます。

`@cloudflare/ci` は現時点では Artifacts リポジトリ前提なので、GitHub でリポジトリを管理している個人がすぐ乗り換える対象ではありません。まずはローカルトレースだけ取り込み、CI は既存のまま様子を見るのが現実的です。
