## 要約

Cloudflare は2026-11-03、**新規の AI Gateway に認証を必須にする**と告知しました。目的は、**不正なリクエストを防ぐ**ことです。

- 新規作成時は**認証が既定でオン**。API では `authentication` を省略するか `true` にする
- `false` を指定して作ると、API は **HTTP 400** を返す
- **一度オンにすると、ダッシュボードからも API からもオフに戻せない**
- 既存のゲートウェイは、認証がオフでも**そのまま動き続ける**

## 何が変わったか

**新規作成**

- `authentication` を省略、または `true` → 認証オンで作成される
- `authentication: false` → 400 エラー

**既存ゲートウェイの更新**

- `authentication` を省略 → 現在の設定を維持
- オンのものをオフにする更新 → 400 エラー
- オフのものは、設定画面か、更新リクエストに `"authentication": true` を入れてオンにできる

**呼び出し側の準備**

- オンにする前に、HTTP クライアントが**有効な Cloudflare API トークン**を送るよう設定しておく
- **Workers バインディング経由のリクエストは、認証済み**として扱われる
- 対応する認可ヘッダーの種類は、公式ドキュメント（AI Gateway authentication）に載っている

## 業務インパクト（一般企業向け）

**新規に作る分から、手順書とテンプレートの見直しが必要です。** 認証オフで作る前提のスクリプトや構築手順は、400 エラーで止まります。

**既存のゲートウェイこそ棚卸しの対象です。** 認証がオフのままだと、ゲートウェイの URL を知った第三者が、自社の契約・費用でモデルを呼べる余地が残ります。今回の変更は既存分を自動では直さないため、**対応は利用者の判断**です。

確認の手順は次の通りです。

- 認証がオフのゲートウェイを洗い出す
- そのゲートウェイを呼んでいるクライアントを特定し、API トークンを送れるようにする
- 準備ができたゲートウェイから認証をオンにする。**オンにすると戻せない**ため、切り戻しはできない前提で、先にステージング環境で試す
- API トークンの発行・保管・更新の担当を決める

**注意点**: 本記事は changelog の記述に基づく。トークンに必要な権限の範囲は、公式ドキュメントで確認が必要。

## 副業・個人活用視点

**自分で作る新しいゲートウェイは、最初から認証付きになります。** 公開するフロントエンドから直接ゲートウェイを呼ぶ構成だと、トークンをブラウザに置くことになり危険です。Workers を間に挟み、バインディング経由で呼ぶ形にすると、トークンを外に出さずに済みます。

**受託案件では、納品物の構成説明に入れます。** 「ゲートウェイは認証付きで、呼び出しは Workers 経由」と書いておくと、運用側が勝手に認証オフの経路を作る事故を避けやすくなります。
