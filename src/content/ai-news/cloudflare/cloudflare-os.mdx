## 要約

Cloudflare が 2026-08-05、「Cloudflare OS」を公開しました。社内業務向けに AI エージェントとカスタムアプリを配置するためのオープンソースプラットフォームです。

この発表の性格をつかむうえで重要なのは、これが「新製品を作って売る」話ではなく、**Cloudflare が自社の働き方を作り替えるために内製したものを、そのまま OSS として出した**という点です。同日に「How we're rethinking work at Cloudflare with Cloudflare OS」という自社適用の記事も出ており、ドッグフーディングの結果を公開する形になっています。

中核はブラウザからアクセスする「エージェントワークスペース」です。社内の文脈とスキルを与えた状態でエージェントが動き、ドキュメント、スライド、スプレッドシート、さらにはカスタムアプリまで生成します。特徴的なのは、すべてを AI の判断に委ねる作りにしていないことです。定型作業は決定論的なワークフローとして固定でき、「コードで確実に処理する部分」と「AI の判断に任せる部分」を混在させる設計になっています。毎回 LLM に判断させると結果がぶれる、という実運用の問題への回答がプラットフォーム側に組み込まれている、と読めます。

アクセス制御には「Gatekeepers」という仕組みが入っています。サービスごとに置かれた Worker がリソースへのアクセスを仲介し、**エージェントは権限ゼロの状態から始まって、必要なリソースを都度申請する**という流れになります。認証情報は生成されたコードから隔離され、アクセスポリシーは参照されたリソースを追跡して、意図しない共有を防ぎます。エージェントに広い権限を先渡しして事故が起きる、という典型的な失敗を構造的に避ける設計です。

生成されるアプリはフルスタックの Workers です。クライアント側のブラウザ UI とサーバー側（SQLite を持つ Durable Object Facets）で構成され、作ったアプリはそのまま共有することも、他人が独立したコピーを作れる「ブループリント」として配布することもできます。後者は地味に効く仕組みで、「隣の部署が作った便利ツールを、自分のデータで作り直す」という展開が現実的になります。

モデルは AI Gateway 経由で任意のものを接続でき、チーム・ワークスペース単位でコストと予算を管理できます。同日発表の AI Gateway User Insights と合わせると、「誰がどれだけ使ったか」まで一気通貫で見える構成です。

想定利用者は「社内の全員」で、非エンジニアからエンジニアまでを対象としています。GitHub 上でスターターリポジトリとともに公開されており、記事中に個別の価格提示はありません（コストはデプロイ先である Cloudflare の利用料に依存します）。

## 何が変わったか

- 社内向けエージェント基盤「Cloudflare OS」がオープンソースで公開された（GitHub にスターターリポジトリあり）
- ブラウザからアクセスするエージェントワークスペースで、社内文脈とスキルを与えたエージェントを動かせる
- ドキュメント / スライド / スプレッドシート / カスタムアプリを生成できる
- 定型作業を決定論的ワークフローとして固定し、AI の判断が必要な箇所だけ委ねられる
- 「Gatekeepers」がサービスごとにアクセスを仲介し、エージェントは権限ゼロ起点で都度申請する
- 認証情報は生成コードから隔離され、アクセスポリシーが参照リソースを追跡して意図しない共有を防ぐ
- 生成アプリは Workers + Durable Object Facets(SQLite) のフルスタック構成でデプロイされる
- アプリを「ブループリント」として配布し、各自が独立したコピーを持てる
- モデルは AI Gateway 経由で任意に接続でき、チーム / ワークスペース単位で予算管理できる
- 対象は非エンジニアを含む全社員（記事中に個別の価格提示はなし）

## 業務インパクト（一般企業向け）

これは「便利な AI ツールが増えた」という話ではなく、**業務システムの作り方そのものに対する提案**です。受け止め方を間違えると評価を誤ります。

従来、社内の困りごとを解決するには「情シスに依頼する」「SaaS を契約する」「Excel マクロで凌ぐ」のいずれかでした。Cloudflare OS が提示しているのは、現場の人間がエージェントに指示して、その場でアプリを作り、必要なら他部署へブループリントとして配る、という第 4 の経路です。これが機能するなら、情シスの役割は「作る人」から「作れる環境と境界を用意する人」へ移ります。

ただし、この移行には代償があります。最大の論点は**生成されたアプリの管理責任**です。誰が作ったか分からないアプリが業務に組み込まれ、作った本人が異動したあとも動き続ける、という状態は、Excel マクロの時代から繰り返されてきた問題です。ブループリント配布は便利ですが、コピーが増えるほど「どれが正なのか」が曖昧になります。導入するなら、棚卸しの周期と廃止の手順を最初に決めておくべきです。

一方で、Gatekeepers の設計は評価できます。エージェントを権限ゼロから始めて都度申請させる方式は、「とりあえず管理者権限を渡して動かす」という現場の妥協を構造的に封じます。認証情報が生成コードから隔離される点も、生成 AI にコードを書かせる際の典型的な事故（キーがコードに埋め込まれる）を避けられます。ここは自前でエージェント基盤を組む場合に最も手間がかかる部分なので、OSS として実装が公開されている価値は大きいはずです。

現実的な進め方としては、まず 1 部署・1 業務に絞って動かし、「誰がどのリソースにアクセスを申請したか」のログを実際に眺めることです。設計の良し悪しは、権限申請のログを見れば分かります。全社展開を先に決める種類のものではありません。

なお OSS である以上、運用・保守は自社の責任になります。「Cloudflare が提供する SaaS」ではないので、アップストリームの更新追従、障害時の切り分け、社内サポートの体制をどうするかは、導入判断の前に詰めておく必要があります。

## 副業・個人活用視点

個人・小規模チームにとっては、**受託の提案材料**として見るのが実用的です。

中小企業で「業務改善に AI を入れたい」という相談は増えていますが、実際に持っていける選択肢は限られています。SaaS を並べるだけでは差別化にならず、フルスクラッチは予算が合わない。ここに「Cloudflare OS をベースに、その会社の業務に合わせたエージェントワークスペースを構築する」という選択肢が加わります。土台が OSS なのでライセンス費用が発生せず、インフラは Cloudflare の従量課金に乗る構成は、小さく始めたい会社に説明しやすい形です。

特に価値があるのは、Gatekeepers を含む権限設計が最初から入っていることです。エージェント基盤を自分で組むと、権限とデータ境界の設計に最も時間がかかります。ここが用意されていれば、案件では「その会社固有の業務ワークフローをどう組むか」に集中できます。工数の配分が変わるということは、提示できる金額と納期が変わるということでもあります。

個人の作業環境としても使えます。決定論的ワークフローとエージェント判断を混在させられる設計は、「毎回同じ手順で処理したい部分」と「都度判断が要る部分」が混ざる個人業務——たとえばリサーチして記事にまとめる、請求処理を回す、といった流れ——に素直に当てはまります。

注意点として、これは触ってすぐ成果が出る種類のツールではありません。自社／クライアントの業務を分解し、どこを固定してどこを委ねるかを決める作業が本体で、プラットフォームはその器です。逆に言えば、業務を分解して設計する力がある人ほど差が出ます。提案の武器にするなら、まず自分の業務で一通り組んでみて、権限申請のログまで含めて運用感を掴んでおくのが近道です。
