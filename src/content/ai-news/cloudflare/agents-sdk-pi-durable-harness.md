## 要約

Cloudflare Agents SDK に **`PiHarness` クラス**が追加されました。**Pi 1.0 と Pi Durable**（Earendil 製のエージェントフレームワーク）を **Durable Objects 上で動かす**ためのものです。

**解こうとしているのは、エージェント運用で最も扱いにくい問題です。** エージェントに数分〜数時間かかる仕事を任せたとき、**途中でプロセスが死んだらどうなるか**。多くの実装では、やり直しです。10分走って80%まで進んだ作業が、コンテナの再起動で消えます。

**`PiHarness` は、この問題に Durable Objects で答えます。** Agents SDK の **Lifecycle capability** という仕組みにより、**再起動・クラッシュ・ネットワーク切断をまたいでエージェントの実行状態が保持**されます。

**構成はシンプルです。** harness に **AI モデル、skills、tools** を設定し、Agent クラスへ登録します。モデルは **Workers AI と AI Gateway 経由の Cloudflare モデル**でも、**独自プロバイダー**でも指定できます。

**ただし、現時点では実験段階です。** 公式ドキュメントに「**Pi Durable の成熟にあわせて `PiHarness` の API は変わる可能性が高い**」と明記されています。**本番採用の判断を今する機能ではありません。** 方向性を把握し、小さく試す対象です。

## 何が変わったか

- **Cloudflare Agents SDK に `PiHarness` クラスが追加**
- **Pi 1.0 + Pi Durable** を Durable Objects 上で動かせる
- **Lifecycle capability** により、再起動・クラッシュ・ネットワーク切断をまたいで実行状態を保持
- harness に **AI モデル / skills / tools** を設定し、Agent クラスへ登録する構成
- モデルは **Workers AI / AI Gateway 経由の Cloudflare モデル**、または**独自プロバイダー**
- **ベータ。API 変更の可能性が公式に明記されている**
- 導入には peer dependency として **`@earendil-works/pi-durable`** と **`@earendil-works/pi-ai`** が必要

## 業務インパクト（一般企業向け）

**この発表の価値は、機能そのものより「問題設定が共有されつつある」ことにあります。** エージェントの PoC は動いても本番に乗らない、という話はよく聞きます。原因の多くは精度ではなく運用側です。**途中で止まったときに何が起きるか、再開できるか、どこまで進んだか分かるか。** こうした問いに、エージェントフレームワーク側が答えを持ち始めています。

**自社でエージェントを検討しているなら、評価軸にこれを加えてください。** 「どのモデルを使うか」より、**「途中で死んだらどうなるか」「同じ処理を2回実行してしまわないか」の方が、本番化の可否を分けます。** PoC の段階ではこの差が見えません。

**一方で、現時点の採用判断は慎重であるべきです。** ベータであること、API が変わる予告があること、**Earendil という外部フレームワークへの依存が増えること**の3点がリスクです。特に3つ目は、Cloudflare 自身ではなく第三者のロードマップに左右される部分が生まれる、という意味です。

**試すなら、本番の周辺業務から始めるのが現実的です。** 定期的なデータ収集、レポート生成、社内向けの集計など、**止まっても業務が止まらない領域**で挙動を見る。そこで「本当に再開するか」「状態がどこまで残るか」を確認してから、業務の中心へ寄せる順序です。

**既に Cloudflare Workers / Durable Objects を使っている組織には、追加コストが小さい選択肢です。** 新しいインフラを契約する必要がなく、既存の課金体系の中で試せます。**評価の障壁が低いこと自体が、検証を進める理由になります。**

## 副業・個人活用視点

**学習テーマとしての価値が高い領域です。** 「エージェントの耐障害性」は、現時点でまだ定石が固まっていません。**定石が無い領域で実際に動かした経験は、記事やセッションの題材として希少価値があります。**

**具体的には、「途中で殺して再開させる」検証が、そのままコンテンツになります。** エージェントを走らせ、意図的にプロセスを落とし、どこから再開するかを観察する。**この手の検証は誰でもできますが、やっている人は多くありません。** 結果がどうであれ（きれいに再開しても、しなくても）、知見として価値があります。

**提案の場面では、「止まったときの話」ができることが差別化になります。** エージェント案件の相談で、多くの提案は「何ができるか」に集中します。**「失敗したときどうするか」を設計に含めた提案は、意思決定者の警戒を解きます。** 技術力の証明ではなく、業務理解の証明として効きます。

**ただし、顧客案件へのベータ投入は避けるべきです。** API 変更が予告されている以上、**納品後に動かなくなる可能性があります。** 保守契約の範囲で面倒を見る覚悟がないなら、安定版が出るまで自分の検証環境に留めてください。

**Durable Objects 自体の理解を深める入口としても使えます。** ステートフルなエッジ処理は、エージェント以外にも用途があります（セッション管理、リアルタイム協調編集、レート制限）。**`PiHarness` を触る過程で身につく Durable Objects の勘所は、別の案件でも使えます。** 投資先としての効率は悪くありません。
