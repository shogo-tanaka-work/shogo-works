## 要約

Cloudflare がオブザーバビリティ関連を **8件まとめて更新**しました。製品ごとに分かれていたログ・メトリクス・トレースを1つの面へ寄せる方向です。

**実務で先に効くのは、機能の数ではなく 2026-12-01 の課金方式変更です。** 従来の**イベント数課金から、容量（GB）課金へ移行**します。**見積もりの軸が変わるため、既存の試算はそのまま使えません。**

| プラン | 込みの量 | 保持 | 超過 |
| --- | --- | --- | --- |
| Free | 1日 0.5 GB 取り込み | 7日 | — |
| 有料 / Enterprise | 50 GB 取り込み + 10 GB・月 ストレージ | 最長1年 | 取り込み **$0.25/GB**、保存 **$0.10/GB・月** |

**イベント数から容量への変更は、ログ1件あたりのサイズが大きい環境ほど不利に働きます。** 構造化ログに大きな JSON ペイロードを載せている場合、イベント数では安かったものが容量では高くなる可能性があります。**逆に、小さいログを大量に出している環境は有利になります。** どちらに転ぶかは自社のログ形状次第なので、**12月1日前に実測が要ります。**

**機能面で目を引くのは Unified SQL API です。** 製品横断のテレメトリを単一の SQL で引けるようになり、**新しい `cf` CLI と Cloudflare の Observability MCP サーバー**に統合されます。**MCP サーバー経由ということは、エージェントに運用データを直接読ませる経路が公式に用意された**ということです。

## 何が変わったか

- **Unified Logs Home（GA）** — Workers Observability と Log Explorer を統合。HTTP イベント、ファイアウォールイベント、Workers、Containers、R2、**AI Gateway** のログを同じクエリ体系で扱える。データセット横断クエリは近日
- **Cloudflare Traces（オープンベータ）** — リクエストの通過経路をスパン分解（別記事で詳述）
- **Unified SQL API（ベータ）** — 製品横断のテレメトリを単一 SQL で。**`cf` CLI と Observability MCP サーバー**に統合。Workers に Analytics Engine 直読みの **SQL binding**
- **新料金（2026-12-01 発効）** — イベント数課金 → **容量課金**
- **Custom Alerts（ベータ）** — SQL API 対応の任意データセットに閾値 / 異常検知 / SLO でアラート。Webhook・チャット・インシデント管理へ通知（全プラン）
- **Domain Analytics（GA）** — トラフィック / パフォーマンス / セキュリティ / キャッシュ / オリジン / DNS を統合表示。**全プランで30日保持**
- **Custom Dashboards（GA）** — 製品横断のダッシュボードをチーム共有
- **Logpush（GA・セルフサーブ開放）** — 従来 Enterprise 限定。外部エクスポートは**月25 GB 無料、超過 $0.10/GB**、Transformers は超過 $0.04/GB

## 業務インパクト（一般企業向け）

**12月1日までの宿題が明確です。** 現在のログ・トレースの**取り込み容量を GB で測る**こと、それを新料金に当てはめて**月額を試算する**こと、この2つです。イベント数しか把握していない組織は、まず測定から始まります。

**「有料プランは 50 GB 込み」が1つの目安になります。** 中小規模のサービスなら込みの枠内に収まる可能性が高く、その場合は実質無料です。**超えるかどうかの境界を知ることが、試算の目的になります。**

**ログ設計の見直しが、そのままコスト削減になります。** 容量課金では、**デバッグ用の冗長なフィールド、重複したコンテキスト、使われていないログレベル**が直接費用です。従来のイベント数課金では、ログを「出すか出さないか」だけが効きました。**これからは「何を載せるか」も効きます。** 12月までの2か月は、ログ棚卸しの good reason になります。

**Observability MCP サーバーの登場は、運用の形を変える可能性があります。** エージェントに運用データを読ませられるなら、「このエラーの急増はいつから始まったか」をエージェントに調べさせる運用が成立します。**ただしアクセス制御の設計が先です。** 運用ログには個人情報やトークンが混ざることがあり、**MCP 経由でエージェントに広く読ませる前に、何が見えるかの確認が要ります。**

**Logpush の全プラン開放は、ログ保全要件への対応をプラン非依存にします。** 「SIEM へ送るために Enterprise」という構成は見直せます。ただし**月25 GB を超えると $0.10/GB の従量**なので、こちらも実測が前提です。

**Custom Alerts の SLO 条件対応は、運用の成熟度を1段上げます。** 閾値アラートだけの運用は「鳴りすぎて無視される」状態になりがちです。**SLO ベースなら「エラーバジェットを使い切りそうか」で鳴るため、通知の数が減ります。** 全プランで使える点も、小規模チームには重要です。

## 副業・個人活用視点

**まず、Free の枠が実用的である点を押さえてください。** 1日 0.5 GB・保持7日は、個人開発や小規模な受託案件には十分です。**「ログ基盤を別途契約する」という工程が、多くの案件で不要になります。**

**提案材料としては、Domain Analytics の全プラン30日保持が使えます。** 「アクセス解析は何を入れますか」という問いに対し、**追加コストなしで30日ぶん見られる**と答えられるのは強いです。Google Analytics の導入と同意取得の議論を回避できる場面もあります。

**Logpush の自分用途としては、顧客への報告が楽になります。** 月次レポートのために管理画面を開いてスクリーンショットを撮る作業が、ログを自分の集計基盤へ送る形に変えられます。**月25 GB 無料の枠内であれば、コストは発生しません。**

**Observability MCP サーバーは、スキルとして売れる領域です。** 「運用データをエージェントに読ませて、障害の初動を自動化する」構成は、現時点ではまだ一般的ではありません。**公式の MCP サーバーが出た直後は、実際に組んだ経験そのものが希少価値になります。** 自分の案件で先に試して、事例として持っておく価値があります。

**12月1日の料金改定は、顧客への連絡ネタとしても使えます。** Cloudflare を導入した顧客に「12月から課金方式が変わるので、現在の使用量を測っておきましょう」と連絡するだけで、**継続的に見ている印象が残ります。** こうした先回りの連絡が、保守契約の更新理由になります。
