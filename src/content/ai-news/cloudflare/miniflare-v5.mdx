## 要約

Cloudflare は 2026-09-08、**Miniflare v5** を公開しました。

Miniflare は表に出にくいコンポーネントですが、**Workers 開発者はほぼ全員が間接的に使っています**。`wrangler dev` でローカルサーバーを立てるとき、Cloudflare Vite プラグインで開発するとき、`@cloudflare/vitest-plugin` でテストを走らせるとき。**その裏側で Workers のランタイムをローカルに再現しているのが Miniflare** です。

今回のリリースは、機能追加ではなく**内部構造の刷新**が中心です。公式が明示している位置づけは、**次世代の CLI（`cf` CLI）に向けた土台の整理**というものです。

具体的な変更は3方向あります。設定面では、**設定の形が `cloudflare.config.ts`（Cloudflare のプログラマティック設定形式）に揃えられました**。あわせて非推奨 API とレガシーオプション（D1 alpha バインディング等）が削除され、`wrappedBindings` のような内部 API も不要となり撤去されています。

機能面では、**組み込みのモジュール探索が削除**され、モジュールグラフの解決は上位ツール側の責務になりました。また**ローカル専用ルートが `/cdn-cgi` 配下から `/cdn-cgi/local` 配下へ移動**しています。永続化オプションは、リソースごとに設定する形をやめ、**共有のルートオプションへ統合**されました。

そして最も重要な但し書きが公式に明記されています。**Wrangler や Vite プラグイン経由で使っている大多数の開発者に、必要な対応はありません。**移行期限の提示もありません。

## 何が変わったか

- 設定の形が **`cloudflare.config.ts` と一致**するようになった
- **非推奨 API とレガシーオプション**（D1 alpha バインディング等）が削除された
- 内部 API の **`wrappedBindings`** が撤去された
- **組み込みのモジュール探索が削除**され、モジュールグラフ解決は上位ツールの責務へ
- ローカル専用ルートが **`/cdn-cgi` → `/cdn-cgi/local`** へ移動
- 永続化オプションが**共有ルートオプションへ統合**（リソースごとの設定を廃止）
- **Wrangler / Vite プラグイン / vitest プラグイン経由の利用者は対応不要**（移行期限の記載もなし）

## 業務インパクト（一般企業向け）

**まず結論として、大多数のチームは何もしなくて構いません。**

`wrangler dev` でローカル開発し、`@cloudflare/vitest-plugin` でテストを回している標準的な構成であれば、Miniflare は依存の奥にあるだけで、直接触れていません。公式も「必要な対応はない」と明記しています。**このニュースを読んで作業計画を立てる必要があるチームは限られます。**

**確認が要るのは、Miniflare を直接 API として使っているケースです。**具体的には、独自のテストハーネスを組んでいる、CI で Workers を起動して結合テストを回す仕組みを内製している、複数の Worker を協調させるローカル環境を自作している、といった構成です。この場合、**設定オブジェクトの形が変わり、永続化オプションの指定位置が変わり、ローカルルートのパスが変わります**。特にローカルルートを直接叩いているテストコードがあれば、`/cdn-cgi/local` への変更で壊れます。

**中期的に見ておくべきなのは、`cf` CLI の存在が公式に言及された点です。**このリリースは、その CLI に向けた基盤整理だと明言されています。つまり、**Wrangler から `cf` CLI への移行が Cloudflare のロードマップ上にある**ということです。現時点で移行期限は示されておらず、`cf` CLI 自体の詳細も出ていません。**今すぐ動く話ではありませんが、来年度の技術計画を組む際には視野に入れておく事項**です。

**「非推奨 API が削除された」という記述の扱いには注意してください。**D1 alpha バインディングのような、そもそも非推奨だったものが対象です。非推奨のまま使い続けていた構成があれば、v5 では動かなくなります。**Miniflare のバージョンを固定しているプロジェクトは、上げるタイミングで一度洗い出す**のが安全です。ただし繰り返しますが、Wrangler 経由であれば Wrangler 側が吸収します。

## 副業・個人活用視点

**個人開発では、この更新を意識する場面はほとんどありません。**

Cloudflare Workers で個人サイトや小さな API を作っている場合、使っているのは `wrangler dev` と `wrangler deploy` でしょう。Miniflare のバージョンが上がったことは、**Wrangler を更新したときに一緒についてくる**だけです。設定ファイルを触る必要も、コードを直す必要もありません。

**むしろ読み取るべきは、`cf` CLI という次世代ツールの存在が明かされたことです。**Cloudflare は Wrangler を長く使ってきましたが、その後継が準備されている。個人開発者にとってこれは、**今から Wrangler 固有の細かい設定に深入りしすぎない方がよい**という示唆になります。学習の投資先として、Wrangler のコマンドオプションを覚え込むより、**Workers のランタイム仕様や `cloudflare.config.ts` の設定モデル**を理解しておく方が、移行後も持ち越せる知識です。

**設定形式が `cloudflare.config.ts` へ統一される流れも、同じ方向を指しています。**JSON や TOML の設定ファイルから、TypeScript のプログラマティック設定へ寄せる動きです。型が効き、エディタで補完が出て、条件分岐も書けます。**個人開発でも `cloudflare.config.ts` 形式を採用しておく**と、この流れに素直に乗れます。

**受託で Cloudflare を扱っている場合は、`cf` CLI の言及をクライアントへ共有する価値があります。**「今のツールがいずれ置き換わる可能性がある」という情報は、長期の運用契約を結ぶ際の前提として共有しておくべきものです。慌てる必要はありません。移行期限も出ていませんし、`cf` CLI 自体まだ公開されていません。**ただ、知らないまま数年後に驚くより、今のうちに前提として置いておく方が誠実**です。
