- **「作れる」と「出せる」を分ける**という軸で教材化する。n8n 教材はワークフローの組み方に寄りがちだが、実務で詰まるのは公開の承認プロセス。テスト実行 → HITL → レビュー差分 → バージョン説明という一連が揃ったので、この流れをそのまま章立てにできる。
- HITL は**全自動より難しい**という前提を先に置く。「どこで人が判断すべきか」を設計させる課題は、自動化教材の中でも応用が利く。Agent Builder のテスト実行を使えば本番データに触れず練習できるため、演習環境として使いやすくなった。
- カスタムロール作成 API は、**作成者とレビュアーを分ける**という設計意図とセットで教える。API があること自体ではなく、ロール設計をコードで管理すると環境の再現ができる、という利点まで示す。
- 権限まわりの修正2件（Code ノード console 出力の redaction、data table 書き込み時の行読み取りスコープ要求）は地味だが、**セルフホスト運用の教材でアップグレード理由として扱える具体例**。「バグ修正だから読み飛ばす」を戒める題材になる。
- MCP の `detailLevel` は、エージェントへ渡す情報量を制御するという文脈で扱う。コンテキスト設計の話（何を渡し、何を渡さないか）に接続できるので、n8n 固有の話にとどめない。
- トークンカウントのローカル対応は、**見積もり精度**の教材に使える。「推測でコストを話す提案」と「実測値を出せる提案」の差は、受託向けカリキュラムで刺さりやすい論点。
- Discord チャネル追加は機能としては小さいが、**承認の場所が増えることの副作用**を扱う入口になる。チャネルを増やすと HITL の判断が見落とされる、という運用リスクは自動化設計の一般論として通用する。
- `src/content/knowledge/ai-tools/` に n8n の教材はまだない。作るなら「ワークフローの組み方」ではなく、この記事の軸（テスト・承認・権限）を先に置く構成のほうが、他の n8n 記事との差別化になる。
