- 「自分は何も変えていないのにアップグレードで壊れる」型の変更が3件同時に入った回。バージョン運用の教材で、リリースノートを読む理由を説明する具体例としてそのまま使える。抽象的に「読みましょう」と言うより、`Array.merge` のように式の中に埋まっていて画面からは見えない例を出すほうが伝わる。
- 破壊的変更を「どこを探せば見つかるか」で分類すると教材になる。式レベル（エクスポートして文字列検索）、権限レベル（誰が何を作れるかの突き合わせ）、構成レベル（トリガーノード ID の重複）で、それぞれ調べ方が違う。チェックリストの形に落とせる。
- エンドユーザーの認証情報作成を team project に限定した変更は、n8n を「個人ツール」から「組織ツール」へ移す過程で必ず通る論点。権限設計の教材で、権限を絞る変更は絞られた側から問い合わせが来る、という運用上の帰結まで含めて扱う。
- Google Ads ノードの API v21 → v25 移行は、2026-08-14 の 2.34.6（Google Ads / Microsoft Teams ノードの API sunset 対応）と同じ系列。依存先 API の世代交代が n8n 側の破壊的変更として降ってくる構造を、2件セットで説明できる。自動化ツールの保守コストがどこから来るかの実例。
- agent サンドボックスの principal 単位分離は、マルチテナントの考え方を教える入口になる。1インスタンスを複数部署で共有する構成で、実行の分離が無いと何が起きるかを先に示してから、この変更の意味を説明する順が理解しやすい。
- skill builder から MCP server のツールを使えるようになった点は、n8n の位置づけの変化として扱う。「ノードを並べる自動化ツール」から「agent の実行基盤」へ移る流れの中に置くと、単体の機能追加より意味が伝わる。Codex の Hooks から MCP を呼べるようになった件（0.148.0）と並べると、業界全体の方向が見える。
- Schedule Trigger のキャッチアップ集約は、運用障害の教材で使える。停止から復帰したときに溜まった実行が一斉に走って二次障害になる、という事故は n8n に限らない。cron 系ジョブの設計論として一般化できる。
- n8n が 2026-08-19 付で日次巡回から週次確認ソースへ移った点は、教材ではなく運用ログ側の情報。ただし「巡回頻度を下げても破壊的変更は見落とせない」という判断基準は、ツール選定・運用設計の講義で触れる価値がある。
