- **今週の中心教材は「既定値の変更は利用者の操作なしに降ってくる」**（0.153.4）。モデル未設定時のバンドル既定が Astra に変わった。**更新するだけで、コストも出力の傾向も変わる。** CLI 系ツールの運用教材では、**モデルを設定ファイルで固定する**という指針をこの事例とセットで示す。同じ週に Claude Code 2.1.257 でも既定 Fable モデルが 5.1 へ変わっており、**2ツールの実例で同じ指針を裏づけられる。**
- **Astra 対応の3段構え（0.153.1 → 0.153.3 → 0.153.4）は、段階的ロールアウトの実装パターンとしてそのまま教材になる。** 「既定は変えず、ピッカーにも出さず、設定でだけ使える」→「別経路（Bedrock）のピッカーへ追加」→「既定化」。**受け入れ側の準備を先に配り、切り替えは後から**という順序はフィーチャーフラグ運用そのもの。自社のプロダクトで破壊的変更を出すときの手順として写せる。
- **同時に、この3段構えのうち利用者の同意なく挙動が変わるのは最後の1歩だけ**という点も教える。**段階的ロールアウトは「安全」ではなく「安全な段階と危険な段階を分離する」手法**である。どの段階で通知が要るかを設計する話につながる。
- **「ポリシーが設定されていたのに効いていなかった」**（0.152.1、Guardian が Node REPL ポリシーを無視）。統制の信頼性を考えるうえで重要な型。**設定した側は効いていると信じるため、不具合が是正されるまで誰も気づかない。** 統制は「設定したか」ではなく「実際に効いているか」を検証しないと担保できない——という一般則の具体例。**同じ週の Claude Code 2.1.260（権限ルールが無効として捨てられていた）と完全に同型**であり、2つ並べると「たまたま」ではなく構造的な問題だと示せる。
- **Guardian のスキップ条件が権限モードごとに違う**（0.153.0）という設計は、**「安全機構を一律に掛けるとコストが見合わない」**実例。確認のみの操作にまでレビューを掛ければ遅くなる。**リスクの段階に応じて検査の深さを変える**という考え方は、CI やコードレビューの設計にそのまま転用できる。前週の Claude Code の「危険な管理設定にだけ承認を要求する」も同じ発想で、**承認・検査の線引きをどう設計するか**という一つのテーマにまとめられる。
- **Guardian のレビュー履歴がコンパクション・再起動・フォークを越えて保持される**（0.153.0）。**エージェントの監査ログは会話の圧縮とは別のライフサイクルを持つべき**という設計の話。会話を縮めたら承認履歴も消えた、では監査にならない。**コンテキスト管理と監査記録を同じ仕組みに載せない**という原則に落とせる。
- **MCP のツール承認がアプリアカウント単位にスコープされた**（0.153.0）のは、**承認の粒度**の話。「このツールを許可した」が「どのアカウントで」まで含まないと、意図しないアカウントに権限が及ぶ。**権限は主体と対象の組で考える**という原則の具体例として素直。
- **MCP のツール別出力上限**（0.152.0）は、エージェント設計の一般論として重要。**MCP ツールの出力はモデルのコンテキストへ直接入るため、1つの饒舌なツールが全体の効率を壊す。** 「上限をツール単位で持てる」設計は、**コンテキストを共有資源として管理する**という発想の表れ。自作 MCP サーバーを設計する側にも出力量の設計責任がある、という話につながる。**同じ週の Claude Code 2.1.261（`bashOutputMaxChars` / `taskOutputMaxChars`）と対**になっており、両ツールが同時期に同じ問題へ対処している点を示すと説得力が出る。
- **カタログスペックの数字は後から訂正される**（0.153.2、Astra Fast の説明が 1.5x → 2x）。**モデル選定の根拠を「公式が言っていた倍率」だけに置くと、訂正のたびに前提が動く。** 自前の計測を1つ持っておく理由になる。なお公式が**「表示テキストのみの変更で、リクエスト処理には影響しない」と明記した**書き方自体も良い題材——読み手が最初に知りたいのは「自分の環境に影響があるか」であり、**影響範囲を先に否定しておくと確認コストが消える。**
- **レート制限バナーを「表示」から「操作」へ変えた**（0.152.0）、**残枠警告を半分の時点＝約5時間前倒し**（0.153.0）。どちらも小さいが良い UX 設計。**エラー表示で終わらせず、その場で次の行動を提示する**／**限界に達してから知らせても手遅れ**。業務システムのアラート設計に読み替えやすい。
- **Bedrock 経由での Astra 提供が CLI 側のリリースに乗る**（0.153.3）という流れは、**「Bedrock 提供＝即座に手元で選べる」ではない**ことの実例。AWS 側にログと課金を寄せる構成を採る企業向けに、**クラウド提供とクライアント対応が二段構えである**ことを説明する材料になる。「アクセス権はあるのに使えない」という切り分けで詰まる典型。
- **同日に stable が2本出る**（0.152.0 と 0.152.1）頻度は、Claude Code と並ぶ日次リリース型ツールの特徴。**「最新に追随する」運用が現実的かどうか**を判断する材料。今週は4日間で stable が7本出ている。
