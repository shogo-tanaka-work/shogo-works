- **非推奨（deprecated）と廃止（removed）の違い**を教える実例として使いやすい。多くの人はこの2つを同じものとして扱うが、実務上の対応はまったく違う。非推奨は「新規に使うな・移行を始めろ」、廃止は「動かなくなった」。今回は前者で、しかも後者の期日が示されていない。
- **「期日が無い告知は、期日がある告知より危険」**という逆説は、教材の結論として効く。期日があれば逆算できるが、無ければ見積もれない。人は期日が無いと後回しにするので、この直感の誤りを最初に壊しておく価値がある。
- **告知が GitHub Releases ではなく changelog 側にしか出なかった**点は、監視設計の教材そのもの。「どのソースを見れば何が分かるか」をマッピングする演習の題材にできる。製品リリースノート＝機能追加、開発者向け changelog＝廃止・非推奨、という傾向は他ベンダーでも観察できる。
- **MCP の移植性という前提を点検させる**論点。MCP は「どのクライアントからでもつながる」ことに価値があるが、各社が自社クライアント向けの専用経路（app server / プラグイン）を整えると、実態は囲い込みへ寄る。標準規格の採用が移植性を保証しないという一般則の、進行中の実例として追える。
- **設定が開発者のローカルにあり組織の台帳に載らない**という構図は、Cloudflare の任意 OAuth スコープの回でも扱った論点と同型である。エージェント連携は「誰がどこに何をつないだか」が見えないまま増える。教材では両者を並べて、可視性の欠落がシャドー IT と同じ構造だと示す。
- **納品済み成果物への影響を先回りで伝える**という実務動作は、伴走支援の価値説明に直結する。期日が出てから連絡するのと、非推奨の段階で伝えるのとでは、受け取られ方がまったく違う。「告知を読んでいることを見せられる機会」という切り口は、支援メニューの説明にそのまま使える。
- **同日の別エントリ（0.149.1）と混同しない**、という判断そのものが教材になる。日付が同じだけで因果を結ぶのは、リリース追跡でもっとも起きやすい誤り。公式が対応関係を書いていない以上、書かない。一次情報の扱い方の実演として提示できる。
- 既存の perception-gaps エントリ（「Claude Code → Codex 簡単移行」は公式には逆方向のみ）との接続。**公式が整備しているのは「Claude Code の中で Codex を使う」方向**であり、今回の案内でそれがさらに明確になった。誤認の訂正は一度で終わらず、裏付けを積み増していく作業だという例として使える。
