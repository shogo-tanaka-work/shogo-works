- **教材の軸は「発効がすでに過ぎている」に置く。** 期限前の告知なら「期限までに棚卸し」で済むが、今回は **19:00 UTC（日本時間 10月15日 午前4時）に発効済み**である。やることが「これから直す」から**「昨夜以降、動かなかったものは無いか」**へ変わる。**期限の前後で対応の性質が変わる**という構造は、受講者が見落としやすい。
- **認証方式で影響が分かれる点を、調査の型として教える。** ChatGPT サインインは対象、API キー認証は対象外。**同じ Codex でも入り方で挙動が違う。** 「自分の環境では問題なかった」が根拠にならない例として強い。影響範囲の切り出しは**「対応不要と言えること」にも価値がある**という営業的な含意まで持っていける。
- **棚卸し対象6か所を、前半と後半で分けて提示する。** ワークスペース既定値 / 保存済みモデル設定 / managed configuration は人が触る場所。**カスタムエージェント / スケジュール済みタスク / スクリプトは無人で走る。** この区別がそのまま「気づきやすさ」の差になる。公式が列挙している6項目をただ写すのではなく、**2群に割って意味づける**のが教材の仕事である。
- **「失敗しても通知が来ない」を教材の核心に据える。** 対話的に使っていればモデルが選べないことはすぐ分かる。毎晩動くタスクに `gpt-5.5` が書かれていた場合、**誰かが成果物を探すまで失敗が見つからない。** モデル退役の話から**「実行されなかったことを検知する仕組みがあるか」**という一般論へ広げられる。監視の提案へつながる入口。
- **managed configuration が対象である点は、権限構造の話として扱う。** 組織が配布している設定に `gpt-5.5` が入っていると**利用者は自分で直せない。** 管理者が動くまで該当ユーザー全員が止まる。**「利用者からの問い合わせを待つ」が最悪の順序**であることを示す。中央管理の利点と、障害時の単一障害点としての側面を同時に教えられる。
- **移行先の利用可否がプランに依存する点を見落とさせない。** `gpt-6.1-sol` は「プランとクライアントで利用可能な場合」という条件付きで、公式がプラン別詳細へリンクしている。**リンクが分かれている=差がある**という読み方を教える。設定を直しても、利用可否が無ければ動かない。
- **30日という予告期間を、変更管理の現実と突き合わせる。** 9月14日予告 → 10月14日発効。**社内の変更管理プロセスを通すには余裕のある長さではない。** 「changelog を見る担当を決める」という運用上の結論まで出すと、教材が実務につながる。無人構成を持つ組織では特に効く。
- **予告期間の記録を蓄積する価値を伝える。** 今回は30日。GPT-4 系 API の退役は約3か月（本日の別記事）。**同じベンダーでも、対象によって猶予が違う。** この差を記録しておくと、顧客の「いつまでに準備すればいいか」に実績で答えられる。**単発の知識より、積み上げた記録のほうが強い。**
- **自分の環境で確認できる題材として課題に出せる。** Codex を個人で使っていてスケジュール済みタスクを組んでいるなら、**日本時間10月15日午前4時以降は動いていない。** 故障の時刻が分かっているうちに確認する練習は、そのまま実務の手順になる。
- **既存 Knowledge への反映は2か所に絞る。** `codex/models.mdx` へ GPT-5.5 の退役日（2026-10-14 発効）と**認証方式による違い**を1行、`codex/enterprise-admin.mdx` へ **managed configuration に埋まったモデル指定は管理者が直す必要がある**という原則を1行。モデル名は変わるが、**「配布設定に書かれたものは利用者が直せない」という原則は残る。**
