- **`codex exec` の信頼の扱い（0.169.0）は、今週いちばん教材価値が高い。** 未信頼のディレクトリでは、`--sandbox workspace-write` を付けてもプロジェクト設定と MCP サーバーが無効のままになる。**サンドボックスの書き込み許可と、プロジェクト設定を読む信頼は別の軸である**ことを、設計として分離した。言い換えると「書き込んでよい」と「このリポジトリの設定を信じてよい」は別の判断で、片方を与えても他方は与えられない。**自作のエージェント実行環境で、この2つを1つのフラグに束ねていないかを点検させる題材になる。**
- **この変更は、失敗の仕方が静かである。** MCP ツールが無効になるだけで、エラーは出ない。エージェントは「そのツールが存在しない世界」で動き、代替手段を自分で探す。**ガードレールが正しく働いた結果が、利用者から見ると「なぜか別のことをした」になる。** 同じ週の Claude Code の既定変更は確認待ちで**止まる**ため気づける。**止まるガードレールと、黙って機能を減らすガードレールでは、運用の難しさが違う**という対比で2本を並べられる。
- **`--trust` が「明示的に信頼を保存する」コマンドとして用意された点は、信頼の永続化を可視化した設計である。** 信頼は暗黙に蓄積されやすい（一度動いたから次も動く）。**保存操作をフラグとして明示させると、「いつ誰がこのリポジトリを信頼したか」が記録に残る。** 自作ツールで trust store を持つなら、暗黙の追加ではなく明示的なコマンドにする根拠として使える。
- **Vertex の増分ツール送信の既定化（0.167.2）は、既定変更に逃げ道（`incremental_tools_legacy_gcp = false`）を用意した例である。** 互換性を壊しうる最適化を既定にするとき、**旧挙動へ戻すスイッチを同じリリースで出すか否か**でベンダーの姿勢が分かれる。今週の Claude Code 2.1.325 も `sandbox.autoAllowBashIfSandboxed` という逃げ道を同時に出した。**「既定を変える」と「戻せる」をセットで設計する**のは、エージェントツールの更新頻度が高い環境では必須である。自社の内部ツールで feature flag を設計するときの原則に落とせる。
- **`features.multi_agent` → `agents.enabled` の移行（0.168.0）は、設定キーの寿命の話である。** 機能が実験段階（`features.*`）から常設（`agents.*`）へ上がると、設定キーの置き場所が変わる。**警告を出して誘導する期間を置くのは良い作法だが、設定ファイルを IaC やテンプレートで配っている組織では、警告が誰の目にも入らない。** エージェントの設定を配布している場合、**警告の出力先を監視対象に入れる**必要があるという論点に使える。
- **Windows まわりの修正3件は、「サンドボックスは OS ごとに別実装である」ことの表れである。** 引用符付きの `cmd.exe` パス、親ディレクトリが読めない作業ディレクトリの PowerShell セッション（0.169.0）、アイドル MCP がファイルシステム I/O を塞ぐ問題（0.168.0）。**サンドボックスの保証は「設計」ではなく「各 OS での実装」が担っている。** 同じ週の Claude Code 側も Linux の bwrap と Windows の PATH 処理の修正を抱えている。**「サンドボックスがあるから安全」と言うときは、どの OS のどの実装かまで含めて言う必要がある**という結論の材料になる。
- **ターミナルのワークスペース（0.168.0 / 0.169.0）は、人間側の並行作業を整理する方向の機能である。** サイド会話、複数タブ、再起動後の再開。**エージェントを増やすのではなく、人間が追える形に並べ直している。** 同じ週の Cursor Projects のマルチプレイヤー化が「複数人 × 複数エージェントの共有」へ向かったのに対し、Codex は「1人 × 複数会話の整理」に留まっている。**並行実行の単位をどこに置くか（個人のタブか、チームの共有空間か）でプロダクトの思想が分かれる**比較教材になる。
- **「承認通知がターミナル入力の要求とネットワークアクセスの要求を区別する」（0.168.0）は、小さいが筋の良い変更である。** 承認を求められたとき、**何を許可するのかが分からないまま押す**のが最大の問題である。「コマンドを実行してよいか」と「外部へ通信してよいか」はリスクの質が違う。**承認 UI の設計は、回数を減らすことではなく、押す判断ができる情報を出すことで改善する**という原則の例に使える。前週の Codex 0.166.0 の「安全ブロックに説明を付ける」と同じ系列である。
- **`Ctrl+S` でアップロードが無効でも診断 ZIP をローカル保存できるようになった点（0.169.0）は、統制下の環境を想定した機能である。** テレメトリやアップロードを禁じている組織では、不具合報告の手段そのものが無かった。**「送信を止める」と「調査できない」を分離した**ことになる。エンタープライズ導入の論点として、**統制を強めたときに失われる運用能力をどう回復するか**という形で整理できる。
- **0.167.1 は本文が Full Changelog リンクのみで、内容の記載が無い。** 週次でまとめる価値はここにもある。**単独で見ると「何が変わったか分からないリリース」でも、週単位で前後の版と並べれば 0.167.0 系のパッチ列として位置づけられる。** リリースノートの質がベンダー内で揺れることを前提に、**版の列として読む**習慣を教える材料になる。
- **運用上の記録**: **rust-v0.168.0（11-13T03:54Z）は日次の巡回で記録が漏れていた。** 同日 08:37Z の 0.169.0 のみが記録されていた。**同一日に stable が2本出ると、1本だけを見て完了扱いにする失敗が起きる。** 週次で GitHub Releases 側と突き合わせたことで拾えた。日次と週次の二重チェックが、この種の取りこぼしに対して実際に機能した例として、巡回手順の設計根拠に残す。
- **最小限の Knowledge 反映案**: 既定スキップのままでよい。ただし Codex を CI / 自動化で使う手順を扱う教材があれば、**`codex exec` が未信頼ディレクトリでプロジェクト設定と MCP を無効にすること**と、**`--trust` で明示的に信頼を保存すること**の2点を注記する価値がある。Vertex AI 経由の構成を扱う箇所には、**ツール更新が既定で増分送信になり、戻すには `incremental_tools_legacy_gcp = false`** を記す。
