- **「設定ファイルは実行される指示である」**という一文を、AI コーディング教材の必修項目にできる。`AGENTS.md` は人間向けドキュメントの見た目をしているが、エージェントにとっては命令である。**見た目がドキュメントであることと、機能が指示であることは別**——この区別は、`CLAUDE.md`、各種 rules ファイル、MCP 設定にもそのまま当てはまる。
- **「未信頼プロジェクト」の判定を誰が行うかが運用側に残る**という論点。機能が直っても、何をもって信頼済みとするかを決めていなければ実質は変わらない。**製品の修正と組織の運用は別レイヤー**という、ハーネスエンジニアリングの基本構図を説明する具体例。
- **管理設定が「効くと思っていたが効いていなかった」ケース**として deny-read ルールの修正を扱える。統制の設計で最も危険なのは、設定が存在するのに条件次第で無効化されること。**設定した後に、想定どおり効いているかを検証する工程**を手順に組み込む理由として使える。
- **`Interrupt` フックは「正常終了しない場合の設計」の教材**。エージェント運用では中断が日常的に起きるのに、後始末は人の記憶に依存しがち。**例外パスを設計に含めるかどうか**が運用の成熟度を分ける、という一般則の具体例。CI・共有環境の話に接続しやすい。
- **タスクの `@` 参照が「分割の単位」を変える**という論点。参照で文脈が繋がるなら、タスクを小さく切っても説明し直さずに済む。ただし**機能が出ただけでは分割は起きない**——どう分けるかを決める設計作業が別途必要、という点まで含めて教えると、ツール導入と業務設計の関係が伝わる。
- **stable と alpha が並行して出る運用**（v0.150.0 stable の直後に v0.151.0-alpha が3本）は、リリース戦略の教材になる。安定版で受け取る人と先行版で試す人を分けることの意味、そして**どちらを業務で使うかを組織として決めておく**必要性。
- **新機能欄より修正欄に重要な変更が入っている**という読み方は、リリースノートの読解訓練としてそのまま使える。目立つ機能は目立つように書かれるが、信頼モデルの変更は「Bug Fixes」の1行に収まる。**リリースノートは重要度順に並んでいない**という前提を持てるかどうか。
