- **「エージェントが古い情報で作業する」問題への、最小の対策例として使える。** 対策としてよく挙がるのは Web 検索の許可だが、**検索結果には三次情報が混ざる。** `cf docs search` は公式ドキュメントだけを返す。**対策の質は、情報源を絞れるかで決まる**という論点が1つの事例で示せる。
- **MCP を立てずに同じ目的を達成している**点が設計の教材になる。必要なのは「検索して URL を得る」「本文を Markdown で読む」の2段だけで、それは CLI と `Accept: text/markdown` ヘッダで足りる。**サーバーを立てる前に、既にある実行能力で足りないかを問う**という順序は、MCP 導入の講義で最初に置くべき話。
- **`Accept: text/markdown` でドキュメント本文が返る設計**は、「機械向けの出力形式を用意する」という発想の実例。HTML をスクレイピングさせるのではなく、読みやすい形を最初から出す。**AI 時代の API / ドキュメント設計**として一般化できる。
- **kebab-case 化は「静かに壊れる変更」の典型例として強い。** 手元では気づかず、**夜間バッチで初めて落ちる。** エラーも分かりにくい（コマンドが見つからない、だけ）。破壊的変更の怖さは「大きさ」ではなく**「発覚の遅さ」**だという論点に繋がる。
- **エージェント定義ファイル（CLAUDE.md、社内手順書）が破壊的変更の影響を受ける**という視点は新しい。スクリプトは grep で探せるが、**自然文で書かれた手順書のコマンド例は見落としやすい。** しかもエージェントはそれをそのまま実行する。**「ドキュメントが実行可能になった」ことの副作用**として、ハーネス設計の教材に置ける。
- **バージョン固定の話を具体化できる。** `cf@latest` を CI で引いている構成は、**ベンダーのリリース日に自分の CI が壊れる**ことを許容している。beta 段階（1.0.0-beta.16）の CLI なら尚更。**「固定するか追随するか」を意識的に選ぶ**という運用判断の題材。
- **保守の営業導線としても使える。** 破壊的変更の告知は、**納品済み案件への連絡の正当な理由**になる。契約の有無にかかわらず、連絡自体が次の仕事につながる。**技術の更新を顧客接点に変える**という受託の型。
- 最小限の Knowledge 反映案: `claude-code/mcp` や `codex/mcp-integration` に **「MCP を立てる前に CLI で足りないか検討する」** という判断軸を1行入れる余地がある。MCP を常に正解として教えないための補助線。
