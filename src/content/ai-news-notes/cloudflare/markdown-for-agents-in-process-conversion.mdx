- **教材の軸は「undefined で静かに壊れる破壊的変更」に置く。** `x-markdown-tokens` が消えたとき、多くの実装はエラーを出さず `undefined` や `0` として扱う。**`undefined > 100000` は false になるため、「小さいから投げてよい」と判定が反転する。** 結果として**大きすぎるページがモデルへ流れ、コスト事故になる。** 公式 changelog は「自分で数えてください」と書くだけで、この経路は書かれていない。**公式が書かない二次的影響を読み取る**練習として非常に良い題材である。
- **「上限緩和と防御の喪失が同時に起きる」という重なりを扱う。** 上限が **2MiB → 6MiB（3倍）**になったのと、**トークン数ヘッダが消えた**のが同じ変更に入っている。**従来より大きなものが、従来の防御なしで通る**状態になる。単独の変更としては安全に見えるものが、組み合わせでリスクになる実例。
- **「どちらのサイズで判定されるか」を読み取らせる。** 上限 6MiB は**解凍後**の HTML に適用され、圧縮後のサイズではない。HTML は gzip がよく効くため、**圧縮後 300KB でも解凍後 6MiB を超えうる。** 「レスポンスが小さいから通るはず」は成立しない。ドキュメントの細部を読み落とすと失敗する典型。
- **内部実装の変更がインターフェースに漏れ出す例として教える。** `Content-Length` が消えたのは**本文をストリーミングするようになったから**、トークン数ヘッダが消えたのは**変換サービスを分離しなくなったから**。どちらも**内部の都合がレスポンス仕様に現れた形**である。「レスポンスヘッダは仕様として安定しているように見えて、実装の都合で消える」という一般則につなげられる。
- **トークン数の数え方の選択を、精度と目的の対応として教える。** **(1) 文字数・バイト数で近似** — 精度は落ちるが閾値判定なら十分。**(2) トークナイザで正確に数える** — ストリーミングで受け取った本文を全量貯める必要があり、**減ったメモリ使用量が戻る。** 「正確さが要るのはどこか」を問わせる。**正確なトークン数が必要な課金見積もりは、変換時点の推定ではなく実レスポンスの usage から取るのが正しい**という結論まで導く。
- **`Content-Length` 依存の洗い出しは、別系統の作業として分けて教える。** プログレス表示、バッファの事前確保、レスポンスサイズのログ。**ストリーミングではサイズが受け取り終わるまで分からない**ため、プログレスは不定（スピナー）か受信バイト数表示に変えるしかない。**同じ破壊的変更が、まったく違う場所に当たる**ことを示せる。
- **「changelog だけでは対象を特定できない」ことを扱う。** 対象の API 名・バインディング名・HTML 以外の入力形式・性能の具体数値が、いずれも記載されていない。**どこで使っている機能の話なのかを特定する作業が読者側に残されている。** 公式ドキュメントへ降りる必要がある、という読み方の実例。
- **個人開発では自前の上限判定が必須である点を強調する。** 個人の API 予算は小さく、**大きなページがそのまま流れると1回で痛い。** 「本文の文字数が N 文字を超えたら投げない」という3行の判定で事故の大半は防げる。**プラットフォームが出していた安全網は、消えることがある**という前提で設計させる。
- **既存 Knowledge への反映は不要と判断した。** `src/content/knowledge/ai-tools/` に Cloudflare の教材がまだない。将来作る場合は、**ヘッダ名や上限値ではなく「外部サービスのレスポンスに依存するときの防御設計」**を軸にする。ヘッダは消えるが、「依存先が消えたときに静かに壊れないようにする」という設計原則は残る。
