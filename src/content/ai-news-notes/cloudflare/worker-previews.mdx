- **この事例の中心的な教材価値は、「自動で隔離されるもの」と「自分で隔離するもの」の線引きにある。** Durable Objects と Containers は Preview ごとに自動分離されるが、**KV / D1 / R2 は別リソースを明示的にバインドしないと分かれない。** 「Preview を作れば全部隔離される」と読むと、Preview から本番 D1 を叩く構成ができあがる。**公式の説明を読んで境界を特定する**という作業を、そのまま演習にできる。
- **プレビュー環境が普及しなかった理由を説明できる題材。** コードを分けるのは簡単で、**状態を分けるのが難しい**。データベースの複製、マイグレーション適用、テストデータ投入、使用後の破棄——この作業量が普及の壁だった。**「なぜ今までなかったのか」を説明できると、機能の価値が正しく伝わる。**
- **URL を2種類（安定・不変）用意した設計判断を扱う。** レビュー中に相手が push して、見ていたものが変わる——という事故を、URL の種類で分けている。**運用上の困りごとから設計が決まる**という具体例。要件定義の教材になる。
- **カスタムドメイン配信の理由が明快な教材になる。** 認証プロバイダ・Cookie・CORS・OAuth リダイレクトが本番と同じ挙動になるから。**「プレビュー環境で認証が検証できない」という詰まりどころ**を知っている人には刺さる。ドメインが挙動に影響する仕組みの復習にも使える。
- **公式の副題「every change your agent makes」は、製品設計の潮目として扱う。** 人間が1日数本の PR を出す前提ではなく、**エージェントが大量の変更を投げる前提**で設計された、と明示している。**設計思想が「人間が使う前提」から移っている事例**は、まだ多くない。発信の切り口として価値がある。
- **検証が律速になる、という構造を教えられる。** エージェントで開発速度を上げても、staging が1つしかなければ検証待ちで詰まる。**部分最適の高速化がボトルネックを移すだけになる**という一般則の具体例。
- **導入判断の軸を絞る練習に使える。** この機能が効くのは「検証環境の数が足りていない」場合だけ。**状態を持たない単純な Worker しか動かしていないなら、急ぐ理由はない。** 新機能を全部追いかけない判断を教える。
- **「作り放題」と読ませないこと。** 数百の Preview を同時に走らせられる、という説明はあるが、課金への影響は changelog に明示がない。**上限と料金が書かれていない機能は、書かれていないだけで無料ではない。**
- 恒久教材へ反映する場合、**Wrangler のバージョン番号やコマンド名は書かない**（変わる）。残すのは **(1) コードより状態の分離が難しい、(2) 自動で分かれる範囲を導入時に文書化する、(3) 高速化はボトルネックを移すだけのことがある** の3点。
