- **RPA が壊れる理由を構造から説明できる教材**。画面操作の模倣で組まれている以上、画面が変われば壊れる。**これは実装の質の問題ではなく、方式の必然**。「もっと頑健なセレクタを書く」では解決しない、という点まで踏み込める。WebMCP はその方式自体を変える提案として位置づく。
- **API と Web ページの関係が反転しつつある**構図。従来は「画面しかないから画面を操作する」だった。WebMCP は「ページの上に関数の契約を置く」。**Web ページが、人間向け UI と機械向け API の両方を同時に提供する**という形。REST API を別に用意するのとは違う道筋である点を押さえたい。
- **「使う側」と「提供する側」の両方になる**という視点が今回の肝。多くの記事は自動化する側だけを扱うが、**自社サイトを持っている組織は提供側でもある**。使う話しか考えていないと、判断が半分抜ける。
- **SEO とエージェント対応を別軸として並べる**のは、事業者向けの説明として効く。検索エンジンに見つけてもらう / エージェントに正しく使ってもらう。**目的も手段も違う**。同じ「集客対策」の枠に入れると設計を誤る。
- **関数の粒度が権限設計になる**話。検索は公開してよい、決済は? **画面経由なら確認ダイアログで止められたものが、関数呼び出しでは止まらない**。UI が事実上の安全装置として機能していたことが、UI を外して初めて見える。**「暗黙の安全装置」を明示的に設計し直す**という一般的な課題。
- **WPT 通過数 215,000 → 230,000 → 730,000** という推移は、数字の読み方の練習になる。**基準（WPT のバージョン、サブテストの数え方）が揃っているかを確認せずに「3倍」と言えるか**。公式が出した数字をそのまま引用するときの注意点。
- **ターミナル描画という機能の目的**が示唆的。人間が見るためではなく、**エージェントの認識を人間がデバッグするため**。AI を業務に入れると、「AI が何を見ているか」を確認する道具が新たに必要になる。**観測性（observability）の対象が増える**という話。
- **アクセシビリティとの重なり**を指摘しておきたい。エージェントに構造が伝わらないページは、スクリーンリーダーにも伝わっていないことが多い。**エージェント対応を口実に、放置されていたアクセシビリティ改善が進む**という実利的な接続。
- **ベータ無料の価格リスク**は、受託の見積もり教材として使える。「今は無料」を前提に提案し、課金開始で採算が崩れる。**期間限定の条件を、恒久的な前提として顧客に伝えない**という基本。
