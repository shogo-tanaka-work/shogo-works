- **教材の軸は「形式の対応」と「到達性」を分けることに置く。** PDF と Office 文書に対応したのは**形式の問題**で、社内ファイルサーバや SharePoint の文書が読めるかは**到達性（URL と認証）の問題**である。要件定義の場でここを混ぜると「対応しているはずなのに使えない」という典型的な齟齬が出る。**公式の対応形式一覧を読んで要件を満たすと判断するのが、なぜ早すぎるのか**を教える題材になる。
- **offset によるページングを「責任の所在」として扱う。** 長文は分割されて返り、モデルが読み進めるかを判断する。**公式はツールを提供するが、読み切る保証はしていない。** 契約書レビューのように最後まで読まないと判断できない用途では、**offset を使い切る制御を自分で書く**必要がある。「モデルが全部読んだ前提で結論を出していないか」を確認する仕組みの有無が、見た目の同じ納品物の中身を分ける。
- **許可ホストと検索の衝突は、回避策ではなく設計判断として提示する。** `web_fetch` は許可ホストで縛れるが、`web_search` と併用すると読む URL が事前に分からない。**縛りが実質効かなくなる。** ここで「閉じた型（許可ホストを限定・権限あり）」と「開いた型（公開 Web を読む・権限なし）」の2型に分け、**混ぜると権限が乗っ取られる経路ができる**という結論まで持っていく。エージェント設計の授業で最も再利用が効く枠組みである。
- **最終 URL が返ることの価値を、出典管理から説明する。** リダイレクト前の URL を残すと後から辿れない。**地味なフィールドが実務の品質を決める例**として扱える。リサーチ納品では出典が辿れるかが信頼の全部である。
- **`fetchWeb()` を「エージェントと関係なく使える道具」として独立して教える。** Durable Object もブラウザも不要で URL から Markdown が返る。**Playwright で本文を抜く処理の保守の重さ**（サイト構造が変わると壊れる）と対比させると価値が伝わる。エージェントを作る予定がない組織にも効く、という射程の広げ方を示せる。
- **「Markdown for Agents 対応サイトには Markdown を直接要求」という分岐を、規格の普及の話として扱う。** 変換を挟まない経路が用意されているのは、サイト側の宣言に意味があるということである。**規格が実装に効いている実例**として短く扱える。
- **バージョン要件の非対称（web_fetch は 0.28.0、web_search は 0.27.0）を依存管理の実例にする。** 両方使うなら実質 0.28.0 が下限になる。**「どちらも入れるなら高い方」という当たり前の判断を明示的に書く**習慣を教える。
- **価格が書かれていないことを、検証の出発点として扱う。** Workers AI Markdown Conversion の課金に従うと読むのが自然だが明記は無い。**推測で埋めず、無いことを記録してから測る**手順をそのまま見せられる。
- **既存 Knowledge への反映は不要と判断した。** Cloudflare の Knowledge 記事が無く、RAG 教材に対しても「前処理の選択肢が増えた」以上の前提変更は無い。将来反映するなら、**個別ツールではなく「取得・変換・読み切りの責任分界」**を軸にする。
