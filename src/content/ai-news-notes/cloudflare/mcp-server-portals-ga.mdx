- **「単一エンドポイントに集約する」は MCP 固有の発明ではない**。API ゲートウェイ、リバースプロキシ、SSO と同じ構造。**多対多を多対1対多に組み替えて中央で統制する**という古典。新しい技術に古い解法が適用される様子を見せる題材として良い。
- **「ログは残るのか」が最初に聞かれる質問**、という提案現場のリアル。エージェントに社内データを触らせる提案で監査の話が出ないことはない。**答えられるかどうかで提案が通るか決まる**。技術選定が営業結果に直結する例。
- **Logpush で既存 SIEM に流せる、という点が本質。** 新しい監査の仕組みを作るのではなく、**すでに運用している枠組みにエージェントの通信を載せる**。新規導入のコストが「ゼロから作る」ではなく「既存に載せる」になると、承認の難易度が変わる。
- **ツール定義がコンテキストを圧迫する問題**は個人利用でも起きる。**「エージェントの回答が急に雑になった」の原因がツール定義の肥大化**というのは実感を伴う話で、受講者の手元で再現しやすい。Cloudflare が制御対象として実装した事実が、問題の一般性の裏づけ。
- **サービストークン認証は無人運用の前提条件**という整理。対話型なら利用者の OAuth で足りるが、**スケジュール実行や他システムからの呼び出しには認可する人間がいない**。ここを飛ばすと共有アカウント使い回しという最悪形に落ちる。設計の抜けが起きやすい箇所。
- **「規模が小さいならポータルは過剰」と言い切る**こと。エージェント1つ・MCP サーバー2つならポータルを挟む手間の方が上回る。**新機能を無条件に勧めない**という姿勢そのものを教材にしたい。判断基準は対応関係の複雑さ。
- **「今は要らないが、いつ必要になるか」を判断できること**が設計の経験値、という締め方。パターンを知っているだけでは足りず、適用タイミングを見極められて初めて使える。**過剰設計と手戻りの両方を避ける**という実務の核心。
- **前提の確認（Cloudflare One / Access が必要）**を落とさない。「すべての顧客」という記述を額面どおり読むと外す。**提供範囲の記述と実際の前提は別**という読解の注意点として、前日の Gemini Enterprise の件と並べて教えられる。
