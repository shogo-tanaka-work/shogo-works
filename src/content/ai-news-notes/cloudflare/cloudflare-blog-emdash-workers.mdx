- **「慎重さの本質は時間の長さではなく、戻せること」**は、そのまま教材の結論に使える。1% から始めて当日中に 100% まで振り切れたのは、フォールバックが確実に効いたからである。段階ロールアウトを何日もかける計画と、当日中に完了する計画の違いは、慎重さの量ではなく設計の質にある。移行計画のレビュー観点として提示できる。
- **service binding でプロキシ層のコストが消える**という具体例は、「二重構成は高くつく」という思い込みを崩す材料になる。安全な切り替え方は知られているのに実行されないのは、たいていコスト見積もりが理由である。技術的な解が既にあることを示せると、判断が変わる。
- **「MCP 化に数時間」の裏返しが効く**。API と検索エンドポイントが整っていれば MCP server は薄く作れる。逆に MCP 対応が重いと感じるなら、問題は MCP ではなく既存 API にある。**AI 連携の見積もりを分解して説明する**フレームとして、伴走支援の場でそのまま使える。
- **CMS が MCP server を持つ意味は「執筆の自動化」ではなく「公開フローの自動化」**である。作成・編集・公開・予約・削除がエージェントから叩けるということは、承認と公開の権限設計が MCP のツール設計に直結するということ。エージェントに公開権限を渡すかを先に決める、という順序を教える実例になる。
- **Customer Zero という立場の開示の仕方**が、提案姿勢の教材になる。Cloudflare は EmDash チームが自社用にオブジェクトキャッシュを専用実装したことも、予約投稿が 0.19.0 まで動かなかったことも書いている。**未成熟さを自分から先に開示する提案は後で揉めない**、という一般則の具体例として提示できる。
- **本サイト自身が Astro + Cloudflare 構成**である点は、教材として強い。読者に「自分の環境と同じ土俵の実測値」を渡せる機会は多くない。850 RPS / 450 RPS / 28,000 RPS の DDoS 吸収という数字は、スケール不安に対する具体的な回答として引用できる。
- **導入事例と製品リリースを区別して読む**訓練の題材。これは changelog の機能追加ではなく自社導入の後日談であり、同じ条件が誰にでも揃うわけではない。「構成の考え方は参考にし、採用判断は自分の要件で行う」という読み分けは、技術記事の読み方の教材にできる。
- WordPress からの移行案件は当面なくならないが、**多くは技術ではなく「切り替え当日が怖い」で止まっている**。プロキシ Worker + Cookie 経路 + 500 系フォールバックという型を手札として持っておくと、その恐怖に手順で答えられる。受託支援のメニュー説明に直接使える。
