- **教材の第一の軸は「公式が言ったこと」と「報道が言ったこと」の分離に置く。** Cloudflare 公式投稿が言っているのは **(1) Deno チームが参加する (2) workerd の self-host を一級サポートにする (3) 今後数か月で続報** の3点だけ。**Deno Deploy の6か月後停止やランタイムの開発終了は公式投稿に一文字も無い。** 多くの二次記事がこれを混ぜる。**一次情報の範囲を線で引く練習**として、ちょうどよい素材である。
- **本記事は `deno.com` に到達できず、日程を一次確認できていない。** この「取れなかった」という記録自体を教材に使う。**取得失敗を明示する記事のほうが信頼される**という原則と、読者が自分で確認する動線を残す書き方を教える。
- **技術的な核は「Durable Objects の単一インスタンス保証をマルチノードで維持する難しさ」である。** Durable Objects は「あるオブジェクト ID に対して常に1インスタンスだけ存在する」ことを保証する。**この保証が分散環境で難しいからこそ、workerd の OSS 実装は単一インスタンスに留まっていた。** 公式が自ら「スケールに適さない」と書いている点が引用価値を持つ。**分散システムの一貫性の教材として、抽象論ではなく実在の製品制約で教えられる。**
- **celld の設計は単独で読む価値がある。** 「外部依存がオブジェクトストレージだけの単一 Rust バイナリ」。**ステートフルな実行基盤を、どこまで依存を削って作れるか**という問いの実例になる。
- **ベンダーロックインの評価軸が「機能」ではなく「出口」で決まる例として扱う。** Workers 単体は workerd で動くが、**Durable Objects を使った時点で実質的に出口が消えていた。** 「状態を持つ部品ほどロックインが強くなる」という構造を、具体的な製品で説明できる。技術選定の教材に直接使える。
- **「発表されていない機能を前提に設計しない」という規律を教える。** 公式は「今後数か月で発表する」段階。**稟議や設計に「将来 self-host 可能」と書くのは発表後にする**という線引きを、具体的な判断として示せる。期待と確定を混ぜる失敗の実例。
- **社内文書の陳腐化の管理という観点を入れる。** 「Durable Objects は self-host 不可」と書いた技術選定資料は、**制約が変わりうる状態になった。** 「2026-10 に改善着手、続報待ち」を添えるだけで、半年後に読む人の誤判断を防げる。**変わりうる前提を変わりうると書く**文書作法の教材になる。
- **人材の動きから方向性を読む、という分析手法も扱える。** Node.js と Deno を作った人物が Cloudflare のランタイムを「どこでも動くもの」にする側に回った。報道ベースの Dahl の動機は「エージェントの数が爆発しており、そのすべてに Linux VM が必要とは思わない」。**エージェント実行基盤を Cloudflare 外へ広げる方向**と読める。ただしこれは解釈であり、公式の方針表明ではないと明示して教える。
