- **この事例の中心的な教材価値は、「対応した」と「使える」の距離にある。** Python Workers は GA になったが、使えるのは PyEmscripten 向けホイールがあるパッケージだけ。**公式自身が「生態系はまだ採用の途中」と書いている**点を読ませると、技術発表の読み方が一段変わる。
- **見積もりの演習にそのまま使える。** 「Python が動くならうちの処理も載る」と見積もると赤字になる。**最初の作業は実装ではなく、依存パッケージの対応確認**。この順番を守るかどうかで案件の成否が決まるという、具体的で反論しにくい例になる。
- **制約の理由を説明できる題材として質が高い。** なぜ今まで `aiomysql` が動かなかったのか。WebAssembly サンドボックスでは POSIX のソケット syscall が常に失敗するスタブだから。**「動かない」には理由があり、理由が分かれば回避策も分かる**という、エンジニアリングの基本姿勢を教えられる。
- **抽象化レイヤーの置き場所を教える好例。** Cloudflare はソケットの翻訳を**システムコールのレベル**で行った。だからドライバ側の改修がゼロで済んでいる。**低い層で吸収すると上の層が全部そのまま動く**という設計原則を、具体的な成果と一緒に示せる。
- **「自社専用に作る」と「標準を作る」の違いを扱える。** Cloudflare は自社ビルドを増やさず PEP 783 を提案して通した。**自社の問題を業界の標準化で解いた**という判断は、OSS 戦略やプラットフォーム戦略の教材になる。1年以上かかった事実も含めて扱う。
- **技術選定の授業で「前提が外れる」という現象を教えられる。** 「Workers を使うなら TypeScript」という前提は長く有効だったが、今回で外れた。**技術選定の結論は前提とセットで記録しておかないと、前提が変わったときに見直せない**という一般則へつなげる。
- **サーバーレスが向く処理・向かない処理の切り分け**に使える。リクエスト単位で完結するものは向き、長時間バッチや重い推論は向かない。「サーバーを持たなくていい」は形が合うときだけ効く、という条件付きの利点として教える。
- **副業・個人開発の文脈では「公開の壁」を扱える。** ローカルで動くものを人に見せる形にする手前で止まるプロジェクトは多い。**その壁の高さは技術力ではなくインフラ作業の量で決まっていた**という指摘は、受講者の実感に刺さりやすい。
- 恒久教材へ反映する場合、**具体的なパッケージ名・コネクタ名・API 名は書かない**（変わる）。残すのは **(1) 言語対応と実際の移植可能性は別、(2) 制約の理由をランタイムの性質から説明する、(3) 移植の見積もりは依存の確認から始める** の3点。
