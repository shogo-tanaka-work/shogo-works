- **教材の軸は「抽象化レイヤーがエラーまで抽象化しているか」に置く。** AI Gateway はプロバイダーを抽象化する前段だが、**エラー応答だけはプロバイダーのものが素通りしていた。** 抽象化レイヤーを選ぶときの確認項目として、「正常系だけでなく異常系も抽象化されているか」を教える具体例になる。**この観点は Gateway 製品全般の評価に転用できる。**
- **リトライ設計の教材として非常に良い題材である。** Google Vertex の資格情報エラーが **500（リトライされる）から 401（リトライされない）**へ変わった。**500 を一時障害としてリトライするのは正しい設計だが、資格情報の誤りに対するリトライは無駄な待ち時間を生むだけである。** 「リトライすべきエラーと、すべきでないエラー」を**ステータスコードの意味から判断する**練習にできる。
- **「リトライで隠れていたエラーが表面化する」という副作用を必ず扱う。** 切り替え直後に**エラー率のグラフが跳ねて見える**可能性がある。公式 changelog はこの運用影響を書いていない。**公式が書いていない影響を自分で読み取る**練習として価値が高い。
- **401 の意味がコンテキストで変わる点は、監視設計の教材に使える。** 通常の Web API の 401 は「利用者の認証失敗」で無視してよいことが多いが、**AI Gateway 経由の 401 は「自社の API キーが失効した」というアラート対象である。** 同じコードを同じルールで扱う監視設定の危険性を示せる。
- **Unified Billing の 503 は「公式が書いていないこと」の実例になる。** 503 は一般に一時障害でリトライ対象だが、資格情報拒否が原因ならリトライしても解決しない。**公式は 503 のうち資格情報由来のものを識別する方法を書いていない。** 受講者に「ここは実装で確認するしかない」と判断させる演習にできる。
- **運用手順書の更新という観点を忘れずに扱う。** 「500 が返るときはプロバイダー側の障害」と書かれた一次切り分け文書は、この変更で誤りになった。**切り分けを間違えると設定ミスを障害として調査することになる。** ドキュメントの陳腐化が障害対応のコストに直結する実例である。
- **既存 Knowledge への反映は不要と判断した。** 現状 `src/content/knowledge/ai-tools/` に Cloudflare の教材がない。将来作る場合は、**エラーコードの一覧ではなく「マルチプロバイダー構成でエラーハンドリングを設計する手順」**を軸にし、その中で具体例として扱う。コード値は変わるが、設計手順は残る。
