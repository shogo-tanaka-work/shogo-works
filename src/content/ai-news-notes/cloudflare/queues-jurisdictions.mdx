- **教材の軸は「作成後に変更できない設定」という性質に置く。** 機能の中身（3値の選択）よりも、**後から直せないことが設計プロセスに影響する**点が本質である。データレジデンシー要件は**プロジェクト初期には分からないことが多い**という現実と組み合わせると、「要件が出る可能性があるなら最初から付ける」という判断が導ける。**不要だった場合の損失が小さく、必要になった場合の救いが大きい**という非対称性の読み方を教える。
- **Workers KV（2026-10-02 GA）との同型性を、ベンダーの設計思想の一貫性として扱う。** 同じ3値、同じ変更不可の制約。**1製品の機能紹介より射程が広く、他製品が同じ対応をしたときに書き直さずに使える**教材になる。「ベンダーの設計は製品横断で一貫する」という一般論の具体例として提示する。
- **「書かれていないこと」の扱いを最重要の論点にする。** KV では「キャッシュは域外に出る」と公式が明記していたが、**Queues の changelog には経路についての記述が無い。** **無いことは保証ではない。** 厳格な要件の案件ではサポート確認が筋で、**「書かれていないから大丈夫」は監査で崩れる**——コンプライアンス案件の読み方として最も価値のある部分である。
- **3択の射程を正確に教える。** `eu` / `us` / `fedramp` は、**日本国内にデータを留める要件には応えない。** EU 顧客向けサービスか、米国政府・公共調達の要件がある場合に効く。**「データレジデンシー対応しました」がどの地域の要件に対する対応なのかを明示する**習慣を教える。混同は「満たしたつもりで満たせていない」状態を生む。
- **「データはどこに保存されますか」への答え方を、信頼の差として扱う。** 「Cloudflare に保存されます」では答えになっていない。**製品ごとの固定方法と制約まで答えられるかが技術者としての信頼を決める。** 情報は公式にあり、読んだ人だけが答えられる、という構造を示す。
- **設計レビューのチェック項目づくりを演習にできる。** 作成時にしか決められない設定（jurisdiction、リージョン、namespace 名、ID 体系）の棚卸し。**短時間で終わり、価値が明確な作業**であり、受託の入口として現実的である。
- **キュー名・リソース定義の環境変数化を、作り直し前提の設計として教える。** 変更不可の設定を持つリソースは**作り直しが前提の運用になる**ため、参照箇所が散らばっていると作業量が跳ねる。制約から逆算した実装上の備えの例として使える。
- **日付の扱いを一次情報の読み方の例として残す。** URL スラッグは `2026-09-18` だが RSS の pubDate は `2026-10-12`。**どちらを採用したかを記事に明記した**判断そのものが、情報源の不一致に出会ったときの型になる。
- **既存 Knowledge への反映は不要と判断した。** Cloudflare の Knowledge 記事が無く、他ツールの教材の前提も変わらない。将来反映するなら、**個別の3値ではなく「変更不可の設定をどこで決めるか」**を軸にする。
