- **Cloudflare の互換性フラグ（compatibility flag）の運用作法を、単独で教材化する価値がある。** 「新しい挙動を選べるが、選ぶまでは変わらない」「既定オン日が設定されたらそこから自動で切り替わる」という二段構え。**日付が発表された時点が対応の開始点**という原則は、`codex mcp-server` の非推奨→削除と同じ構造で、**deprecated 系の一般則として揃えられる。**
- **「既定オン日が未設定」を、対応不要ではなく待機状態と読ませる。** フラグの存在を知らないと、既定オンの日に何が起きたか分からなくなる。**知っていて動かない**と**知らずに動かない**の差を、運用の教材で明示する。
- **新規案件では最初からフラグを立てる**という判断の型。既存の稼働中サービスへ後から適用すると検証コストが乗るが、新規ならコストはゼロに近い。**「将来の既定変更に備えるコストは、着手時点が最も安い」**という一般則の具体例。
- **「偶然動いていた import が動かなくなる可能性」**は、仕様準拠化に伴う典型的な副作用。仕様に寄せることは、非準拠の書き方を許さなくなることでもある。**互換性改善＝無条件に安全ではない**という点を、ステージング検証の必要性とセットで教える。
- **エッジ実行環境に対する前提の更新**が論点。サイズ上限 64 MiB・圧縮後制限撤廃・Node.js API 既定有効という3点で、「エッジは制約が厳しいから既存アプリは載らない」という数年前の判断根拠が古くなっている。**技術選定の教材で「調査結果には賞味期限がある」実例として引く。**
- 副業・受託向けには、**着手前に判断できる範囲が広がる＝見積もり精度が上がる**という切り口。「やってみないと分からない」という返事を減らせることが、そのまま提案力になる。
- 恒久教材へ反映する場合、フラグ名とサイズ上限の数値は変わりうるので書かない。残すのは**互換性フラグの運用作法**（未設定＝待機、日付発表＝開始、新規は最初から）だけにする。
