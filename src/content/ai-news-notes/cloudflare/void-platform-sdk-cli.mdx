- **教材の軸は「作れるようになった次に何で詰まるか」に置く。** AI コーディングツールの教材は「作れる」で終わるが、**現場の次の壁はデプロイ先である。** 社内で他人に使わせる画面を作った瞬間に権限の話になる。**この順序を先に示すと Void の位置が理解できる。** 機能一覧から入ると「また新しいフレームワーク」に見えてしまう。
- **「2つの悪い選択肢」を具体的に描く。** 全社員にクラウド権限を渡す（情シスが通せない）か、情シスが全部代行する（速度が出ない）か。**後者が新しいボトルネックになる構造**を説明できると、3つ目の選択肢の価値が伝わる。**受講者の組織で実際に起きていることなので共感から入れる。**
- **本質は「アカウントの権限」と「デプロイする権限」の分離だと言い切る。** ここが技術的な新しさより重要である。社員は Platform に出し、Platform が Workers へ展開する。**社員は Cloudflare アカウントを触らない。** この分離は Void に限らず一般化できる設計パターンである。
- **Workers for Platforms の読み替えを、設計の勉強の題材にする。** 元は「自社の顧客に Workers を提供する」仕組み。**顧客を社員に置き換えるとそのまま社内配布環境になる。** 同じ技術を別の対象へ向けると別の製品になる例として優秀。**オープンソースなのでコードを読んで確認できる**点も教材として強い。
- **「設定を書かない」設計の意味を、作る人の層の変化から説明する。** `void/db` や `void/ai` の import だけでつながる設計は、**バインディング設定ファイルという最初の壁**を外すためのもの。慣れた人には数分の作業が、初めての人には越えられない壁になる。**誰のための設計かを読む練習**になる。
- **立ち上げコストを正直に書く。** 自己ホストには Workers for Platforms + R2、**PostgreSQL（Cloudflare だけで完結しない）**、ログインプロバイダ、ドメインが必要。**「npm install で終わり」ではない。** ここを軽く書いた教材は、やってみた受講者の信頼を失う。**個人は Platform 不要**という区別も明示する。
- **オープンソースであることを稟議の文脈で扱う。** 自社アカウント内で動き、コードが読め、フォークも他プラットフォーム移行もできる。**「このベンダーが止めたらどうするか」に答えやすい。** 一方で**サポート体制は公式に明示されていない**（GitHub / Quick Start / Discord のみ）。基幹業務では確認が必要、と両面を書く。
- **Astro 併用は、このサイトの構成と直結するので具体例として使える。** 静的部分は Astro、動的部分だけ Void。**全面移行の判断を先送りできる**のは受託案件での実務的な利点である。「新フレームワークへの移行」ではなく「デプロイ基盤の追加」という枠組みで考えさせる。
- **「CLI がエージェント前提」は権限の話として扱う。** エージェントがログを読みデバッグしデプロイする。便利さの話で終わらせず、**エージェントにデプロイ権限を渡すなら記録とロールバックが前提**という線を引く。Void CLI はロールバックを含むが、**誰が何をいつ出したかの記録設計は運用側の宿題**である。
- **提案メニューとして組み立てやすい形を渡す。** 「社内アプリの配布基盤づくり」＝ Platform 構築 ＋ 権限・上限・監視のルール設計。**単発開発より寿命が長く、立ち上げ作業として規模もある。** 課題（全社員に権限を渡せない／情シスが代行で手一杯）が説明しやすく共有されやすい点も、提案の通しやすさに効く。
- **AI Gateway 経由の構成を既定にする理由を教える。** `void/ai` が設定なしで AI Gateway につながるため、**ログ・キャッシュ・レート制限が最初から効く。** 「とりあえず API キーを直接呼ぶ」構成との差は、顧客へ渡した後に出る。**利用量が見えることは説明材料になる。**
- **既存 Knowledge への反映は見送る。** Cloudflare の Knowledge 記事が未整備であり、**記事化したばかりの公開直後の製品で恒久ページを作るのは早い。** 採用実績が出てから判断する。関連リンクは空配列のままにしておく。
