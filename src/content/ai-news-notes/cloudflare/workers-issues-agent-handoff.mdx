- **「落ちないが壊れている」問題という分類が、この更新の最良の教材。** 公式の実例2件（マイグレーションのリトライループ、サブリクエスト上限超過）はどちらもサービスを止めない。**ユーザー報告も来ず、エラー率の割合が小さければダッシュボードでも気づかない。** 放置されると (1) 課金、(2) 特定条件のユーザーの体験、という2つの形で表に出る。
- **監視導入の効果を「障害対応が速くなる」と説明しない。** 障害は監視がなくても気づく。**効果は「気づいていなかった問題が見つかる」こと。** この区別ができていないと、導入初期の検知件数の多さを「問題が増えた」と誤解される。**導入前に「増えたのではなく見えるようになった」と説明しておく**という運用の知恵。
- **自動化の下流に何があるかで、上流が送るべき情報の形が変わる**という設計原則。人が見る前提のエラー通知と、エージェントが処理する前提のエラー通知は、必要な情報量と構造が違う（ソースマップ適用済み、バージョン込み、業務識別子付き）。**自社のログ設計に「これはエージェントが読んで調査できる形か」という問いを加える。**
- **エージェントへの権限の線引きを、連携を設定する前に決める。** 調査だけ / 修正案まで / PR まで / マージまで。**「最初は調査と報告まで」から始めて、質を数週間見てから広げる**という順序。本番へ自動で手が入る経路は、動くことを確認してから広げる種類の自動化。
- **最初の1週間は連携先を設定せず検知だけ有効にする**という手順。何がどれだけ検知されるかを見てから、どの条件でエージェントへ渡すかを決める。**これを飛ばすと初日に大量のセッションが起動してコストと埋没が同時に起きる。** 新しい自動化を入れるときの汎用的な進め方。
- **OpenTelemetry の識別子に個人情報を入れない**という方針を実装前に明文化する。識別子は外部サービス（Claude Code / Cursor / Devin）へ渡る。**内部 ID だけで重大さの判別は十分にできる。** 後から変更するとログの連続性が失われるため、先に決める必要がある。
- **「暴走した alarm」「過剰なログ出力」を検知対象に含めている**点に運用経験が出ている。**エラーとして現れないが課金に直結する問題**という分類。自社の監視設計で「エラーではないが金がかかっている状態」を検知しているか、という問いに展開できる。
- **実際に運用される監視の条件は「見なくても回ること」。** ダッシュボードは作られて忘れられる。**人が見に行く必要がない構成にすること**が提案価値であり、「監視を入れる」こと自体ではない。
- **個人開発では、エラー検知の欠如が「使われない理由」を隠す。** ユーザーが少ないと問題のフィードバックが来ず、作った本人の環境では動く。**機能や宣伝の問題だと思っていたものが、実は特定条件のエラーだった**という可能性を、検知がないと検証できない。
