- **「新しく計測できるものが増えた」のではなく「同じことをコードを歪めずに書けるようになった」**という性質の見極めから入る。機能追加とエルゴノミクス改善を区別できるかは、リリース情報の読解力そのもの。**後者の方が既存コードへの影響は大きいことがある。**
- **span を引数で引き回す設計を「臭い」として名指しする。** ビジネスロジックの関数が `span` を受け取っている状態は、**ドメインの関心事とインフラの関心事が混ざっている。** テストでダミーを用意する手間、責務の読み取りにくさ。**分離手段が提供された以上、整理の対象になる**という判断まで含めて教える。
- **可観測性を入れない理由が「技術」ではなく「変更範囲」だったという指摘。** 計測1か所のために経路上の全関数シグネチャを変えることになり、レビューが重くなり「今は入れない」に落ちる。**技術的にできることが組織の都合でやられない**典型例で、受講者の実感に合う。
- **「最初に全部仕込む」か「入れない」の二択から抜ける**という整理。局所的に追加できれば、必要になってから入れられる。**先行投資を減らせるのは時間が限られた個人にいちばん効く。** 設計判断とリソース制約を結びつけて話せる。
- **`recordException` の受け口の広さを、実務的配慮として評価する。** JS のエラーは形が揃わない（Error / 文字列 / 独自オブジェクト）。**正規化コードを毎回書かずに済むのは地味だが積み上がる差。** こういう細部を評価できるかが、API 設計を語るときの説得力になる。
- **OpenTelemetry 仕様への追随は、学習投資の話として扱う。** 各社が独自 API ではなく仕様に寄せているなら、**仕様側を一度覚えればどの環境でも通用する。** Cloudflare / AWS / GCP で学び直さない。**学習効率という軸で技術選定を語る**のは受講者が求めている視点。
- **ベンダー固有 API への依存度が移行可能性に直結する**という観点を加える。仕様準拠が進むほど計測コードの移植性が上がる。**ロックインの評価を「できるか」ではなく「書き直す量」で測る**という実務的な尺度。
- **案件としては「動いているが遅い」の調査から入る形。** 上流を触らず計測を差し込めるなら作業範囲が明確で、**成果物が定義しやすい小さな案件**になる。改修を請ける前の第一段という営業の組み立てまで含めて教材化したい。
