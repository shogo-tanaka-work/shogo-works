- **教材の軸は「プロンプトで頼む」と「コードで検証する」の違いに置く。これが本件最大の教材価値である。** 「根拠を示して」「推測しないで」とプロンプトに書く方法は、**守られたかを確認する手段がない。** Cloudflare は引用が証拠パッケージに実在するかをアプリ側で機械的にチェックしている。**同じ目的に対して、検証可能な手段と検証不能な手段がある**という区別は、ハルシネーション対策の教材の中核に置ける。本サイトの harness-engineering カテゴリとの相性が特に良い。
- **「未確認」「確認したが一致なし」「不在の証拠を確認」の3値区別は、独立した演習にする価値がある。** 多くのシステムがこれを2値（問題あり / 問題なし）に潰しており、**データ欠損が「問題なし」として出力される。** 受講者に自分の作ったシステムの出力フォーマットを見直させ、この区別が入っているかを確認させる。入っていなければ、状態を1つ追加するという具体的な改修になる。**抽象論ではなく、その日に直せる課題として出せる。**
- **「自律性を削ることで監査可能性を得る」というトレードオフを教える。** 証拠収集を決定論的コードへ寄せ、synthesis エージェントは新しい証拠を取りに行けず、分類も承認語彙の外から選べない。**これはエージェントの能力を意図的に制限する設計である。** 「より自律的なほど良い」という素朴な前提を崩す題材として使える。監査が必要な業務では再現性が導入可否を分ける、という実務的な理由まで示せる。
- **小規模でも真似できる部分の切り出しが、教材として実用的である。** 4エージェント並列は規模が必要だが、**(1) モデルを呼ぶ前にコードで情報を集める (2) 引用の実在をコードで確認する (3) 未確認とデータなしを分ける の3点は1人のシステムにも入り、工数はそれぞれ数時間。** 「大手の事例は参考にならない」と受講者が切り捨てないよう、持ち帰れる粒度まで分解して示す。
- **Workers / Workflows / D1 / R2 / Durable Objects の役割分担は、小規模構成の設計指針としてそのまま使える。** 状態は D1、証拠アーティファクトは R2、段階の調整と再開は Workflows、チャット状態は Durable Objects。**無料枠・低額枠で同じ部品が揃う**ので、手を動かす課題として出しやすい。
- **「harness 本体は非公開、Clef だけオープンソース」という点は正直に扱う。** 構成は読めるがコードはない。**自分で作る前提の参考資料**であり、コピーして動かせるものではない。事例記事の読み方として「どこまでが再現可能か」を先に確認する習慣を教える。
- **既存 Knowledge への最小反映を検討する価値がある。** `harness-engineering` カテゴリは本サイトの中核テーマで、**「検証をコードへ寄せる」という原則と3値区別は、恒久的に残すべき結論**に当たる。ただし本記事は事例1件であり、原則として一般化するには他社事例と突き合わせたい。**別 PR で単独判断するのではなく、harness 設計の原則をまとめる回で、引用検証と3値区別を節として立てる。** 速報の詳細（Cloudflare の製品構成）は持ち込まない。
