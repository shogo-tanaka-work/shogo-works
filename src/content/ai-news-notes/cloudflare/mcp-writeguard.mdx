- 「読み取り MCP は入れたが、書き込みを許すかで止まっている」という状況は多くの組織で共通する。リスク階層による**段階的解禁**は製品非依存の設計パターンとして教材化できる。Cloudflare の製品名を主役にせず、考え方を主役にして書く。
- エージェントの失敗は人間の失敗と規模が違う（1件の誤操作 vs 数千件の一括処理）という点を、統制が必要な理由の起点に置く。ここを飛ばして権限設計の話に入ると、「面倒な手続き」としか受け取られない。
- エージェント帰属（誰の操作か下流で判別できる）は、監査要件を満たすうえで見落とされやすい観点。MCP 教材の「導入前チェックリスト」に組み込む候補。ログにサービスアカウント名しか残らない問題は、具体例で示さないと伝わらない。
- 現時点でプライベートベータのため、手順の教材化は時期尚早。GA まで概念レベルの紹介に留める。逆に、リスク階層の分類演習は今すぐ課題にできる。**受講者が使っている MCP サーバーのツールを4段階に振り分ける**ワークが、そのまま導入前の棚卸しになる。
- 分類演習の副産物として「そもそもこのツールをエージェントに渡す必要があるか」という問いが立つ点を、講師側で拾えるようにしておく。ツールを渡さないことが最も確実な統制である、という結論は教材の締めとして強い。
- 個人の作業環境（Claude Code + MCP）への応用は、企業向けの話より受講者に刺さりやすい。書き込み系サーバーを別プロファイルに分ける、作業内容ごとに接続を切り替える、といった具体的な運用に落として提示する。
- 4段階の名称（Read Only / Minimal Impact / Contained Write / Critical）は Cloudflare 固有。教材では名称を暗記させず、「読み取り／小さい書き込み／範囲が限定された書き込み／重大」という意味のほうを覚えさせる。
