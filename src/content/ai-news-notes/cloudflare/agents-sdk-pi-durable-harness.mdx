- **エージェントの PoC が本番に乗らない原因は、精度より運用側にあることが多い。** 途中停止、二重実行、進捗の不可視。**PoC の設計段階で「失敗時の挙動」を観察項目に入れる**だけで、本番化の判断精度が上がる。
- 上の一般形: **デモで見えるのは成功パスだけ。** 評価したいなら失敗パスを意図的に作る。これは AI に限らず、あらゆるシステム評価に当てはまる。
- **「途中で殺して再開させる」検証は、誰でもできるが実施者が少ない**領域である。結果がどうであれ知見になる。**定石が無い分野では、やってみた記録そのものに価値がある。**
- **ベータで API 変更が予告されている機能を顧客案件へ入れない**という線引き。納品後に動かなくなるリスクを、保守契約の範囲で引き受ける覚悟があるかで判断する。**「新しいから使う」は理由にならない。**
- **依存の増加を、ベンダーの数で数える。** `PiHarness` は Cloudflare 製だが、中身は Earendil のフレームワークである。**自分がコントロールできないロードマップが何本あるか**を数えるのは、技術選定の基本動作。
- **既存インフラの範囲内で試せることは、検証の障壁を大きく下げる。** 新規契約・新規予算が不要なら、検証は「やってみる」で始まる。**評価コストの低さ自体が採用判断の要素**になる。
- **「止まったときどうするか」を含む提案は、技術力ではなく業務理解の証明として効く。** 意思決定者が気にしているのは能力の上限ではなく、失敗時の被害である。**提案の構成にリスクと復旧を入れる。**
- **検証は、止まっても業務が止まらない周辺業務から始める**という順序。定期集計、レポート生成、社内向け処理。**本番投入の前に、失敗が許される場所で挙動を見る。**
- **Durable Objects の理解は、エージェント以外にも転用できる。** セッション管理、協調編集、レート制限。**学習投資は「その機能にしか使えないか」で評価する**と、時間の配分を誤らない。
