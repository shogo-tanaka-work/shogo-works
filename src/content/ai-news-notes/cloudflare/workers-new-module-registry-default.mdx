- **互換性日付の考え方を先に説明する。** 日付を固定することで、プラットフォーム側の既定変更から既存コードを守れる。**守られている代わりに、更新は自分の判断で行う**ことを教える。
- **「既存は変わらない、日付を上げると変わる」を軸にする。** 受講者が最も誤解しやすい点。何もしなくて良い人と、確認が要る人を分けて考えさせる。
- **移行の型として使う。** 「フラグで先に試す → 検証環境で動かす → 問題があれば従来版フラグで逃がす」の3段階は、他の既定変更にも使い回せる。
- **依存ライブラリの点検を題材にする。** 自分のコードより、依存先の `require()` やトップレベル `await` が原因で壊れる点を扱う。
- **同日告知の Request.signal も並べて見せる。** 同じ日付で複数の既定が変わる場合、個別に追わず**日付更新の一括チェックリストにまとめる**と運用が楽になる。
- **受講者への問い**: 自分の Worker の互換性日付はいつか。それを上げるとき、誰が何を確認するか。
- 恒久教材へ反映する場合は、**日付（11/17）やフラグ名を書かない**（変わる）。残すのは「互換性日付は更新の契機として棚卸しする」「先にフラグで試し、逃げ道を用意する」の2点。
