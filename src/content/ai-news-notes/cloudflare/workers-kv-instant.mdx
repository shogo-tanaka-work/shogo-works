- **制約を明示するほうが汎用化より使う側に親切**という設計観。「何でも入れられます」と言われると入れてはいけないものを入れて失敗する。「毎秒1回しか書けません」と言われれば書き込みの多いデータは入れない。**自分が API やライブラリを作るときの指針になる。**
- **価格表は機能の説明でもある。** 読み取りが60%安く、ストレージが $100/MB・月。この2つの数字だけで「読み取り中心・小容量」という用途が読める。**製品を評価するとき、機能説明より価格表のほうが設計意図を正確に語ることがある。**
- **制約4点を用途のふるいとして順に当てる手順**（書き込み頻度 / 容量とキー数 / メタデータ依存 / list の挙動）。「新しいものが出たから移行」ではなく、**用途ごとに分類して該当分だけ移す**という移行の作法。
- **namespace をアプリケーション単位ではなくデータの性質で分ける**ことになる制約。一見不便だが、**どのデータがどういう読み書きパターンを持つかを整理させる**効果があり、設計が明示化される。良い制約の例。
- **「設定をコードに埋める」運用が持続しなくなる境目**は、他人に使わせ始めた時点。値の変更依頼が毎回開発側へ来る構造は、依頼する側も受ける側も負担。**技術的な改善ではなく運用の持続性の問題**として捉える。
- **コストの主体がどこにあるかを見極める。** 本件は読み取りが実質無料でストレージが高い。**「念のため大きめに」という発想が直接コストになる**ケースで、実使用量を測ってから入れる規律。
- **プライベートベータの製品を顧客案件に入れない判断**。API 互換があるなら、**既存方式で作って GA 後に切り替える**順序が安全。互換性がある場合の移行コストの低さを設計段階で確保しておく。
- **100倍という数字の裏に必ず引き換えがある**という読み方。性能の劇的な改善が制約なしで得られることは稀で、**改善の記事を読むときは引き換えを探す**のが基本動作。
- **棚卸し自体に独立した価値がある。** instant モードを使わなくても、自社の KV 利用を用途別に分類する作業は設計の見直しになる。新製品を「棚卸しのきっかけ」として使う発想。
