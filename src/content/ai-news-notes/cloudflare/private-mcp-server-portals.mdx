- **この事例の中心的な教材価値は、「なぜ OAuth の入口だけ閉じられないのか」を説明できる点にある。** MCP サーバー本体はサーバー間通信なので Gateway 経由に閉じられる。**OAuth の authorization / token エンドポイントは、利用者のブラウザから直接叩かれる**ため閉じられない。**人間のブラウザが経路に介在するかどうか**が線引きになっている。この区別は MCP に限らず、あらゆる認証連携の設計で効く。
- **制約を先に言う方が受注につながる、という営業面の教材。** 「完全に閉じられます」と言って後から訂正するより、**最初から「ここまでは閉じられ、ここは開きます」と線を引く**方が信頼される。**制約を説明できる人は、制約を知っている人として扱われる。**
- **「何から守りたいのか」を具体化させる演習に使える。** データ・業務ロジック・tool 定義を守りたいなら、この構成で守れる。**「自社が何かを認証している事実」まで守りたいなら足りない。** 脅威モデルを言語化しないまま「セキュアにしたい」と言うと、判断ができない。
- **前提条件の重さを見積もる練習になる。** この機能は Cloudflare One / Access の上に乗っている。**「MCP のために Zero Trust 基盤を入れる」は順番として無理がある。** 新機能の紹介を読むとき、**その機能が立っている土台の導入コスト**を見る習慣を教えられる。
- **小さな changelog を並べて方向を読む、という読み方の教材。** 同日の Worker Previews、前日の Browser Run の `outboundByHost`、そして本件。**単体ではどれも1〜2段落の告知だが、並べると「エージェントが閉域資源に触るための配管を敷いている」と読める。** ニュースを1件ずつ消費するのではなく、方向を読む練習。
- **中小企業案件の定型的な相談（「データを外に出すのは怖い」）への回答パターンとして使える。** 抽象的な安心論ではなく、**具体的な構成として語れる選択肢が1つ増えた**という形で提示する。
- **サーバー単位のスイッチである点は、設計の柔軟性の例。** 公開 MCP サーバーとプライベート MCP サーバーを同じ portal に混在させられる。**全体設定ではなく対象単位の設定**にすることで移行が段階的にできる、という設計パターン。
- 恒久教材へ反映する場合、**設定画面の項目名や製品名の組み合わせは書かない**（変わる）。残すのは **(1) ブラウザが介在する経路は閉じられない、(2) 何から守るかを先に言語化する、(3) 新機能はその土台の導入コストとセットで見る** の3点。
