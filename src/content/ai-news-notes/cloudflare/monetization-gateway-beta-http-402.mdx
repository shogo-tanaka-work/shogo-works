- **HTTP 402 は仕様に20年以上あったが使われなかった**という事実が、最良の教材。理由は「人間は画面遷移で払うから、402 を返すよりリダイレクトする方が実用的だった」。**技術仕様が使われるかどうかは、仕様の良さではなく利用者の性質で決まる**という一般則。顧客がエージェントに変わった瞬間に、同じ仕様が実用的になった。
- **「契約を結ぶ工程のコストが、小口需要を構造的に排除していた」**という視点。与信・請求書・担当者・稟議。**この工程が不要な顧客（エージェント）が現れると、売れる商品の粒度が変わる。** ビジネスモデルの制約が技術ではなく手続きだった、という分析の型。
- **「人間には月額で売れないが、エージェントには1回で売れるもの」**という商品発見のフレーム。深さは不要、代替が面倒、という2条件。エージェントは「自分で実装するか買うか」を判断するため、**実装コストと価格の比較が購買判断になる。** 従来の購買心理と全く違う。
- **提供元が自社製品の課金に使っている（AI Gateway の Machine Payments）**という dogfooding の読み方。新しい決済プロトコルを評価するとき「提供元自身が本番で使っているか」を問う型として使える。
- **オープン標準に準拠していることの実務的な意味。** 現在は暗号資産しか選べないが、それは**実装の都合であってプロトコルの制約ではない。** 「今は使えないが、標準なので将来の選択肢が残る」という判断は、技術選定の議論でよく必要になる。
- **売り手の話を買い手の話へ反転させる訓練。** 課金の仕組みができたということは、**自社のエージェントが外部の有料 API を買い始める**ということでもある。支出管理と上限設定の設計は、収益化の検討より先に必要になる可能性がある。**発表を自分がどちら側に立つかで読み替える**習慣。
- **「収益化できる」と「収益が出る」の距離。** 課金の仕組みがあっても、支払う意思と手段を持った買い手が来なければ0円。クローズドベータという状態を正確に評価する練習。
- **決済の障壁は技術ではなく社内規程**という実務知。暗号資産の受領は、技術的な実装は数日、社内の会計・決済規程の変更は数か月。**提供範囲が広がったときに動けるかは、規程確認を先に済ませたかで決まる。** 「待ちの期間に何を進めるか」の具体例。
- **少額入金が大量に発生する形態の記録管理**は、個人の確定申告で実務的な負担になる。受領時レートでの円換算を都度記録する。**始める前に記録の取り方を決める**——後からまとめて整理できない種類の作業である、という警告として使える。
