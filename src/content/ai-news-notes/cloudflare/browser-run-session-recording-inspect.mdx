- **デバッグ教材の「再現性」の節に、対処法の追加として入れる。** 受講者が持っている手札は「ログを仕込む」だけである。**仕込んでいなかった情報は取れない**という当たり前を先に突く。調べたい観点はたいてい仕込んでいなかった方にある、という実感がある人が多いので、ここで引き込める。
- **「記録を先に取る」と「あとで観点を選ぶ」を分けて教える。** 今回の構造は、**録画（全部取る）→ Inspect（読む観点を後から選ぶ）** という2段である。ログ設計の常識は「必要なものを選んで出す」なので、**発想が逆であることを明示**しないと通らない。オブザーバビリティの章へ接続できる。
- **HAR を「組織をまたぐ共通語」として扱う。** 標準形式で書き出せるので、社内の別チームや相手先ベンダーへそのまま渡せる。**再現手順を文章で伝える往復が消える**という効果が、受講者の実務感覚に一番近い。演習: 自分が直近で「再現手順を書いて送った」場面を1つ挙げさせる。
- **最重要の論点は Network タブに headers と payload が含まれること。** 認証トークン、セッション Cookie、フォームの個人情報が録画に残る。**便利さの話で終わらせると、そのまま情報持ち出しの事故になる。** 「デバッグに便利だから全部録画してベンダーへ渡す」という自然な運用が、そのまま NG になる形を具体例として示す。
- **個人利用のほうが事故りやすい点も扱う。** 自分のアカウントでログインして自動化している場合、認証情報が録画に入る。**公開リポジトリや記事に HAR を貼る**という事故が起きやすい。共有前に中身を見る、というだけの習慣で防げるので、手順として短く教える。
- **changelog に上限が書かれていない点を、一次情報の読み方の演習に使う。** 保存期間・録画数の条件は session recording ドキュメント側にある。**書かれていない＝制限がない、ではない。** Cloudflare の guardrails 回（2026-09-14）で使ったのと同じ論点なので、**同じ読み方を2回目として強化**できる。
- **受託・保守の文脈が最も金額に近い。** 「たまに失敗する」案件で、**保守契約に「失敗時は録画を確認して原因を報告する」と書ける**ようになる。見積もりの根拠が立つという形で、技術更新が契約条件に直結する例として扱える。
- **再現を回すコストとの比較も入れる。** 再現の試行は相手サイトへのアクセス回数と実行時間を消費する。**録画を読む方が安い場面がある**という費用の見方は、個人開発の受講者に効く。ただし録画自体の保存コストがあるので、常時録画を勧める前に条件確認、という順序で締める。
- 恒久教材へ反映する場合、**Cloudflare 固有の製品名とタブ構成は書かない。** 残すのは「**再現できない失敗は記録の設計で解く**」「**全部記録して観点は後から選ぶ**」「**記録には資格情報と個人情報が入る前提で共有ルールを決める**」の3点。他社のブラウザサンドボックスにも同じ機能が来るため、汎用の章として書ける。
