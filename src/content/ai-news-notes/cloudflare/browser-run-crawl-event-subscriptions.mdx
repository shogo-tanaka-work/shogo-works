- **「ポーリングが面倒」ではなく「ポーリングは実行時間を食う」が本質**、という理解の訂正から入る。サーバーレスでは待っている間も課金され、リクエストの実行時間上限に先に当たる。**同期的に待つという発想がそもそも環境に合っていない**という話に繋げられる。
- **「投げて忘れる」への寄せ方を一般則として教える。** 完了を知る手段が別にあるなら、投げたら離れる。**サーバーレス固有ではなく、時間のかかる処理を扱うときの基本形。** バッチ、メール送信、動画変換でも同じ。1つの事例から横に広げやすい。
- **失敗の検知という観点を落とさない。** ポーリング側が落ちると完了に気づけない。**逆に、失敗したジョブに気づかず古いデータを使い続けるという静かな事故**も起きる。Queues の再試行とデッドレターで「後続が失敗したときの扱い」を自前で書かずに済む点が実利。
- **やり直しの単位を小さくする、という設計判断。** クロール＋加工＋保存＋通知を1本で書くと、どこかで落ちたとき全体をやり直す。**クロールはコストの高い処理なので、やり直し単位の粒度が直接お金に効く。** 疎結合の価値を抽象論でなく金額で説明できる。
- **RAG のインデックス更新との噛み合いが、いちばん実務的な題材。** 従来は「クロールが終わったころに定期実行」という時間ベースの妥協をしていた。**スケジュールの余白を取るという回避策が消える。** 妥協していた箇所を名指しできると、受講者は自分の実装を思い出す。
- **`crawl.updated` は顧客向け画面の話として扱う。** 進捗が見えないと利用者は「動いているのか」を気にする。**技術的難易度が低く効果が分かりやすい**ので、提案に入れる価値が高い。技術と体験を繋ぐ例。
- **見積もりの不確実性がどこにあるかを教える。** 情報収集の自動化案件で技術的に読みにくいのは、集める部分ではなく待ち受けの部分。**そこが既製品になると価格を下げても利益が残る。** 見積もりの構造を分解して考える訓練になる。
- **Wrangler CLI でアカウント単位に設定する、という粒度も確認させる。** Worker 単位ではない。**設定の置き場所がどこかで運用の責任者が変わる**（アプリ開発者かアカウント管理者か）という、地味だが実務で揉める点。
