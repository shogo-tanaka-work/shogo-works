- **導入は「手順の変更に、なぜ再デプロイが要ったのか」から。** スキルがコードに含まれていたため、手順書の修正が開発のサイクルに縛られていた。**ファイルにすると、変更の頻度が違うものを分離できる**。
- **「誰が書けるか」を、設計の中心に置かせる。** エージェント自身も書けて、スクリプトは `exec` で実行される。**書き込み権限は、実行内容を決める権限と同じ**重みを持つ。レビューと変更履歴の演習にする。
- **寛容な読み込みの落とし穴を説明する。** 規則に反するスキルも、警告つきで読み込まれる。**警告をログで拾わないと、不備が気づかれずに動き続ける**。書く前に `parseSkill()` で確認する手順を入れる。
- **破壊的変更の読み方を教える。** 便利な機能と同じ更新に、削除された API が含まれる。**バージョンを上げる前に、削除項目を自分のコードで検索する**習慣を付ける。
- **スキルの置き場所を比較させる。** Workspace は手軽、R2 は共有と一元管理、コードは固定。**用途によって使い分ける**考え方を示す。
- **受講者への問い**: 自分のエージェントの手順書は、誰が、どの経路で更新できるか。間違った手順が書き込まれたとき、どこで気づけるか。
- 恒久教材へ反映する場合は、**パス名、クラス名、バージョン番号を書かない**（変わる）。残すのは「手順をコードから分離する」「書き込み権限を統制する」「更新前に削除項目を確認する」の3点。
