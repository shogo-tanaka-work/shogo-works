- MCP 教材は「仕様の話（2026-07-28 確定）」と「実装の話（今回）」を分けて構成する。既存の `claude/mcp-2026-07-28-spec-to-claude` が仕様側の正本なので、こちらは実装・運用編として位置づけ、重複した仕様解説を書かない。
- ステートレス化の意味を説明するときは、プロトコルの用語から入らず「これまでは常駐する何かが必要だった／今はリクエストが来たときだけ動けばよい」という運用コストの話から入る。非エンジニア向けにはこの順序でないと刺さらない。
- `Mcp-Method` / `Mcp-Name` ヘッダーは、教材の「エージェントの統制」章で使える具体例。「本文を開かずに何が呼ばれたか分かる」＝ネットワーク層で監査できる、という抽象化まで持っていくと、他のプロトコルにも応用が効く。
- Dynamic Client Registration の非推奨化は、「開発時に便利な仕組みが企業運用では問題になる」典型例。DCR という固有名を覚えさせるより、この一般則の題材として扱う。
- 12か月の非推奨予告ポリシーは、教材の寿命設計そのものに関わる。教材内に「仕様バージョンを明記し、更新時期の目安を書く」という運用ルールを持ち込む根拠として引用できる。
- ハンズオンにするなら `createMcpHandler` を使った最小サーバーが適切。ただし SDK の API は動く可能性があるため、教材本文にコードを固定で埋め込むのではなく、公式ドキュメントへのリンクと「何を作るか」の設計だけを記述する形にする。
