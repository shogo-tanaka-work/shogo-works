- 「エージェントにスクレイピングさせるか、ツールを渡すか」という対比は、MCP を学ぶ前段の導入として使いやすい。**スクレイピングの脆さ（DOM 変更で壊れる）を先に体験させてから**ツール提供の話に入る構成が有効。順序を逆にすると「なぜわざわざツールを定義するのか」が伝わらない。
- ブラウザ標準（Chrome 146 で実験搭載）に依存するため、手順の教材化は仕様の安定を待つ。現時点では「そういう方向の標準が動いている」に留め、`document.modelContext` という API 名も変わり得る前提で書く。
- ツールが訪問者のセッション・権限で動く点はセキュリティ上の重要論点。「サイトが提供するツールをエージェントが訪問者の権限で叩く」構図は、サーバー側 API に認証をかける従来の発想では整理しきれない。企業導入編のリスク整理の題材として独立させる価値がある。
- 既存 MCP 教材との関係を整理しておく。`cloudflare/mcp-next-generation-stateless` がサーバー側の実装・運用、この記事が配信面。同じ MCP でも「作る話」と「配る話」で章を分けないと、受講者が混乱する。
- ダッシュボードのワンクリックで有効化できる＝**Web 担当が単独で有効化できてしまう**という運用リスクは、技術解説ではなくガバナンスの論点。誰が判断するかを決める話として扱う。
- 準備として筋が良いのは、Site MCP Server パックで露出できる MCP サーバーを先に作っておくこと。ハンズオン課題を設計するなら、WebMCP そのものではなく「後から配信面を足せる MCP サーバーを作る」を課題にしたほうが、成果物の寿命が長い。
- HTMLRewriter によるエッジ注入は、Cloudflare 固有の技術だが「配信経路で HTML を書き換える」という発想自体は汎用。既存サイトに手を入れずに機能を足す手法の実例として、Workers 教材からも参照できる。
