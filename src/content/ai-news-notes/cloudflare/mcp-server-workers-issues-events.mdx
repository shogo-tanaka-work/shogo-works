- **教材の軸は「MCP の方向」に置く。** MCP はこれまで**クライアントが聞いて、サーバーが答える**仕組みだった。ツールを呼ぶ、リソースを読む——いずれもエージェント側が起点である。**サーバー側から「いま何か起きた」と伝える経路はなかった。** 今回それが開いた。**MCP を「ツール呼び出しの規格」として覚えた人には見えにくい変化**なので、方向の図で示すと理解が早い。
- **ポーリングの何が問題だったかを数字の感覚で説明する。** 本番エラーを起点にエージェントを動かすには、**定期的に「新しい issue はあるか」と聞き続けるしかなかった。** 間隔を短くすれば検出は速くなるが呼び出しが増え、長くすれば検出が遅れる。**このトレードオフ自体が消えた**という形で提示する。「便利になった」より具体的である。
- **「ポーリング不要」の裏返しを必ず同じ分量で扱う。** ポーリングは**こちらの都合で頻度を決められる**仕組みだった。push になると**頻度は issue の発生側が決める。** 深夜に issue が連続したとき、エージェントは何回動くのか——**この問いを設計の段階で持たせる。** 便利さだけ説明して導入させるのが最悪の形である。
- **「誰も指示していないのにエージェントが動く」状態を設計項目として立てる。** 決めるべきは3つ。(1) **エージェントが調査だけするのか、修正まで試みるのか**、(2) **スコープをアカウント全体にするか単一 Worker にするか**、(3) **連続発生時の挙動。** 公式が (2) の両方を用意しているのは、**ここが設計の選択肢だから**である。アカウント全体にすると、関係のない Worker の issue でもエージェントが動く。
- **スコープ設計を「設定1つで運用が変わる箇所」の代表例として扱う。** 技術的な難易度はゼロだが、運用の結果は大きく変わる。**複数サービスを1アカウントで動かしている組織では、アカウント全体の購読が関係のない issue でエージェントを起動させる。** こうした箇所を事前に指摘できる人は**実装者ではなく設計者として扱われる。** 単価の差がここで付く、という形で動機づけられる。
- **API トークンの権限追加を、使い回しの問題へ接続する。** **Notifications Write** と **Workers Observability Write** が必要で、**どちらも Write 権限**である。接続先 URL は変わらないため、**既存環境では「トークンの権限を足す」形の変更**になる。**1つのトークンを複数用途で使い回していると、この追加で他の経路にも Write 権限が渡る。** 用途ごとにトークンを分ける判断の機会として提示する。
- **「設定したのに何も来ない」の原因を先に教える。** 前提が3つある。(1) **対象 Worker で Issues を有効化**、(2) **MCP Events の webhook に対応したクライアント**、(3) 権限2つ。**Issues は SDK 不要の組み込み機能だが、有効にしていなければ event は飛ばない。** 対応クライアントも、接続すれば自動で使えるものではない。**つまずきの典型を先に渡す**のは教材の役割である。
- **障害対応の起点が移る構成を、人件費と比較できる形で示す。** 従来は「監視が検出 → 人へ通知 → 人が調査」で、エージェントを挟む場合も**人が「調べて」と指示する必要があった。** 今回は検出時点で調査が始まる。**夜間・休日の一次切り分けは、これで実用的になる。** 夜間対応の人件費と直接比較できるため、**投資対効果の説明がしやすい領域**である。ただし**提案には暴走を止める設計を必ず含める**——止め方の説明がない自動化は情シスに通らない。
- **情報源の境界を明示した判断を、そのまま教材にする。** changelog は MCP Events の仕組みを定義していない。**確認できたのは `events/list`、`events/subscribe`、event 名 `cloudflare.alert.workers_observability_real_time_issue` の3つだけ**で、署名の検証方法・他のメソッド・capability のキー名は書かれていない。記事では**それ以外を扱わないと明記した。** 二次情報には仕様の説明が出回っているが、一次確認なしでは書かない。**境界が明示された記事のほうが、実装でつまずいたときに戻ってこられる。**
- **実験的な拡張の段階は、試して書ける余地がいちばん大きい時期だと伝える。** `events/list` を叩いて何が返るかを確かめた記録は、**そのまま一次情報になる。** 公式ドキュメントに書かれていないという理由で価値が出る構造を示せる。**標準が固まってからでは、この余地はなくなる。**
- **既存 Knowledge への反映は不要と判断した。** 関連しうるのは MCP を扱う既存教材（`claude-code/mcp`、`codex/mcp-integration`）だが、**いずれも「MCP はクライアント起点である」と断定した記述は持っていない**（push は追加された経路であり、従来の経路は残る）。将来反映する場合は、**メソッド名ではなく「エージェントを動かす起点が誰か」**を軸にする。経路は増えるが、**起点の設計責任という論点は残る。**
