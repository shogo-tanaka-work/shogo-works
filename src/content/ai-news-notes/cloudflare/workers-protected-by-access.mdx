- **既定値の設計（secure by default）**を教える教材として使いやすい。認証の設定漏れは規律の問題に見えて、実際は「既定が安全でない」ことの帰結である。既定を安全側にし、外す方を明示的操作にする、という原則の具体例。
- **vibe coding の後始末**という切り口が教材として現実的。生成から公開までのリードタイムが短くなるほど、認証・ログ・権限・削除が抜ける。今回の機能は認証の部分にしか答えていないので、**残り3つが未解決である**ことを示す材料になる。
- **ポリシーの優先順位（ホスト名単位 > Worker 単位 > アカウント単位）**は、具体的なものが勝つという一般的な設計パターン。CSS のカスケード、IAM の権限評価、ファイアウォールルールと同型であることを示すと応用が効く。
- アカウント単位ポリシーの副作用（公開 API にも認証がかかる）は、**強い既定値が持つ両刃性**の実例。「全部に適用する」設定は事故を減らすと同時に別種の事故を生む。除外の書きやすさとセットで評価する、という判断軸を教えられる。
- **公開用と社内用でアカウントを分ける**という構成上の解は、環境分離の教材へ接続できる。ポリシーで頑張るより境界を分ける方が単純になる、という設計判断の例。
- `wrangler.jsonc` の `access` ブロックによるローカルシミュレートは、**セキュリティ機能が定着するかは開発体験で決まる**という論点の実例。摩擦があると外される、という現象を具体的に説明できる。
- プレビュー URL の扱いは独立した教材価値がある。**一時的だと思われているものが実際には長く残る**、URL の推測困難性は認証ではない、という2点は多くの現場で見落とされている。
