- **導入は「サブパス配信で何が面倒だったか」から。** 成果物をパス名のフォルダへ入れ直す作業は、ビルドとデプロイの境界を曖昧にする。**成果物は常にルート基準、公開パスは設定で決める**という分離が、この機能の設計思想。
- **「どこに置くか」と「どこで見せるか」を分けて考えさせる。** ファイルの置き場所と URL は別の概念。**両者を設定でつなぐ**考え方は、リバースプロキシ、CDN、リダイレクトの教材にも共通して使える。
- **検証の観点を必ず入れる。** パスのずれは、トップは開くが画像やリンクが壊れる形で現れる。**絶対パスのリンク、画像、スクリプトの読み込み先**を一覧にして確認する演習にする。
- **バージョン要件を確認する習慣を示す。** 新しい設定キーは、古い CLI では無視されることがある。**導入前に必要バージョンを確認する**手順を、チェックリストへ入れる。
- **受託の切り口。** 既存サイトの一部だけを置き換える提案では、**影響範囲が小さく説明しやすい**。どのパスを預かるかを契約で明確にしておく。
- **過剰適用への警告。** 単独のサイトをルートで配信するだけなら不要。**要件があるときだけ使う**。
- 恒久教材へ反映する場合は、**設定キー名や対応バージョンを書かない**（変わる）。残すのは「公開パスと成果物の構造を分ける」「パス配下配信ではリンク解決を必ず検証する」の2点。
