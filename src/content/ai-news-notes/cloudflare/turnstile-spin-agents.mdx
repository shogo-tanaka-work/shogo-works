- **「動作テストでは見つからない欠陥」の代表例として使う。** 人間が操作すればウィジェットが出て送信も成功する。**検証の抜けはボットを投げるまで分からない。** 機能テストと security テストが別物だという話を、抽象論ではなく1つの具体で説明できる。チェックリストに追加できる形の教材。
- **2段構えの設定で片方だけ入れる、という失敗パターンの一般性。** Turnstile 固有ではなく、**フロント側の表示とサーバー側の検証が対になっている仕組みはすべて同じ**（トークン検証、署名検証、CSRF）。**「表示されているから効いている」という誤読**は繰り返し起きる。横に展開できる。
- **ダッシュボードで検出できる、という点を強調する。** 推測でなく機械的に確認できる。**確認コストがゼロに近いなら、やらない理由が無い**という判断の型。受託案件の点検メニューとして即座に商売になる形でもある。
- **エージェントにコードを変更させることの審査を飛ばさない。** 「プラン提示 → 承認 → 変更」の承認を誰がやるのか、レビューとテストを通すのか。**セキュリティを入れる作業だからこそ中身を読む体制が要る**という逆説。便利な話の直後に必ず置きたい論点。
- **ベンダーが公開 Skill を出すという提供形態の新しさ。** 製品ドキュメントを人間が読んで実装する前提が変わりつつある。**「エージェントが読める導入手順」を用意するかが採用率に影響しうる**という視点は、API 提供側に立つ受講者に刺さる。先例が少なく、動きとして追う価値がある。
- **Spin 自体は7月提供、今回はエージェント経由の追加**という切り分けを正確に教える。**「新機能」と「既存機能への導線追加」を混同すると、いつから使えたのかを誤って説明する。** リリース情報の読み方の訓練として地味に重要。
- **65,000 件超という実績値の読み方。** 多いと感じるか少ないと感じるか。**ダッシュボード経由だけの数字**であり、手動実装は含まれない。**公式が出す数字は計測範囲を確認してから解釈する**という習慣に繋げる。
- **新規構築の標準手順に組み込む話で締める。** 手作業だと「あとで入れます」が忘却に直結するが、依頼1回なら忘れない。**品質の下限を個人の注意力ではなく仕組みで上げる**という発想は、1人で受託している人にいちばん効く。
