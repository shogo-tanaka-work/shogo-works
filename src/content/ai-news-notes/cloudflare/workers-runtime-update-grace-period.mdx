- **教材の軸は「上限と保証は違う」に置く。** 猶予が最大20分になっても、公式は**猶予終了前に切れることはありうる**と明記し、再接続とリトライを求めている。**「40倍になった」だけを読むと再接続を省く判断に繋がる。** 公式文の留保を読み落とすと設計を間違える、という読解の練習にそのまま使える。
- **「見えない更新」という概念を導入する好機である。** マネージドランタイムでは、自分のデプロイでもトラフィック急増でもないタイミングで足元が入れ替わる。**Workers に限らず Lambda / Cloud Run でも同じ構造**がある。今回30秒→20分という具体的な数字が公式に出たことで、抽象論ではなく事実として教えられる。
- **「ログを自分のシステムの中だけで探しても見つからない障害」の実例として扱う。** 再現しない・ログに出ない・ユーザー報告だけがある。**原因の候補にプラットフォーム側の更新を持っているかどうかが、調査時間を左右する。** 障害切り分けの教材として、環境要因を候補に挙げる訓練に使える。
- **LLM 時代に1リクエストの寿命が伸びたことを、設計前提の変化として説明する。** 30秒上限は「短いリクエストを大量に捌く」前提に最適化された数字である。**ストリーミング応答・長時間エージェント・常時接続はいずれもその前提を外れる。** 「プラットフォームの既定値は、想定された使い方を物語る」という読み方を教える。
- **再接続の設計を状態の置き場所から教える。** 接続を使い捨てにできる形にするには、状態を Durable Objects のようなサーバー側に置く必要がある。**「再接続を実装する」は、接続中にメモリに持っている状態を外に出すという設計変更**であることを明示する。
- **リトライの安全性（冪等性）を、LLM 固有のコストと結びつける。** 再実行が二重課金・二重書き込みになる構造を避ける必要がある。**冪等性は教科書的な話に見えるが、LLM 呼び出しでは金額として現れる**点が実感を伴う。
- **「入っていても見た目が変わらない実装」を価値として説明する教材にする。** 再接続とリトライは画面に出ない。だからこそ入っていない納品が存在する。**公式が明記している事実を提案書の根拠に使える**という、技術文書の実務的な使い方を示せる。
- **既存システムの点検が短時間で終わる作業であることを示す。** 30秒を超えるリクエストの洗い出しと再接続の有無確認。**「たまに切れる」という既知の不具合を抱えた顧客は多く、原因候補の提示が受託に繋がる。** 小さい作業から入る営業の型として扱える。
- **コストは変わらない点を必ず添える。** 長時間動かしやすくなっただけで課金は変わらない。**「20分まで動かしていい」と読むと見積りを誤る。**
- **既存 Knowledge への反映は不要と判断した。** Cloudflare の Knowledge 記事が無く、他ツールの教材の前提も変えない。反映するなら**「マネージドランタイムの更新は利用者に見えない」という恒久的な原則**だけを残す。
