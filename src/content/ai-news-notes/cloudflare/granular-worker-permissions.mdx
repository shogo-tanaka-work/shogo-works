- **教材の中心は4ロールの列挙ではなく、従来の Read / Write 二分法では表現できなかった2つの状態。** (1)「可観測性データは見せるがコードは見せない」（Metadata Read-Only）、(2)「更新はさせるが消させない」（Editor）。**この2つが表現できなかったことが何を招いていたか**を先に示す。
- **Editor / Admin の間に引かれた「削除」の線を重点的に扱う。** デプロイの誤操作は前バージョンの再デプロイで復旧できるが、削除はルーティングもバインディングも失う。**CI/CD に削除権限を渡す理由は通常ない。** この1点の変更で、自動化の事故の最悪ケースが「ロールバック可能な障害」に収まるという説明は具体的で刺さる。
- **エージェント運用の文脈が本命。** 「ログを見て原因を調べてほしい」だけのエージェントに全 Worker のデプロイ権限を渡さざるを得なかった状況を描く。**Metadata Read-Only は「調査はさせるが手は出させない」の直接的な答え。** エージェントを本番に入れる審査で通しやすい構成、という実務的な価値まで示す。
- **演習: 手元の API トークンの棚卸し。** 用途と実際の権限を突き合わせる。**自動化に渡したトークンから優先**する理由（人間は自分が何をしたか認識できるが、CI/エージェントは誤動作に気づくのが遅れる）を考えさせる。
- **個人開発者向けの動機づけは「事故が起きても誰も助けてくれない」。** 組織なら気づく人がいるが個人にはいない。**だからこそ渡す権限を絞る**という論理は、セキュリティ教材で個人受講者を動かすのに有効。
- **受託の文脈で「全 Admin をください」が通らない／通っても信頼を削るという実感を扱う。** 個別 Worker に Editor で依頼できるようになったのは受注場面で効く。**権限要求の粒度がそのまま専門性の印象になる**という視点を入れる。
- **トークン棚卸しは独立した小案件として成立する**と示す。「CI に渡しているトークンが全削除権限を持っています」は具体的で、対処が明確で、リスクの説明が容易。**セキュリティ提案が抽象的になりがちという一般的な弱点の、例外として扱える。**
- **絞りすぎの事故を必ず警告する。** 削除と再作成でデプロイを実現している構成では Editor で止まる。**変更前に既存パイプラインの1回分のログを読む。** 「善意でやっただけに説明が難しい事故」という言い方が記憶に残る。
- **Terraform 対応がある点は、構成管理へ組み込む話に接続できる。** 権限を手作業で管理しない、という IaC の原則の実例。
- 恒久教材へ反映する場合、**ロール名は書かない**（変わる）。残すのは「Read/Write の二分法では足りない」「削除は他の書き込みと分けて扱う」「エージェントには調査専用の権限を用意する」の3点。
