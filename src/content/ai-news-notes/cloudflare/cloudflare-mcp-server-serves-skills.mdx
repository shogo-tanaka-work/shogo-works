- **教材の軸は「MCP の役割が、ツールを配ることから文脈を配ることへ広がった」に置く。** Cloudflare API MCP server のツールは `search()` と `execute()` の2つのままで、**増えたのはその使い方を教える文書のほう**である。MCP をツール呼び出しの規格として覚えた人には、この転換が見えにくい。**「ツールの数が増えていないのに、できることが変わった」**という形で提示すると理解が早い。
- **解いている問題が「能力」ではなく「配布と更新」であることを明示する。** MCP でツールを増やすのはエージェントの能力の問題、MCP でスキルを配るのは**配布と更新の問題**である。後者は地味だが、**チームで使う段階で確実にぶつかる。** 1人で使っている間は問題として見えないため、「なぜこれが重要なのか」を人数の軸で説明する必要がある。
- **「10台のマシン × 4種類のエージェント」という具体で手間を見せる。** 従来の導入はローカル配置が前提で、Claude Code は `~/.claude/skills/`、Cursor は `~/.cursor/skills/` と置き場所が分かれる。**エージェントが混在するチームでは経路が4本に分かれ、さらに更新のたびに全員が引き直す。** MCP 経由なら URL を1つ共有して終わる。**抽象的な「楽になる」ではなく、作業量の掛け算で見せる**のが効く。
- **便利さと引き換えに何が見えなくなるかを、必ず同じ分量で扱う。** ローカルにファイルがあれば `git diff` で変更が見える。**MCP 経由では取得のたびに最新が来るため、いつ何が変わったかの把握が難しくなる。** スキルは**エージェントへの指示文**であり、モデルの文脈に直接入る。**これはサプライチェーンの問題として扱うべき**で、「配布元を信頼する判断」はローカルでも必要だが、**リスクの形が違う**（内容の変化が観測できない）点が本質である。
- **「便利さだけ説明して導入させる」のが最悪の形だと教える。** 提案や社内導入の場面で、**見えにくくなる側を一緒に説明できるかどうかで信用の差が出る。** 導入後にサプライチェーンの議論が出てくる順序は避けられる。**技術の説明責任を扱う題材**として使える。
- **「設定を変えていないのに挙動が変わる」経路を扱う。** 今回の変更は**接続先 URL が変わらない。** 既に Cloudflare API MCP server を繋いでいる環境では、**クライアント側が拡張に対応した時点でスキルが届き始める。** 「何も変えていないのにエージェントの振る舞いが変わった」という問い合わせの典型的な原因である。**変更の責任がサーバー側とクライアント側に分散している構成**の理解に使える。
- **組織として決めるべきことを3点に整理して提示する。** (1) この経路を使うか**組織として**決める（各自が勝手に足すと誰が何を読んでいるか分からない）、(2) 既存の接続環境を洗い出す（上記の「変えていないのに変わる」対策）、(3) **API トークンのスコープを見直す**（認証方式は変わっていないが、そのトークンが関わる範囲は広がった）。**「標準の MCP 設定を配る仕組みがあるか」が前提条件**であり、無い組織はまずそこから作る話になる点も押さえる。
- **「公式が書いていないことを自分で確かめる」練習として使う。** changelog は対象プラン、対応クライアントの具体名、配信スキルの範囲を書いていない。**`skills/list` が通るか試すのが最短の確認方法**である。**試して確かめた記録はそのまま記事になる**——公式に無い情報だからという理由で価値が出る構造を示せる。
- **情報源の制約を記事に明記した判断を、そのまま教材にする。** 執筆環境から `modelcontextprotocol.io` が DNS 解決できず、**拡張仕様の一次確認ができなかった。** そのため `skills/list` と `skill://<name>/<path>` は Cloudflare 公式 changelog を一次情報とし、**仕様の詳細（他のメソッド、capability のキー名、確定日）は検索結果の二次情報なので記事では扱わないと明示した。** 「到達できなかったものを、推測で埋めない」判断の実例として使える。
- **既存 Knowledge への反映は不要と判断した。** 関連するのは `claude-code/mcp`、`claude-code/skills`、`codex/agent-skills`、`codex/mcp-integration` の4本だが、**いずれも「スキルはローカルに置く」という前提を誤りにする記述は持っていない**（MCP 経由は追加された経路であり、従来の経路は残る）。将来反映する場合は、**ヘッダ名やメソッド名ではなく「スキルをどこから配り、誰が中身を保証するか」**を軸にする。配布経路は増えるが、**「エージェントの文脈に入るものの出所を管理する」という論点は残る。**
