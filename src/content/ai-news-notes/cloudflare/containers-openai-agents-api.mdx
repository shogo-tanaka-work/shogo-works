- **「頭脳と進行管理」と「手を動かす場所」の分離**という構図を、エージェント設計教材の基本図として使う。役割分担が公式告知の中で明示されているため、図解に落としやすい。**どこを外部に任せ、どこを自社で持つか**という設計判断の型として、他の構成にも転用できる。
- **最重要の注記は「自社インフラで動くから外部に何も出ない」は誤り、という点。** セッション管理とコンテキスト圧縮は OpenAI 側を通る。**分離できるのは実行場所とアクセス範囲であって、モデルとのやり取りではない。** ここを曖昧にした説明が稟議や提案で通ってしまうと、後で信頼を失う。**教材では、誤った説明文と正しい説明文を並べて比較させる**演習にすると定着する。
- **「どこで実行され、何に接続でき、終わったら何が残るか」**という3つの問いは、エージェント案件の承認プロセスで必ず出る。**この3問に答えられるかをチェックリスト化**して配る。技術選定の前段に置く。
- **PoC は OpenAI ホスト、本番で Containers へ切り替える**という進め方は、導入プロジェクトの段階設計として教える価値がある。**検証したいこと（業務に使えるか）と関係ない作業で時間を使わない**という原則。実行環境を後から差し替えられる前提が立つこと自体が価値、という読み方を示す。
- **アイドル自動停止 → 課金が作業量に連動**という設計を、コスト設計教材へ接続する。**PoC がコスト理由で止まる**という失敗は多い。常時起動とセッション単位起動の差を、そのまま見積もりの差として示せる。
- **受託向けには「正確に説明できること自体が差別化になる」**という論点を強調する。多くの提案者が「自社環境で完結します」と雑に言う領域で、線を正確に引ける人は少ない。**技術力ではなく説明の精度で選ばれる**という実例として使う。
- **ベータを納品物に含める場合の契約論**は、同日の OpenAI Agents API の記事と共通。2記事をまとめて1つの「ベータ API を案件で扱う」パートにできる。
- 同日の `chatgpt-openai/agents-api-public-beta` と対で読ませる設計にする。**片方だけだと「便利な API が出た」で終わるが、2つ並べると「実行環境をどこに置くかが設計論点になった」という構造が見える。** 教材では必ずセットで扱う。
- 恒久教材へ反映する場合、**テンプレート名や製品名は書かない**。書くのは「エージェントは進行管理と実行環境を分離できる」「分離しても文脈はモデル提供側を通る」という2点だけにする。
