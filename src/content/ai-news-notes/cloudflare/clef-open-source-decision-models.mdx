- **分類は本質的に生成ではない**という指摘。選択肢から選ぶ処理に文章生成モデルを使っていたのは他に選択肢がなかったからで、専用モデルが出れば戻る。**「この処理は本来どういう性質か」を問い直す**習慣が設計者の差になる。分類・ランキング・抽出・スコアリングで同じ動きが起きうる。
- **汎用 LLM で分類する実装の3つの弱点**（出力形式の不安定さ / 確信度が取れない / コストとレイテンシ）を分けて書けること。**どの弱点が自分の案件で効いているか**を特定できないと、置き換えの判断ができない。
- **確率が付くと自動化を三段構えにできる**（高確率は自動、低確率は人、中間はログに残して検証）。**自動化で最も揉める「どこまで任せるか」を閾値という数字で動かせる**のが本質。最初は閾値を高くして実績を見ながら下げる、という段階的拡大の型。
- **「答えだけ返す」か「確信度も返す」かは意識して選ぶ設計判断。** 答えだけを返す仕組みは、使う側から判断の余地を奪う。自分が作る API や関数でも同じ選択が発生する。
- **レイテンシ数十ミリ秒は「対話の途中に挟める」水準**という閾値感覚。数百ミリ秒だとユーザーが待つ処理には入れにくい。**体感の境目を数字で持っておく**と設計判断が速くなる。
- **公式のレイテンシ数値は条件（入力長・同時実行数・ホスティング先）が明記されていない**ため、自社条件での実測が前提。ベンダー公表値をそのまま設計に入れない規律。
- **ベンダーが自社モデルについて語るベンチマーク順位は第三者検証ではない**（本件はベンチマーク名に競合名が入っている）。分類タスクは**自社データ100件程度での現行実装との比較**が唯一の判断材料。
- **Apache 2.0 であることは技術的自由ではなく交渉材料**。「外部送信不可」で止まる案件に「では自社内で動かす」と返せるかどうかが、案件が進むかの分岐になる。9B / 27B というサイズは自前ホスティングが現実的な範囲。
- **自前ホスティングの利点と引き換えに運用負担が発生する**（モデル更新・推論サーバー・障害対応）。提案の時点で伝えないと、半年後に「誰も面倒を見られない」状態になる。利点だけを言わない規律。
- **価格未開示の段階でできるのは技術検証までで、コストを含む導入判断はできない**。この区別を曖昧にして稟議を書くと後で数字が合わない。「検証できること」と「判断できること」を分けて扱う。
- **ファインチューニングはプロンプト調整とは別の上限を持つ**。プロンプト調整で精度を上げる作業には天井があり、そこに当たったときの次の手として位置づけておく。
