- **教材の軸は「レイテンシが積み上がる構造」に置く。** speech-to-text → モデル → text-to-speech と並ぶため、**各段の遅延が合計される。** この構造を理解すると**どこを速くすれば効くかが判断できる。** モデルだけ速くしても音声認識が遅ければ体験は変わらない。**遅延の予算をシステム全体で配分する**考え方は、音声以外のリアルタイム処理にも使える。
- **「一番賢いモデルを選ぶ」判断が通らない例として扱う。** テキストのチャットなら3秒待てるが、**電話で3秒の無音は「切れたのか」と思われる。** 社内検討ではテキスト用途と同じ基準（ベンチマークのスコア、長文処理能力）で比較してしまいがちで、**音声ではそれが通話品質を直接下げる。** 基準の違いを体感で説明する。
- **「用途特化の小型モデル」という選択肢を知識として渡す。** 汎用の大きいモデルを使うのが当然になっているが、**特定領域に絞って学習させた小型モデルが速度と安定性で勝つ場面がある。** PhoneLLM Mini（Nemotron 3 Nano 30B を電話・サポート領域で事後学習）はその実例。**顧客に「一番賢いモデルを」と言われたときに説明できるか**で提案の質が変わる。
- **`enable_thinking: false` を「性能を諦めた設定」と誤解させない。** 電話応答で求められるのは長い推論の末の最適解ではなく、**聞かれたことを正しく把握し、必要ならツールを呼び、短く答えること。** **事前に当該ドメインで学習させる方が、汎用モデルに毎回考えさせるより速くて安定する**という割り切りである。
- **`temperature: 0` の推奨は、業務適用の観点から説明する。** 顧客対応では**同じ質問に毎回同じ答え**が求められ、揺れはクレームや説明責任の問題になる。**揺れを抑える設定が公式推奨になっている**こと自体が、業務前提の設計を示している。
- **alpha 版の扱いを、提案の作法として教える。** モデル名に `alpha-2` が入っている。**顧客に黙って alpha を本番に入れると、仕様変更時に自分が責任を負う。** 「PoC として作り、本番適用は GA を待つ」という段取りで提案する。**この伝え方ができるかが継続受注に関わる。** 実務的で、技術教材が扱わない部分。
- **「公式に記載がない項目」を確認対象として明示する。** **価格もコンテキストウィンドウも本告知に記載がない。** 音声エージェントでは**会話履歴をどこまで保持できるか**が応答品質に直結するのでコンテキストウィンドウは重要、通話量が多い用途では**トークン単価が事業性を決める。** 「書いていないことに気づく」読み方の練習になる。
- **Durable Object + Realtime SFU の構成は、状態管理の教材になる。** 音声エージェントは**セッション状態を持つ**必要があるため、Durable Object との組み合わせが理にかなっている。**なぜその部品が選ばれたか**を読む練習として適している。
- **Python Workers の GA との関係を押さえる。** Pipecat は Python のフレームワークで、**Python Workers の一般提供が音声エージェントを Workers 上で動かす道を開いた。** **一つの機能の GA が別の用途を解放する**という依存関係の読み方は、プラットフォームを評価するときに効く。
- **「エージェントにプロンプトを渡せばデプロイできる」は鵜呑みにさせない。** 評価コストが下がる可能性は示唆されているが、**実際に通して確認する**必要がある。公式の記載と実測を区別する姿勢を教材の態度として一貫させる。
- **受託の文脈を具体的に示す。** 電話応対の一次受け、予約受付、営業時間外の問い合わせ。**人を置けない規模の事業者にニーズが分かりやすい。** 試作コストが下がると提案前に動くものを見せられる点が重要で、**音声は実際に聞かないと判断できない。**
- **検証課題として実測レイテンシの記録を出す。** 公式は設計意図を書くが、**実際の応答時間や日本語音声での振る舞いは記録されていない。** Durable Object 構成での実測、**既定の DeepSeek V4 Flash との比較**は公式にない情報。**alpha 版のうちの記録は GA 後の比較対象としても価値が残る。**
- **既存 Knowledge への反映は見送る。** Cloudflare の Knowledge は未整備で、**alpha 版のモデルを恒久ページに書くのは早い。** ただし**「遅延の予算を配分する」「用途特化モデルを先に探す」という2つの原則**は、将来の音声・リアルタイム系 Knowledge の核になるので、この記事を参照元として残す。
