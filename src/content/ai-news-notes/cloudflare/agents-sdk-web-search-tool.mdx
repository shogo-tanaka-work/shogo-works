- **教材の軸は「同じ能力が、どの層に置かれるかで実務が変わる」に置く。** Web Search API は 2026-10-02 に既に出ていた。**今回増えたのは検索能力ではなく、エージェント構築時の既定の部品という位置**である。「新機能か」で判断すると今回の変更は小さく見え、「どこに置かれたか」で見ると大きい。**この読み方の違いを教えるのに、10日差の2段構成はちょうどいい教材になる。**
- **ツール定義が手順を含んでいる点を扱う。** `web_fetch` も渡すと「検索結果を `web_fetch` で読め」とモデルへ指示される。**つまりツール定義がワークフローを運んでいる。** プロンプトに手順を書く／ツールの説明文に手順を書く、という設計の分かれ目として具体的に説明できる。
- **結果形式が「本文を返さない」ことの理由を文脈長から説明する。** タイトル・URL・切り詰めた説明文だけを返すのは、**検索と読み取りを分けて文脈を節約する**設計である。RAG の初学者は「検索結果に本文が入っていないと使えない」と考えがちなので、**2段階に分ける設計の必然性**を教える良い入口になる。
- **provider が設定値（1行）であることを、構成管理の問題として扱う。** `provider: "exa"` を書き換えると検索結果が変わり、**結果が変われば回答も変わる。** 評価セットが無い状態で切り替えると品質の変化に気付けない。**「切り替えられる」は「記録が必要」とセットである**ことを教える。
- **プロンプトインジェクションの経路として正面から扱う。** 検索結果の説明文も、`web_fetch` が読むページ本文も信頼できない入力である。**許可ホストで縛る設計と検索の自由度は原理的に衝突する**（検索から来る URL は事前に分からない）。**この衝突は回避策ではなく設計判断**として提示し、「読むだけのエージェント」と「書き込み権限のあるエージェント」を分ける結論まで持っていく。
- **呼び出し回数の主体が人からモデルへ移ることをコストの論点として教える。** ボタンを押す回数ではなく、モデルの判断回数で課金が決まる。**リサーチ1回で検索5回は普通に起きる。** モデルに渡す「最大件数」がコストのパラメータでもある、という二重性を扱う。
- **公式が書いていないことの一覧を作る練習に使える。** オプションの全量、エラーハンドリング、価格——いずれも changelog に無い。**「無い」を列挙してから検証に進む**手順を、そのまま実演できる題材である。
- **単価化の例として「3社比較表」を扱う。** 公式は ceramic.ai / Exa / Linkup を並べるだけで、向き不向きを書いていない。**実クエリ20本で比較した記録は、誰でもできるが誰もやらないため資産になる。** 「公式に書かれていない情報を自分で測る」という価値の作り方の具体例として使う。
- **既存 Knowledge への反映は不要と判断した。** Cloudflare 向けの Knowledge 記事が無く、RAG / エージェントの恒久教材に対しても「検索の調達が1本に寄る」以上の前提変更は無い。将来 Cloudflare 教材を作る場合は、**個別機能ではなく「検索・取得・実行をどの層に置くか」**を軸にする。
