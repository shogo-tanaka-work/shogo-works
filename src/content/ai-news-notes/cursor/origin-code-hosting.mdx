- **「同期」という語の非対称性**が、そのまま教材になる。Origin の GitHub 同期は real time だが push は GitHub に向かい、GitHub が source of truth のまま。**双方向同期と片方向レプリカを区別せずに導入判断すると事故る**という一般則の実例として使える。PR コメントだけは双方向という点も、粒度によって同期方向が違う例として扱える。
- **既定で有効・管理者はオプトアウト、という配り方**は企業導入編の題材になる。Enterprise だけオプトアウト可能ということは、裏返すと何もしなければ有効になる。**「オプトインとオプトアウトのどちらで配られたか」を新機能の確認項目に入れる**という運用ルールを教えられる。
- 権限モデルは GitHub 側をそのまま継承する（read / write 権限を持つ人が Origin でも閲覧できる）。**権限を二重管理しない設計**の良い例。SSO やアクセス管理を扱う教材で、既存の信頼源に寄せる設計として紹介できる。
- **移行コストの中身を分解する材料**になる。リポジトリを移すだけでは終わらず、CI・デプロイ・権限・監査・外部連携がぶら下がる。Depot / Buildkite が既存の GitHub Actions ワークフローをそのまま実行できるようにしてあるのは、**移行コストのうち最大の塊を回避する設計**。技術選定を教えるときの分解例として使える。
- **early beta のスコープの絞り方**そのものが設計論の教材になる。公式は「essentials から始めている」と明言し、repos / PR / browsing / GitHub sync の4点に絞った。Issues も Wiki も入っていない。**何を入れないかを先に決める**というプロダクト設計の実例。
- 「エージェントのスケールに合わせて設計した」という位置づけは、**コードホスティングがエージェントの作業場として再設計され始めた**流れの一例。ツール選定を教える教材で、比較表ではなく前提の変化として説明する材料になる。
- 教材化の時期に注意。**early beta なので初期スコープは数か月で変わる**。機能一覧をそのまま教材に固定すると古くなる。恒久的に残すのは同期の非対称性と権限継承の考え方まで。
