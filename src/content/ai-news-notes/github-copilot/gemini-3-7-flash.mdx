- **「新モデルは Business / Enterprise で既定オフ」は、個別モデルの話ではなく一般則として教材化する。**MAI-Code-1.1-Flash（2026-08-11）、Kimi K3、そして Gemini 3.7 Flash と、同じ構図が繰り返されている。個別記事はその実例として参照させ、教材本体は「新モデル追加時の管理者判断フロー」を扱う。
- 判断フローとして教えるべき項目は、**誰がいつ判断するか / 基準は何か / 有効化したモデルの棚卸しはいつやるか**の3点。これを決めていない組織は、開発者からの要望が来るたびに個別対応する状態に陥る。
- 既定オフという設計自体は統制として正しい、という評価も併記する。**「使えなくて不便」ではなく「把握していないモデルに社内コードが渡らない」**という読み方を教えないと、統制を敵視する読者を作ってしまう。
- **同じ「Flash」でもベンダーが違えば単価が違う**点は、コスト教材の注意事項として使える。モデル名の語感で単価を推測させない。倍率は必ずドキュメントで確認するという手順を教える。
- Copilot に軽量モデルの選択肢が複数ある状態（MAI-Code-1.1-Flash / Gemini 3.7 Flash）は、**モデル選定の演習を組む好機**である。ベンチマークを読ませるのではなく、同じ作業を両方に投げて比較させる課題にする。軽量モデルは得意不得意が実作業で顕著に出る。
- 対応面が8つ（VS Code / Visual Studio / CLI / cloud agent / Copilot アプリ / JetBrains / Xcode / Eclipse）に及ぶ点は、**組織内で IDE が割れている前提**の教材で使える。モデルの選択肢が IDE によって違うと、説明も統制も複雑になる。
- ロールアウトが段階的である点は、教材の FAQ 項目にする。「設定したのに見えない」は問い合わせの定番であり、順番待ちの可能性を先に説明しておくと減らせる。
