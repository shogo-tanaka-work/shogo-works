- **「スキル」と「MCP サーバー」を別々に教えてきた構成を見直す契機になる。**1.0 は両者を1つのパッケージに入れる仕様なので、教材側も「配布単位はプラグイン、その中身がスキルと MCP」という順序で説明した方が実態に合う。個別技術を先に教えて後から統合を説明する順序だと、読者が配布の全体像を掴むまでが遠い。
- 標準構成（`plugin.json` の `$schema`、`skills/`、`mcp.json`、`com.github.copilot/`）は**手を動かす教材にしやすい**。ディレクトリを4つ作るだけで形になるため、MCP サーバーの実装より先に「包装の型」を体験させる導入が組める。
- **共通部分と固有部分の分離**は、この題材の核心として扱う。`com.github.copilot/` を他クライアントが無視するという仕組みは、ベンダー固有拡張を持つ標準の一般的な設計パターンでもある。プラグインに限らない話へ広げられる。
- 「オープン標準」を額面通り教えない。AWS / Anysphere / Microsoft / OpenAI / Vercel / Google が支持表明した段階と、実際に各クライアントが仕様通りに動く段階は別である。**支持表明 → 実装 → 相互運用の検証**という3段階で見る読み方を教える。
- 企業導入編では `managed-settings.json` での統制がそのまま使える点を扱う。ただし**「新しい配布形式が来ても既存の統制が効く」という安心と、「マーケットプレイス経由で入れられる対象が増える」というリスクは同時に発生する**。片方だけ説明すると判断を誤らせる。
- 既存の Copilot プラグイン教材があれば、後方互換で移行不要という点を明記して更新する。読者が「作り直しが必要」と誤解すると、既存資産を持つ組織ほど動きが止まる。
- 演習案: 社内向けの小さなスキル1つと、ダミーの MCP サーバー1つを1プラグインに包み、`com.github.copilot/` に Copilot 固有の設定を1つ置く。共通部分に Copilot 固有の前提を混ぜた場合と分離した場合で、他クライアントへの移植コストがどう変わるかを比較させる。
