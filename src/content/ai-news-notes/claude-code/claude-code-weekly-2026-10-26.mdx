- **今週の中心は「境界の内側だと思っていた処理が、外側で動いていた」事例である**（2.1.309 の、サンドボックス内 Bash がシェル起動ファイルをサンドボックス外で実行していた修正）。3週分を並べると系列になる。**前々週（2.1.292 / 294 / 295）は「迂回・解釈のずれ・すり抜け」、前週（2.1.299）は「正規化後の文字列で照合が外れた」、今週は「境界そのものが漏れていた」。** つまり**ガードレールが効かない理由は「書き方」「照合」「境界」の3層に分かれる。** 受講者に「自分のサンドボックス設定はどの層で壊れうるか」を考えさせる枠組みとして使える。
- **シェルの起動ファイルは、ほぼ全員が忘れる攻撃面である。** サンドボックスを有効にしても `.zshrc` / `.bashrc` が外で走るなら、起動ファイルに書いた処理には制限が掛からない。**「サンドボックスを有効にした」と「サンドボックスの中だけで動く」は別**という話を、1行の修正で説明できる。自作のサンドボックス・コンテナ設計でも同じ穴が開く（entrypoint、プロファイル、`ENV` の読み込み順）。
- **symlink 経由でルールが外れる修正が、今週2か所に出ている**（macOS の `denyWrite` グロブ、profile store の書き込み保護）。**パスベースのルールは、パスが一意でないと成立しない。** 「拒否ルールは実体パスで評価しているか」を確認する観点は、権限設計の演習にそのまま使える。前週の「正規化後のサーバー名」と合わせると、**識別子の正規化を間違えるとルールは静かに無効になる**という一般論に昇格できる。
- **`--mcp-config` の設定ファイルを、サンドボックス内のコマンドと自動承認された編集が書き換えられた**（2.1.309）。これは**「制御の設定ファイル自体が、制御の対象になっていなかった」**という構造で、教材価値が高い。自作のエージェントでも、許可リストを書いたファイルが書き込み可能な場所にあれば同じことが起きる。**設定ファイルの置き場所と権限は、ルールの内容と同じくらい重要**という結論へ一息でつながる。
- **Windows のフック fail-open が2版続けて修正された**（2.1.309 の PowerShell exit code 2、2.1.310 の Git Bash 不在時の `PreToolUse` / `PermissionRequest`）。**フックが「落ちたら通す」挙動になっていたことが問題である。** セキュリティ機構の既定は fail-closed にする、という原則の実例として使える。**同じ機構が2版続けて別の条件で fail-open だった**点も重要で、「1件直したから安全」と言えない例になる。
- **`claude ultrareview` のワークスペース信頼要求（2.1.309）は、「セキュリティを足すと既存の自動化が止まる」の典型である。** CI から呼んでいれば `--trust-workspace` を足すまで止まる。**正しい変更が、正しく運用を壊す。** この種の変更をどう周知し、どう段階適用するかは、ハーネスエンジニアリングの運用章の素材になる。公式が環境変数での無効化（`CLAUDE_CODE_DISABLE_ULTRAREVIEW_TRUST_CHECK=1`）を同時に用意している点も、移行設計として参考になる。
- **`allowedMcpServers` の変更（2.1.305）は、「allowlist から deny list へ」の方向転換である。** allowlist に載せていなかった `managed-mcp.json` の stdio サーバーが、アップグレードで読み込まれるようになった。止めたければ `deniedMcpServers` を使う。**allowlist 運用をしていた組織は、アップグレードで方針が反転したことになる。** 「不許可」と「未記載」を区別しない設計の危険性として扱える。実務では**アップグレード後に `/mcp` を見る**という手順まで含めて教える。
- **`claude_code.safety_event` の追加（2.1.307）は、今週の修正群と対で読むと意味が立つ。** 権限ルール・auto mode・安全チェック・フック・サンドボックスが**止めた／確認した／差し戻した**呼び出しが、OpenTelemetry イベントとして出るようになった。**今週は「漏れていた経路を閉じた週」と「止めた記録を取れるようにした週」が同じ週である。** ガードレールは効いていることを確認できないと運用できない、という主張の裏付けになる。
- **MCP の権限統制が、今週は3製品で同時に動いている。** Claude Code の `allowedMcpServers` 変更と `--mcp-config` 保護、**GitHub Copilot のグローバル既定ポリシーの対象に「MCP servers in Copilot」が入ったこと**（10-22、展開完了 10-26）、**n8n 2.45.0 の「MCP ツール権限の全面見直し」**（10-20）、**Microsoft Copilot Cowork の federated コネクタ（MCP、利用者自身の権限を使う）**（10-21）。**MCP は「つながるか」から「誰に何を許すか」の段階へ移った。** 1社の機能追加ではなく業界の収束として扱えるため、MCP の章はこの週を区切りに書き換える価値がある。
- **`sed -i` の扱いの変更（2.1.309）は小さいが、巻き戻し前提の運用に効く。** 実ファイル編集として扱われ、`/rewind` で戻らなくなった。**「エージェントの編集は全部巻き戻せる」という前提が、コマンド経由の編集では成立しない**ことの実例。チェックポイント運用を教えるときの注意点として扱う。
- **`sandbox.allowNestedUserNamespaces` は、公式自身が「サンドボックスのファイル保護を回避しうる」と書いている設定である**（2.1.305）。**必要な人だけが使う抜け道を、警告付きで公式が用意する**という設計判断の例になる。禁止するのではなく、明示的に有効化させて責任を移す。自作ツールでも同じ場面が来る。
- **`cleanupPeriodDays` が極端に大きいと最近のファイルが消える不具合（2.1.310）は、設定値の境界テストの教材になる。** 「保持期間を長くしたら消えた」という直観に反する挙動で、**大きな値の側のテストが抜けていた**ことが読み取れる。設定を受け取るコードで、小さい値と 0 は試すが大きい値は試さないのはよくある。
- **最小限の Knowledge 反映案**: 既定スキップのままでよい。ただしサンドボックスを扱っている教材があれば、**「2.1.308 以前では、サンドボックス内の Bash がシェルの起動ファイルをサンドボックス外で実行していた」**の1行を注記として入れる価値がある。サンドボックスの保証を前提にした手順は、この版より前では成立しない。MCP の権限ルールを扱う教材には、**`allowedMcpServers` の挙動が 2.1.305 で変わり、未記載のサーバーが読み込まれるようになった**ことを注記する。
