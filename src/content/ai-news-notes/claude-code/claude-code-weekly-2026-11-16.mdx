- **今週の中心は「既定値がどちらに倒れているか」である。** 2.1.325 は、サンドボックス内の Bash を**既定で通常の権限フローに従わせる**ようにした。これまでは「サンドボックスの中だから確認は要らない」という前提で動いていた。**サンドボックスを「権限チェックの代わり」として扱うのをやめ、「権限チェックに加えて効く層」として扱い直した**と読める。多層防御の原則そのもので、どちらか片方で足りると設計すると、片方が破れた瞬間に何も残らない。同じ週に「サンドボックスが worktree の settings / hooks を守り切れていなかった」修正が入っていることが、その理由を裏から説明している。
- **そのうえで、この変更は無人運用を確実に止める。** `sandbox.autoAllowBashIfSandboxed: true` を足さないと、スケジュールタスクが確認待ちで座る。**「安全側の既定」と「無人で動く」は両立しない**ため、ベンダーは安全側を既定にして、無人運用側に明示的な opt-in を求めた。ハーネス設計を教えるときの題材として素直で、**無人実行は「権限を広げる設定を明示的に書いた状態」でしか成立しない**と言い切れる。CI にエージェントを入れる回で、設定ファイルに書くべき項目の根拠として使える。
- **スケジュールタスクと `/loop` が skill の実行前に確認を求めるようになった点は、信頼の単位が「skill」へ下りたことを示す。** 対象は `allowed-tools` や hooks を宣言している skill である。つまり**「何をするか宣言している skill ほど確認が要る」**という、一見逆向きの設計になっている。宣言しているから危険が分かる、分かるから確認できる、という順序で読むと筋が通る。`permissions.allow` に `Skill(<名前>)` を足す運用は、**skill を1つずつ許可リストへ載せる**ことであり、プラグイン・skill を増やすときの棚卸しコストとして教材に入れる価値がある。
- **権限チェックの抜け穴が5週連続で出ている。** 10月第3週の起動ファイル、第4週の symlink と設定ファイル、11月第1週の `--restricted` × Read 許可、前週の4件（環境変数の前置き / `sed` / worktree / `/rewind`）、そして今週の 2.1.321・2.1.323・2.1.325 の各件。**「複合コマンドの一部が確認なしに通った」「allow ルールが名前と別のプログラムを起動できた」は、前週の「検査する文字列と実行する文字列がずれる」とまったく同じ構造である。** コマンド文字列をパースして権限を判定する設計は、パーサーの表現力が shell に追いつかないかぎり漏れ続ける。**「ルールベースの権限チェックは、入力言語が shell である限り原理的に未完成」**という結論を、5週分の実例で支えられる。
- **`Read(./.env)` のような相対 deny ルールが `cd` の後にプロジェクトを外れていた件は、ルールの解釈基準の話である。** 相対パスは「どこから見た相対か」を決めないと意味を持たない。**deny ルールだけは、基準が動いた瞬間に「何も拒否しない」へ倒れる**ため、allow ルールの同種のバグより影響が大きい。自作のガードレールで相対パスを受け付けるなら、**基準ディレクトリを固定するか、絶対パスへ正規化してから保存する**という設計指針に落ちる。
- **コミットされた `.claude/settings.local.json` が利用者自身の設定として扱われていた件は、信頼境界が「ファイルの場所」で決まっていた例である。** `.local.json` は本来コミットしない慣習だが、慣習は強制ではない。**リポジトリに置けるファイルを「ユーザーの意思」として読むと、リポジトリを作った側がユーザーの権限を書ける。** CI の `pull_request_target` 問題と同型で、並べて説明できる。自作ツールで設定ファイルを読む順序を決めるときの点検項目になる。
- **Artifact の確認漏れ3件は、「公開」という操作の確認が一度で済まされていた話である。** とくに「auto mode が最初の変更しか判定していなかった」は、**1回の承認が後続の全変更を覆っていた**ことを意味する。組織外から見えるものへの書き込みは、**変更ごとに承認の対象を区切る**必要がある。エージェントに外部公開の操作をさせるときの設計原則として一般化できる。
- **「起動元シェルの API キーで課金していた」は、認証とアカウンティングが別経路で決まる怖さの実例である。** claude.ai のログインで動いているつもりのセッションが、環境変数のキーで課金されていた。**動いている事実は、どこへ課金されているかを教えてくれない。** 前週の「失効後に別のサインインへ流れて課金先の組織が変わる」警告と同じ系列で、2週続けて課金経路の取り違えが修正されている。コスト管理を教える回で、**利用額の可視化より先に「誰の資格情報で動いているか」を確定させる**という順序の根拠に使える。
- **`--permission-mode auto` が auto mode 利用不可のときに「より緩いモード」で開始していた修正（2.1.323）は、fail-open の典型である。** 安全チェックが使えないなら、普通は厳しい側へ倒す。実装は緩い側へ倒していた。**「機能が使えないときにどちらへ倒れるか」は、正常系のテストでは絶対に出てこない。** 前週の `claude -p` の終了コード（拒否されたのに exit 0）と同じ型で、**fail-open はガードレールの最も見つけにくい不具合**という主張を2例で支えられる。
- **Code Mode（2.1.323）は、ツール呼び出しのコストに対する構造的な回答である。** Claude が JavaScript を書いてツールを呼ぶ。1回のツール呼び出しごとにモデルへ往復するのをやめ、**手続きをコードで書いて一括実行する**設計で、同じ週の Codex の「ターミナルのワークスペース」とは方向が違う（あちらは人間側の並行作業の整理）。実験的 opt-in のため実務投入はまだ早いが、**「エージェントの実行単位がツール1回から手続き1本へ上がる」**という流れの観測点として記録しておく価値がある。
- **最小限の Knowledge 反映案**: 既定スキップのままでよい。ただし Claude Code を CI / 無人実行で使う手順を扱う教材があれば、**`sandbox.autoAllowBashIfSandboxed`**、**`permissions.allow` への `Skill(<名前>)`**、**追加ディレクトリは `--add-dir`（`additionalDirectories` 設定では読み取り専用 git コマンドが通らない）** の3点を注記する価値がある。モデル一覧を扱う箇所には、**Fable 5.2 が既定の Fable モデルになり、保存済みの Fable 5.1 の選択が `fable` へ移る**ことを記す。Opus 4.8 の fast mode 削除（2026-11-30）も引き続き残す。
