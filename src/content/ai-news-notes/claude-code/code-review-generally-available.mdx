- **教材の軸は「書く速度を上げると、次はレビューが詰まる」に置く。** エージェント活用の教材は「速く書ける」で終わりがちだが、**現場で次に起きるのはレビュー待ちの滞留**である。この因果を先に見せると、Code Review の位置が理解できる。**機能紹介から入ると「便利なレビューbot」にしか見えない。**
- **失敗パターンから入る構成が効く。** レビュー自動化の典型的な失敗は、**指摘が多すぎて全部無視されるようになること**である。一般論の警告、起こりえない条件への指摘が並ぶと、開発者はまとめて読み飛ばす。この経験は受講者側にもあることが多く、共感から入れる。
- **「問題・引き金・修正方法」という指摘形式を、教材の中心に据える。** 公式がこの形を決めたのは、**その指摘が現実に踏まれる経路を示せるかを要求するため**である。ここは Claude Code に限らず一般化できる。**自分でレビュー指示を書くときのテンプレートとしてそのまま渡せる。** 製品が有料プラン限定でも、この形式の価値は残る。
- **深度の割り振りを演習にする。** Quick / Standard / Deep をリポジトリ単位で選ぶ構造なので、「このリポジトリ一覧をどう割り振るか」という課題が作れる。**課金・認証・外部公開 API・個人情報の経路は Deep、社内管理画面や使い捨ては Quick** という基準を自分で言語化させる。**これは製品の操作ではなく組織の設計**であり、教材としての寿命が長い。
- **「全部 Deep」が答えにならない理由を数字で示す。** 約20分 → 6〜10分という短縮が売りなのに、全リポジトリを Deep にすれば待ち時間は戻る。**速度とコストのトレードオフが設定1つに現れる例**として扱いやすい。
- **6〜10分という数字の意味を、作業の流れで説明する。** 20分だと人は別作業へ移り、戻るのは数十分後か翌日。**6〜10分なら待てるので、指摘 → 修正 → 再提出が1回の作業時間に収まる。** 「3倍速」という比率より、この境目のほうが実務では効く。**数値を体感へ翻訳する書き方の例**になる。
- **導入の難所が開発者側ではなく管理者側にあることを明示する。** 開発者の学習コストはほぼゼロ（設定不要で自動実行）。詰まるのは **GitHub App のインストールと対象リポジトリの選定**で、情シス・リポジトリ管理者の承認が必要になる。**「使い方」ではなく「通し方」の教材が要る領域**である。
- **クレジットの期限は、順序の教材として使える。** 請求期限 2027-01-15、ただし**請求から30日で失効**。この組み合わせは「早めに確保しておく」が損になる構造である。**検証対象と計測指標と担当者を決めてから請求する**という順序を、手順として固定して教える。
- **「自動レビューは人間の承認を置き換えない」を明文化する教材にする。** 公式はこの線を定めていない。**定めていないことを教材側で補う**のは価値が高い。指摘ゼロなら承認を省略してよいか、という問いは必ず現場で出る。
- **計測指標を一緒に渡す。** レビュー待ち時間、指摘の的中率（実際に修正された割合）、手戻りの回数。**導入の成否を語れるようにしておかないと、次の稟議が通らない。** 支援案件ではここが成果物になる。
- **GitHub 限定である点は、断定を避けつつ明記する。** 公式が挙げているのは GitHub App のみで、GitLab / Bitbucket の記載はない。**「対象外」ではなく「記載がない」**として書く。問い合わせの多い部分なので、曖昧にしない。
- **既存 Knowledge への反映は最小限にとどめる。** `claude-code/overview.mdx` に「Team / Enterprise で Code Review が GA（PR の一次レビュー）」の1行、`claude-code/daily-operations.mdx` に**「レビュー深度はリポジトリの性質で割り振る」という原則**だけ置く。所要時間・クレジット額・期限は変わるため記事側に残す。**数値は記事、原則は Knowledge** の切り分けを守る。
