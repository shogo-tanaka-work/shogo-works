- 既存教材 `ai-tools/claude-code/auto-mode.mdx` は「Maxプラン加入者向けの自動承認モード（v2.1.111〜）」と書いており、2026-08-14 以降は前提が古くなる。Pro / Max / Team が既定、Enterprise / API / クラウド経由は1か月以内に追随、という状態へ更新が必要。
- `plan-mode-worktrees.mdx` の権限モード表（`acceptEdits` / `autoAccept` 等）と auto mode の関係を、教材内で一度整理しておく必要がある。読者は「モードが多すぎてどれを選べばいいか分からない」状態になりやすい。既定が auto になったことで、選択の起点が変わる。
- 89% 対 13.6% という数字は、教材で「AI の方が安全」という結論に直結させない。「人間の承認は回数が増えると機能しなくなる」という運用上の一般則の実例として扱う方が、読者の自分の運用への転用が効く。承認疲れ（alert fatigue）は AI に限らない話。
- 管理者向け教材の演習として使える題材: 期限が切られた既定変更に対して、`defaultMode` / `disableAutoMode` の方針をどう決めるか。技術判断ではなくリスク許容度の整理である点が要点。チーム別に設定を分ける設計まで書かせると実務に近い。
- 「不可逆な操作をブロックする」という説明の限界を教材で明示する。ファイル操作は分類器が判定できるが、Slack 送信・メール送信・外部 API 経由の副作用は、分類器から見た可逆性と業務上の可逆性が一致しない。ここが組織側で明示的に拒否設定を書く理由になる。
- MCP プロキシ経由の指針は、MCP 教材（`mcp.mdx`）と接続できる。「MCP サーバーを繋ぐと、Claude Code の権限モデルの外側に影響範囲が伸びる」という構造を説明する具体例として使う。
- 副業・受託の文脈では「技術的に安全な操作 ≠ 契約上やってよい操作」という区別が中核。クライアントのリポジトリで auto mode を使うかどうかは、分類器の性能とは別の判断軸である、という整理は他ツールにも転用できる。
- 演習化は容易。Shift+Tab でのモード切り替えと、`defaultMode` を managed settings に書く作業は個人環境で試せる。`disableAutoMode` の効果確認は組織設定が要るため、紙上の設計に留める。
