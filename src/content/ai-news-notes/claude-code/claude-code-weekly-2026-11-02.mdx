- **今週は「公式のリリースノートを全部読んでも、いちばん重い話にたどり着けない」週だった。** Cursor の Marketplace で配られた偽の `Anthropic.claude-code` は、Anthropic の CHANGELOG にも GitHub Releases にも載らない。**追跡対象を「製品の公式ソース」だけに置くと、配布経路で起きた事故は構造的に見えない。** 自分のソース巡回リストが「製品の公式」で閉じていないか、を点検させる教材として使える。本リポジトリの運用でも、Cursor が週次ソースだったため4日間どこにも載っていなかった。
- **拡張のバージョン番号が「公式に存在しない番号」だった点は、検知の手がかりとして教えられる。** 公式 CHANGELOG は 2.1.312 の次が 2.1.314 で、**2.1.313 は欠番である。** 偽物はその欠番を使った。**「インストールされている版が、公式の版一覧に存在するか」を確認する**という単純な照合が、この種の事故では効く。SBOM やロックファイルの検証を教えるときの入口になる。
- **「拡張を消しても終わらない」が、この攻撃の設計上の要点である。** ペイロードは LaunchAgent（macOS）やスケジュールタスク（Windows）として**拡張の外側に**永続化スクリプトを置く。**アンインストールはアプリケーションを消すが、アプリケーションが作った OS レベルの常駐物は消さない。** マルウェア対応の初歩だが、「拡張機能」という軽い語感のせいで見落とされやすい。インシデント対応演習の題材として素直。
- **資格情報のローテーションを「信頼できる別のマシンから」行う、という指示の意味を説明する価値がある。** 侵害された可能性のあるホストで新しい鍵やトークンを作れば、それも取られうる。**復旧手順には「どのマシンで実行するか」が含まれる。** 手順書を書くときに抜けがちな項目で、実務の現場でそのまま使える指摘。
- **`permissions.blockWritesOutsideWorkingDirectories`（2.1.314）は、「全権限モードでも効く拒否」という新しい層である。** 従来は権限モードを緩めると書き込み範囲の制約も緩んだ。この設定は**モードに依存せず作業ディレクトリ外を拒否する。** ガードレールの設計で「利用者が緩められる層」と「緩められない層」を分ける例として扱える。管理者が managed settings で入れるべき設定の候補。
- **`--restricted` の修正（2.1.316）は、「許可ルールと機能の組み合わせで境界が漏れる」型である。** `--restricted` セッションが、**Read の許可ルールに覆われていれば作業ディレクトリ外のファイルをアップロードできていた。** 制限モードと許可ルールが独立に評価されていたことになる。前3週の「境界の漏れ」系列（起動ファイル、symlink、設定ファイル自体）に続く4例目で、**ガードレールの不具合は単体ではなく組み合わせで出る**という一般論の裏付けが積み上がっている。
- **PowerShell フックの fail-open が、今週また別の条件で修正された**（型キャスト・`param`・`using`・属性で始まるコマンドでは exit code 2 で止まらなかった、2.1.316）。**前週は「PowerShell の exit code 2 が止めない」「Git Bash が無いと通す」の2件だった。** 同じ機構が3週にわたり別条件で fail-open だったことになる。**「1件直したから安全」と言えない例**として、前週のメモに書いた指摘がそのまま強化された。フックのテストは「正常系で止まる」ではなく「あらゆる入力形で止まる」を要求する。
- **`claude-opus-4.8` のドット表記の修正（2.1.314）は、識別子の表記ゆれの害を定量的に示す例である。** ドットで綴ったモデル ID が古いモデル扱いされ、**context window・出力上限・effort・thinking・コストのすべてが誤っていた。** 「名前の綴りが1文字違うだけ」が課金とコンテキスト長に直結する。前週の「symlink 経由でルールが外れる」「正規化後のサーバー名」と並べると、**識別子の正規化の失敗はルールを静かに無効にし、設定を静かに別物にする**という2系統の害に整理できる。
- **ゲートウェイのモデル照合漏れ（2.1.316）は、allowlist / denylist 実装の典型的な穴である。** リクエストが名指しする**全モデル**を `availableModels` / `deniedModels` / `models` と照合していなかった。**1つのリクエストが複数のモデルを名指しできる設計なら、検査も全件に回さなければならない。** 自作のポリシーレイヤーで「最初の1件だけ見る」実装は珍しくない。修正後はフィールド名付きの 400 を返す点も、エラー設計の良例。
- **`pooled_budget` と `managed.policy_mode: layered`（2.1.316）は、企業の AI 予算統制が「個人上限の集合」から「グループ共有枠」へ進んだ例である。** ポリシーの `layered` は、マッチした全ポリシーを下から順に重ねる。**「最初にマッチした1つだけ適用」から「全部重ねる」への変更**で、既存の設定の意味が変わりうる。ポリシー設計を教えるときの first-match / merge の違いの実例として使える。
- **Opus 4.8 fast mode の 2026-11-30 削除は、「フォールバックしない」点が肝である。** 削除後はエラーになり、通常の Opus 4.8 へは落ちない。**「新しい方へ自動で寄せる」設計と「止める」設計の違い**で、ここは後者である。モデル退役の棚卸しを教えるときに、**退役告知を読むときは必ず「代替へ自動で流れるか、止まるか」を確認する**という読み方として扱える。GitHub Copilot の 2026-11-16 廃止（代替が自動有効）とは逆であり、同じ週に両方の型が出ているので対比教材にしやすい。
- **最小限の Knowledge 反映案**: 既定スキップのままでよい。ただし Claude Code の導入手順を扱う教材があれば、**「拡張・プラグインは公式の配布元から入れ、インストール済みの版が公式の版一覧に存在するか確認する」**の1行を追記する価値がある。モデル退役を扱う箇所には、**Opus 4.8 fast mode が 2026-11-30 に削除され、通常の Opus 4.8 へフォールバックしない**ことを注記する。
