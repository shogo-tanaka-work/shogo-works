- **サブエージェントの fork 既定化は、既存教材の前提を静かに変える。**サブエージェントに渡す文脈を明示的に組み立てる説明をしている教材があれば、fork が会話全体とプロンプトキャッシュを継承する挙動と食い違う。教材を書く前に、現行版で実際にどう渡るかを確認する。
- **プロンプトキャッシュの継承はコスト教材の材料になる。**v2.1.229 のワークフロープレフィックススタガーと合わせて、「同じ文脈を持つ兄弟エージェントを立てるときにキャッシュをどう効かせるか」という一本の流れとして説明できる。個別バージョンの話にせず、マルチエージェントのコスト構造という節にまとめる。
- **権限バイパス4件は「ガードレールは実装であって保証ではない」ことの実例。**PowerShell の変数上書き、Cygwin symlink、ネスト git repo の trust 継承、Gateway の不正 `email_domain`。いずれも設計上は防いでいるつもりの経路が抜けていた。エージェントの安全設計を扱う教材で、**許可制御を単一の防御線にしない**という原則の裏づけに使える。
- とくに **Gateway の不正 `email_domain` が管理者権限を与えうる**件は、設定値の検証を扱う教材の具体例として質が高い。「空文字や不正フォーマットが、拒否ではなく全許可に倒れる」というのは典型的な fail-open の失敗形。起動時検証（fail-closed）へ変えた修正まで含めて1つの事例になる。
- ネスト git リポジトリの trust 継承は、**信頼の粒度**という論点で扱う。親を信頼したら子も信頼される設計は直感的だが、モノレポや vendored ディレクトリでは意図しない範囲へ広がる。ディレクトリ単位の信頼モデルを説明する教材で使える。
- セッション間メンションと `SendMessage` は、`/config` に accept / hold / refuse があることまで含めて教える。**割り込みを受け入れるかどうかは設定で選べる**という点を落とすと、「勝手に他セッションから割り込まれる」という誤解を生む。
- Windows 環境の扱いは教材で薄くなりがちだが、今回の修正2件（PowerShell、Git Bash の symlink）はどちらも Windows 固有である。**Windows 前提の読者向けに注意節を持つ**価値がある。
- GitLab 対応は、教材の例示が GitHub に偏っていないかを見直す契機になる。受託や企業内では GitLab の比率が低くない。
