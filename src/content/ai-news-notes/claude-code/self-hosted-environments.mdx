- 既存教材 `ai-tools/claude-code/web-and-headless.mdx` は実行環境をローカルと Anthropic のクラウドの二択で説明している。第三の選択肢として self-hosted environments を足す余地があるが、Team / Enterprise 限定かつ運用負荷が高いため、教材本体に厚く書くより「こういう選択肢もある」の1段落に留めるのが妥当。
- **教材化で最も重要なのは「何がオンプレになって、何がならないか」の切り分け**。ファイル成果物は自社に残る、プロンプト・応答・ツール実行結果は Anthropic へ送られる、トランスクリプトは Anthropic に保存される。この3行を最初に置かないと、読者は「完全なオンプレ化」と誤解する。
- 誤解を放置すると実害が出る種類のトピック。企業へ提案する立場の読者が「データが一切外に出ません」と説明してしまうと、後で信用問題になる。教材では、誤解しやすい点を明示的に否定形で書く。
- ZDR 利用組織が対象外である点は、セキュリティ要件のトレードオフの実例として扱える。「より厳しい設定を選んでいると、新機能が使えない」という構造は、AI ツールに限らず企業システム全般で起きる。
- fixed mode から始めて on-demand へ、という導入順序は、可動部を1つずつ増やすという一般的な運用原則の具体例。教材では順序の理由（オーケストレータという新しい故障点が増える）まで書く。
- 運用コストの見積もりが導入判断の分かれ目。Claude Code はほぼ毎日リリースが出るため、runner のイメージ更新に追従する継続作業が発生する。「専任リソースが必要」という公式表現を、具体的な作業内容に分解して示すと判断材料になる。
- 副業・受託の文脈では、単発の構築案件ではなく月次保守として設計する方が実態に合う、という提案設計の話が使える。継続作業が発生する機能を単発で受けると、半年後に陳腐化して支援者の評価が下がる、という構造。
- 演習化はできない（Team / Enterprise 契約とコンテナ基盤が要る）。「社内システムに繋ぎたいが実行環境をどうするか」を紙上で設計させる演習に留める。
- 関連: 同時期の Claude Code v2.1.225 で `claude self-hosted-runner` の `--base-dir` 不備を起動時に検出する修正が入っている。導入するならこのバージョン以降を使う。
