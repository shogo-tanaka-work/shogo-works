- **「設定ファイルを読む権限モデル」と「設定ファイルを無視する権限モデル」の違い**は、権限設計の教材の中核に置ける。前者は設定に手が届く人が制限を緩められる。後者は実行者だけが制限を決める。**信頼境界をどこに引くかによって、同じ機能でも安全性の意味が変わる**という一般則の、非常にきれいな具体例。
- **CI での適用例が最も分かりやすい**。外部コントリビュータの PR が `.claude/settings.json` を変更できる構造では、リポジトリ側の設定に依存した権限制御は成立しない。**「攻撃者が書き換えられる場所に、防御の設定を置いてはいけない」**という原則を、身近な題材で教えられる。
- **`--restricted` を常用すると使えるタスクが狭まる**（コマンド実行・WebFetch が落ちるのでビルド・テスト・依存解決ができない）。安全機能を「常にオン」にする発想の限界を示す好例。**セキュリティ設定は用途ごとに使い分けるもので、最も厳しい設定を全体に適用するのは設計の放棄**という話に接続できる。
- **`.gitignore` は AI ツールの送信範囲を定義しない**という論点は、AI コーディングツールの導入審査を教える際の必須項目にできる。今回の修正対象は「未コミットの資格情報ファイルとそのエディタ swap / 一時 / バックアップ」で、`.gitignore` を丁寧に書いている組織でも `.swp` `.swo` `.tmp` `.bak` まで網羅している例は少ない。**git の関心事と、外部送信の関心事は別**。
- **AI ツール導入審査のチェック項目が「モデル」「学習利用の有無」で止まっている**という現状の指摘に、この事例を1つ添えると説得力が出る。抽象的なセキュリティ論より、実際に起きた不具合1件の方が審査項目を1つ増やす力がある。**リスクを一般論で語るか、具体例で語るか**は、提案の通りやすさを決める。
- **`/usage-credits` は「申請が記録として残る」ことの価値**を教える題材になる。口頭やチャットでの上限引き上げ依頼は記録に残らない。ツールに経路を持たせると、誰がいつ何のために上限を上げたかが可視化される。**フローをツール化する目的は、便利さより監査可能性であることが多い**。
- **`experimental.cacheTtl` と OAuth 更新時のキャッシュ取りこぼし修正**は、LLM 運用コストの教材にできる。プロンプトキャッシュは「効いていると思っていたが実は切れていた」という失敗が起きやすい。**コスト削減施策は、効いていることを確認する手段とセットで設計する**という一般則へ落とせる。
- **クラウドプロバイダー経由（Bedrock / Vertex / Foundry）と直接契約の機能差**が徐々に埋まっている流れは、企業導入の意思決定を教えるときの材料になる。導入時点の機能差は永続しない。**「今できないこと」ではなく「差が埋まる方向か」を見る**という判断軸。
