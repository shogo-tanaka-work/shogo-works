- **Todo ツールの無効化は、既存教材の前提を壊しうる。**Claude Code の作業進行をタスクリストで説明している教材があれば、新しいモデルでは出なくなる。スクリーンショットや出力例を含む教材ほど影響が大きい。教材を書く前に、対象モデルでの実際の挙動を確認する。
- ここから **「エージェントに外部のタスク管理を持たせるべきか」**という設計論へ展開できる。ツールを外した判断の背景（モデル側が作業の筋道を保てるようになった）は公式に明示されていないが、**足場を外せるほどモデルが強くなると足場自体がノイズになる**という一般則の実例として扱える。scaffolding の考え方を教える材料になる。
- **前版の権限修正が1日で revert された事実は、「リリースノートの読み方」を扱う教材の核になる。**修正が入った＝定着した、ではない。しかも巻き戻しの理由は「修正が広すぎて正常な操作を止めた」と読める（Windows の auto mode 退行が同時に修正されている）。**セキュリティ修正と使い勝手のトレードオフ**という論点がここに出ている。
- 速報を教材へ取り込むときの時間差の扱いとしても使える。**速報の直後に教材化すると、翻る可能性のある情報を恒久的な教材に固定してしまう。**数日置いて確定させる、という運用判断の根拠にできる。
- **`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` のような「戻せるスイッチ」の存在**は、破壊的変更の出し方として良い例。教材では「既定が変わったが戻せる」というパターンを、ユーザーへの影響を抑える設計として紹介できる。
- `forward_user_identity` は、**ゲートウェイ経由の利用でコストを部門別に按分する**という実務課題の解になる。企業導入編でコスト配賦を扱うなら具体例として使える。オプトインである点も含めて説明する。
- `CLAUDE_CODE_TOOL_MEMORY_LIMIT` は、**エージェントの実行環境を隔離する**話に接続できる。暴走したビルドがセッションを巻き込む事故は CI 的な使い方で起きる。cgroup という OS レベルの仕組みで防ぐ、という層の分け方を教えられる。
- GitLab 対応は v2.1.232（プラグインマーケットプレイス、トークン秘匿）と v2.1.233（MR URL、`--worktree`）で揃った。**2版にまたがって機能が完成する**例として、バージョン単位ではなく機能単位で追う読み方を教える材料になる。
