- **ハーネスエンジニアリング教材の「なぜ CI ガードレールが要るのか」の冒頭に置く。** 実測値が揃っている一次情報は貴重。**8倍の出荷量 / 80%を Claude が執筆 / テスト10倍 / CI ジョブ25倍（半年）** の4数字はそのまま使う。抽象論にならずに始められる。
- **教えるべき核は「速くなった負荷はどこへ移動するか」という問い。** 受講者は「AI で開発が速くなる」で思考を止める。**速度の向上は負荷の消滅ではなく移動である**という一般則を、CI という具体例で教える。同じ問いはレビュー、デプロイ、運用にも当てはまる。
- **70日 → 29日 → 1日未満という応急処置の寿命の並びは、意思決定の教材として極上の題材。** 「凌ぐか作り直すか」を感覚で決めている受講者に、**寿命を記録すれば判断が定量化できる**ことを示す。**演習: 自分の現場で3回直した箇所を挙げさせる。** ほぼ全員が出せる。
- **非対称性の説明を落とさない。** 応急処置で買える時間は短くなり、作り直しに必要な時間も短くなった。**この2つが同時に起きているから、意思決定の閾値が動く。** 片方だけ話すと「だから作り直せ」という乱暴な結論になるので、必ず両方揃えて説明する。
- **エージェント固有の論点を強調する。** 公式の「人間は無関係なテスト失敗を判断できるが、エージェントには文脈が要る」という指摘は、**CI 出力の質がエージェントの生産性を直接決める**という命題に展開できる。**ノイズの多い CI はエージェントを暴走させる**。ハーネス設計の中心的な主張として使える。
- **listener / selector という2コンポーネント構成は、図で説明すると理解が速い。** 遅延がなぜ危険か（20分の遅延 = 数万件の未反映）を数字で示し、**「非同期にすると障害が遅延として現れ、エラーとして現れない」**という副作用へ接続する。バックプレッシャーの章と相性が良い。
- **個人開発向けには縮小版を用意する。** 25倍は起きないが、**「CI が遅くてローカル確認で push するようになった」**は起きる。GitHub Actions のパスフィルタで足りる、という現実的な落とし所まで書く。**大掛かりなサービスを作らせない。**
- **提案・営業の文脈での使い方も教える。** 「ツール導入」から「プロセス設計」へ提案を格上げする材料になる。**公式が出している「体感スケールの10〜20倍を見込め」は出典付きで引用できる数字**なので、設計レビューの基準としてそのまま使わせる。
- 恒久教材へ反映する場合、**Anthropic 固有の実装（in-memory データストア、ジャーナル畳み込み）は書かない。** 残すのは「速度向上は負荷を移動させる」「応急処置の寿命を記録すると作り直しの判断が定量化できる」「CI 出力の質がエージェントの生産性を決める」の3点。**実装は変わるが、この3つは変わらない。**
