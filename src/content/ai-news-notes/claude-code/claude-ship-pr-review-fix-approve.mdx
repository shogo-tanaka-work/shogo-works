title: "教材化メモ：AI に承認を任せる前に、「観測モード」と「人が必須の範囲」を先に決める"
noteFor: "claude-code/claude-ship-pr-review-fix-approve"
date: 2026-11-23
tags: ["claude-code", "claude-ship", "code-review", "ガバナンス", "承認ポリシー"]
---

- **3つの役割に分けて教える。** 指摘する（Code Review）、直す（PR Steward）、承認を決める（Claude Approvals）。役割ごとに「AI にどこまで任せるか」を議論させると、全部任せるか全部拒否するかの二択を避けられる。
- **観測モードを導入手順の定石にする。** 判断を表示するだけで強制しない段階を挟み、AI の承認が人の判断と合うかを見てから必須にする。他の自動化にも使える段取りとして教材にできる。
- **承認ポリシーを「ファイルで管理する」点を押さえる。** 規則がリポジトリ内にあるため、変更履歴とレビューが残る。口頭ルールとの違いを説明しやすい。
- **人の目が入らない抜け道を演習にする。** 必須チェックにしていない、GitHub 側の「承認1件」を Claude が満たす、レビュー無しで承認する規則を書く、の3例は、設定ミスで統制が空洞化する典型として使える。
- **費用の見積りも教える。** PR 数、レビューの深さ、実行頻度、PR Steward の作業量で変わるため、まず1リポジトリと月額上限から始める流れを示す。
- **対象外条件を確認させる。** Team・Enterprise の GitHub のみで、ZDR・HIPAA 構成・顧客管理鍵の組織は不可。自社の契約構成と照らす習慣づけになる。
- 恒久教材へ反映する場合、**クレジット額や期限、ベータ名称は書かない**。残すのは「役割の分離」「観測モードから始める」「承認の根拠をファイルで管理する」「最終責任は人」の4点。
