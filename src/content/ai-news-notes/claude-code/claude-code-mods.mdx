- **「外側に足す拡張」と「内部に割り込む拡張」の区別**が、この更新の核。hooks とプラグインは前者、mods は後者。**権限リクエストの許可/拒否に介入できる時点で、拡張は便利機能ではなく統制の一部になる。** 拡張機構を評価するときの第一の問いとして使える。
- **ロード順を統制の手段に使う設計**（`sec-default` が最初にロードされ、後続の改変を制限する）。優先順位を暗黙に決めず、**「最初に入るものが制約を敷く」という形で明示する**やり方。自社でプラグイン機構を作る際の型になる。
- **統制の最低保証が上位プランにしかない**という構造（`sec-default` は Team / Enterprise）。個人プランの業務利用は「土台が無いところで運用している」状態になる。**プラン差が機能差ではなく安全性の差として出る**ケースの読み方。
- **「全面禁止」が最適解にならない理由。** 組み込み機能自体が mod 化されていくため、禁止が標準機能の無効化に近づく。**拡張機構の禁止は、時間が経つほどコストが上がる**という一般則。許可リスト方式へ寄せる判断。
- **拡張を統制を強める側に使う発想。** 自社固有の形式（社内ID、顧客番号）の秘匿値マスキングは、汎用実装より自前のほうが精度が出る。**「拡張＝緩める」と決めつけると、強める用途を取りこぼす。**
- **サンドボックス化されていない拡張を入れる判断**は「知らない人のシェルスクリプトを実行する」のと同じ。小さな TypeScript 関数なら読める、という前提が成り立つかどうかが分岐点。**読まずに入れる運用はルールとして明文化しておく必要がある。**
- **ルールを文書で配ると守られず、コードで配ると実行時に効く**という差。チーム内の運用ルールを mod として配布する発想は、**規約の実装可能性**という観点でそのまま他領域へ転用できる。
- **作った拡張の保守を誰が持つか**を決めてから作る規律。本体の更新で壊れる前提のものを渡して終わりにすると、数か月後に負債として戻ってくる。支援・受託の場面で特に重要。
- **公式が「機能を作る側」から「土台を作る側」へ移ると、利用者側の不満の持ち場が無くなる**。できるのに作らないのは自分の選択になる。**道具をどこまで自分で作るかの判断**は、手に馴染む度合いと保守負担のトレードオフとして毎回出てくる。
- **レビューを人だけに任せない形の実例**として `You should know`（側で動くサブエージェントが見落としを指摘）。有効化条件（テレメトリ有効のファーストパーティセッション）が付いている点も含め、**自動レビューの導入条件の設計例**として見る価値がある。
