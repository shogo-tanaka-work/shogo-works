- **今週いちばん強い教材は、コマンド置換のみを対象にした再帰削除が無確認で通っていた件**（2.1.281）。**削除対象が実行時にしか決まらないため、静的な allow ルールでは原理的に守れない。** 権限設計の章で「許可ルールは文字列として評価される」という原則を教えるとき、これ以上に分かりやすい実例はない。**受講者が今週まで使っていたツールで起きていたこと**として始められるのも強い。
- **4件の抜けを「同じ型」として並べる**のが教材としての要点。シンボリックリンク経由の着地先（2.1.280）、コマンド置換の再帰削除、NUL バイト入りルールのワイルドカード展開、macOS の `/.vol` 系パスの承認前読み取り（いずれも 2.1.281）。**すべて「チェックの対象と、実際に効く対象がずれていた」**という構造である。**個別の不具合ではなく、判定と実行の間にずれが生まれる場所を探す**という視点を渡せる。
- **NUL バイト入りルールのワイルドカード展開は、棚卸しの手順まで書かないと片手落ちになる。** 更新すれば展開は止まるが、**それまで意図より広く許可していた期間があったことは戻らない。** 前週の資格情報露出（2.1.275）と同じ型で、**(1) 更新、(2) 自分の allow / deny ルールの読み直し、(3) その期間に通った操作の確認**の3段構えになる。**2週連続で同じ手順を要求されている**点を示すと、手順を定型化する動機になる。
- **「何もしなくても変わる」の実例が今週も出た**（2.1.280 の Pro / Team Standard の既定モデル変更）。Sonnet から Opus へ移ることでコストと速度の前提が変わる。**既定値の変更は、変更履歴の中でも扱いを別にする**という原則を、前週の 2.1.278（分類器のサーバー側既定）と並べて2例で示せる。**同じ週に Codex も音声会話と worktree を既定 ON にしており、3例そろった。**
- **Bedrock upstream の `assume_role` / `guardrail` は、企業導入の標準構成そのもの**（2.1.281）。開発者ごとに資格情報を配らず、**ゲートウェイが STS でロールを引き受けて呼ぶ。** さらに **ガードレールを upstream 単位で強制**する。**「AI ゲートウェイを1か所に置く」構成の具体例**として、前週の課金・透過性の話とセットで企業導入の章に置ける。**全 upstream に設定するか無設定かの二択**という制約も、設計上の割り切りとして扱う価値がある。
- **`"attribution": false` は、バージョン混在環境での設定ファイル互換性の教材**（2.1.281）。**古い CLI がこのキーを持つ設定ファイルごと読み飛ばす。** フラグを1つ足すだけで、同じファイルに書いた他の設定まで失われうる。**チーム共有の設定ファイルを扱う章**で、「設定は足すだけでは安全でない」という形で使える。
- **モデル可用性の管理設定と MCP ツール出力のログ記録**（2.1.283）は、情シス審査で必ず聞かれる2項目にちょうど対応する。**「使えるモデルを管理者が絞れるか」「エージェントが外部ツールから何を受け取ったかが残るか」。** 導入提案のチェックリスト項目として、公式機能名まで添えて示せる。
- **統制を締める機能と緩める機能が同じ週に出る**という現実も扱いたい。Claude Code 側は権限チェックの抜けを4件塞いだが、**同じ週に GitHub Copilot の JetBrains 版は「低リスクの操作を自動承認する」assisted approvals を public preview で出している**（しかも低リスクの基準は非公開）。**ベンダーの方向性を一枚岩として語らず、機能単位で評価する**という姿勢を教える場面。
- **無視されているテレメトリ環境変数を起動時に通知する**（2.1.282）という設計は小さいが、**「設定したつもりで効いていない」型の問題への正攻法**である。同週の GitHub Copilot の managed settings バリデータ（09-25）と同じ発想で、**設定を入れた後に効いていることを別の手段で確かめる**という原則が、ベンダー側の実装として現れている。**統制の教材で、原則と実装の両方を示せる回。**
