- **教材の軸は「制約が外れると保守性が落ちる」に置く。** 入れ子条件分岐はフローの複雑さの上限を外す。**制約があるうちは複雑な判定が複数フローに分かれていて、1つあたりは読めた。** 入れ子が入ると1フローに全部書けるが、**3段4段になると作った本人以外読めない。** Workspace Studio を触るのは多くの場合エンジニアではなく業務側の担当者なので、**異動後に誰も触れないフローが業務の中核に残る**という現実的なリスクを具体例として示せる。
- **「機能では強制できないことを運用ルールで決める」という考え方を教える。** 対策は **(1) 入れ子の深さの上限を決める（例: 2段まで） (2) 入れ子を使ったフローには判定の意図を説明欄に残す** の2つだが、どちらもツール側に強制手段がない。**技術的制約が無い領域をガバナンスで埋める**という設計判断の実例になる。
- **Gmail Skip Replies は「既存の壊れ」を見つける教材になる。** スレッドトリガーは**返信ごとに再発火する**のが既定で、チケット起票・通知・行追加のような**重複しても気づきにくい処理**を静かに増やしていた可能性がある。**実行履歴で同一スレッドの複数実行を探す**という点検手順を、そのまま演習にできる。重複判定を自前で書いていたフローは、その判定を消せる——**消せるコードは消す**という保守の原則につながる。
- **Search for a Doc は「検索を挟むと分岐が増える」ことを教える素材。** これまでのフローは対象ファイルが特定済みであることを前提にしていた。検索を内側に持つと、**0件のとき・複数件のときの扱いを決めなければならない。** 公式発表はこの点に触れていない。**「公式が書いていない分岐を自分で洗い出す」**という読み方の練習になる。
- **Meet Calendar Outputs の招待者リストは、個人情報の取り扱いの教材に直結する。** 招待者リストは**社外の人の氏名とメールアドレスを含む。** フォローアップメール下書きのテンプレートで宛先を自動設定すると、**社外参加者が含まれる場合に意図しない共有が起きうる。** 「便利な出力の中に個人情報が混ざる」典型例である。
- **既定で有効・管理者制御は既存ポリシー踏襲、という提供形態を押さえさせる。** 追加のセットアップ手順が無く、前提プリミティブの管理設定は先行投入済み。**つまり今の設定がそのまま新ステップに適用される。** 全体で許可していれば新機能も全体で有効。**「何もしない」が「全部有効にする」と同義になる**ケースの実例として強い。
- **ロールアウト「2026-10-13 開始・可視化まで最大15日」を、サポート対応の観点で扱う。** 10-28 頃まで環境によって見える・見えないが分かれる。**「ドキュメントにあるのに自分の環境に出ない」という問い合わせが発生する期間**であり、先に説明しておけば無駄な調査を防げる。Rapid Release / Scheduled Release の両方に段階展開される点も押さえる。
- **受託の観点として「顧客の契約内で完結する」利点とジレンマを扱う。** Workspace を使っている顧客なら追加契約なしで使えるため稟議が通りやすい。一方で**顧客内で完結する自動化は保守の継続契約につながりにくい。** だから納品物の価値を**「読める状態で渡すこと」**に置く——入れ子の深さを抑え、判定の意図を残す。**技術力の見せ方が実装から設計へ移る**という話に展開できる。
- **既存のAIニュース記事との重複を避ける。** `gemini/workspace-studio-drive-gmail-chat-steps`（2026-09-02）と `gemini/workspace-studio-meet-calendar-automation`（2026-05-06）が同じ Workspace Studio を扱っている。**本件は2026年10月フィーチャーリリースの別内容**（入れ子条件分岐・Doc 検索・Skip Replies・招待者リスト）であり、教材化の際は時系列で「ステップの追加 → ロジックの強化」という進化として並べると理解しやすい。
- **既存 Knowledge への反映は不要と判断した。** `src/content/knowledge/ai-tools/gemini/` に Workspace Studio を正面から扱った教材がまだない。将来作る場合は、**ステップの一覧ではなく「保守できるフローの設計基準」**を軸にする。ステップは増え続けるが、入れ子の深さを抑える・意図を残すという基準は残る。
