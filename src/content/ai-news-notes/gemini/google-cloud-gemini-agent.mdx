- **教材の軸は「情報が足りない発表の読み方」に置く。** 設計の説明は非常に厚いのに、**提供状況・価格・必要エディション・ロールアウト日が1つも書かれていない。** こういう発表を読んだときにやるべきは、厚い部分に引きずられず**「決められる判断があるか」を確認する**こと。本件では決められる判断がないため、評価は「構想として読む」で止める。**この見極めができないと、イベント発表のたびに検討工数を使うことになる。**
- **エージェント統制の評価軸リストとして流用できる。** (1) エージェントごとに identity があるか (2) 最小権限でセキュリティ管理者が承認するか (3) 外部システムへの認可はどう伝播するか (4) 全アクションがエージェント単位で監査ログに残るか (5) 実行環境は隔離されているか。**どのベンダーのエージェントを評価するときにも効くので、社内の評価シートへ入れる価値がある。**
- **「人のアカウントを借りて動くエージェント」の問題を教えられる。** エージェントに固有の identity がないと、監査で「誰がやったか」が追えない。**`@agents.company.com` のメールアドレスと自前ストレージを持つ常設エージェントは、組織図の中の扱いを決める必要を生む。** 所有者は誰か、退職したらどうなるか、そのストレージの中身は誰の管理下か。**情報管理規程に行の追加が必要になる話**として扱える。
- **プロジェクト単位のリアルタイム上限は、自作エージェントにも入れるべき仕組みとして教える。** 自律エージェントは**何回モデルを呼ぶかが事前に分からない。** 上限到達で停止する挙動は**予算超過より停止を選ぶ**設計判断で、業務が止まる副作用はあるが請求書で気づくより健全。**自社でエージェントを作る場合も同じ仕組みが必要。**
- **MCP を学ぶ投資の回収可能性が上がった、という論拠に使える。** 接続先に「任意の MCP サーバー（社内ネットワークの内外とも）」が入っている。**Claude Code / Codex / Cursor に続いて Google Cloud の主力エージェントも MCP を前提にした。** MCP サーバーを書ける技能が特定ツールに紐づかない資産になるという説明の根拠。
- **モデル振り分けが標準になりつつあることの証拠として引用できる。** Google 自身が **Gemini と Anthropic の Claude を振り分ける**と書いている。**「1つのモデルに最適化する」設計をプラットフォーム側が否定し始めている。** 受託で「特定モデルに依存した実装は将来の負債になる」と説明するときに、公式の例として引ける。
- **既存 Knowledge への反映は不要と判断した。** `gemini/workspace-features.mdx` と `gemini/overview.mdx` はいずれも提供中の機能を扱っている。**提供条件が未公表のものを教材へ入れると、前提が確定した時点で全面的な書き直しになる。** 提供開始の告知が出てから反映する。
