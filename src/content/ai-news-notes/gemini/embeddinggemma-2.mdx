- **教材の軸は「1つの埋め込み空間に載る意味」に置く。** RAG の入門教材はテキストしか扱わないため、受講者は**モーダルごとに別モデル・別空間が必要だった事情を知らない。** 「テキストのクエリで音声を引ける」が何を単純化するのか（構成が1つ、ベクトルストアが1つ、結果マージが不要）を具体的に示すと、設計の勘所が伝わる。
- **「ベンチマークは選定の理由にならない」という原則を教える題材として良い。** 公式が出しているのは MTEB Code 78.68 と MAEB で、**日本語のビジネス文書での精度は分からない。** 自社文書50件・クエリ50件での正解率測定という**具体的な測り方**まで含めて教える。ここを教えないと、受講者は「公式が先頭と言っているから」で選定してしまう。
- **動画58フレーム・音声5.5分という上限は、チャンク設計を教える実例になる。** 「モデルが動画に対応している」と「長時間の動画を検索できる」は別である。**シーン分割やチャプター単位のチャンク化が実装工数の主要部分になる**という見積もりの感覚を伝える。
- **オンデバイス＋Apache 2.0 の組み合わせは「データを外に出せない案件」の教材として中核に置ける。** ただし**埋め込みだけオンデバイスでも生成が API なら意味が薄い**という点を必ず扱う。**「どこまでを外に出さないのか」を先に決める**という順序を教える。
- **埋め込みモデルの差し替えコストを必ず扱う。** モデルを変えると**既存ベクトルは全部使えず、全文書の再埋め込みが必要**になる。受講者が見落とす典型的な論点で、**「新しい方が良い」が移行の理由にならない**ことを教える。契約・見積もりの観点（差し替え費用を契約に書く）まで含めると実務的になる。
- **transformers.js でのブラウザ内実行は、個人開発の教材として使える。** サーバーを持たずに動き、**データが端末から出ない**ので、プライバシーを売りにできる。個人が差別化を作る手段の具体例である。
- **既存 Knowledge への反映は不要と判断した。** 現状 `gemini/` 配下に埋め込み・RAG を恒久的に扱う教材がない。将来 RAG 系の Knowledge を作る場合は、**モデル名の一覧ではなく「埋め込みモデルを選ぶときに測る項目」**（日本語精度、対象モーダル、ライセンス、差し替えコスト、推論の実行場所）を軸にした節を置き、その中で具体例として扱う。
