- **「生成する機能」と「実行する機能」を同じ機能群の中で切り分ける訓練の題材。** コンテンツ生成・リサーチは確認してから使うが、メール送信とカレンダー変更は外部に不可逆な影響が出る。**社内案内を「何ができるか」ではなく「どこから先は人が確認するか」で書く**という原則を、この事例で示す。
- **既定を「下書きまで」に置き、慣れてから広げる**という運用設計は、AI エージェント全般に共通する型。可逆・不可逆の境界で権限を分けるという考え方は、Claude Code の権限モードや Codex の承認ポリシーとも同じ構造なので、**ツール横断の共通原則として1章にまとめられる。**
- **横断リサーチのアクセス範囲は、権限設計の教材へ接続する。** 権限そのものは広がらないが、個別には気づかない断片が統合されると意味を持つ。「アクセスできる」と「一覧できる」は違う、という論点。**出典付きであることが辿れる担保になっている**点も、設計の良し悪しを語る材料になる。
- **段階展開が発表より前（2026-09-02 開始、発表 09-09）に始まっている**という時系列そのものが教材素材。管理者が知る前に現場で使える状態になっている、という構図は Workspace の更新で繰り返し起きる。**「発表を見たら、まず自組織で有効かを確認する」**という手順として一般化する。
- **英語のみという制約を「猶予」と捉える読み方**を教える。日本語対応を待ってから運用を考えると、現場の利用が先行して後追いになる。Workspace は英語先行・後追い多言語化が通例、という運用知識をここで渡す。
- 副業・個人編では、**アプリ切り替え時間は請求できない**という切り口が具体的で伝わりやすい。出典付き横断リサーチが見積もり根拠にそのまま使える、という実利まで落とす。逆に「送信は任せない」を明確な禁止事項として置く。
- 提案の型としては、**実演の順序が効く**題材。「Chat から依頼 → Docs 生成 → Drive 保存 → 共有」という一連を見せてから運用ルールの話に入る。機能紹介で終わらせないための構成として、支援メニューのテンプレートに組み込める。
- 恒久教材へ反映する場合、対象エディションの列挙とロールアウト日付は書かない。残すのは**「生成」と「実行」の切り分け**と、**確認手順**だけにする。
