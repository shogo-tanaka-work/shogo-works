- **「音声をテキストにする」と「音声を読める文章にする」の区別**を、教材の入口に置ける。フィラー除去・言い直しの吸収・自動整形を認識側が担うと、後処理の LLM 層が要らなくなる。**アーキテクチャの層は、モデルの能力が上がると統合される**という一般則の具体例。RAG やエージェント構成でも同じことが起きる。
- **「最大3話者」という制約から逆算して導入場所を選ぶ**という発想は、導入支援の実務スキルとして教える価値がある。制約を隠して全社展開するのではなく、**制約に収まる場所（1対1の商談、少人数定例）から始めて実績を作る**。制約は避けるものではなく、最初の適用範囲を決める材料。
- **カスタム語彙への対応が「用語集を作る仕事」を生む**という論点は、AI 時代の仕事の変化を説明する好例。ツール導入は誰でもできるが、業界固有の語彙を棚卸しして辞書に落とす作業は、その業界を知っている人にしかできない。**AI が普及するほど、ドメイン知識の値段が上がる**という話に接続できる。
- **WER の数字（4.0% / 2.6%）をどう読むか**は、ベンチマークリテラシーの教材になる。平均値は自社の音声環境を保証しない。FLEURS の多言語値（5.50% / 5.04%）が単一言語より悪いことも含め、**条件が変われば数字は変わる**という当たり前を、具体的な数値の並びで示せる。
- **レイテンシ70%改善が精度より体感に効く**という点。音声 UI では待ち時間が使用感を支配する。**改善指標のどれがユーザー体験に直結するかを見極める**という視点は、AI プロダクト評価の一般則として教えられる。
- **function calling への対応が示す方向**——音声認識が「文字起こしの入口」から「操作の入口」へ移る。この設計思想を先に理解しておくと、**いま作るものの最終形を「音声 → テキスト → 人が読む」ではなく「音声 → 行動」に置ける**。エージェント設計の教材として、他社製品の動向と並べて扱うと理解が深まる。
- **API が用途で2系統に分かれている**（Live API / Interactions API）点は、API 設計の教材になる。同じモデルでも、リアルタイム対バッチで求められる保証が違う。**1つのエンドポイントで両方を賄おうとすると、どちらも中途半端になる**という設計判断を読める。
