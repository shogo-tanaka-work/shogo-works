- **教材の軸は「インジェクション対策は入口ではなく出口で考える」に置く。** インジェクションの話は「悪い指示を入れられる」側に注目が集まるが、**被害の大きさは情報が外へ出る出口があるかで決まる。** 本件は入口ではなく出口を絞った対策である。この視点の転換が、本件の最大の教材価値。
- **除外リストが攻撃の形をそのまま示している点を使う。** 「既出」に数えないのは Claude 自身の出力、システムプロンプト、添付文書、`bash` / `read` / MCP ツールの出力。**つまり「エージェントが自分で読んだものに URL を仕込む」経路が全部並んでいる。** 添付 PDF に `https://attacker.example/?data=` を埋める、という具体例で説明できる。
- **「出口を数える」演習に展開できる。** エージェントが外部へリクエストを送れる経路は web_fetch だけではない。**画像の読み込み、Webhook、メール送信も出口である。** 自分が設計したエージェントについて出口を列挙させる課題は、入口の防御を工夫させるより効果が高い。
- **壊れ方の見え方の違いを比較教材にできる。** 本件は `url_not_in_prior_context` という専用エラーで落ちるが、**同日の `allowed_hosts` 側では `web_search` が黙って結果を除外する。** 同じ日の同じ製品の2つの変更で、失敗の可視性が違う。**「エラーで落ちる」と「黙って減る」のどちらが運用しやすいか**を考えさせられる。
- **MCP ツールの設計方針を見直す題材になる。** URL を返して「あとは fetch して」とする実装から、**ツール自身がコンテンツを取得して返す**実装へ寄せる必要が出る。これは手間だが筋が通っている。**社内システムの内容を取るなら、認証を持つ MCP サーバーが取るのが正しく、認証を持たない web_fetch に取らせる構成は元々きれいではなかった。** 制約が設計を正す例。
- **制限が増える変更の説明の仕方を教えられる。** 現場からは「使いにくくなった」と受け取られる。**説明の軸は「エージェントが自分で読んだものに書かれた URL は信用しない」の一文に集約できる。** 制限の理由を1文で言えるかどうかが、現場の納得を分ける。
- **自社のエージェント実装へ取り込む基準として使える。** 「外部へのリクエストを許す URL は、人が明示的に渡したものに限る」。**Claude に限らず一般的な防御であり、自社で LLM エージェントを作っている場合に同じ制限があるかを確認する基準になる。**
