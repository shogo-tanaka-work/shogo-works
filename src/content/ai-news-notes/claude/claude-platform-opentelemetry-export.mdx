- **教材の軸は「エージェントは作れるが、動かし続ける設計は別スキル」に置く。** エージェント構築の教材は飽和しつつあるが、**運用設計の教材は足りていない。** OpenTelemetry は特定ベンダーに縛られない標準なので、ここを押さえると Claude 以外でも同じ話ができる。**教材の寿命が長い領域**である。
- **機能の列挙から入らず、「これまで何が見えなかったか」から入る。** Managed Agents の内部で走る複数のモデル実行と server tools は、外から追えなかった。**自前でログを仕込んでもサーバー側の内側は埋められない。** この制約を説明できると、機能の意味が伝わる。逆に span の種類を列挙するだけの教材は読まれない。
- **content mode は技術選択ではなくデータガバナンスの判断だと、最初に線を引く。** `metadata_only` と `content` の違いは「見える情報の量」ではなく、**プロンプトと応答がどこに保存されるか**である。公式自身が「保存とアクセス制御は監視基盤側の設定に従う」と書いている。**責任の移転**として教えると、情シス・法務の確認対象が Claude 側ではなく自社の監視基盤側だと分かる。
- **「まず入れてみる」が危険な理由を具体的に言う。** 既定は `metadata_only` なので事故は起きにくいが、**Full content に切り替えた後で気づくと手遅れ**である。業務データがプロンプトに入る構成では、監視基盤の保存期間がそのデータの保存期間になる。**順序（決める → 入れる）を教材の手順として固定する。**
- **2つの経路を「権限の違い」で分けて教える。** SDK トレーシングは権限不要で開発者が自分で始められる。API トレーシングは Admin 権限が必要で**組織の承認が前提**になる。受講者が自分の環境で何から試せるかが即座に分かる。PoC の設計で手戻りを減らす実用的な区別である。
- **トークン集計の罠は、そのまま演習問題になる。** (1) SDK span と API span を両方足すと二重計上、(2) 判別は kind（`CLIENT` / `SERVER`）、(3) compaction 分は `gen_ai.usage.*` に含まれないので別途加算、(4) span は欠落しうる。**公式ドキュメントに書いてあるが分散している。** 「この構成で正しい合計を出す式を書け」という形の演習にすると定着する。
- **「ダッシュボードの数字を請求の根拠にしない」を原則として渡す。** best effort 配信で span は落ちうると公式が明記し、正確な使用量は Usage API を使えと案内している。**監視の道具と課金の台帳は別**という線引きは、Claude に限らず一般化できる。この種の原則は数値が変わっても残る。
- **0.75 MB の上限は、数字の裏にある理由まで教える。** 英語 200k トークン相当で、**多くの監視基盤とプロキシの 1 MB 制限を下回る値**として選ばれている。1M トークンには約 4 MB。**制約が外部の都合から決まっている**例であり、「なぜその数字なのか」を読む練習になる。切り捨て順序（システムプロンプトと古いメッセージから、ツール結果は末尾から）も実務で効く。
- **検証できる範囲が広く、教材の素材を自分で作れる。** 長いプロンプトで `anthropic.content.truncated` が `true` になる条件、実際に何が消えるか、Langfuse や PostHog の無料枠での接続。**公式は仕様を書いているが、実測の記録は見つけにくい。** 個人のアカウントで一通り通せる規模なので、受講者にそのまま課題として出せる。
- **既存監視基盤の有無で提案の規模が変わる点を、営業の観点で明示する。** Datadog / Grafana / New Relic / Splunk を運用中なら「AI 部分を同じ画面へ載せる」で済み稟議が軽い。持っていない組織では**監視基盤の導入から始まる**ため話の規模が別物になる。**同じ機能が顧客の状況で別の提案になる**例として使える。
- **既存 Knowledge への反映は最小限にとどめる。** `claude/overview.mdx` に「Claude API は OpenTelemetry でトレースを出せる（ベータ）」の1行と、**「全文を出すかはデータの置き場所の判断である」**という原則だけ置く。上限値・属性名・パートナー一覧はベータ中に変わるため記事側に残す。**数値は記事、原則は Knowledge** の切り分けを徹底する。
