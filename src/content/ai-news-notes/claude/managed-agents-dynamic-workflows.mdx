- **教材の軸は「オーケストレーションを委譲すると、可観測性が自分の仕事になる」に置く。** 分割・並列化・集約のコードを書かなくてよくなった代わりに、**ワークフローのコードは見えず、run を管理するツールコールも各スレッドの戻り値も見えない。** 抽象化を上げると実装は減るが検証は増える、という一般則の具体例として強い。
- **最重要の論点は `result: {"type": "completed"}` が成否を示さないこと。** 公式は「**run のスレッド上の作業が失敗していても、スレッドが作成できなくても completed で終わりうる**」と明記している。**「正常終了」と「作業成功」を別の概念として扱う**という設計原則を教える素材になる。300件投げて50件落ちても completed、という具体例が効く。
- **検証の設計として「外側で件数を数える」を必ず教える。** 中が見えない処理に対しては、**投入件数と結果件数をワークフローの外で突き合わせる**しかない。適用先を選ぶときの基準として「**件数が合っているかを別の手段で検証できる処理か**」を立てさせる。
- **budget は安全弁ではなく有効化の前提条件として教える。** run の寿命は既定24時間、同時 open は既定10、1つの run が起動できるエージェントは1,000。**止める仕組みが budget しかない。** さらに budget 到達時、各スレッドは開始済みリクエストを完了させるため**稼働スレッド数ぶん超過しうる**（同時64なら64リクエスト分）。**「上限に当たってから止まるまでにどれだけ超えるか」を見積もる**という考え方の実例になる。
- **使用量の集計方法は、公式が指定した手順をそのまま教材にできる。** スレッドを列挙し、run の `workflow_run_id` を持つものの `usage` のトークン数を合計する。**`list_cost` の合計は誤り**で、セッションのランタイムが抜け落ち各数値が別々に丸められる。**「合計してよい値と、合計すると壊れる値」**の区別を教える良い題材である。
- **冪等性の要件が公式に明記されている点を強調する。** 「**run は同じ作業に対して複数のスレッドを作りうるので、ツールは2回呼ばれても安全にすること**」。外部システムへの書き込み（発注・送信・課金）を run に使わせる設計は、ここを満たすのが前提。**分散処理の at-least-once セマンティクスを、エージェントの文脈で教えられる。**
- **webhook が発火しない点は、既存の監視設計との接続で扱う。** run イベントは webhook を発火せず、イベントストリームの購読かイベント一覧の取得が必要。公式はレートリミットの節で**ポーリングを避けるよう明示**している。「新機能が既存の監視経路に乗らない」ことを見落とす失敗例として使える。
- **レートリミットの合算は、本番との同居リスクとして教える。** run のスレッドのモデルリクエストは**組織の Messages API のレートリミットに他のトラフィックと合算**される。64スレッド同時なら通常の API 利用を圧迫する。**非機能要件が機能追加で変わる**実例である。
- **「API はそれを保証しない」という書き方の読み取りを教える。** inline agent はツール・MCP・スキルの部分集合を受け取り、公式は「全部もらうが、API はそれを保証しない」と書く。**保証しない側に倒して設計する**のが正しい読み方。同じ言い回しは同時実行スレッド64やフェーズの順序にも付いている。
- **既存 Knowledge への反映は、現時点では不要と判断した。** `src/content/knowledge/ai-tools/claude-code/dynamic-workflows.mdx` は **Claude Code 側の別機能**で、Managed Agents API の話とは対象が違う。混同を招くため、同じ記事への追記はしない。将来 Managed Agents の教材を作る場合は、**「規模の壁を越える代わりに検証を自分で持つ」という設計判断**を軸にし、イベント名や上限値は参照に留める（ベータのため変わる）。
