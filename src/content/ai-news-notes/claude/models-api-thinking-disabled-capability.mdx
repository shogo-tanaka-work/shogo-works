- **教材の軸は「モデル ID の文字列から情報を読み取らない」に置く。** `model.includes("opus")` のような分岐は、**モデルが増えるたびに壊れる。** しかも壊れ方が「追加した瞬間」ではなく「そのモデルで特定のパラメータを使ったとき」なので、テストで拾いにくい。**壊れ方の遅さを含めて教えると、受講者の記憶に残る。**
- **3つの変更を並べて方向性を読む練習に使える。** 2026-09-28 の Sonnet 5.5 の破壊的変更（thinking を切るには `between_tools`）、10-01 の `line` フィールド、10-05 の `capabilities.thinking.types.disabled`。**単発では読み飛ばす大きさだが、並べると「ID をパースさせない方向へ API を整えている」という意図が見える。** リリースノートの読み方の教材として、題材がきれいに揃っている。
- **「モデル一覧を定期取得してキャッシュする」という実装パターンを教える。** 毎リクエストで問い合わせる必要はないが、**capability は増える方向に変わるのでキャッシュは短命にする。** キャッシュ期限の決め方を、変化の方向から逆算させる演習にできる。
- **コーディング規約に落とす、という発想を教える題材になる。** 技術的には1行の修正だが、**「モデル ID をパースしない」を規約に書くかどうかで、新しく書かれるコードが同じ罠にはまるかが変わる。** 個別の修正と規約化の違いを扱える具体例である。
- **追補で検出した経緯そのものが運用の教材になる。** 公開日が date-only のエントリは、時刻比較で窓に入らず取りこぼしやすい。**本件は前日の窓に入っていたが当日のサマリーに記録されなかった。** 巡回設計を扱うなら、「date-only は日付で候補にし、記録済み URL との差分で判定する」という手順の必要性を示す実例になる。
- **既存 Knowledge への反映は、`claude/interleaved-thinking.mdx` を候補として検討した。** thinking の扱いを恒久的に説明している教材なので、**「モデルによって受け付ける type が分かれており、capability で判定できる」という1〜2行の追記は筋が通る。** ただし本記事単体の依頼範囲ではないため、今回は追記していない。**thinking 関連の更新が次に来たときにまとめて反映する**のが効率的である。
