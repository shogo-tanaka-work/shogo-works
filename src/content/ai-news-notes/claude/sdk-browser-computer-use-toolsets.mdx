- **教材の軸は「自前実装とベンダー標準で、審査での説明の重みが違う」に置く。** URL ポリシーと承認コールバックを自分で書くと「テストしていない分岐が残っていないか」を問われる。**SDK 標準なら、その議論自体を回避できる。** 同じ機能でも、誰が実装したかで審査の通りやすさが変わるという構造は、AI ツール導入提案の教材として実用的である。Claude for Google Workspace の回で扱った「アプリの約束とプラットフォームの権限」と同じ型なので、3例目として並べられる。
- **「デモまでは速く、実用まで長い」という開発の非対称性を教える題材になる。** ブラウザ操作エージェントは典型例で、長い部分（ループの堅牢化、URL 制限、承認の差し込み）が SDK に入った。**受講者が「動いた」で完了と判断しがちな領域なので、何が残っているかを先に示す教材価値が高い。** 事故の発生順（想定外 URL → 勝手に送信）まで含めて説明すると具体的になる。
- **トークン固定費の計算を必ず演習に入れる。** browser use 約 6,600、computer use 約 4,500 トークンが毎リクエストに乗り、スクリーンショットが画像入力として追加される。**「1件処理するのにいくら」を出す練習は、受託で月額固定を請け負って赤字にならないための実務訓練である。** token counting エンドポイントで事前に測るという手順まで教える。`configs` でメンバーを落とせばトークンが減る（`zoom` 無効化で約 410 減）という最適化も、効果が数字で示せるのでよい題材。
- **ベータ段階のツールの扱い方を、ここでも反復する。** 対象業務を2つ程度に絞り、数週間で挙動を実測する。**仕様が変わる前提で、契約上の SLA を伴う設計には使わない。** Claude for Google Workspace の回と同じ検証設計を当てられるので、受講者には「beta と書かれていたらこの手順」というパターンとして定着させる。
- **「API のない Web システムに届く」という価値は、中小企業向け提案の中核として教える。** 古い業務システムへの手打ち作業は相談として非常に多い。ブラウザ操作は API がなくても届く唯一の経路で、**Haiku 5.5 の単価と組み合わせると価格面でも提案可能になった。** ただし computer use には `computer_toolset_20260801` が必須という版数の制約を忘れないよう併記する。
- **既存 Knowledge への最小反映は今回は不要と判断した。** `ai-tools/claude/` 配下に browser use / computer use を恒久的に扱う教材が現状ない。**ベータであり、トークン量やメンバー構成が変わる見込みが高いため、確定していない仕様を教材へ入れない。** GA 後に「ブラウザ・デスクトップ自動化と承認設計」の節を作り、その中で SDK クラスを扱う。
