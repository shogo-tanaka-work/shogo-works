- **この事例の中心的な教材価値は「統合された成果物からは、捨てられた選択肢が見えない」点にある。** Claude が並列スレッドの出力を自分でレビューして1つにまとめるということは、**採否の判断が人の目を通らずに済んでいる**ということ。効率化が説明責任を削る、という一般則の具体例として扱う。
- **「どこを人が見るか」を、成果物単位ではなくプロセス単位で設計させる演習に使える。** 従来は「出力を見る」で足りた。並列委譲が入ると「スレッド構成を見る」「食い違いの解消方法を見る」という別のレビュー点が必要になる。**レビュー点は自動化の段数が増えるたびに上流へ移動する**、と教える。
- **コストが依頼文で決まり、事前に読めない**という性質は、AI 活用のコスト教育に向く。同じ内容の依頼でも Claude が何スレッドに分けるかで消費が変わる。**「使った分」ではなく「どう分解されたか」で課金が決まる**構造を、実際の使用量モニタリングを見せながら説明すると腹落ちしやすい。
- **段階展開の条件が「既存 project を持たない Pro / Max の Claude Code クラウドセッション利用者」と極端に細かい**点は、そのまま教材になる。同じプランでも来る人と来ない人がいる。**「プラン名だけでは機能の有無を説明できない」**という、企業研修で毎回問題になる論点を具体例で示せる。
- **2026-09-16 の Cowork / chat 統合と合わせて「2週続けて社内の共通認識が崩れた」という時系列で扱う**と、単発の機能紹介より価値が出る。手順書に製品の画面構成を書くと壊れる、という結論へ持っていける。
- **各スレッドが専用ブランチとリポジトリのコピーを持つ**点は、開発者向け教材では「生成物の後始末」の話に接続する。1依頼で複数ブランチが生える運用は、**削除の責任者を決めないと確実に散らかる**。AI が作った成果物のライフサイクル管理という論点の入口に使える。
- **個人事業主向けには「並列化は単価の根拠にならない」を明示する。** クライアントから見た成果物は同じ。**短縮分を値引きに使うと単価が下がるだけ**なので、検証の厚みや提案数に振り向ける、という具体的な置き換え方を演習させる。
- **公式が機能紹介の中にコスト警告を書いている**という事実自体を読み取らせる。ベンダーが自ら「上限の消費が早まる」と書くのは珍しい。**そう書かざるを得ないほど消費が増える**、と読むのが正しい、という資料の読み方を訓練する。
- 恒久教材へ反映する場合、**ベータ条件・展開順・プラン名は書かない**（変わる）。残すのは **(1) 委譲の段数が増えるとレビュー点が上流へ移る、(2) 依頼の分解のされ方でコストが決まる、(3) 段階展開は社内の共通認識を壊す** の3点。
