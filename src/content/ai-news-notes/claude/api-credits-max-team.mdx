- **教材の軸は「取り消せない設定」の扱い方に置く。** リンクした Console 組織は利用者側では変更できない。**AI ツールの設定には、押す前に決めておかないと後戻りできないものがある**という一般則の、具体的で小さな実例である。情シス教材で「設定変更の可逆性を事前に確認する」という作法を教えるとき、大げさな事例よりこういう身近なものが効く。ロールアウトが数日かけて進むため「画面に出た人が先に押す」事故が起きやすい、という時間的な要因まで含めて説明できる。
- **共有残高は「枠の配分ルール」を教える題材になる。** 組織内の API キー保有者全員が同じ残高を見る。技術的には制御できず、**運用ルールで埋めるしかない**構造である。Claude for Google Workspace の回で扱った「技術で縛れない部分はルールで埋める」と同じ型なので、2例並べると原則として定着しやすい。
- **「繰り越しなし」から予算の性質を読む練習に使える。** 同じ月 $200 でも、繰り越せる枠と繰り越せない枠では使い方が逆になる。前者はためて大きく使う、後者は毎月小さく使う。**金額ではなく条件が用途を決める**という読み方を、受講者に自分で導かせる。
- **カバー範囲の切り分けは、誤解の予防として教材に入れる価値が高い。** 「Max を契約したから Claude Code の API 利用も無料」という誤解はほぼ確実に発生する。対象は Claude Platform（Messages / Batches / Playground / Managed Agents / Agent SDK）で、**対話的な Claude Code と Bedrock / Vertex / Foundry 経由は対象外。** サブスクリプションと API 課金が別勘定であるという構造の説明に使える。
- **クレジットが尽きても Claude プランへ課金が流れない点は、良い設計として取り上げる。** 「上限に達したら止まる」は不便だが、**想定外の請求が出ない**という意味で企業導入では評価される。止まる設計と課金が伸びる設計のどちらを選ぶかは、組織のリスク許容度の問題だと示せる。
- **既存 Knowledge への最小反映を検討する。** `claude/claude-max-plan.mdx` は Max プランの内容を扱う教材で、**月次 API クレジットという特典が増えたことが反映されていないと不完全になる。** 金額（5x $100 / 20x $200）と「Claude Code の対話利用は対象外」の2点だけを別 PR で追記する。カバー範囲の詳細まで持ち込むと速報寄りになるので入れない。
