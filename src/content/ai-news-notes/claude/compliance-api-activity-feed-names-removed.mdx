- **「遡及する破壊的変更」という珍しさを教材の入口にする。** 通常の破壊的変更は当日以降のデータに効くだけで、過去分を取り直せば元の形が取れる。**そこが移行猶予の源泉**である。今回はそれが無い。**猶予がどこから生まれていたのかを逆から理解させられる**、良い反例。
- **ID を主キーに、表示名は都度引く。** この設計にしていれば影響は「引く先が変わる」で済んだ。**外部 API のレスポンス項目を検索キーや判定条件に直接使うと、項目が消えた日に機能が落ちる**という一般則へ繋げる。今回の被害の大小が設計判断で決まっていたという点が効く。
- **「監査を維持するために監査対象が増える」構図を見せる。** 名称取得が `read:compliance_user_data` スコープの下に移った。**キーを誰が持ち、どこに置き、利用をログに残すかという新しい管理項目が発生する。** セキュリティ強化が運用負荷に化ける典型で、実務の手触りがある。
- **日付見出し単位で「確認済み」にすると取りこぼす**という、リサーチ運用そのものの教訓。今回は Opus 5.5 と拒否課金の隣に埋まっていた。**派手な発表の陰に後退方向の変更が置かれる**のは珍しくない。受講者自身の情報収集の癖に直接刺さる。
- **eDiscovery の文脈まで踏み込む。** 「いつ誰がどのファイルを扱ったか」を Activity Feed 単体で示せなくなる。**ログの完全性をどう説明するかは法務と情シスの合意事項**で、技術変更が契約や手続きに跳ねる例。技術者が法務と話す必要性を実感させたい。
- **DLP 判定でファイル名パターンを使う実装の脆さ。** `契約` `人事` `_confidential` といった命名に依存する判定は、そもそも命名規則の遵守が前提で脆い。**今回の変更は、脆い判定が脆いままでいられなくなったという読み方もできる。** 落ちたことを機に中身ベースの判定へ移る動機になる。
- **Microsoft 365 のベータ解除は「禁止の根拠が消える」話として扱う。** 「ログが取れないから Office 内での利用は禁止」という制限を続けている組織は多い。**前提が変わったのに制限だけ残るという典型的な硬直**の例。ルールの棚卸しをいつやるかという運用の話に繋げられる。
- **副業案件としての即効性を最後に置く。** 遡及する変更は顧客側で確実に作業が発生する。**リリースノートを読んでいることがそのまま声をかけられる理由になる**という、地味だが再現性の高い営業の形。派手なスキルではなく習慣が仕事を生む例として締めたい。
