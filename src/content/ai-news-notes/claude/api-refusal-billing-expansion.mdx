- **本題は「3カテゴリが課金対象になった」ではなく「残りは誤検知が多いと公式が認めた」こと。** 選定基準が明示されているため、選ばれなかった側から精度の情報が読み取れる。**公式ドキュメントの読解演習として質が高い題材**。表面（価格改定）と裏（精度開示）の二層を読ませる。
- **「成功したリクエストだけが課金される」という素朴な理解を壊す。** mid-stream refusal は以前から課金、出力前拒否も一部が課金へ。**AI の課金は結果の成否ではなく消費した計算資源で決まる**、という原則に戻して説明する。
- **カテゴリ名をハードコードしない、という実装上の教訓。** 公式が「測定結果に基づく選定」と書いている以上、対象は変わりうる。**変わることが明示されている値を定数に埋め込まない**は一般的な設計原則で、この事例は根拠が文書に書いてある珍しいケース。
- **リトライ設計の見直し**が実務アクションとして具体的。安全性判定による拒否は、同じ入力で再試行しても結果が変わらない。**拒否とエラー（レート制限・ネットワーク）を区別してリトライ対象を絞る**。無課金の頃は無害だった実装が、課金対象になった瞬間に無駄な支出へ変わる。
- **「段階的な移行の1歩」として読む**視点。今回で終わりではなく、精度が上がった領域から順に移る方向。**将来「拒否はすべて課金」になる前提で設計しておく**方が後で楽、という予測にもとづく設計判断の練習。
- **負担配分の筋道が説明可能であること**を教えたい。誤検知が多い領域では請求しない → 精度が上がったものから通常課金へ。**社内で「断られたのになぜ払うのか」と聞かれたときの回答**として、そのまま使える構造になっている。反発されにくい設計の実例。
- **全プラットフォーム適用（API / Bedrock / AWS / Google Cloud / Foundry）**という点を落とさない。「うちは Bedrock 経由だから関係ない」という誤解が起きやすい。**クラウド経由でもモデル提供元の課金ルールが効く**、という構造理解に繋げる。
- 演習案: 自分の API ラッパーのコスト集計コードを見て、①拒否をコスト集計から除外していないか、②拒否をリトライしていないか、③カテゴリ名がハードコードされていないか、の3点を点検させる。**読んで終わらず手元を直すところまで**行かせる。
