- **教材の軸は「許可リストを1か所に統一すると、粒度が落ちる」というトレードオフに置く。** `allowed_hosts` 1か所で web 検索・取得・サンドボックスのすべてが決まるのは監査の説明コストを下げる。**一方で「検索で参照させたいだけ」のホストを追加すると、サンドボックスからも通信できてしまう。** 統一の便益と粒度の喪失は同時に起きるという構造で、セキュリティ設計の教材として扱う価値が高い。「設定が1か所になって分かりやすくなりました」で止めない。
- **「エラーを返す制限」と「黙って除外する制限」の違いは、デバッグ教材の中核に使える。** `web_fetch` は `url_not_allowed` を返すが、`web_search` は結果を除外するだけ。**後者は症状が「情報が出てこない」になり、原因が許可リストだと気づけない。** 同じポリシーでもツールによって失敗の見え方が違うという観察は、トラブルシュートの手順書を書く練習に直結する。
- **サブドメインの完全一致ルールは、受講者に必ず1回間違えさせる価値がある。** `docs.example.com` は `["example.com"]` に含まれない。**直感に反するので、説明だけでは定着しない。** 演習で設定を書かせて落とすのが早い。ワイルドカード `*.example.com` でまとめるか個別列挙するかの判断も、セキュリティ要件との兼ね合いとして一緒に考えさせられる。
- **「締めている環境だけが作業を要求される」という構造は、皮肉だが重要な観察である。** `unrestricted` と self-hosted は対象外なので、この変更で困るのは `limited` を選んでいる組織だけ。**セキュリティを厳しくしている側に移行コストが乗る**というパターンは AI ツールの更新で繰り返し起きる。「緩くしておけば楽」という誘因が構造的に存在することを示せる。
- **セッション作成の 400 は「失敗の早さ」として評価できる。** エージェントが動いてから取得に失敗するのではなく、設定矛盾をセッション作成時に弾く。**失敗を早い段階へ寄せる設計は、運用では望ましい。** ただし CI やバッチで一斉に落ちる形で現れるため、更新告知を読んでいないと朝のジョブ障害として体験することになる。リリースノートを読む運用の必要性と繋げられる。
- **既存 Knowledge への最小反映は今回は不要と判断した。** `ai-tools/claude/` 配下に Managed Agents のネットワーク設定を恒久的に扱う教材が現状ない。**この変更だけのために新規 Knowledge 記事を作ると速報寄りで薄くなる。** Managed Agents の環境設計をまとめた教材を作る段で、`limited` / `unrestricted` / self-hosted の違いと `allowed_hosts` の統一的な役割を1節として扱う。
