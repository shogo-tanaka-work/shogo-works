- **`tool_choice` の `any` / `tool` が 400 になった、という一点から設計原則を引き出せる。** 強制ツール利用は「モデルに判断させるが、判断を上書きする」という中間の設計である。**モデル側の推論能力が上がると、上書きが品質を落とす方向に働く。** だから仕様から消える。「判断させる処理」と「確定的に実行する処理」を混ぜない、という原則の実証例として繰り返し使える。
- **強制ツール利用の使用目的を3分類する型**（構造化出力の確保 / 分類判定の強制 / 外部呼び出しの保証）。3つ目は**そもそもモデルに任せる必要がなかった**ケースが多い。移行作業が設計の棚卸しになる、という典型。
- **「リクエストは成功するが、中身が落ちる」挙動の危険性**（thinking ブロックのアカウント境界）。エラーが出る変更より、**エラーが出ない変更の方が本番で危ない。** 移行検証の設計では「エラー監視」ではなく「出力の差分比較」が必要になる、という使い分けを教えられる。
- **退役告知と破壊的変更は別の日に別の場所へ出る**という運用上の事実。09-30 の退役告知だけを読むと、09-28 の Sonnet 5.5 の破壊的変更5点を見落とす。**「移行先のリリースノートも読む」を手順として明文化する**価値がある。
- **後継公開から2日で前世代の期限が切られた**という時間感覚。提供経路（API / Bedrock / AWS / Google Cloud / Foundry）が揃った時点で期限を出す、というベンダー側の判断パターンを読む材料になる。
- **モデル ID が散る場所のチェックリスト**（コード / 設定 / 環境変数 / インフラ定義 / CI / 社内 Wiki / 手順書）。最後の2つは動作に影響しないが、**後から誰かが参照して動かないものを作る**という遅延型の負債になる。
- **「モデル退役の監視と対応」を小さな保守契約として切り出す**という提案の型。退役は予告されるため、対応は予測可能な作業である。**予測可能な作業を契約に入れておくと、発生時に無償対応か関係悪化かの二択を避けられる。** 受託の収益構造を変える具体策として説明できる。
- **退役日を切り替え日にしない**という運用規律。期限当日の切り替えは、問題が出たときの逃げ場がない。**期限の1週間前完了を標準にする**という線引きは、モデル退役に限らず EOL 対応全般に使える。
