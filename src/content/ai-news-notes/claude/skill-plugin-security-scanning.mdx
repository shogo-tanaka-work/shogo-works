- 公式ドキュメントの7リスク指標（コード実行 / 指示の改変 / MCPサーバー参照 / ネットワークアクセス / ハードコード認証情報 / ファイルシステムのスコープ / ツール呼び出し）は、Skill に限らず「AIエージェントに何かを持ち込むときの点検軸」としてそのまま教材化できる。プラグイン・MCPサーバー・カスタムコマンドにも同じ軸が使える。
- 「自動検査は必要条件であって十分条件ではない」という判断の立て方は、企業導入編の中核テーマ。検出範囲が非公開なツールをどう運用ルールに組み込むかの実例として扱う。
- Skill を作る側の教材では、この7指標を「避けるべきこと」ではなく「良い Skill の書き方」として提示する。認証情報は環境変数、ファイルアクセスは Skill ディレクトリ内、ネットワークアクセスは用途を明示 — いずれも品質の話でもある。
- 「初回審査と更新時審査を分ける」という運用設計は、Skill 特有ではなく変更管理の一般則。教材では前者を人手、後者を自動、という役割分担のパターンとして提示する。
- 命名の紛らわしさ（Claude Security / Claude Security プラグイン / Skill・プラグイン検査）は教材内で必ず区別を明記する。読者が混同すると「コードベースをスキャンする機能」と誤解する。
- 公式ドキュメントが未更新である点は、教材執筆時の一般的な注意として使える題材。「リリースノートが先行しドキュメントが遅れる」状況で、どちらを正とするか（＝両方の日付を確認する）という調査手順を教える具体例になる。
- ベータかつ Enterprise 限定のため、演習として手を動かす教材にはできない。運用ルールを紙上で設計する演習（受け入れフローの図を書く）に留めるのが現実的。
