## 教材化ポイント

### 1. 「エージェントが長時間タスクで崩れる」問題の、公式な失敗事例として使う

エージェント教材で最も需要があるのに一次情報が乏しいのが、**なぜ長時間タスクが崩れるか**である。この発表は Anthropic 自身が「初期の試行では、エージェントが急速にプロジェクトの状態を見失い、効果的な協調をやめた」と書いており、**ベンダー公式の失敗記述**として引用できる。失敗分が最終成果物の約7%として残っている、という定量も付いている。

**教材への落とし込み方:**

- 「エージェントを長く走らせると賢くなる」ではなく「**状態管理をしないと必ず崩れる**」を先に置く
- 崩れ方の具体（前提を忘れる / 同じ作業を繰り返す / 互いの成果を無視する）を列挙し、受講者の実体験と接続する
- 対策が「モデルを強くする」ではなく「**状態を外へ出す**」だった点を明示する。ここを取り違えると、受講者は「もっと良いモデルを待つ」という誤った結論に行く

### 2. Prove2Me の3つの工夫を、汎用の設計原則へ翻訳する

Prove2Me そのものは数学専用だが、担った機能は汎用である。教材では**数学の文脈を外して**提示する。

| Prove2Me がやったこと | 汎用の設計原則 |
| --- | --- |
| 定理文の DAG を維持 | **依存関係つきの共有タスクグラフ**を会話の外に置く |
| 定理文と証明をファイル分離 | **インターフェースと実装を分離**し、検証コストを下げる |
| 各定理文に自然言語の説明を付与 | **検索・再利用のためのメタデータ**を成果物に必ず添える |

**教材への落とし込み方:**

- この対応表をそのまま図表にする。数学を知らない受講者でも設計の話として読める
- 個人・小規模チーム版の代替（Markdown のタスクファイル、GitHub issue、Notion DB）を示し、「専用プラットフォームがないとできない話ではない」ことを明示する

### 3. 「検査系のあるタスクを選ぶ」という判断基準

Lean は完璧な検査系である。教材としては、**エージェントに任せる仕事の選び方**の基準に落とすのが最も実用的。

**教材への落とし込み方:**

- 「検査系がある仕事 / ない仕事」の仕分け演習を置く（ある: テスト付きコード、スキーマ変換、型付け、lint。ない: 企画の良し悪し、文章のトーン、顧客への提案内容）
- **検査系がない領域で長時間走らせると、間違いも同じ速度で積み上がる**という一文を必ず入れる
- 検証の多重化（Lean カーネル → comparator → 独立実装 nanoda）を、「自己申告の完了」と「独立検査の通過」を分ける設計として説明する

### 4. 誇張への予防線を教材側で先に張る

このニュースは「AI が350年の難問を解いた」と要約されやすい。**公式は「新しいのは検証であって新しい数学ではない」と明記している。**

**教材への落とし込み方:**

- 「解いた」ではなく「**既存の証明を機械が検査できる形へ翻訳した**」と言い換える
- 業務への読み替えを「答えのない問題を解く」ではなく「**正しさの基準が定義済みの作業を桁違いの量でこなす**」に固定する
- コスト面の但し書き（社内研究モデル、出力トークン約60億）を添える。手法は参考になるがコスト構造は別、という線を引いておかないと、受講者の見積もりが崩れる
