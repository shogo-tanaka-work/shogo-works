- **この事例の教材価値は「機能が増えていないのに実務影響が出る」点にある。** できることは変わらず、呼び出し場所だけが変わる。**受講者は機能追加にばかり注目しがちなので、配置変更の方が手順書を壊すという逆説を体験させる題材として使える。**
- **演習: 自組織のAIツール手順書から「UI要素名」を数えさせる。** 「Cowork を開く」「◯◯タブをクリック」のような記述は、UI 変更のたびに無効になる。**「何をするか」で書いた手順書は変更に強く、「どこを押すか」で書いた手順書は弱い**という一般則をここで教える。
- **段階展開（staged rollout）を「障害と見分ける技術」として扱う。** 同じプランでも人によって画面が違う期間が出る。**これを知らないと情シスは障害調査を始める。** 前日の Gemini MCP コネクタ（即日展開）と対比させると、展開方式の違いが問い合わせ対応をどう変えるかが立体的になる。
- **「非可逆な移行」はAIツール全般で増えている論点として一般化する。** 評価期間を置いて戻す、という前提が通用しない。**検証は移行後にしかできないので、事前準備の中身が「戻す準備」ではなく「壊れる箇所の特定」になる**という発想の転換を教える。
- **設定の統合（Global instructions → Instructions for Claude）は、移行時チェックリストの作り方の題材。** 公式自身が「意図どおりか確認せよ」と書いている箇所は、**ベンダーが移行リスクを認識している箇所**である。**告知文の中で「確認してください」と書かれた部分を拾う読み方**を訓練する。
- **権限モード（Manual / Auto）は、既定値の重要性を教える好例。** 既定が Manual なので何もしなければ従来どおり。**「既定値が安全側かどうかを最初に確認する」**という型を、前日の Gemini MCP コネクタ（既定で有効＝危険側）との対比で強調できる。
- **Enterprise の30日前通知は「準備期間の使い方」の演習に使える。** 通知を待つのではなく、**先行移行している Pro / Max 利用者に実物を確認してもらう**という段取りが現実的。組織内に先行事例が自然発生する構造を利用する発想。
- **恒久教材へ反映する場合、モード名や展開日は書かない**（変わる）。残すのは3点。**(1) 手順書は UI 要素名ではなく目的で書く、(2) 段階展開中は画面差が正常、(3) 既定値が安全側かを最初に見る。**
