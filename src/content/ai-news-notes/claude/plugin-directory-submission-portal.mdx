- **「作れる」と「配れる」は別、という切り分けを最初に置く。** MCP や Skills の講座は作り方に寄りがちで、受講者は動くものを手元に持って終わる。**そこから先が無いことに気づかないまま満足する**のがいちばんもったいない。ディレクトリ提出という出口ができたことは、カリキュラムに「配布」の章を足す理由になる。
- **提出即時スキャンを「品質基準の既製品」として使う教え方。** 自前で審査項目を設計させるより、公式スキャンが何を弾くかを調べさせる方が早く深い。**通らない作りは社内向けでも危ない**という結論に自分で辿り着かせられる。
- **アナリティクスが2系統に分かれている点が教材の核。** 表示回数とインストール数を分けて見ると「説明が悪い」「名前が悪い」を切り分けられる。**これは広告運用の CTR / CVR とまったく同じ構造**で、技術者が苦手な「作ったあとに伸ばす」の入り口として使いやすい。
- **検索キーワードが見えるという事実から、命名の話へ繋げる。** エンジニアはツール名を内部構造から付けがちで、探される言葉と一致しない。**「何をするか」ではなく「何と検索されるか」で名付ける**という発想転換は、副業で成果に直結する。
- **Enterprise Managed Auth を飛ばさない。** 「プラグインが誰の権限で動くか」を組織が握れるかは導入審査の必修項目。**提出要件に入っている事実から、組織向け配布の前提を逆算させる**ことができる。認可の設計を後回しにすると作り直しになるという実例として強い。
- **「掲載されている」は安全の保証ではない、と必ず言う。** 自動スキャン通過を「Anthropic が保証した」と読む受講者が必ず出る。**通っていないものと区別できるようになっただけ**で、判断は利用側に残る。ここを曖昧にすると誤った安心を教えることになる。
- **発見体験の統合予定は、手順書を書くタイミングの話として使う。** 数週間で変わると公式が言っているものを今スクリーンショット付きで手順化すると、作った直後に古くなる。**「いつ書くか」も設計判断**という、教材運営そのものに跳ね返る題材。
- **狭い業務を狙う戦略は、副業講座の結論として置ける。** 汎用ツールは大手が出す。**ディレクトリ内検索では狭い言葉で一位を取る方が現実的**という、検索が効く場所ならどこでも成立する話。前日の Cloudflare MCP portals の回（組織側の統制）と対にして、「作る側」「入れる側」の両視点を揃えたい。
