- **「上位モデルを選んでおけば安全」が崩れた実例**として扱える。Terminal-Bench 4.0 で Sonnet 5.5（70.6%）が Opus 5.5（66.4%）を上回り、しかも価格は半額。**モデルの階層は価格の階層であって、能力の全順序ではない**。用途ごとに測る、という当たり前の結論を、具体的な数字で裏づけられる教材。
- **ベンチマークを複数並べて読ませる練習に向いている**。Terminal-Bench では勝ち、FrontierCode（46.2% 対 54.4%）では負ける。**1つの指標で順位をつけると誤る**という構図が、同じ発表の中に両方ある。「どのベンチマークが自分の業務に近いか」を選ぶところから始める、という流れを作れる。
- **Sonnet 5 の Terminal-Bench 10.3% → Sonnet 5.5 の 70.6%** という伸びは、数字として異常に見える。**ベンチマークのバージョンが上がっている（4.0）ことと、世代交代が重なっている**点に注意させたい。前世代の低スコアをそのまま「7倍良くなった」と読むと外す。一次情報の数字をどう引用するかの教材。
- **モデル差し替えが移行作業になる**、という点が今回いちばん実務的。`tool_choice: "any"` と `thinking: "disabled"` が 400 エラー。**「真面目に作った実装ほど壊れる」**という逆説が効いている。構造化出力を確実にするための強制ツール利用、レイテンシを抑えるための thinking 無効化——どちらも品質を上げるために入れた設定である。
- **プロバイダーによって挙動が割れる**ケースを教材にできる。旧 computer use ツールは Bedrock では動き、Claude API と Google Cloud では拒否される。**マルチクラウド構成が、切り分けを難しくする方向に働く**典型。「冗長化したら障害調査が複雑になった」という実例として具体的。
- **thinking ブロックのアカウント紐づけ**は、マルチテナント設計の落とし穴として使える。会話履歴を共通プロキシで引き回す構成は珍しくない。**「動くが、期待した推論の継続が起きない」という、エラーにならない壊れ方**をする。エラーが出ない不具合をどう検知するかの話へ繋げられる。
- **9月22日に Opus 5.5、28日に Sonnet 5.5、数週間後に Haiku 5.5**。**1週間で2モデル**という更新頻度そのものを教材にする。社内ドキュメントにモデル名と価格を直書きすると、書いた翌週に古くなる。**「変わる値を本文に埋め込まない」という文書設計**の話に落とせる。
- **「待つ」という選択肢を明示的に扱いたい**。Haiku 5.5 が数週間後に来ると公式が言っている以上、大量処理用途で今から Sonnet 5.5 に作り込むのは最適でない可能性がある。**技術選定における「決めない」判断の価値**。ただし待ち続けると何も出ないので、どこで線を引くかもセットで。
