- **教材の軸は「モデルの能力をコードに書くか、API に聞くか」に置く。** `if (model.startsWith("claude-opus"))` のような分岐は、**新モデルが出るたびに直す必要があり、直し忘れると新モデルで動かない機能が黙って増える。** エラーにならないので気づかず、数か月後に「なぜか検索が効かないモデルがある」として発覚する。capability 問い合わせへ置き換える設計の価値を、具体的な壊れ方で説明できる。
- **「名前が近いのに別の問いに答えるフィールド」の実例として優れている。** `capabilities.server_tools.code_execution`（このモデルにツールを渡せるか）と `capabilities.code_execution`（渡したコードが他ツールを呼べるか）。**公式がわざわざ注意書きを添えているのは、取り違える人が出ると想定されているということである。**
- **取り違えの被害が2方向に分かれる点を教える。** トップレベルを見て判定すると**使えるモデルを使えないと判定する**（エラーにならず気づきにくい）。`server_tools` を見ずにツールを渡すと**リクエストが失敗する**（気づける）。**同じ取り違えで、気づける失敗と気づけない失敗の両方が起きる。**
- **防ぎ方を実装の形で教えられる。** どちらも boolean なので型では気づけない。**capability の読み取りを1か所の関数に閉じ込め、`modelAcceptsCodeExecutionTool()` と `codeCanCallOtherTools()` のように関数名で問いを表す。** フィールド名を各所で直接読む実装は、この種の取り違えを必ず起こす。
- **自分が API を設計する側になったときの命名の教材にもなる。** `code_execution` と `server_tools.code_execution` は、名前だけ見ると**後者が前者の詳細のように見える**が、実際は別の問いである。**公式が注意書きを書かざるを得なかった名前は、命名の失敗例として参照する価値がある。**
- **capability 報告の細分化という流れの中で読ませる。** 2026-10-01 の `line`、10-05 の `capabilities.thinking.types.disabled`、10-06 の `capabilities.server_tools`。**週単位で細かくなっている。** 単発の変更として覚えるのではなく、**モデル ID のパースから capability 問い合わせへ移行できる範囲が広がっている流れ**として教える。
- **コードレビューのチェック項目として1行で使える。** 「モデルの能力をコードに書いているか、API に聞いているか」。**Claude に限らず複数モデルを扱う実装すべてに当たる観点である。**
- **既存 Knowledge への最小反映を検討したが、今回は不要と判断した。** `claude/model-lineup-2026.mdx` はモデル一覧と使い分けで、**capability API の読み方を扱う節がない。** フィールドが週単位で増えている段階なので、落ち着いてから「Models API でモデルの能力を問い合わせる」節をまとめて作る方が、更新漏れが出にくい。
