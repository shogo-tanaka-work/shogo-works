- **教材の軸は「4つの期限が並んでいる」という事実に置く。** GPT-4o の退役を単体で扱うと「ID を直す作業」で終わる。**2026-12-11 / 2027-01-06 / 2027-01-14 / 2027-01-20** を1枚の表にして見せると、**1件ずつ対応すると棚卸し・テスト・リリースを4回繰り返す**ことが一目で分かる。段取りの話へ持ち込めるかどうかが、教材の価値を分ける。
- **対象が「GPT-4 系すべて」ではない点を、最初に正確に押さえさせる。** 対象は5つのスナップショット ID だけで、**GPT-4-turbo は別エントリ・別の停止日**である。「GPT-4 が終わる」という雑な把握が、対応漏れと誤った期限の両方を生む。**公式の表をそのまま読む練習**として良い題材。
- **ファインチューニング済みモデルの扱いが、この告知のいちばん重い部分である。** ベースモデルと同日に停止するため、**ID の置き換えではなく再学習が必要**になる。学習データの再整備・評価・品質比較まで含めると工数の桁が変わる。**「同じ退役告知でも、影響の重さは構成によって違う」**という一般論へ展開できる。
- **「スナップショット固定は安全」という思い込みを崩す。** 日付入りモデル ID で挙動を固定するのは正しい運用だが、**固定したスナップショットには退役日が来る。** 再現性のための固定と、保守の期限はトレードオフである。この構造は OpenAI 以外のベンダーでも同じで、**原則として残る知識**である。
- **棚卸しの対象リストを具体的に渡す。** コード / 環境変数 / 設定ファイル / プロンプトテンプレート / バッチスクリプト / 社内ツール / 業務部門が作った自動化。**最後の1つが毎回残る。** 情シスの台帳に載っていないものを数える方法（API キー単位の利用ログから逆引きする等）まで示すと実務になる。
- **3か月という期間の読み方を教える。** ID 置き換えだけなら余裕があるが、**再学習と評価を回すなら着手が年明けでは足りない。** 同じ期間が構成によって「十分」と「不足」に分かれる。**期限の長さを工数と突き合わせて読む**練習として使える。
- **移行先が一本（`gpt-6-luna`）である点の副作用を押さえる。** 選択の判断は軽くなるが、**mini 前提のコスト試算は組み直しになる。** 「移行先が決まっている=何も考えなくてよい」ではない。単価確認を移行手順の必須ステップとして入れる。
- **提案の形を「期限一覧付きの棚卸し」として教材化する。** 1件だけ直すと1月に同じ依頼が来る。4つの期限をまとめた表を先に出し、**全系統を一度に洗い出す提案**にすると単価と納得感が上がる。**表を自分が持っていることが提案の速さになる**という点が、受講者に効く。
- **退役履歴の蓄積そのものを成果物として勧める。** 告知日・対象・停止日・移行先を積み上げると、**「このベンダーはスナップショットを何か月で切るか」**が見えてくる（今回は約3か月）。モデル選定の助言の根拠になる。**更新を続ける一覧は、単発記事より読まれ続ける。**
- **既存 Knowledge への反映は `chatgpt/models.mdx` に退役日の行を足すだけにとどめる。** 本文の移行手順や工数の話は記事側に置く。**モデル一覧は「いつ止まるか」を持つべきページ**で、そこに日付が無いと読者が誤解する。逆に手順を Knowledge へ入れると更新が追えなくなる。
