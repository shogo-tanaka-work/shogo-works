- **エージェント教材の章立てを「基盤」と「業務分解」に分ける根拠として使える。** これまでエージェント入門は、どうしてもコンテキスト管理・再開処理の説明に紙幅を取られていた。それが外部化されたことで、**教材の重心を業務分解へ移す正当な理由ができた。** 「配管の作り方」を教える章は、原理の理解として残しつつ、実装演習からは外す。
- **コンテキスト圧縮・永続セッション・復旧の3つは、外部化されても「何が起きているか」は教える。** ブラックボックスのまま使うと、長い会話で挙動が変わったときに原因を切り分けられない。**「仕組みは理解する、実装はしない」**という扱いを明示する。これは HTTP を理解しつつ自前実装しないのと同じ整理で、受講者に伝わりやすい。
- **実行環境の選択（OpenAI ホスト / 自社インフラ / ベンダーサンドボックス）は、AI ガバナンス教材へ直結する。** 「エージェントが触れるデータとネットワークの範囲を誰が決めるか」という問いになる。同日の Cloudflare Containers の実装例とセットで扱うと、抽象論で終わらない。**PoC 段階と本番段階で置き場所が変わりうる**点を演習の前提条件に組み込む。
- **MCP のベンダー中立性を示す実例として引く。** 同じ MCP サーバーが Claude 側でも OpenAI 側でも接続先になる。**ツール資産をベンダーに固定しない設計**という文脈で、MCP 教材の導入部に置く価値がある。「いま MCP でツールを書く投資は無駄になりにくい」という判断材料になる。
- **「ベータを納品物に含めるか」は、受託向け教材の実務パートに入れる。** 仕様変更リスクの明示、改修の別途見積もり、動かなくなったときの責任範囲。**技術の話ではなく契約の話**であり、ここを教える教材は少ないので差別化になる。
- 提案の作り方を変える題材としても強い。**「基盤を構築します」から「業務をこう分解します」への移行**は、AI 案件の提案書テンプレートを書き換える具体的な理由になる。shogoworks の伴走支援メニューでは、業務ヒアリングの工程を前段に厚く置く構成へ接続する。
- 恒久教材へ反映する場合、**API の個別機能名は書かない**。書くのは「エージェント基盤の配管はプラットフォーム側へ移りつつある」「自前実装の価値はツールと業務知識に寄る」という結論と、実行環境の選択が統制設計になるという指摘だけにする。
