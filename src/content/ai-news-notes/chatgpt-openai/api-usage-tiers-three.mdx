- **教材の軸は「ティア条件」と「月間利用上限」の区別に置く。** ここを混同する受講者が多い。**ティア条件は累計クレジット購入額（一度到達したら戻らない）**、**月間利用上限はその月に使える上限**で、別の軸である。Grow に到達しても月 $200,000 を超えて使えるわけではない。演習で両者を分けて書かせる価値がある。
- **「レート上限のための作り込み」を課金で外せる、という判断を教える題材になる。** リトライのバックオフ、キュー、時間帯分散はそれ自体が保守コストである。**累計 $500 で Grow に届くなら、作り込みを外す方が安い場合がある。** 「技術で解くか課金で解くか」の比較を、具体的な数字で演習にできる。
- **Luna 系の Grow が 180,000,000 TPM（Astra/Sol/Terra 系の 4.5 倍）という点は、モデル選定の教材で使える。** 単価の安いモデルの方がレート上限も緩いという構造は、**「大量の単純処理は安いモデル、難しい処理だけ上位モデル」という振り分けが、コストと上限の両面で合理的**であることの裏付けになる。モデルを1つに決めない設計を教える根拠に使える。
- **既存情報が一斉に古くなる瞬間の実例として記録に残す。** 「5段階」と書いた記事・社内資料・比較表はこの日を境に誤りになった。**確認日を書く習慣**を教える題材として、変化が明確で分かりやすい。
- **下側の条件（Build が累計 $5 で月 $500）は、API 入門の心理的ハードルを下げる数字として使える。** 「API を試すには大きな初期費用が必要」という誤解を具体的な数字で解ける。入門教材の最初に置くとよい。
- **既存 Knowledge への反映は不要と判断した。** API の利用ティアを恒久的に扱う Knowledge が現状なく、ティア構造は今回のように段階数ごと変わる。**変わりやすい数値を教材本体に入れるべきではない。** 将来「生成AIのコスト設計」系の Knowledge を作る場合は、ベンダー別の数値表ではなく**「レート上限に当たったときに技術で解くか課金で解くかを決める手順」**を軸にする。
