## 教材化ポイント

### 1. 「ツール呼び出しでターンが止まる」という前提の更新

エージェント教材はほぼ例外なく「モデルがツールを呼ぶ → アプリが実行 → 結果を返す → モデルが再開」という同期のループ図で説明している。`async: true` はこの図そのものを書き換える。

**教材への落とし込み方:**

- 既存のループ図の隣に「非同期版」を並べ、**モデルが止まる区間がどこで消えるか**を色で示す
- 「OpenAI がジョブを預かるわけではない」点を明記する。ここを誤解すると、リトライとタイムアウトの設計が抜ける
- Background mode との違いを1行で対比させる（Background = レスポンス生成が非同期 / async tool = ツール実行中もモデルが進む）

### 2. 「受理」と「反映」を分けて教える

`response.steer.accepted` は受理通知であって反映保証ではない。実行済みアクションは取り消せない。ここは教材で最も事故につながる箇所である。

**教材への落とし込み方:**

- 「ステアリングでできること / できないこと」の対比表を置く（できない側: 送出済み出力の巻き戻し、実行済みアクションの取消、開始済みツールのキャンセル）
- 外部システムへ書き込むエージェントでは、**取り消せない操作の前に承認ステップを置く**という設計原則とセットで扱う
- 自動継続が走るため `response.create` を再送してはいけない、という手順上の注意を明記する

### 3. プロンプトキャッシュとコストの教材への接続

`configuration_update` の価値は「推論強度を変えられる」ことより「**キャッシュを壊さずに変えられる**」ことにある。コスト教材があるなら、この一点を軸にできる。

**教材への落とし込み方:**

- 「プロンプト接頭辞を書き換える = キャッシュが切れる」という原則を先に説明し、その回避策として位置づける
- 長いコンテキストを毎回積むユースケース（社内文書 QA、コードベース質問）での月額差として具体化する

### 4. モデル依存機能の扱い

ステアリングは `gpt-6-astra` 専用、WebSocket 必須。`none` 推論強度は非対応、EU データレジデンシーでは Fast mode 非対応。

**教材への落とし込み方:**

- 「API の新機能 = 全モデルで使える」ではない、という前提を明示する
- モデル選定教材があれば、**機能可用性の軸**（対応モデル・必要な接続方式・リージョン制約）を比較表に足す
- 情シス向けには WebSocket 疎通の確認項目として残す
