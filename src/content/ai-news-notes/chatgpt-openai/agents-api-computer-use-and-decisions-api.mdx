- **「作る / 借りるの境界は、ベンダーの発表のたびに動く」**という視点が、この記事の核。今回は「セッション管理・オーケストレーション・文脈圧縮・復旧」が借りる側へ移った。**過去1年の発表をこの軸で並べ直すと、それ自体が1本の講義になる**。技術選定を静的な比較表ではなく時間軸で教える方法として有効。
- **差別化にならない部分を見分ける訓練**。顧客が価値を感じるのはエージェントが何をするかであって、セッション管理の出来ではない。**「作っても差別化にならないが、作らないと動かない部分」**をリストアップさせる演習は、受託・自社開発の両方で使える。
- **残すべきものと渡してよいものの線引き**を型にできる。残す = 自社の業務知識が入る部分（どのツールを持たせるか、どう判断させるか、どこで人間に確認を取るか）。渡す = 汎用部分。**この線引きは AI に限らずシステム設計一般の原則**なので、汎用教材へ昇華できる。
- **パブリックベータを本番に載せない**という判断基準。仕様は変わる。**「新規に作るものから試す、既存は並走させる」**という進め方は、新技術導入の一般則として教えられる。
- **コンピュータ操作（GUI 自動化）は壊れやすいという性質は変わらない**——RPA の教訓をそのまま接続できる。「AI が操作するから壊れない」わけではない。**適用条件（画面変更の頻度が低い / 失敗の手戻りが小さい）を先に決める**という判断の型が、RPA 導入の失敗事例と対比して教えやすい。
- **API を持たない業務システムという日本企業特有の制約**に触れられる。基幹系や業界特化パッケージに API がなく自動化が止まる構図は、受講者の実感に直結する。**ただし安易な期待を持たせないこと。**
- **Decisions API は「出力形式が安定しない」問題への構造的な解**という説明が分かりやすい。JSON で返せと指示しても崩れる——これは全員が経験している。**選択肢を先に定義する API は、プロンプトエンジニアリングで解こうとしていた問題を設計で解く**。この対比は「プロンプトで頑張る vs 構造で解く」という教材テーマになる。
- **Bedrock Managed Agents は「データが AWS を出ない」制約への回答**。金融・医療・公共・契約で縛られた受託。**「以前できないと結論した案件の前提が変わった」という掘り起こしの型**は、営業教材としても使える。ただし限定プレビューである点を正直に伝えることを必ず併記する。
- 時系列として、**Bedrock の OpenAI モデル・Codex・Managed Agents 限定プレビューは 2026-04 に AWS 側が先に発表**している。**ベンダー2社の発表タイミングがずれる**という観察は、情報収集の教材で「片側だけ見ていると遅れる」実例になる。
