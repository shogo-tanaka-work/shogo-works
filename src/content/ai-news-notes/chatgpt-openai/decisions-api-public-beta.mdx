- **教材の軸は「生成と判定を分ける」に置く。** 生成AIの入門教材は「文章を作らせる」から始まるため、受講者は**判定も生成 API でやるものだと刷り込まれる。** Decisions API は、**判定は判定の API でやるという選択肢**が公式に用意されたことを示す具体例である。ここを教えると、設計の初手が変わる。
- **confidence を使った「自動 / 人手」の切り分けは、AI 業務導入の教材の中核に置ける。** 「AI に任せるか任せないか」の二択で考えている受講者が多いが、**確率が返るなら閾値で帯を切れる。** 演習として「問い合わせ振り分けで、confidence いくつ以上を自動化するか」を業務リスクから逆算させると、判断の練習になる。
- **閾値を放置する危険性も必ず扱う。** モデルが更新されれば確率分布は変わる。**「一度決めた閾値を見直す工程」を設計に含めないと、精度低下に気づけない。** 月次サンプリングによる正解率測定を、運用設計の必須項目として教える。
- **料金体系の単純さを見積もり演習に使える。** 入力 $0.10 / 1M トークン、出力課金なし、キャッシュ課金なし。**生成 API の「入力＋出力＋キャッシュ」より見積もりが簡単**で、受講者が自分で概算を出せる。月1万件の振り分けを題材に計算させるとよい。
- **制約の読み取り演習に使える素材がある。** 対応モデルが `gpt-6-luna` のみ、画像は base64 インラインのみ、**HTTP/HTTPS の画像 URL と `file_id` は非対応**、public beta。**「使える」と判断する前に制約を列挙する**習慣を付けさせる題材として、制約が明文化されているのでちょうどよい。
- **既存 Knowledge への反映は不要と判断した。** `chatgpt/models.mdx` はモデル一覧で、エンドポイント単位の設計論は扱っていない。将来「生成AIの処理設計」系の Knowledge を作る場合は、**「生成 / 判定 / 抽出 のどれをやりたいのかを先に決める」**という節を置き、その中で Decisions API を判定の選択肢として扱う。
