- **最も事故が起きる論点は「同じ画面に、機微データを扱う経路と外部へ出る経路が同居している」こと。** 公式が「公開ソースへ送る検索に PHI を含めるな」と注意を書いているのがその証拠。**利用者から見ればどちらも同じ ChatGPT の画面**で、経路の違いを意識し続けられる設計にはなっていない。**「入れていいデータ／いけないデータ」という粗い教育では足りず、「同じツールでも、この機能を使うと外へ出る」という粒度が要る**——AI 利用教育の粒度設計の実例として非常に使える。
- **「検索」と「構造化アクセス」の違い**は、MCP / プラグイン設計の教材として価値が高い。「PubMed を検索できる」は以前から可能だった。今回できるのは**識別子とバージョンを特定して扱う**こと。**要約・検索で足りる用途と、精度が要る用途は別物**で、後者を前者の道具でやると**もっともらしいが微妙に間違った出力**になる。自作 MCP で「テキストで返すか、構造を保って返すか」を選ぶときの判断軸。
- **read-only という設計判断。** ChatGPT はカルテへ書き戻さない。**「AI に読ませる」と「AI に書かせる」の間には責任の所在という断絶がある**——まず read-only から始めるという段階論は、多くの領域で妥当な進め方として教えられる。
- **有効化の主体が管理者であること**の一般化。個人が試せる範囲と、組織が有効にしなければ使えない範囲を分ける設計は、**機微データを扱う AI 機能の標準形**。医療に限らない。
- **規制産業向け提案のチェックリスト**として、この発表の要素列挙がそのまま使える：ロールベースアクセス制御 / SSO / 監査ログ / BAA / read-only / 機微データの扱いの明示。**「便利です」から入る提案と「アクセス制御と監査ログはこうなります」から入る提案の差**は、この領域では決定的。
- **監査ログは後から追加できない要件**という指摘。「誰が、いつ、どのデータを、どんな質問で参照したか」が残らない構成で運用を始めると、後で監査に答えられない。**後回しにされがちだが、設計時に決めなければならない項目**の代表例。
- **米国前提の発表を日本の文脈でどう扱うか**という読み方の訓練。Epic も CMS Coverage も米国制度。**そのまま使えないが、論点の構造は移植できる**——「使えない」で捨てず「何が論点として抽出できるか」で読む。
- **見出しではなく提供条件を読む習慣。** 「ChatGPT が電子カルテとつながった」を持って行くと「うちでも使えますか」→「実は個人アカウントでは EHR 連携は使えません」と訂正することになる。**制約を先に言う**という、Astra のメモと共通する原則。
