- **「メトリクス定義を持ち込める」という一文が、この機能の本体である。** 機能紹介としては地味だが、業務データ × LLM の失敗要因の大半はここに集約される。教材では機能の使い方より先に、**「自社の指標の定義を書き出せるか」という問い**から入る構成にすると刺さる。書き出せない組織が多数派である、という前提で作る。
- **権限モデルの説明材料として質が高い。** 「接続したアカウントの既存権限でクエリが実行される」は、研修で必ず出る「AIに社内データを見せて大丈夫か」への直接的な回答になる。**プラグインが権限を拡張しないことと、接続アカウントに強い権限を渡すと運用で穴が空くことは別問題**である、という2段構えで説明すると誤解が減る。
- ai-governance 系の教材に、**「最小権限の接続アカウントを用意する」** を具体的な作業項目として足せる。抽象的な最小権限原則より、AIツール接続という具体的な場面のほうが実行されやすい。
- **BIツール依頼の2層構造（作り込むダッシュボード / 軽い問い合わせ）** という切り分けは、この記事に限らず AI 導入の効果測定で使える枠組み。「どの層の仕事が消えるか」を先に特定してから導入効果を見積もる、という手順の教材にできる。
- 監査ログの所在について**公式が触れていないことを記事で明示した**のは、教材の書き方としても踏襲したい。**「公式が書いていない」と書くことは、調べ漏れではなく判断材料**である。導入チェックリストに「未記載＝要確認」の欄を作る運用に接続する。
- 副業文脈の「メトリクス定義の整理を単体の仕事にする」は、**AI導入支援の商品設計の実例**として shogoworks の成長戦略側の教材と接続できる。ツール導入そのものではなく、その前工程に値段が付くという構図。
- `@Data` というメンション起動の UI パターンは、プラグイン全般に広がっている。**「機能を呼び出す」から「参加者を呼ぶ」へのメタファの変化**として、プロンプト設計の教材で触れる価値がある。
