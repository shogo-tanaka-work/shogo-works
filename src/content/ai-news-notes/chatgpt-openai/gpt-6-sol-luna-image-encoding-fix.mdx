- **「評価結果がモデルの実力ではなく不具合を測っていた」**という構図が、この記事の教材的な中心。公開 09-22、修正 09-25。その間に評価した人は、モデルではなくバグを測っていた可能性がある。**測定対象が安定していない期間に測る**という問題は、AI に限らず性能評価全般に通じる。
- **評価ログに「実施日」を必須項目にする**という具体的な運用改善。ベンダーが修正告知を出したとき、**日付が記録されていなければ再評価の対象を特定できない**。結果として「全部やり直すか放置するか」の二択になり、実際には放置される。**記録の粒度が、後の意思決定の選択肢を決める**という一般原則の実例。
- **入力種別（テキストのみ／画像込み／ツール利用）を記録する**理由が本件で具体化する。今回の修正対象は「画像入力を使うユースケース」だった。**絞り込みの軸を記録していないと、絞り込みができない**。ログ設計を「あとでどう検索したいか」から逆算する、という設計思想の説明に使える。
- **モデル公開直後の評価を「暫定」として扱う**二段構えの運用。初回は方向性の確認まで、本評価は公開から2〜4週間後。**急ぐ場合も「暫定である」と明記しておけば、後から見直す根拠になる**。これは AI 導入に限らず、新製品・新バージョンの評価一般に適用できる型。
- **いったん「使えない」と結論が出ると、次に見直されるまで長い**という組織の慣性。自動化の検討が止まっている理由が、実は修正済みの不具合だった——という状態は起きる。**否定的な結論にも再評価のトリガーを設定する**という発想は、実務的だがあまり語られない。
- **公式が改善幅を数値で出していない**点の扱い方。「degraded」という定性的記述だけ。したがって「どれだけ良くなったか」は公式値で語れず、自分で測るしかない。**ベンダー告知に何が書かれていないかを読む**訓練として、短い告知文ほど良い教材になる。
- **不具合の技術内容も非公開**なので、「自社の使い方では影響が小さかった」と推測で結論するのは危険。**情報が足りない状態での推測を、結論として扱わない**という判断の規律。
- **単価差が桁で効く**という見積もりの話。Sol は入力 $2、Luna は $0.10 で20倍差。**不具合下の評価で Luna を候補から落としていたなら、提案の競争力が変わる**。モデル選定を「性能の優劣」ではなく「単価×通る範囲」で設計する、という実務の型に接続できる。
- **重要な告知が changelog の2段落に入る**という情報収集の論点。製品ブログは大きな発表を出すが、**「すでに使っているものが変わった」情報は changelog 側に出る**。しかも今回は利用者側のアクション要求（再評価の推奨）が changelog に入っていた。**本番で使っているなら API changelog を監視対象にする**という結論。
- **一次情報に戻る根拠として使える**。公開直後の SNS 上の「速い/遅い/賢い」という評判は、配信側の状態が揃う前の観測であることが多い。本件はそれが公式の修正告知で裏づけられた形である。**「同じものを測っていない」という疑いを持つ習慣**の具体例。
