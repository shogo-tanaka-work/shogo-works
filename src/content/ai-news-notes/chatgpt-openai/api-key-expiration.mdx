- **「守るべきルール」と「破れないルール」の差を教える題材として、極めて分かりやすい。** 社内規程に「定期ローテーション」と書いてあるが確認手段がない、という状態は受講者の多くが自覚している。**規程 → 設定への移行**という一般則を、この1事例で説明しきれる。セキュリティ教材の導入に置く。
- **手順の順序を間違えると事故になる、という点を必ず強調する。** 「上限を設定する」より先に「既存キーの棚卸し」が来る。**新規キーにしか期限が付かない**ため、上限設定だけで安心すると最も古いキーが放置される。**正しい順序を答えさせる演習**にすると定着する（順序を入れ替えた選択肢を混ぜる）。
- **期限の長さは「自動化の水準に合わせて決める」**という判断軸を教える。短いほど安全という単純な話ではなく、切り替えが手作業の環境で30日にすると形骸化する。**セキュリティ設定は運用能力とセットで決める**という原則の実例。ここは受講者が自社に持ち帰って即判断できる粒度になる。
- **「どのキーがどのシステムで使われているか」の把握が前提条件**である点は、資産管理（CMDB）の話へ接続できる。把握していない状態で期限を付けると業務が止まる。**AI 導入の前に必要な足回り**として、ガバナンス教材の前段へ置く。
- **委託先へのキー発行に契約期間と同じ期限を付ける**という使い方は、フリーランス・小規模事業者向けに具体的で強い。「返してもらう」という人の運用に頼らない設計。**外注を使う個人事業者**にもそのまま当てはまるので、副業教材にも流用できる。
- **個人開発の `.env` 消し忘れ → リポジトリ公開**という事故の形は、受講者の実体験に触れやすい。**検証用は7〜30日、本番用は長め**という用途別の使い分けを、具体的な運用テンプレートとして配る。
- 恒久教材へ反映する場合、**OpenAI 固有の設定画面名は書かない**。書くのは「認証情報の管理はプラットフォームの強制力へ移せる」「既存の認証情報は自動では守られない」という2点と、棚卸し → 上限設定 → 影響範囲の確認という順序だけにする。他ベンダーにも同じ構造が来るため、汎用の章として書く。
