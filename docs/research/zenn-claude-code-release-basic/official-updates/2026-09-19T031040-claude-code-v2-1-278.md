# 2026-09-19 Claude Code v2.1.278

## 公式内容の日本語要約

**changelog は2項目だけだが、片方は課金の変更である。** auto mode では、シェルコマンドやネットワークリクエストを実行する前に分類器（classifier）が安全性チェックを行う。v2.1.278 以降、**Claude API 利用アカウント・Enterprise プラン、および Claude Platform on AWS / Amazon Bedrock / Google Cloud Agent Platform / Microsoft Foundry / ゲートウェイ経由の構成で、このチェックをサーバー側へ既定で寄せる。** サーバーが実行したぶんは**セッション自身のモデルリクエストに含まれ、分類器のオーバーヘッドとしては課金されない**。

**ただし「該当すれば必ず無料になる」ではない。** サーバー側チェックがセッションへ届かない場合、Claude Code は従来どおり自前の分類器リクエストを使い、**そのぶんは今までどおり課金される**。届かない主因は、リクエストヘッダやボディのフィールド（`safeguards`）を落とす / 書き換える LLM ゲートウェイ・プロキシである。レスポンス側で `safeguard_results` を落としたり tool-use ID を書き換えたりする実装も同じく該当する。プラットフォームやリージョンへの展開がまだ届いていない場合も起こる。

**該当した最初のアクションでプロンプトに通知が出て、操作が保留される。** 「この セッションは対象外」という趣旨の文面で、ゲートウェイを特定できた場合はその名前も出る。Enter で続行（保留中のアクションとそれ以降は自前の分類器を使い、従来どおり課金）、Esc / Ctrl+C でキャンセル。`-p` の非対話実行では stderr へ、`stream-json` 出力では `system` 警告として流れる。**Pro / Max / Team プランにはこの通知は出ない。**

**自前ゲートウェイがサーバー側チェックに対応できないと分かっている場合は、`CLAUDE_CODE_AUTO_MODE_SERVER=0` で最初から要求しない設定にできる**（通知は出なくなり、課金は従来どおり）。公式は**この変数を一時的なもので将来削除されうると明記している**ため、恒久設定として運用ドキュメントへ書き込むべきではない。もう1つの追加は `/status` の **`Auto mode server` 行**で、そのセッションの分類器がサーバー側で動いているか（`Enabled` / `Disabled`）を確認できる。

## できるようになったこと

- Claude API / Enterprise、および Claude Platform on AWS / Bedrock / Agent Platform / Foundry / ゲートウェイ構成で、auto mode の分類器チェックがサーバー側既定になり、該当時は分類器ぶんが課金されない
- `/status` の `Auto mode server` 行で、そのセッションがサーバー側チェックで動いているかを確認できる
- `CLAUDE_CODE_AUTO_MODE_SERVER=0` で、サーバー側チェックを要求しない挙動に固定できる（通知も出なくなる）

## 影響範囲

- 対象ユーザー: Claude API 利用アカウント、Enterprise プラン、Claude Platform on AWS / Amazon Bedrock / Google Cloud Agent Platform / Microsoft Foundry、および Claude apps ゲートウェイ経由の利用者。Pro / Max / Team は対象外
- 対象プラン: Enterprise と API 課金が中心。Bedrock / Agent Platform / Foundry / 署名済みゲートウェイセッションでは、そもそも auto mode 対応モデルが Sonnet 5 / Opus 4.7 以降 / Fable 系に限られる
- API / UI / 管理者機能: 課金（分類器リクエスト）、`/status` 表示、環境変数、ゲートウェイのパススルー要件

## 教材化メモ

**単独記事にしない（バージョンリリースのため規約により週次ロールアップへ）。** ただし週次側では「版数の1項目」ではなく**課金の変更**として扱う。

教材素材としての要点は、**ゲートウェイの「透過性」が値段に直結し始めた**ことである。これまで LLM ゲートウェイの評価軸は統制・ログ・コスト可視化だったが、ここでは**未知のリクエストフィールドをそのまま通すか**という実装品質が、そのまま分類器ぶんの課金の有無に変わる。企業導入の章で「ゲートウェイ選定の評価項目にパススルー適合を入れる」という具体例に使える。v2.1.276（2026-09-18）の 400 エラー、v2.1.277 の `CLAUDE_GATEWAY_PROXY_IS_EGRESS_BOUNDARY` と合わせ、**3日連続でゲートウェイ経路の話が出ている**点も並べて示せる。

**もう1つは「既定の変更は静かに効く」という論点。** 対象アカウントは更新しただけで課金の扱いが変わるが、**変わらなかった側（ゲートウェイが非対応）には通知が出るだけで、コストは据え置かれる**。つまり「更新したのに安くならない」が起き、原因は自社のゲートウェイ側にある。`/status` の `Auto mode server` 行で切り分けられることまでをセットで教える。
