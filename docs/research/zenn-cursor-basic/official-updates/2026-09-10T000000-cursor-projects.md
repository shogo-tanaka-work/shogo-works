# 2026-09-10 Cursor Projects

## 公式内容の日本語要約

**Projects は、機能追加・マイグレーション・アプリ1本といった大きな仕事の単位**を扱う機能である。**数か月にわたって文脈を保持し、数千のサブエージェントへタスクを委譲し、指示されなくても繰り返しの作業を実行する。**

左ナビゲーションからアクセスする。**Project 内のコーディネーターエージェント自身はコードを書かない。** 作業を計画し、実装するエージェントへ委譲し、完成した成果を確認のために戻す。コーディネーターは利用者に代わってエージェントを作成・管理し、必要なだけ並列に走らせる。

**Cloud Agents が基盤である。** Project はクラウド上の自前マシンで動くため、ノート PC を閉じても止まらない。手元のマシンでテストが要る場面では、コーディネーターがローカルエージェントを立ち上げてそこで実行する。

**共有コンテキスト。** Project ごとに、クラウド / ローカルの全マシン間で同期されるファイル群を保持する。エージェントは調査結果や成果物に加え、**コードベースについて学んだことや、利用者の作業の進め方の好みを書き込む。** あるエージェントがサービスのテスト方法を突き止めれば、以降の全エージェントがその手順を使える。

**Subscriptions。** コーディネーターに Slack チャンネルの監視、スケジュール実行、全 PR の追跡を指示できる。**プロンプトを待たずに、検知したシグナルを起点に動く。** Slack を接続してバグ報告チャンネルへ向ければ、バグが来るたびに委譲を始める。

ベータで、2026-09-10 から全ユーザーへ順次提供。

## できるようになったこと

- 機能・マイグレーション単位の大きな作業を、コーディネーターエージェント経由で並列のサブエージェントへ委譲できる
- クラウド上で動くため、ローカル環境を閉じても作業が継続する
- コードベースの知見と作業の好みを Project 単位で蓄積し、以降のエージェントが再利用できる
- Slack チャンネル監視・スケジュール・PR 追跡をトリガーに、指示なしで動かせる

## 影響範囲

- 対象ユーザー: Cursor 利用者全般（ベータ、順次提供）
- 対象プラン: 記載なし（全ユーザーへロールアウト）
- API / UI / 管理者機能: 左ナビゲーションの Projects、Cloud Agents、Slack 連携

## 教材化メモ

- **「コーディネーターはコードを書かない」という設計の明示が重要である。** 計画・委譲・検収に専念する層を分けるのは、人間の組織で言えばマネージャー職の定義そのものである。**AI 時代の組織論（ドラえもんスキル / AI オーケストレーション）の教材で、製品側が同じ構造を採用した実例**として引ける。
- **蓄積される共有コンテキストが「コードベースの知見」だけでなく「利用者の好み」を含む**点は、コンテキストエンジニアリングの実務論点。**誰の好みが、いつ、誰によって書き込まれたかが追えないと、チームで使ったときに暗黙のルールが混線する。** 教材では、共有コンテキストをレビュー対象にする運用まで踏み込む。
- **Subscriptions は「プロンプトを待たない」ことが本質である。** エージェントが外部シグナル起点で自走する構成は、権限設計の難度を一段上げる。同じ週に GitHub Copilot が shell / file / network の企業管理権限を GA しているのと対比すると、**Cursor は自走の範囲を広げる側、GitHub は統制を固める側に、同時期に動いている。** どちらを先に入れるかという議論の材料になる。
- **「数千のサブエージェント」はコストの話でもある。** 並列度が上がるほど、1タスクあたりの費用は読みにくくなる。前週の Codex 週次まとめで扱った「既定モデルが勝手に変わる」問題と合わせて、**エージェント運用のコスト統制は、モデル固定と並列度の上限の2軸で考える**という整理ができる。
- 記事化はしない（週次確認ソースの更新、かつベータ）。ただし**今週の週次確認ソースの中では最も大きな機能追加**であるため、週次サマリーで明示する。**一般提供へ移った時点で単独記事化を再評価する。**
