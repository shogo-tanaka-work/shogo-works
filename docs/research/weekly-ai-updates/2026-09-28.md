## 価格・課金（今週の最重要項目）

**Microsoft Copilot の課金が2本立てになる（2026-09-25 告知、Message Center 通知 MC1479276、Q4 CY2026 展開開始）。**

**据え置き側（per-user の User Subscription License / USL）** — Microsoft 365 の Copilot Chat、Word / Excel / PowerPoint / OneNote / Outlook / Teams 内の Copilot、Microsoft 製エージェント（Researcher / Analyst / Facilitator）、メール・カレンダー・ファイル・人・組織文脈への Work IQ グラウンディング、**モデル選択と Auto**。

**従量課金側（Copilot Credits / usage-based billing、UBB）** — **Copilot Cowork、Copilot Studio で作るエージェントとアプリ、Dynamics 365 / Power Platform の AI 機能、Work IQ API。** 同日の報道では **Code、Autopilot、長時間稼働エージェント、フロンティアモデル（Astra / Fable）**も UBB 側として整理されている。**UBB の利用には USL が前提。**

**クレジットの条件（公式 Copilot Credits Guide, September 2026 より）** — **テナント単位でプール。** 購入は2手段で、**(1) pay-as-you-go $0.01 / クレジット（後払い、請求月末締め）、(2) Pre-Purchase Plan（P3）1年前払い、9段階（300,000 クレジット / 5% 割引 〜 300,000,000 クレジット / 20% 割引）。未使用分は年間期間の末で失効。** どちらも **MACC を減額。** 消費量は**タスクの複雑さ**で決まる。

**管理者が先にやること。** **Enterprise テナントでは、管理者が Microsoft 365 管理センターで spending policy を作るまで UBB の機能は有効にならず、クレジットも消費されない。** USL に含まれる機能を使い続けるだけなら作業は不要。**FinOps 機能は 2026-09 時点で preview、利用者自身のクレジット消費量・残量・履歴の表示は 2026-09 に GA。** 管理者は**グループごとに利用可能なモデルファミリを制限**でき（Cowork から開始）、これは Auto が選べるモデルにも影響する。spending policy は **Microsoft Graph API** から管理できる。

**判断材料としての注意点が2つある。** 1つは、**「タスクの複雑さで決まる」という説明は見積もりの材料としてほぼ情報量がない**こと。Microsoft は estimator を提供しているが単価表は出していない。**estimator で試算し、spending limit で上限を切る**という順序になる。もう1つは、**前払いクレジットの年度末失効**である。**20% 割引を狙って大量購入し使い切れなければ、割引分以上に損をする。**

**既定値の置き方が GitHub Copilot と正反対である。** Microsoft は**未設定なら消費されない**（安全側）、GitHub は **10-22 から未設定なら有効**（利便側）。**同じ週に、同じ企業向け製品群で、既定値の思想が逆方向に動いた。**

## 今週の横断的な論点

**1. エージェントの実行場所が、開発者のローカルから離れ続けている。** 今週だけで **GitHub Copilot の VS Code 1.139 リモートエージェント実行（Dev Containers / SSH / Tunnel / WSL）**、**Codex 0.157.0 の背景サーバー自動起動**、**Claude Code の cloud sessions GA（日次側で記事化済み）**が同じ方向へ動いた。**「どのマシンで動いているか」を前提にした統制は、いずれ効かなくなる。**

**2. サンドボックスと承認の設計が、同じ週に逆方向で出た。** **GitHub Copilot app のローカルサンドボックス（09-23）は「OS が強制できなければエラーで止める」**という厳格側の設計である。一方 **JetBrains の assisted approvals（09-22）は「低リスクの操作を自動承認する」**もので、**公式告知は低リスクと高リスクを分ける基準を示していない。** 同じベンダーが同じ週に、統制を締める機能と緩める機能を並べて出している。**導入判断は機能単位で行う必要がある。**

**3. モデル名を実装へ直書きする運用の負債が、実装側の対処として現れた。** 09-18 に案内された廃止の代替モデルが、09-22 に1世代古くなった。**同じ週の n8n 2.41.0 が MiniMax ノードのモデル一覧をハードコードから API 取得へ変えた**のは、この問題への構造的な答えである。**ベンダーの退役スケジュールに追随できる実装かどうか**が、選定の観点になりつつある。

**4. 「AIが PR にレビューを付ける」領域で競合が同時に動いた。** **Cursor の Security Review（09-23、悪用可能なバグに絞り、攻撃経路と修正案を添える）**と、**GitHub の agentic autofix × Copilot Memory（09-25、修正パターンを蓄積して code review / cloud agent へ波及）**である。**選定の観点は検出精度だけでなく、既存の CI・権限・予算の統制へどう載るか**になる。
