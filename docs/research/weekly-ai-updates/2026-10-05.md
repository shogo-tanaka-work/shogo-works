## 権限と統制（今週の最重要領域）

**今週は「権限を渡す口が増えた週」と「権限が効いていなかったことが分かった週」が重なっている。**

### 1. GitHub Copilot がデスクトップアプリを操作する（2026-10-01、public preview）

**computer use** が public preview で公開された。Copilot が利用者の代わりにデスクトップアプリを操作する。公式が挙げる操作は、**アクセシビリティ経由のアプリ内容と視覚的文脈の読み取り**、コントロールのクリック、テキスト入力・編集、キー押下、スクロール、ドラッグ、**複数アプリをまたいだワークフローの操作**。対象は GitHub Copilot CLI と GitHub Copilot app の macOS / Windows 版。

**安全側の作りは3段ある。** **既定は無効（オプトイン。CLI は `/computer on`、app は Settings > Computer Use）**、**アプリを操作する前に承認を求める**、**organization-managed settings で機能を無効化できる**。利用者は「常に許可」に設定したアプリの一覧を確認できる。macOS ではアクセシビリティと画面収録の権限付与へ OS が誘導する。

**ここで効くのは「要求される OS 権限が何を意味するか」である。** アクセシビリティと画面収録は、**そのアプリが画面上の全情報を読める**権限である。**権限の境界が「ファイルとコマンド」から「画面と入力デバイス」へ広がった。** Copilot に限らず、**この2つの権限を要求する AI ツールの審査基準を社内で決めておく**必要がある。

**「常に許可」の一覧を利用者が確認できる**という点は実務的に重要である。承認は一度与えると忘れる。**棚卸しできる画面があるか**は、エージェントに強い権限を渡す製品の審査項目に入れるべきである。

### 2. dynamic workflows が全プランで使える（2026-10-01、public preview）

**dynamic workflows** が Copilot CLI / app / SDK で public preview になった。「タスクの進め方を定義するプログラム」で、**ロジックはコードで書き、分析的な判断はエージェントが担う**。**全プランで利用でき、プレミアム枠の制限は無い。** app は既定で利用可能、**CLI は `--experimental` または `/experimental on` が必要**である。

できることは、コマンド実行、ツール利用、他サービス呼び出し、並列実行、段階間での構造化結果の受け渡し、**サブエージェントによる検証**、**チェックポイントでの停止とレビュー後の再開**。

**設計としては評価できる。** チェックポイント停止とサブエージェント検証が標準機能に入っているのは、**非決定的な部分を工程の中に閉じ込める**という発想が製品側で定型化された証拠である。

**一方で統制上の空白がある。** **固有の管理設定が changelog に示されていないのに、全プランでコマンド実行と外部サービス呼び出しができる。** 既存の Copilot 管理設定のどれで止まるのかは、**changelog の記載だけでは判断できない。** 自社で確認する必要がある。

**クライアント間で既定値が違う**点（app は既定有効、CLI は experimental）も、手順書をクライアント別に書かないと噛み合わない型の罠である。

### 3. Microsoft Copilot に plugin registry、同日に統制ドキュメントが更新（2026-09-30）

Microsoft 365 Copilot Blog に「**Introducing the plugin registry — one place to discover and govern plugins for Microsoft Copilot**」が掲載された。**blog 本文は取得できていない**（`techcommunity.microsoft.com` は WebFetch でタイトルのみ返却。前週も同じ症状）。

**ただし同日に更新された一次ドキュメントがある。** `learn.microsoft.com` の「Govern access, tools, and connections for plugins and agents」が **2026-09-30T11:54Z に更新**されており、統制の対象を **plugin package / agent / skill or MCP server / connector package / connector connection / external service** の6種類に分けている。要点は2つ。

- **パッケージ単位の制御は、構成要素・接続・外部サービスまで自動では及ばない。** **パッケージをブロックしても、外部アカウント・資格情報・consent の付与は取り消されない。**
- **agent 用のツール（plugin / skill / MCP server / connector）は、それを参照する agent とは独立に制御できる。**

**「ブロックしても consent は残る」という境界が公式に明記された**ことが、そのまま統制のチェックリストになる。AI ツールを止めるとき、**(1) パッケージの可用性、(2) 構成要素（MCP server / connector）、(3) 接続と同期、(4) 外部サービスの consent と資格情報**——の4層を別々に処理する必要がある。**1か所切れば止まる、という思い込みが最も危険**である。

### 4. n8n がインスタンス資格情報のカスタムロールを入れた（2.42.0、2026-09-29）

**インスタンス資格情報に対する view / use / manage のカスタムロール**を作成できるようになった。あわせて**粒度の細かい資格情報共有の feature flag**、**資格情報を workflow runner に対して検証**、**保存 / 公開 / 実行の拒否時にポリシー違反をスコープ付きで表示**、**SSO が有効なとき SSO を主要なサインイン手段として表示**が入っている。バグ修正側では、**システムインスタンスロールから半チェック状態の権限を除去**し、**quick-connect の OAuth 資格情報を認可されるまで一覧に出さない**よう直された。

**資格情報の権限を「見える / 使える / 管理できる」の3段に割る**という設計は、AI ワークフロー基盤の統制の型になる。実行者に「使える」だけ渡して「見える」を渡さなければ、**資格情報を知らないまま自動化を回せる。**

**ただし 2.42 系列は beta チャネルである**（窓終端時点で `beta` = 2.42.2、`stable` = 2.41.6）。stable で使えるようになるのは次の昇格後になる。

## モデル供給の構造（今週の観察）

**同一モデルが1週間のうちに3製品へ入った。**

| 日付 | 製品 | 入ったモデル | 対象プラン |
| --- | --- | --- | --- |
| 2026-09-28 | GitHub Copilot | **Claude Sonnet 5.5**（GA） | Pro / Pro+ / Max / Business / Enterprise |
| 2026-09-29 | GitHub Copilot | **GPT-6.1 Sol**（GA、段階ロールアウト） | **Pro+ / Max / Business / Enterprise（Pro は対象外）** |
| 2026-09-29 | OpenAI Codex | **GPT-6.1 Sol を既定モデルへ**（0.159.1） | 全般 |
| 2026-09-30 | Microsoft Copilot | **GPT-6.1 Sol / Claude Sonnet 5.5** | 不明（blog 本文未取得） |

**読み取れることは3つある。**

**1. モデルの供給は共通で、差は「どの製品の管理設定で止められるか」だけになっている。** GitHub Copilot は model policy、Microsoft Copilot は Anthropic ファミリのテナント単位オフ、Codex は既定モデルの明示指定。**同じモデルに対して、製品ごとに別の統制手段を持たなければならない。**

**2. 「最新モデルが使えるか」はプラン表の静的な比較では決まらない。** 同じ週に出た2モデルで対象プランが違う（Sonnet 5.5 は Pro から、GPT-6.1 Sol は Pro+ から）。**モデル単位の対象表を自前で持たないと、プラン選定の判断ができない。**

**3. 新モデルは既定ポリシーで自動的に有効になる**（GitHub Copilot）。**モデル追加のたびに管理者が審査する運用にしたい組織は、全体既定を先に切っておく必要がある。** 後追いで無効化する運用は、追加から無効化までの期間が常に開く。

**なお Microsoft Copilot については、`learn.microsoft.com` の Copilot Cowork のモデル選択ドキュメントが窓終端時点で GPT-5.5 Frontier / GPT-5.6 Sol / GPT-5.6 Terra / GPT-6 Astra / Claude Sonnet 5 / Opus 5 / Claude Fable 5.1 の世代のままで、今週追加された2モデルが載っていない。** **blog が先、ドキュメントが後**という順序で、**管理者が設計判断に使える情報が遅れて来る。** `source-catalog.md` が「モデル追加告知は blog 側に出る」「release notes だけで完了扱いにしない」と定めている根拠が、今週も再現した。

### 今週の構造的な観察

**1. 「予告が発効する週」の処理が、週次運用の価値を示した。** 今週の期限到来3件（GitHub Copilot の4モデル廃止、xAI の STT EOL、code review の既定 effort）は、**いずれも前週以前に予告として記録してあったもの**である。予告を記録しておかなければ、発効日に「何かが変わった」と気づくだけで、**何が変わる予定だったかを照合できない。** 2週続けて同じ項目を追った xAI の案件は、**告知 → ずれの確認 → 確定**の3段を記録できている。

**2. 「権限を渡す口」の増え方が、ベンダー横断で同期している。** 今週出たものを並べると、**GitHub Copilot の computer use（画面と入力デバイス）**、**dynamic workflows（コマンド実行と外部サービス呼び出し、全プラン）**、**VS Code の定期実行スケジュールと PR 自動マージ（preview）**、**Manus のイベント駆動 Automations（メール / Slack / Notion / カレンダー）**。**共通するのは「人間がトリガーを引かなくても動く」か「人間が使う画面をそのまま触る」である。** 承認フローを組織として決めていない場合、preview のうちに方針を決めるべき領域になっている。

**3. 「統制の対象としての MCP」が管理機能に実装されつつある。** GitHub Copilot は **MCP servers ポリシーを 2026-10-22 の既定有効化対象に含め**、Microsoft Copilot は **MCP server を「agent と独立に制御する対象」として管理ドキュメントに組み込んだ**。**社内の AI 統制台帳に、ツール単位ではなく MCP サーバー単位の行が必要になる。**

**4. blog がドキュメントより先に出る構造が、判断を遅らせている。** Microsoft Copilot のモデル追加と plugin registry はいずれも blog が先で、**learn のドキュメントは窓終端時点で追随していない**（モデル一覧は未更新、plugin registry は名称が現れていない）。**使えるようになる日と、設計判断に使える情報が揃う日がずれる。** blog を一次の入口として巡回する運用（`source-catalog.md` の既定）は正しいが、**blog だけでは課金区分も管理設定も分からない**という制約は残る。
