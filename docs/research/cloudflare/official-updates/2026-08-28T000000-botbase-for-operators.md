# 2026-08-28 BotBase for Operators

## 公式内容の日本語要約

BotBase は、Cloudflare が管理する**既知のボット／エージェントのディレクトリ**で、ダッシュボードに統合され、サイト運営者が自動化トラフィックを扱う判断材料になる。今回、**ボットを運用する側（オペレーター）向けの機能**が公開された。

これまでオペレーターにとって申請はブラックボックスで、**申請がどう処理されているか見えなかった**。新しいインターフェースでは、**申請ステータス（Waiting for review / Accepted / Rejected）の追跡**と、**既存申請の編集**ができる。レビューの一部は自動化された。

大きい変更は分類方式である。**単一のラベルを付ける方式をやめ、3つの軸で申告させる**形になった。

1. **ボットが何をするか** — インデックス作成、ユーザーの代理として動作、データ収集、モデル学習、SEO 支援
2. **コンテンツをどう使うか** — サイト運営者が既に使っている Content Signals モデルを参照する
3. **誰が運用しているか** — 直接のオペレーターか、中間プラットフォームか

3軸目は、**AI アシスタントや汎用エージェントで特に効く**。インフラを提供する事業者と、実際にリクエストを送る判断をしているプロダクトが別、という構造を区別できるようにするためである。

## できるようになったこと

- ボットオペレーターが申請状況を追跡し、既存申請を編集できる
- ボットの目的・コンテンツ利用方法・運用主体を分けて申告できる

## 影響範囲

- 対象ユーザー: ボット／エージェントを運用する事業者、および自動化トラフィックを制御するサイト運営者
- 対象プラン: BotBase（Cloudflare ダッシュボード）
- API / UI / 管理者機能: オペレーター向け申請 UI の新設

## 教材化メモ

- **「単一ラベル」から「多軸の申告」への移行**は、分類設計の教材としてきれいな題材。ボットを「良い／悪い」や「検索／AI」の1軸で分けようとすると、**同じクローラーが用途によって扱いを変えるべきケース**を表現できない。用途・コンテンツ利用・運用主体という直交する軸に分けると、サイト側は自分のポリシーに合った条件で許可・拒否を書ける。**分類が破綻したら軸を増やす**という判断は、社内のデータ分類やタグ設計でも同じ形で起きる。
- **「インフラ運用者」と「リクエストを送る判断をしたプロダクト」を区別する**という論点は、エージェント時代の責任分界として重要。エージェントが第三者のインフラ経由でアクセスしてきたとき、**誰に対してポリシーを適用するのか**は、robots.txt の時代には無かった問題である。
- **申請プロセスの可視化（ステータス追跡と編集）**は、審査系の仕組みを作るときの定石。ブラックボックスの申請は問い合わせを生む。**ステータスを見せるだけでサポートコストが下がる**という運用設計の実例。
- 自社サイトを Cloudflare で運用しているなら関係するが、本サイト読者の主要関心（企業の AI 導入・副業活用）からはやや外れるため記事化は見送る。**AI クローラーの扱いを巡って課金・許諾の仕組みが具体化した段階で拾い直す。**
