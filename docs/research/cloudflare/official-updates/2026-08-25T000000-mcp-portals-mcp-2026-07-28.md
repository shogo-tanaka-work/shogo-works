# 2026-08-25 MCP server portal が MCP 2026-07-28 仕様に対応

## 公式内容の日本語要約

Cloudflare の **MCP server portal** が、MCP の **2026-07-28 仕様**（ステートレス）に対応した。ポータルの `/mcp` エンドポイントは、2026-07-28 のステートレス要求と、従来の 2025 系 Streamable HTTP クライアントの**両方を自動で受け付ける**。

上流（upstream）の Streamable HTTP サーバーへ接続する際は、ポータル側が **2026-07-28 対応かどうかを確認し、対応していなければ 2025 のハンドシェイクへフォールバック**する。クライアント側のプロトコル選択と上流側のプロトコル選択は独立しており、**どちらか片方だけ先に上げてもポータルの再設定は不要**。

SSE（server-sent events）接続は従来どおり旧プロトコルを使う。

対象は Cloudflare One / Access の MCP server portal を使っている組織。ネットワーク・セキュリティ製品側の更新だが、**MCP が絡むため巡回・記録の対象**とした（`source-catalog.md` の Cloudflare 節の判定基準による）。

## できるようになったこと

- MCP server portal の `/mcp` が MCP 2026-07-28 のステートレス要求を受理
- 上流サーバーの対応状況を検出し、非対応なら 2025 ハンドシェイクへ自動フォールバック
- クライアント側・上流側それぞれが独立にプロトコルを移行できる（ポータルの再設定不要）

## 影響範囲

- 対象ユーザー: Cloudflare One / Access の MCP server portal 利用組織
- 対象プラン: Cloudflare One / Access（changelog に個別のプラン記載なし）
- API / UI / 管理者機能: プロトコル層。管理者側の設定変更は不要

## 教材化メモ

- **「両側が独立に移行できる」設計は、プロトコル移行の教科書的な良例**である。仕様が上がるたびに全体を同時更新しなければならない構成は、実運用では移行が止まる。**中間層が両方を受け、上流には能力検出してフォールバックする**という形にしておくと、移行が段階的に進む。MCP に限らず API バージョニング一般の設計原則として教えられる。
- **MCP の仕様バージョンが日付形式（2026-07-28）である点**は、教材で明示する価値がある。セマンティックバージョンではないため、「新しいほうが大きい数字」という直感が効かない。自社が今どの仕様で話しているかを、日付として把握しておく必要がある。
- **ステートレス化の意味**を押さえておくと、エージェント基盤の設計判断につながる。セッション状態を持たない要求は、スケールアウトとリトライが容易になる一方、接続をまたいだ文脈は別途持たせる必要がある。SSE が旧プロトコルのまま残っているのも、この差の表れとして説明できる。
- 記事化は見送ったが、**MCP portal を実際に運用している読者にとっては設定不要で恩恵が出る類の更新**である。「何もしなくてよい更新」を記事にするより、MCP 仕様の世代交代というテーマでまとめて扱うほうが教材価値が高い。
