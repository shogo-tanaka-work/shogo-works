# 2026-11-04 Dify 1.19.0

## 公式内容の日本語要約

**ネストしたワークフローのトレース**が主題。1.18.0 で入ったコンソールのドリルダウンを土台に、外部トレース（Langfuse 等）へ **Workflow Tool 内部の実行ステップが含まれる**ようになった。子ステップは呼び出し元の Tool span の下に入り、ネストや繰り返し呼び出しでも階層が保たれる。整形済みプロンプトとレスポンス、トークン使用量、project / trace / observation のリンクも参照できる。**保存済みのプロバイダー設定はそのまま使えるが、過去のトレースへは遡及適用されない。**

**Workflow Tool をアプリと一緒に持ち出せる**ようになった。`.ifpkg` パッケージに、Workflow Tool が束縛しているバージョンのワークフローが推移的な依存込みで入る。インポート先に既にあるツールは再利用し、無いものは再作成・公開・登録して参照を貼り替える。**Dify のアプリエクスポートはすべてパッケージ形式 v2 になった**（Workflow Tool を持たないアプリも含む）。v1 のインポートと明示的な YAML エクスポートは引き続き利用できる。

**Agent ファイル**は複数選択・ドラッグでの並列アップロードに対応し、成功分は1つの原子的なバッチとして束縛される。PDF のインライン表示、シンタックスハイライト付きのソース表示、テキスト切り詰めの明示、PDF が読めないときのダウンロード操作も入った。

**開発者向け**に、ワークスペースの Skill を OpenAPI と `difyctl` から管理できるようになった（`get` / `describe` / `get skill version` / `export` / `import` / `publish` の6コマンド）。アカウント呼び出し元と対応するワークスペース権限、Skills 有効化が前提。**既存 Skill への上書きインポートは destructive に分類される。**

バンドルされるプラグインデーモンは **0.6.14-local** へ上がる。

## できるようになったこと

- Workflow Tool の内部ステップを外部トレースで階層ごと追える
- Workflow Tool 込みでアプリを別ワークスペースへ持ち出せる
- Skill をコマンドラインから取得・エクスポート・インポート・公開できる
- Agent ファイルを並列アップロードし、PDF をその場で読める

## 影響範囲

- 対象ユーザー: self-hosted で Dify を運用している利用者
- 対象プラン: self-hosted（Docker Compose / ソース / difyctl）
- API / UI / 管理者機能: **アップグレード前に公式の upgrade guide を読む必要がある、重い更新である。** ①**Docker Compose は v2.35.0 以降が必須**になった（root の `.env` 上書きが効くための最低バージョン）。②**アプリパッケージが常に v2 形式になる**ため、**古いインポーターは新しいパッケージを拒否しうる**。③ローリング更新では**トレースキューの分離が要る**（新規タスクは `OPS_TRACE_QUEUE=ops_trace_v2` 既定。API / worker / Beat で揃え、カスタムの `CELERY_QUEUES` 等には新キューを含める。旧プロデューサーと滞留分が尽きるまで旧ワーカーは `ops_trace` に残す。**旧キューを purge してはいけない**）。④API / worker / web / Agent Backend / Local sandbox のイメージを `1.19.0` で揃え、プラグインデーモンは `0.6.14-local` にする。⑤環境ファイルの構成が変わり、共通設定は `docker/envs/core-services/api-worker.env` へ移る（従来の `shared.env` も読まれ、競合時は `api-worker.env` が勝ち、root の `docker/.env` が両者より優先）。1.18.0 より前から上げる場合は 1.18.0 の upgrade guide にも従う

## 教材化メモ

- **「ネストしたワークフローが追えない」はエージェント基盤の実務上いちばん効く不足だった。** ワークフローがツールとして別のワークフローを呼ぶ構造では、**外側だけ見ても失敗箇所が分からない**。1.18.0 のコンソール内ドリルダウン → 1.19.0 の外部トレースへの反映、という順で埋めてきた流れを示すと、**可観測性は後付けが難しい**という話の実例になる。過去トレースへ遡及しない点も、計測の追加は常に「その時点から」という原則どおりである。
- **アップグレード手順そのものが教材になる。** トレースキューの移行は、**新旧のプロデューサーとコンシューマーが一時的に共存する**前提で、「旧キューを purge するな」「滞留・実行中・予約・スケジュール・リトライのすべてが尽きるまで旧ワーカーを残せ」と明示している。キューを使うシステムの無停止移行の手順として、そのまま説明に使える粒度である。
- **パッケージ形式 v2 への一斉切替は、互換性の方向に注意が要る。** 新しい版は古い版が読めないパッケージを出す。**エクスポート元を上げると、まだ上げていない環境へ持ち込めなくなる。** 環境を複数持つ組織では**上げる順序（インポート先を先に上げる）**が決まる。公式も「package destinations を先に上げよ」と書いている。依存関係のある移行順序を教える好例。
- **`difyctl import skill` が destructive 分類である**点は、CLI 設計として評価できる。操作カタログと CLI ヘルプが read / write / destructive を区別している。**破壊的操作を型として分類する**設計で、自作 CLI の設計指針に使える。
