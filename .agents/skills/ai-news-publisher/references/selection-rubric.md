# AIニュース公開選別基準

## 判定カテゴリ

### A: 優先してAIニュース化

次のどれかに当てはまる場合。

- デフォルトモデル、主要モデル、フラッグシップ機能の変更
- 利用者の操作フローが変わる
- 企業導入・管理・権限・監査・セキュリティに影響する
- 料金、プラン、上限、モデル退役に関係する
- API / SDK / CLIの実装方法に影響する
- 既存教材の内容が古くなる
- 読者が「今どう使えばいいか」を知る価値が高い

### B: Knowledgeへ最小反映

次のような更新。

- 既存教材の前提、手順、料金、モデル一覧、対象プランが古くなる
- AIニュース記事だけでは、既存教材を読んだ人が誤解する
- 独立したKnowledge記事にすると速報寄りで薄いが、教材の正確性には関係する
- 管理者向け注意や関連リンクとして短く入れておきたい

Knowledgeへ入れるのは、ニュース本文の要約ではなく「恒久的に残すべき結論」です。

### C: 保留

次のような更新。

- 重要そうだが、公開先や読者像が未確定
- beta / previewで提供範囲が狭い
- 公式情報が短く、実務手順に落とし込むには不足
- 既存教材構成を変える必要がある
- ユーザーに方針確認した方がよい

### D: 見送り

次のような更新。

- 小規模バグ修正のみ
- release noteとしては重要だが、教材読者の学習価値が薄い
- 非公式情報または未確認情報
- 同じ内容がすでに教材へ反映済み
- 一時キャンペーン、イベント告知、採用広報など

## 日次リリース型ツールの扱い（Claude Code / Codex）

Claude Code と OpenAI Codex は**ほぼ毎日パッチリリースが出る**ため、通常の枠取りに任せると
上限4本を構造的に占有し、読者から見て「版数の羅列」になる。この2ツールだけ別の基準を当てる。

### 判定は「バージョンリリースかどうか」で分ける

**バージョン番号が付いたリリース（`v2.1.248`、`rust-v0.150.1` など）は、内容にかかわらず
単独記事にしない。** 判定 D（見送り）とし、日次サマリーの「公開記事化結果」へ
`見送り（週次ロールアップへ）` と残す。週1回、`weekly-ai-news-rollup` Skill が
ツールごとに1本へまとめて記事化する。

**「中身が重要かどうか」で判断しない。** この2ツールのリリースは、権限・サンドボックス・
資格情報・セキュリティ修正をほぼ毎回含む。それを条件にすると結局ほぼ全部が単独記事に残り、
版数の羅列に戻る。実際に一度そうなった（2026-08-28 の 2.1.248）。判定は
**タイトルにバージョン番号が付くか**という機械的な線で行う。

詳細メモ（`docs/research/<tool>/official-updates/`）は従来どおり毎日作成する。追跡精度は落とさない。

### 単独記事にしてよいもの（例外）

次の2つだけが例外である。

1. **バージョンリリースではない独立発表** — 製品面・機能面が新しく登場したもの。
   例: Claude in Chrome の GA、self-hosted environments の公開ベータ、auto mode の既定化、
   Codex の Record & Replay、役割特化プラグインの発表。**リリースタグではなく公式ブログや
   製品ページで発表されるもの**が該当する。
2. **期限が切られているもの** — 退役日・発効日・料金改定日が明記された告知。
   例: GPT-5.4 の退役予告、`codex mcp-server` の非推奨化。読者が期限までに棚卸しを
   迫られるため、週次を待たせない。

### セキュリティ修正の扱い

**バージョンリリースに含まれるセキュリティ修正は、単独記事にしない。** 週次ロールアップの
「今週の要点」の冒頭で、対応が必要な旨を明示する。最大で7日遅れることは許容する。
当日の記録は詳細メモに残るため、追跡そのものは落ちない。

ただし、セキュリティ問題が**バージョンリリースとは別に**公式アドバイザリとして告知された
場合は、例外1に当たるため単独記事にしてよい。

### 上限枠との関係

例外に当たって単独記事にする場合も、**1回の実行で両ツール合わせて最大2本**までとする。
残りの枠は他ツールへ回す。日次の記事構成が特定ツールへ偏るのを防ぐためである。

## 本数上限

**1回の実行でAIニュース化するのは最大4本**とします。

候補が5件以上あるときは、下のスコアリングで点数を付け、上位4件だけを記事化します。5件目以降は日次サマリーの「公開記事化結果」に `見送り（本数上限）` として、スコアと見送り理由を残します。同点で並んだ場合は、次の順に優先します。

1. 期限や発効日が決まっているもの（退役予告、ポリシー発効、料金改定）
2. 管理者の作業が発生するもの
3. 利用者の操作フローが変わるもの
4. 機能追加のみのもの

本数を絞る目的は2つあります。1つは読者側で、1日に7本並ぶと個々の記事が埋もれること。もう1つは実行コストで、生成した記事は以降の全ターンで文脈として再送されるため、本数が増えるほど1本あたりの実効コストが上がることです。

## スコアリング目安

各項目を0から2で評価します。合計6点以上ならAIニュース化候補です。候補が上限を超えたら、この合計点で順位を付けます。

| 観点 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 重要度 | 小さい | 一部ユーザーに重要 | 多くの読者に重要 |
| 持続性 | 一過性 | 数か月は有効 | 半年以上価値が残る |
| 実務影響 | ほぼなし | 使い方の補足になる | 手順や判断が変わる |
| 既存教材影響 | なし | 追記で改善 | 更新しないと古くなる |
| 公式情報の十分性 | 不足 | 最低限ある | 十分説明できる |

Knowledgeへ最小反映するかは、上記スコアとは別に次で判断します。

- 既存Knowledgeの記述が誤りになるか
- 既存Knowledgeで紹介している使い方・料金・モデル選定が変わるか
- ニュース記事へのリンクだけでは読者導線として弱いか
- 追記が数行から数段落で済むか

## 判断メモの書き方

各ニュースについて、短く次を残します。

- 判定: A / B / C / D
- 理由:
- 推奨アクション:
- 予定ファイル:
- 注意点:

## ありがちな判断

- 新モデル公開はAになりやすい。Knowledgeへはモデル一覧や使い分けだけ反映する。
- 管理者向けの新機能はAまたはB。読者が一般ユーザーだけならCもありうる。
- patch releaseは基本D。ただし重大な退役、権限、安全性、API破壊的変更を含む場合はB以上。Claude Code / Codex は「日次リリース型ツールの扱い」の条件表で判断する。
- 広告・収益化ニュースはAIニュース候補。既存教材カテゴリに入れる前に方針確認。
- 業界別agentテンプレートはAIニュース候補。汎用Knowledgeには設計思想だけ最小反映する。
